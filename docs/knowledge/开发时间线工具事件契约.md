# 开发时间线工具事件契约

## Summary

timeline 的工具事件(pre_tool_use / post_tool_use)有三个 JSON 列:调用参数 `tool_args`、工具结果摘要 `tool_result_summary`(简称摘要)、`metadata`。这三列在任何时候都必须是合法 JSON,超长时只截字段的值。

摘要按「摘要契约 v2」写入,形状为 `{"v":2,"success":…,"payload":{…}}`。Claude Code 和 CodeBuddy 共用这一份契约:取不到的字段就不写,不推测。

失败调用也记为 post_tool_use,摘要里 `success:false`。失败有两种来源:

- Claude Code:PostToolUseFailure 事件;
- CodeBuddy:PostToolUse 事件,响应里带 `is_error:true`。

被权限拒绝的调用不记录,只留一条 pre。

没有 `v` 的旧摘要按 v1 理解。读取方解析失败时,按"摘要未知"处理。

## Context

2026-10-16 复核本地库时发现三类问题:

- 约 15% 的 Bash 摘要因整串截断而无法解析;
- 失败调用一条都没有记录;
- Read / Edit / Write / Agent 的摘要 payload 全为空。原因是代码读的是响应里并不存在的字段。

据此把摘要改为 v2 并在此成文。sync 等下游按这份契约读取字段。

## Findings

### 摘要 v2 的形状

| 字段 | 含义 |
|---|---|
| `v` | 契约版本,固定为 2(常量 `SUMMARY_VERSION`) |
| `success` | 宿主是否报告失败。失败、被中断、退出码非 0、响应带 `is_error` 或 `error`,都记为 `false` |
| `payload` | 按工具区分的内容。取不到的字段不写,不写成 null |

### payload 字段与可得性

能从调用参数取的信息,一律取自调用参数,所以两个 agent 一致。

| 工具 | 字段 | Claude Code | CodeBuddy |
|---|---|---|---|
| Read / Edit / Write / MultiEdit | `file`(取自 `tool_input.file_path`) | ✓ | ✓ |
| NotebookEdit | `file`(`notebook_path`,没有则 `file_path`) | ✓ | 未实测 |
| Bash | `exit_code` | 失败时从错误文本 "Exit code N" 解析;**成功时没有** | ✓(来自响应的 `exitCode`) |
| Bash | `stdout_preview` / `stderr_preview` | ✓ | ✗(宿主不给输出) |
| Bash | `category`(test / build / lint / git_write,按命令文本识别) | ✓ | ✓ |
| Bash | test 类的 `pass` / `fail`(从输出解析的测试数) | ✓ | ✗ |
| Bash | build / git_write 类的 `pass` / `fail`(由退出码推出) | 仅失败时有 | ✓ |
| Bash | `duration_ms`(测试运行器自报的耗时,不是事件耗时) | ✓ | ✗ |
| 任意工具 | `interrupted` | 只在为 true 时写;缺省表示未中断或未知 | 同左 |
| 任意工具(失败时) | `error` | ✓ | Bash 有;Read 失败只给错误码,不写 |
| 任意工具(失败时) | `exit_code` | 能从错误文本解析时写 | 响应带退出码时写 |
| Agent / Task | `subagent_type`(取自调用参数) | ✓ | ✓ |
| Skill | `skill`(取自调用参数) | ✓ | ✓ |
| WebFetch / WebSearch | `url`(取自调用参数;WebSearch 通常没有) | ✓ | ✓ |
| TaskCreate / TaskUpdate / TaskGet | `taskId` / `subject` / `status` | ✓ | 未实测 |
| 其它工具 | `response_preview` | ✓ | ✓ |

### metadata 的工具事件键

| 键 | 写入时机 |
|---|---|
| `tool_use_id` | pre 和 post 都写,宿主给了就写(两个 agent 都给) |
| `subagent: {id, type}` | 事件发生在子 agent 内(payload 带 `agent_id`)时写。只写入,读取方不展示;事件的 `session_id` 仍是主会话 |
| `duration_source` | 事件有 `duration_ms` 时写:`host` 表示宿主测量的值(Claude Code);`estimated` 表示用 post 写库时刻减最近一条 pre 估算(CodeBuddy,仅写类工具和 Bash) |

### 调用参数的净化

- Write 不存文件正文,改为记 `content_bytes` 和 `content_lines`,pre 和 post 都这样处理。
- Edit 和 MultiEdit 的 `old_string` / `new_string` 保留,但单个片段截到 4KB。

### 上限常量(`src/core/timeline/constants.ts`)

| 常量 | 值 | 作用 |
|---|---|---|
| `RESULT_SUMMARY_MAX_BYTES` | 8KB | 摘要整体上限 |
| `SUMMARY_FIELD_MAX_BYTES` | 2KB | stdout / stderr / error / response 预览,每个字段的上限 |
| `ARGS_MAX_BYTES` / `ARGS_FIELD_MAX_BYTES` | 64KB / 16KB | 调用参数的整体上限 / 整体超限时单个字段的上限 |
| `METADATA_MAX_BYTES` / `METADATA_FIELD_MAX_BYTES` | 8KB / 2KB | metadata 同上 |
| `EDIT_SNIPPET_MAX_BYTES` | 4KB | Edit 片段上限 |

截断在 UTF-8 字符边界进行,并接上 `... [truncated]`。整体仍超限时,单字段上限减半后重试;实在放不下,就写入占位对象 `{"_truncated":true,"_original_bytes":N}`。不能解析的摘要入库时替换为 `{"_invalid":true}`。

### v1 与 v2 的区别

- v1 没有 `v` 字段。
- v1 中 Read / Edit / Write / Agent 的 payload 基本为空,字段缺失表示"当时没采到",不代表"真实为空"。
- 修复前的 v1 Bash 摘要可能是被截断的非法 JSON。
- v1 没有任何失败记录。
- v1 的 `lines_changed` 从来没采到过,v2 已删除。
- 存量数据不改写。旧版全局 cgraphx 在升级之前,会继续写 v1 形状。

### 读取方规则

- 任何读取方解析摘要或 metadata 失败时,都按"该信息未知"处理,不报错、不中断展示或统计。
- 没有 `v` 的摘要按 v1 理解。

逐个核对的现状(2026-10-16):

| 读取方 | 结论 |
|---|---|
| store `rowToEvent` | 摘要原样返回字符串,不解析;`tool_args` / `metadata` 解析失败时分别得到 null / `{}`。不会抛异常 |
| sync `isSuccessful` | 解析失败按成功处理。只采信 `post_tool_use` 且成功的编辑事件,所以 `success:false` 的 Edit / Write 不会进入上报的产出。上报的事件字段不含摘要 |
| web 时间线事件行 | 摘要只做字符串截断显示,不解析 |
| task 产出 | 只读 `tool_args` 里的路径和 commit 文件,不读摘要 |

## Evidence

- 契约产出:`src/core/timeline/post-tool-summary.ts`(`summarizeToolResponse`、类型 `ToolResultSummaryV2`)。
- 长度控制:`src/core/timeline/json-cap.ts`(`truncateUtf8`、`capJsonValue`),在 `TimelineStore.insert` 中统一收口。
- 调用参数净化:`src/core/timeline/tool-args.ts`(`sanitizeToolArgs`)。
- 失败入口:`src/core/timeline/hooks.ts`(`postToolUseFailureHook`)。只为 `capabilities.postToolUseFailure` 为真的 agent 接入,命令带 ` 2>/dev/null || true` 后缀。
- CodeBuddy 2.167.0 的原始 payload 样本:`docs/features/2026-10-16-timeline采集的数据质量问题/实测/codebuddy-2.167.0/`。
- Claude Code 响应形状:取自本机 transcript 的 `toolUseResult`。
  - Bash:`{stdout, stderr, interrupted, isImage, noOutputExpected}`;
  - Read:`{type, file:{filePath,…}}`;
  - Edit:`{filePath, oldString, newString, originalFile, structuredPatch}`。

## Impact For Future Changes

- 新增摘要字段时,先写进本文的可得性表,再改生成器。字段只从生成器一处产出。
- 不要在摘要里依赖响应里的字段名:两个 agent 的响应形状不同,能取自 `tool_input` 的都取自 `tool_input`。
- 新增 timeline hook 时,命令要能容忍旧版全局 cgraphx(加容错后缀);有 agent 不支持的事件,就在 agent 描述里加能力开关。
- 不升 timeline 的 schema 版本:新信息放进已有的 JSON 列。原因见「平台上报」中的旧版全局 cgraphx 约束。

## Reuse Guidance

在这些场景下先读本文:

- 读取或解析 `tool_result_summary`、`metadata`;
- 给 sync 或报表增加基于工具结果的统计;
- 排查"摘要为空、无法解析、失败没记录"之类的问题;
- 接入新 agent 的工具事件。

## Open Questions

- Claude Code 是否每个非零退出的 Bash 都走 PostToolUseFailure,还没有在真实会话里实测。如果是,成功的 Bash 可以补记 `exit_code:0`。
- CodeBuddy 下 Task* 工具和 NotebookEdit 的响应形状,还没有实测。
