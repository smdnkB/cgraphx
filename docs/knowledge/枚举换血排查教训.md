# 枚举换血残留排查教训

## Summary

2026-07-31 分类体系换血(document_type 17→7)的残留排查中,指定 grep 命令报「零命中」后,加宽扫描仍挖出两批真实残留——排查命令的盲区有三类:① 枚举词表漏列值(模式里 13 个废除值漏了 concept,因为它同时是高频普通名词/字段名,设计者潜意识当它"不算枚举");② 值出现在非标准位置(驼峰 `documentType: "concept"` 在 CLI JSON 语境,蛇形 `document_type:` 模式匹配不到);③ 散文引用模式(`concept` 主条目、「X 主条目」式引导)不在任何值匹配模式里,但同样会把 agent 导向废除值。教训:换血类破坏性变更的排查,grep 模式必须覆盖「值的全部出现形态」(蛇形/驼峰/散文引导),且宁可宽(宽了逐条核实误报)不可窄;误报判定口径要事先写清(字段名/CLI 参数/状态机值/普通名词 = 误报)。附带教训:删除随包分发的模板资产(template-runbook.md)必须同步登记 deprecated-assets.json,否则已部署项目升级留孤儿残渣(CLAUDE.md §8 早有约定,实操仍漏)。

## 背景

换血排查闸门(S-3)的指定命令是三条 grep:`document_type: <废除值>`、废除词+类型语境、`source_type: <旧值>`。全部零命中,闸门判定通过。controller 另做了加宽扫描(驼峰 documentType/sourceType 全目录),立即命中 agents/knowledge-recall.md 5 处 `documentType: "concept"`;最终 quality-review 又发现 3 处 skill 散文里的「`concept` 主条目」引导(knowledge-recall/implementation/subagent-implement)——两个独立环节各漏一批。

## 结论:三类盲区

1. **词表盲区**:废除值清单 13 个,grep 模式只列了 12 个——concept 被漏,因为设计排查时把它当"字段名/普通名词"而非枚举值。凡是同时兼任普通名词的枚举值(concept/note/api),最容易被潜意识排除出模式。
2. **形态盲区**:值以驼峰(`documentType: "concept"`)出现在 CLI/JSON 语境,蛇形命名的模式天然匹配不到。枚举值在代码/文档里有蛇形、驼峰、引号变体、赋值变体多种形态。
3. **散文盲区**:「就走 knowledge-write 的 `concept` 主条目」这类引导句不含 `document_type:` 前缀,任何值匹配模式都抓不到,但 agent 照做就会产出废除值文档——危害与直接写旧值等价。

## 排查清单(下次枚举换血直接复用)

- grep 模式覆盖值的**全部出现形态**:蛇形 `document_type: X`、驼峰 `documentType.*X`、引号变体、`X 主条目`/「X 型」式散文引导;
- 废除值清单逐字核对后再写模式(防"兼职普通名词"的值被潜意识漏掉);
- 误报口径事先定义并写进任务:字段名(concepts:)、CLI 参数(find --concept)、运行时状态机值(phase: exploration)、文件名(.exploration-queue.json)、英文散文 = 误报,逐条标注理由;
- 宁可宽不可窄:宽模式命中后逐条人工判定,不做"看起来像误报就跳过";
- 排查与复审分离:闸门任务与最终 quality-review 各扫一轮(本次正是复审兜住了闸门的漏)。
