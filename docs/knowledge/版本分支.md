# 版本分支

## Summary

版本分支是一个版本开发期间汇集各需求的分支,名字是 `dev/<数字>.<数字>.<数字>`(如 `dev/2.0.11`),又称 dev/x.y.z 分支,由 `/release-start` 在主干上拉出,是可选的版本流程的主轴。需求不直接在版本分支上提交:每个需求在自己的需求副本里做,以合并提交「合入需求：<标题>」合入;整个版本的改动(改版本号、主目录里写的知识库和 DDL 知识、发版审核报告)以 `chore(release):` 开头提交,其余直接提交由提交拦截(commit-msg 钩子,`cgraphx release guard`)当场拦下。发版前由 `/release-review` 出发版审核报告、给出结论,你说「发」后版本分支才以合并提交合入主干。`dev/zhangsan`、`develop` 这类分支不算版本分支;不跑 `/release-start` 的项目没有版本分支,照旧在当前分支上开发。

## 命名与边界

- 口径 K8 版本分支(定于 2026-10-27-版本流程与需求副本)= 名字匹配 `^dev/[0-9]+\.[0-9]+\.[0-9]+$` 的分支。算:`dev/2.0.11`、`dev/2.1.0`;不算:`dev/zhangsan`、`develop`、`main`。项目里本来就有的 `dev/` 开头分支不匹配就照旧。
- 主干是 `main`,没有 main、有 master 时用 master。版本号读主干上 `package.json` 的 version;tag 名 `v<版本号>`,带说明:`git tag -a v2.0.10 -m "发布 2.0.10"`。同一时间只有一个在做的版本。
- 「发版审核」是 `/release-review` 对版本分支做的审核,产物是发版审核报告。报告里用到的口径定于同一需求:
  - K5 疑似夹带 = 本版本里没声明、又不属于所在需求的改动。算:版本分支上不以 `chore(release):` 开头的直接提交(绕过了拦截);某需求的合入改了别的需求目录;合入改的代码不在该需求 plan「涉及范围」里(没有 plan 按 spec 写到的模块判)。不算:`chore(release):` 提交(单列为已声明的版本级提交);开版本前已进主干的提交(单列);版本开发期间从主干同步进来的提交(单列为「同步主干」);本需求自己的需求目录,以及知识库、DDL 知识、本需求接口测试用例这类流程产物;plan 和 spec 都没写范围的需求标「未声明范围」,不判。
  - K6 敏感改动 = 改了表结构、依赖清单或配置的文件:`*.sql`;`package.json`、`pom.xml` 这类依赖清单和锁文件;`.env*`。只改代码和文档不算。
  - K7 缺陷 = 本版本合入的需求,测试报告里没通过的用例,加上需求第一次合入之后带进来的 fix 提交。不算:第一次合入前、开发过程中的 fix 提交;缺测试报告(记进风险)。

## 关键约束与陷阱

- **提交拦截放行什么**:当前分支是版本分支时只放行两种提交——合并提交(有 MERGE_HEAD:`git merge --no-ff`,以及冲突后用 `git commit` 收尾),和提交说明以 `chore(release):` 开头的提交。看的是第一行有内容的:编辑器里写说明时,钩子拿到的文件里注释还没去掉,用注释开头的提交模板时第一行是注释,只看首行会把 `chore(release):` 提交误拦;别的分支一行判断就放行。片段是纯 shell、不调 cgraphx,每次提交不多起 node 进程,PATH 里没有 cgraphx 的图形客户端也不会被拦死。拦截装在 git 上,不支持 hooks 的 agent、终端里手敲的提交都拦得住;`git commit --no-verify` 能绕过,发版审核把绕过的提交列为疑似夹带。
- **拦截由谁装、谁卸**:只由 `/release-start` 装,它每次都跑 `cgraphx release guard`(幂等:片段被 husky 这类钩子管理工具冲掉了就补回,装过的记号在仓库本地 git 配置 `cgraphx.releaseGuard`);`cgraphx install` 不装,否则没跑过 `/release-start` 的项目里已有的 `dev/x.y.z` 分支也会被拦;`cgraphx release guard --remove`、`cgraphx uninstall` 卸掉。
- **「按版本走」的记号**:`cgraphx release guard` 每次都在本地 git 配置写 `cgraphx.releaseFlow`,拦截没装上也写。发完版、跑 `/release-start` 之前主目录停在 main 上,这时 `/dev-merge` 看到记号就先停下问(先开版本 / 这次合进 main / 不再按版本走),不会让留着的副本悄悄绕过审核合进 main;回答「不再按版本走」就是 `release guard --remove`,两个记号和拦截一起清掉,以后不再问。不用记号、改看「本地有没有已合进主干的版本分支」行不通:想退出就得删旧版本分支,留着它们打补丁的团队会一直被问。
- **钩子装在 core.hooksPath 指的目录,只动本机**:提交拦截和 timeline 的提交记录片段都写进 `git rev-parse --git-path hooks`(用 husky 9 的项目是 `.husky/_`),不是写死 `.git/hooks/`;片段紧跟 shebang 插入,原钩子以 `exec` 结尾时片段照样执行。按钩子的情况分别处理:
  - core.hooksPath 指向仓库外的共用目录(全局配置的 `~/.githooks` 这类)→ 不写、卸载也不碰:写进去会让这台机器上所有仓库每次提交都起 cgraphx、所有 `dev/x.y.z` 分支都被拦,在一个项目卸载还会删掉别的项目在用的片段。`release guard --json` 返回 `unsupported` + `reason: outside_repo`。
  - 钩子文件不是 shell 脚本或是二进制(`not_shell`,链接看它指向的文件)→ 不写,也不给要加的几行:sh 片段加进去会让钩子报错、每次提交都失败。
  - 钩子文件是链接(`symlink`)→ 不写,给出要加的几行(加到第一行 shebang 之后,没有 shebang 就放最前);说清指向哪里(链接悬空时按链接里写的路径说)、加进去的后果(指向被跟踪的文件会随提交给全组,指向仓库外会影响所有用它的仓库)。
  - 钩子文件被 git 跟踪(husky 5~8 的 `.husky/commit-msg`;链接指向的、整个 `.git/hooks` 链进仓库的也算)→ 不写:工作区这份里有这段片段(团队提交的、自己照提示加了没提交的)→ 算已装上(`present`);没有 → `tracked`,给出要加的几行;工作区里没有这个文件也不新建。卸载时团队提交的不删,`release guard --remove` 返回 `unsupported` 并提示到仓库里删掉那几行再提交;只有工作区这份有的(本机没提交的,如 2.0.10 顺着链接追加的)删掉。写进去会出现在 git status 里,主目录一直有改动,`/dev-start` 报 `dirty_main`;提交出去又会让全组(包括不用 cgraphx 的同事)在版本分支上被拦。在本机配 clean / smudge 过滤规则藏起改动也试过:写入时改的权限位会被暂存进索引、末尾没有换行的文件一经检出就一直显示改过、团队自己提交的片段会被当成本机改动删掉、切分支或换钩子目录后卸载撤不干净,`git archive` 还会把片段打进包里,所以不做。提交拦截没装上时,发版审核照样把版本分支上的直接提交列进疑似夹带。
  - cgraphx 在工作区里新建的钩子文件写进 `.git/info/exclude`(git 目录里的,如 `.git/hooks`,不用写),免得被 `git add -A` 提交给全组、开副本时被当成没被跟踪的文件删掉;队友之后提交了同名钩子,拉取时被换掉,就按被跟踪处理,不再写。
  - 装上的片段连同写进过的文件登记在 `<git 公共目录>/cgraphx/hook-snippets.json`:换了钩子目录(husky 8 的 `.husky` 升到 husky 9 的 `.husky/_`、`.githooks` 换成别的)再装时,旧目录里的片段一并删掉;卸载按登记全删。文件归谁按 git 自己的判断,不按路径前缀:建在主工作区里(如 `.claude/worktrees/`)或 bare 仓库目录里的 worktree 各算各的,别的 worktree 的只在卸载时删;副本整仓复制带过去的登记里是主目录的文件,在副本里装、卸都不碰。
  - timeline 的会话开始钩子按登记补回缺了的:husky 9 每次装依赖都重写 `.husky/_/` 下的钩子,新开的 worktree、被别的工具覆盖也会缺。补不上的(队友提交了同名钩子、成了链接)在会话开始的提示里说一次原因和要加的几行,删掉这条登记,不再每次重试。
  - 钩子目录不是 `.git/hooks` 时,新片段装上后清掉 `.git/hooks` 里旧版本留下的片段(两边解析链接后再比;`.git/hooks` 链到仓库外不动);卸载时钩子文件链接到本仓库里的文件,删掉 2.0.10 顺着链接写进去的旧片段。
  - 只保证高频场景:没设 core.hooksPath、husky 5~9、副本、从 2.0.10 升级。同一仓库的多个 git worktree、钩子目录在子模块里、链接的钩子、非 UTF-8 的钩子、写不进的钩子、只差大小写的 cwd 出了问题记作已知限制(spec F8 细节方案末尾),不为它们加机制。
- **合并说明格式是归组的依据**,写错了审核报告就认不出是哪个需求:
  - 需求合入版本分支:`合入需求：<标题>`(全角冒号);同一需求第 2 次起 `合入需求：<标题>(第 N 次)`(半角括号);标题 = 需求目录名去掉日期段。
  - 整版改动:`chore(release): 版本号 <旧>→<新>`、`chore(release): <版本号> 发版审核报告`。
  - 合入主干:`发布 <版本号>:合入 <标题>、<标题>`(半角冒号,标题之间用顿号);开版本期间主干上多出的提交,正文逐行写 `<短 hash> <说明>`。
  - 副本里同步主目录的分支:`同步 <分支>`。
  - 手动合并、说明不是这个格式,或标题找不到需求目录 → 报告照常列出,标「未关联需求目录」。
- **合并提交要靠 post-merge 才记得下**:`git merge` 只触发 post-merge、不触发 post-commit。timeline 用 post-merge 片段把合并提交记成 git_commit:`commit_files` 为空、增删行为 0,统计放在 `metadata.merge`(`parents`、`files`、`insertions`、`deletions`,相对第一父提交),免得需求的文件再算一遍产出;快进不记,同一 hash 已有记录不再记。快进看 post-merge 当场取的 `git reflog -1 --format=%gs HEAD` 含不含 `: Fast-forward`(带 `-m` 时后面还跟一段括号,所以按「含」判断),读不到 reflog 才看父提交数:只看父提交数时,`git pull` 快进到同事在 GitLab 上做的合并提交,HEAD 也有两个父提交,会被记成本机的合并。读提交的地方要看 `metadata.merge` 才知道一次合入带进了多少改动。
- **发版审核报告**:
  - 位置 `docs/releases/v<版本号>-发版审核.md`;头部一行 `> 版本分支: dev/<版本号> · 起点: v<上个版本号> · 审核时最新提交: <7 位 hash> · 日期: <YYYY-MM-DD>`;不写 `> 产物:`、不登记进产物注册表、不上报平台(它属于整个版本,平台的产物都挂在需求下);写完以 `chore(release): <版本号> 发版审核报告` 提交到版本分支。
  - 结论:和主干合并的预演有冲突 →「不能直接合」;否则「风险」一节不空 →「有风险」;否则「可以发」。进风险的只有版本号没改、需求缺测试或测试有没通过的用例、疑似夹带;敏感改动、两个需求都改了的文件、未关联需求目录、未声明范围只列出,不进风险(改表、改依赖是需求的正常内容,算风险的话结论会一直是「有风险」)。
  - 起点 = 版本分支第一父链上最早一个不在主干里的提交的第一个父提交(开版本的那个点),不用 `git merge-base main dev/x`:把主干合进版本分支拿热修复之后,两条线最近的交汇点移到了热修复上,这次合并会被当成名为 main 的需求,热修复的文件和行数算到它头上,热修复还会被误列进「开版本前已进主干」。第一父链上第二个父提交已在主干里的合并认作「同步主干」,单列一节写带进了主干上的哪些提交,不归需求、不进各项统计;`/dev-merge` 数「第 N 次」和找撞上的需求也用同一个起点。
  - 过期:报告头部记的最新提交之后,版本分支第一父链上又出现了合入 → 过期,要重跑 `/release-review`,这次不合;只多了 `chore(release):` 提交(审核报告本身、补改版本号)不算。
- 合并预演用 `git merge-tree --write-tree`,不动工作区,要 git 2.38 以上;更低版本时 `/dev-merge`、`/release-review` 提示升级后停下。
- 合入主干时不打 tag、不发布、不推送;版本号在版本分支上改好,下一次 `/release-start` 才给刚发的版本打 tag。上个版本分支还没合进主干时,`/release-start` 停下,先 `/release-review`。

## 代码入口

- `src/core/release/`:release 子系统门面与 `cgraphx release guard`;commit-msg 片段原文、版本分支正则 `VERSION_BRANCH_PATTERN` 在这里。
