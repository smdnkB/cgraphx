# 开发任务投入时长口径

## Summary

开发任务的投入时长(又称实际投入)有两个指标,都只算归属该任务的 timeline 事件(会话 + 绑定区间,左闭右开):**活跃时长**(去间隔活跃时长)= 事件按时间排序,相邻间隔超过 1 小时就断开,各连续段首末差之和;**工作时长** = 区间内第一条到最后一条事件的时间差。先按每条绑定段算,任务合计是各段之和——多个会话并行做同一任务时重叠时段**不扣除**(A、B 并行各 3h → 6h,表示 agent 干了多少活,不是人的时间跨度)。会话数按不同会话去重。不统计 token。

## Context

上一个需求(任务会话映射)明确不定义投入时长;web 开发任务页需要展示,于是在 `2026-10-14-cgraphx-web开发任务浏览` 需求的澄清中定下本口径,写入其 spec §3。

## Findings

- 断点 1 小时沿用 task-history agent 的「去间隔活跃时长」,两边数字可对照;区别是 task-history 按时间窗算全项目,本口径只算归属事件。
- 工作时长不用绑定区间长度:生效中的绑定没有终点,按区间算会随时间一直涨。
- 区间内没有事件或只有 1 条事件时,两个指标都是 0。
- 一条绑定段超过 10000 条事件时(timeline 查询上限),只按最近 10000 条计算,页面标注「统计基于每段最近 10000 条事件」。

## Evidence

- 计算只有一处:`src/core/task/report.ts` 的 `computeSegmentStats`(段级)与合计逻辑;断点常量 `ACTIVE_GAP_MS` 在 `src/core/task/constants.ts`。
- 段内归属事件取自 `src/core/task/attribution.ts` 的 `queryBindingEvents`。

## Impact For Future Changes

- 其它地方(CLI、报告、项目管理上报)要展示投入时长时,经 task 门面复用 `computeSegmentStats` / `getTaskReport`,不要另写一份,否则会出现两套数字。
- 改断点或聚合方式(求和 → 并集)是业务口径变更,先改 spec 再改 `report.ts`。

## Reuse Guidance

回答「某任务花了多久」「为什么 web 上的时长和 task-history 报告不一样」时先读这里。

## Open Questions

- 项目管理工具上报是否沿用「并行求和」,还是需要另一个「人的时间跨度」(并集)指标,尚未讨论。
