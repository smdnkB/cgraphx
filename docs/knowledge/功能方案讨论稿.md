# 功能方案讨论稿

## Summary

功能方案讨论稿(简称讨论稿)是 dev-clarify 落盘的《需求功能方案》,文件是 `docs/features/<feature-id>/<前缀>-功能方案-v<N>.md`。里面有:
- 口径表;
- 全景图「用户会这样用」;
- 功能点表;
- 每个画了图的功能点一节「Fx 怎么走」(PlantUML)。

它**不是契约**:人终确认的那一版由 dev-spec 原样收成 spec 第一节,之后以 spec 为准,讨论稿不再维护。

生命周期有四个状态:审卡中的 v1(带「审卡中」那一行)、已收拢、终确认、已收进 spec。多功能点需求一定有讨论稿;单功能点、bug、重构、数据任务画了图也有。

dev-spec、dev-handoff、dev-start、unit-spec、ui-case 和审核子 agent 都按它的结构取内容。改讨论稿的结构,要连着查这几处。

## 命名与边界

- 规范名「功能方案讨论稿」。常见叫法:讨论稿、v1 / v2、「审卡中」(还在审卡的 v1)、「Fx 怎么走」(每个功能点一节)。
- **和对话版**:⑦ 在对话里给的《需求功能方案》只写讨论稿路径,图只在讨论稿里。走不到 ⑤、又一张图都没画的需求没有讨论稿,功能方案只在对话里;交接时由 dev-handoff 照抄。
- **和 spec 第一节**:spec 第一节收的是终确认那一版从「一句话」到「体验决策」的部分;`---` 以下的「功能点明细」不收。
- **和交接文件**:拆会话时,交接文件指向讨论稿,按功能点写明收哪几部分。

## 关键约束与陷阱

- **收录范围三处要一致**:dev-spec 第 1 步、讨论稿范例开头那句、dev-clarify「澄清结果」那段,都是「一句话」到「体验决策」。原来写的是「到「非目标」」,讨论稿里没有这一节,2026-10-31 改了。
- **两份范例逐字同步**:dev-spec 结构范例的第一节,和讨论稿范例的上半部分逐字相同(spec D13 有意这样定,防止范例成为「不照收」的反例)。改一边必须同步另一边;两个文件里都没写这条提醒。
- **下游按结构取内容**:
  - dev-handoff 按功能点裁。编排图写了「判断见「F2 … 怎么走」」而 F2 归别的会话时,F2 那一节两边都带。
  - dev-start 看到有终确认的讨论稿就给 `/dev-spec`;带「审卡中」那一行的,给 `/dev-clarify`。
  - unit-spec、ui-case 从「Fx 怎么走」的图派生场景。
  - ⑥ 的审核子 agent 读讨论稿全文,另外拿配图规则文件的路径。
- **「审卡中」是中间状态**:换会话或写完 spec 回来改时,接着目录里最新那一版,不重建 v1。
- **图号只在节内有效**:跨功能点引用写节标题。边界编号在一个功能点里接着编。
- **两套画法**:「Fx 怎么走」里的图守 `功能点配图.md`(25 个框,可以写接口名、服务名);全景图守 `泳道图画法.md`(15 个框)。活动图有两个渲染坑,见 `PlantUML活动图渲染陷阱.md`。
