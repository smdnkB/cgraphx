# 功能方案讨论稿

## Summary

功能方案讨论稿(简称讨论稿)是 dev-clarify 落盘的《需求功能方案》,文件是 `docs/features/<feature-id>/<前缀>-功能方案-v<N>.md`,也是澄清时人审稿的地方。`---` 以上有:
- 一句话;
- 功能清单:编号 / 功能点 / 类别 / 从哪进 → 到哪去 / 一句话,不做的也列;
- 每个功能点一节 `### Fx 名称(类别)`:一句说明、按场景配的图(不画图的写行为链和边界)、图下每一步的口径表(编号 / 哪一步 / 怎么判定 / 算不算例子 / 依据,依据写到表名.字段)、体验决策。

`---` 以下供 spec 用:必须在 spec 前解决的问题、已锁定技术约束、留给 spec 的细节决策、影响半径与风险、现实约束清单。

它**不是契约**:人终确认的那一版由 dev-spec 原样收成 spec 第一节,之后以 spec 为准,讨论稿不再维护。

生命周期有四个状态:审卡中的 v1(带「审卡中」那一行)、已收拢、终确认、已收进 spec。澄清走到 ④ 就有讨论稿,不分画没画图。

dev-spec、dev-handoff、dev-start、unit-spec、ui-case、doc-workload、doc-delivery 和审核子 agent 都按它的结构取内容。改讨论稿的结构,要连着查这几处。

## 命名与边界

- 规范名「功能方案讨论稿」。常见叫法:讨论稿、v1 / v2、「审卡中」(还在审卡的 v1)。
- **和对话**:2026-11-01 起对话里不再发功能点卡片,提案只写进讨论稿。④ 对话里只说写到了哪几节、哪几处要拍板;⑦ 只给讨论稿路径、功能点一行和待确认。
- **和口径**:没有全局口径表。口径写在用到它的那张图下面,K 编号全文唯一;共用的只在第一次用到的那一节写全,别处写「见 Fx」。有分歧的口径要人二选一:写稿前就知道的在 ③ 问;④ 写到某一步才发现的,口径表先写默认那种,列进那一批「要你拍板的」。
- **和 spec 第一节**:spec 第一节收终确认那一版 `---` 以上的正文;`---` 以下不收。
- **和交接文件**:拆会话时,交接文件指向讨论稿,按功能点写明收哪几节;口径表里写「见 Fx」而 Fx 归别的会话的,照抄那几行。

## 关键约束与陷阱

- **两份范例逐字同步**:dev-spec 结构范例的第一节,和讨论稿范例 `---` 以上的部分逐字相同(spec D13 有意这样定,防止范例成为「不照收」的反例)。改一边必须同步另一边;两个文件里都没写这条提醒。
- **下游按结构取内容**:
  - dev-handoff 按功能点裁。图里写了「判断见 F2」而 F2 归别的会话时,F2 那一节两边都带。
  - dev-start 看到有终确认的讨论稿就给 `/dev-spec`;带「审卡中」那一行的,给 `/dev-clarify`。
  - unit-spec、ui-case 从各功能点那一节的图、行为链和口径表派生场景。
  - doc-workload 从功能清单取一级骨架。
  - ⑥ 的审核子 agent 读讨论稿全文(含 `---` 以下的现实约束清单),另外拿配图规则文件的路径。
- **「审卡中」是中间状态**:换会话或写完 spec 回来改时,接着目录里最新那一版,不重建 v1。
- **图号只在节内有效**:跨功能点引用写 F 编号(「判断见 F2」)。边界编号在一个功能点里接着编。
- **画法**:各功能点的图守 `功能点配图.md`(25 个框,可以写接口名、服务名);标黄标绿等通用画法见 `泳道图画法.md`。活动图有两个渲染坑,见 `PlantUML活动图渲染陷阱.md`。2026-11-01 起不再画全景图和功能点关系图,功能点之间怎么串,看功能清单的「从哪进 → 到哪去」和各图的入口、出口。
