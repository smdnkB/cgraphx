# 平台上报

## Summary

平台上报指本地 cgraphx 把本仓库采集的研发数据按白名单同步到研发管理平台(cgraphx-server),又称平台同步 / 接入平台,命令组为 `cgraphx sync`。上报的数据包括会话、事件、开发任务绑定段、commit、产出、参考。员工用平台账号接入一次(`sync connect`),之后由 hook 拉起的后台 sync-worker 自动同步,1 小时内在平台可见;离线时数据积压,联网后补传;重复上报不重复计数。边界:本流程只把数据送到平台;投入、阶段、完整度等口径都由平台计算,平台上的补绑也不回写本地。本地 web 与本地命令的输出不受影响。

## 触发与前置

- 前置:项目已 `cgraphx install`(sync hook 与 `sync_*` 表就绪);本仓库有 `origin` 远程地址;平台已登记该仓库,且接入者是项目成员。
- 接入:员工在终端执行 `cgraphx sync connect --server <平台地址> --user <账号>`,交互输入密码,或用 `--password-stdin`。
- 自动同步:Stop / SessionEnd / SessionStart 三个 hook 拉起后台 `sync-worker`。
- 手动:`cgraphx sync now` 立即同步;`cgraphx sync status` 查看状态;`cgraphx sync disconnect` 断开。

## 参与者与系统

- 本地 sync 子系统 `src/core/sync/`:接入、上报内容构造、执行器、hook、安装器。
- timeline / task 门面:只读提供事件、commit、绑定段。
- markdown 的 `docs` 命令:执行时写入精确参考记录。
- 研发管理平台:客户端协议 v1(`/api/client/v1/connect | tasks | ingest | status`),契约在 cgraphx-server 仓库 `packages/contract/src/client.ts`。

## 主链路与状态流转

- **接入**:先校验已有凭据。仍可用就提示已接入,不重新签发;否则换取新凭据,写入 `.cgraphx/task-source.json`。这份凭据就是任务源配置,拉任务和上报共用。接入时清空上报进度,以回传全部历史。
- **同步状态**:正常 → 连续失败(可重试错误,超 1 小时才提示)/ 暂停(账号停用、仓库未登记或停用、非项目成员、凭据失效)→ 恢复后自动补传。被平台判为格式不合法的会话单独隔离,不挡其它数据;升级 cgraphx 后自动重试。
- **进度**:每个会话记录"已确认的最大事件 id"和"附属内容哈希"(绑定、commit、产出、参考)。只有收到整批 200 才推进进度。

## 异常分支

- 不可重试的拒绝:暂停自动上报,本地照常记录,积压保留;会话开始时提示一行原因。凭据失效要员工重新接入;其余原因由 worker 定期探测,恢复后自动继续。
- 413:拆成更小的批次重发。
- `validation_failed`:二分定位到单个会话后隔离。
- 网络 / 5xx:记录连续失败的起点,等下次触发再试。

## 关键约束与陷阱

- **hook 里绝不发网络请求**。hook 只做文件检查(已接入? worker 存活? 距上次拉起是否满 1 分钟),然后 spawn 一个脱离的 `sync-worker`,自己立即返回。网络请求全部发生在 worker 里。
- **两个标记文件,语义不能合并**:`.cgraphx/sync.lock` 只在单次同步期间持有,让前台 `sync now`、`connect` 与后台互斥;`.cgraphx/sync-worker.pid` 在 worker 整个生命周期都持有,包括同步后睡 10 分钟的尾随期。只用一把锁的话,worker 睡眠时锁是空的,hook 会反复拉起新 worker。
- **sync 的状态只放在自己的 `sync_*` 表里**,有独立的 `sync_schema_versions`,不升 timeline / task / markdown 的 schema 版本。原因:timeline 打开库时,发现版本比自己支持的高就抛错,而 agent 的 PATH 里优先命中的是旧版全局 cgraphx,升一次版本,旧版 hook 就全部写库失败。
- **hook 命令统一加 `2>/dev/null || true` 后缀**:旧版全局 cgraphx 不认识 `sync-*` 命令,会报 `unknown command` 并以退出码 1 退出。加了后缀,它在 Claude Code 里就不会显示报错。
- **白名单靠正向构造**:上报对象只能在 `payload.ts` 里逐字段赋值,禁止对本地记录做展开或透传。`prompt_text` 只用来解析斜杠命令名,命令原文只用来推断参考;两者都不出本机。发送前还会再断言一遍路径是仓库内的相对路径。
- **终端 commit**(不在任何会话里提交的)挂在固定的终端会话 `cgraphx-terminal-<hash>` 下,只带 commit、不带事件,所以平台上的时长为 0。
- **产物类型只按路径映射**,映射表只在 `artifacts.ts` 定义一处。`commitHash` 只在包含该改动的 commit 已经出现在远程任意分支上时才带,判断依据是本机的远程跟踪引用;否则平台显示「未推送」。
- **参考**:只算四个沉淀目录(知识库、表结构知识、代码地图、设计地图)。精确记录来自 `docs find --concept` 的命中和 `docs show --body` 的正文读取;命令文本推断作补充。推断时 cd 前缀的解析见「Bash 事件 cwd 是执行后的目录」。上报口径与本地 web「任务参考」的口径不同,本地 web 暂未对齐,另立需求。
- **接入要持同步锁**:接入会清空上报进度。如果此时后台正在同步,这一轮结束时会把旧账号的进度写回去,换账号后部分会话就不再回传。所以 connect 在签发凭据之前先取锁,取不到就放弃。worker 的活动标记里也带上了连接时间,接入后正在睡眠的旧 worker 醒来就会补跑回传。
- **不用回执里的 `accepted` 计数判断进度**:服务端遗留问题 P4,各项计数口径不一致。
- 每次 `connect --force` 都会签发新凭据,旧凭据在平台上仍然有效(服务端遗留问题 P1)。

## 代码入口

- `src/core/sync/index.ts`:门面。
