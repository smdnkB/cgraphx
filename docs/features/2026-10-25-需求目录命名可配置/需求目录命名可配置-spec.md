## 功能方案

> 原样收录 clarify 终确认的功能方案;业务要变,回 clarify 改,再同步这一节。

**一句话**:原来需求目录名的格式写死在 skill 里,是 `YYYY-MM-DD-[业务ID-]<标题>`,聚合项目没法在目录名里带上模块。这次项目可以在 `docs/guides/feature-standards.md` 里写自己的命名格式(如 `order-2026-10-25-REQ-1024-订单导出`),agent 建需求目录时照它命名,程序照常识别。没写规范的项目,按默认格式建的目录一切照旧。

**功能方案**(✅ 已采纳 · 🔧 你改过 · ➕ 建议新增已留 / ✂️ 已砍)

用户会这样用:

    负责人写 docs/guides/feature-standards.md
    (格式 / 模块表 / 跨模块取法 / 表外取法 / 例子),提交进 git
              │
              ▼
    任一成员要新建需求目录:写 spec · 写 plan · 交接 · 出线框 · 出图解 ·
    小需求直接实现、要放 sql/ 脚本
              │
              ▼
    agent 读规范 → 定模块、确认命名 → 建 docs/features/order-2026-10-25-REQ-1024-订单导出/
              │
              ├──→ 产物前缀 order-REQ-1024-订单导出(spec / plan / 交接 / 线框 / 接口用例)
              │
              └──→ 需求列表、我的需求索引、平台任务名、会话自动归属照常识别

    没有规范文件:按默认格式 YYYY-MM-DD-[业务ID-]<标题>,和现在一样

**体验决策**:
- **规范放 `docs/guides/feature-standards.md`**,和其他项目规范放在一处。没选 `docs/features/README.md`:打开需求文件夹就能看到,但规范会分在两个地方。
- **日期段必须保留**,放在哪由规范定。没选「日期可省」:同一模块的目录不会再按时间排,同名需求还要加后缀。
- **文件前缀带模块**。没选「不带模块」:两个模块的同名需求文件名会一模一样,文件前缀和平台任务名也不再一致。

## 怎么实现

### 细节方案:F1 项目写自己的需求目录命名规范

路径与节名按体验决策:`docs/guides/feature-standards.md` 的「需求目录命名」一节。

| # | 决策 | 选择 | 没选的(为什么) | 理由(依据) | 影响面 |
|---|---|---|---|---|---|
| D1 | 规范的写法 | 一行「格式:」给出反引号包住的模板,占位写法沿用 dev-spec 默认格式:必填段 `<名称>`、可选段 `[名称-]`、日期固定写 `YYYY-MM-DD`;模板里新增的段(如 `<模块>`)在同一节给取值表和表外取法 | 自由描述——agent 判断不了哪些段要确认、日期段在不在(F2①);YAML / JSON 配置——规范只给 agent 读(边界外「程序校验目录名」),机器语法没有读者 | dev-spec「产物位置与命名」现有的 `YYYY-MM-DD-[业务ID-]<标题>` 就是这套写法 | F2① 的判断依据是格式里有没有 `YYYY-MM-DD`;F5 的例子按此写 |

规范写法(F5 使用指南的例子照此给):

```markdown
# 需求目录规范

## 需求目录命名

格式:`<模块>-YYYY-MM-DD-[业务ID-]<标题>`

| 模块 | 代码目录 |
|---|---|
| order | order-service/ |
| user | user-center/ |

- 跨模块需求:取主改动模块
- 表外的改动:公共代码记 `common`
- 例子:`order-2026-10-25-REQ-1024-订单导出`
```

命名口径(dev-spec「产物位置与命名」改后的规则):

- 有 `docs/guides/feature-standards.md`「需求目录命名」一节 → feature-id 按其格式;格式里没有 `YYYY-MM-DD` → 按 F2① 原文提示,改用默认格式。
- 没有 → feature-id = `YYYY-MM-DD-[业务ID-]<标题>`,和现在一样。
- 文件前缀 = feature-id 去掉日期段(D6)。
- 敏感字符(`/ \ : * ? " < > |`)拒绝、标题不转英文 slug、重名追加短后缀,对规范新增的段同样适用。
- 已有目录一律复用(F2③)。

### 细节方案:F3 日期段不在开头,程序照常识别

| # | 决策 | 选择 | 没选的(为什么) | 理由(依据) | 影响面 |

| D4 🔒 | 日期段的识别与去除 | 日期段 = 目录名里第一个前后紧挨连字符或名字首尾的 `YYYY-MM-DD`(只看数字位数,不校验日期是否真实存在,和现在一样);标题 = 去掉日期段,以及它与相邻段之间的一个连字符;去掉后为空(目录名就是一个日期)→ 视为没有日期段 | 只认开头,或只认第一段之后——模块段自带连字符(`order-service-2026-…`)时会漏;按规范格式定位——程序要读规范文件,项目一加规范,老目录的解析就跟着变 | 现有两份规则只认开头(`src/core/features/scanner.ts:42`、`src/core/task/feature-name.ts:9`);凡以 `YYYY-MM-DD-` 开头的名字,第一段就是开头那段,结果与现在相同 | 需求列表和我的需求索引的标题与兜底日期、目录任务名、会话自动归属 R2 的日期比较;目录任务名会声明到平台,平台只认第一次声明的名字 |

### 全局约束

- 默认格式零变化:以 `YYYY-MM-DD-` 开头的目录名,日期、标题、目录任务名、文件前缀与改动前逐字相同;没有规范文件的项目,建目录的行为与现在相同。
- 不动:需求目录的根与层级、产物注册表路径规则(`ARTIFACT_MAPPING_VERSION` 不加)、任务键 = feature-id、sync 上报字段、CLI 与 web 的输出列。
- skill 只改 `assets/claude-template/` 下的源文件;根目录 `.claude/` 是部署副本,不手改。
- 没有新的运行时资产,`scripts/copy-assets.cjs`、`deprecated-assets.json` 不变。
- 交付时 CHANGELOG「Unreleased」记一条;知识库「开发任务」「开发任务绑定」两条按 D4 改口径(走 `/knowledge-write`)。
