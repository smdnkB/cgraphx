# 规格说明: skill 流程新增「UI 功能测试」环节

> feature-id: 2026-08-23-ui功能测试
> 负责人: liulongfei
> 日期: 2026-08-24

## 目标与范围

**目标**:在 cgraphx skill 流程的接口测试环节之后补一环「UI 功能测试」——代码完成后,agent 通过 Playwright MCP 打开浏览器,运行目标 web 项目,按用例操作页面、验证功能行为。测试链从「接口层」延伸到「页面层」,填补「接口测通过但 UI 层没人验」的缺口。

**范围**:

1. 新增两个 skill:`write-ui-test`(从需求 spec 派生 UI 功能测试用例,不碰浏览器)+ `run-ui-test`(按用例驱动浏览器执行、截图、出报告)
2. `FLOW-MAP.md` 新增「UI 功能测试流程」节
3. 需求目录新增 `ui功能测试/` 产物目录及命名约定
4. features 阶段派生扩展:UI 功能测试报告计入「已验证」(含 `src/core/features/scanner.ts` 与测试改动)

**明确非目标**:

- 视觉回归测试(像素/样式一致性对比)
- 跨浏览器兼容性矩阵
- 性能/压力测试
- DB 副作用核实(归 `run-api-test`,UI 测试只看 UI 表现)
- 测试数据自动准备(全部人工)
- 测试失败后修代码/改用例/自动重跑(只报告,交用户决定)
- 把 Playwright MCP 捆绑进 `cgraphx install`

## 与既有测试流程的定位与分工

- 定位同接口测试/单元测试:**代码完成后的独立后置流程**,从 spec 派生,不进 plan(延续「测试流程后置」沉淀)。
- 与接口测试**仅推荐顺序,非硬前置**:纯前端需求、接口已在测试环境验过的需求,可直接跑。
- 与接口测试分工:接口测试验接口契约与数据层(DB 副作用);UI 功能测试验页面表现与交互(渲染/跳转/提示/输入响应)。两层各司其职,UI 测试不重复验库。

## 已确认规格

### S1 write-ui-test(用例派生)

**行为**:

1. 用户指定需求(feature-id / spec / 需求名)
2. 读需求 spec,按功能点/验收标准派生用例,**一功能点一用例**
3. 每条用例必含要素:功能点名、操作步骤(自然语言)、预期表现(UI 上应看到什么)、数据前提(需要什么存量数据)、登录账号(如需登录)
4. 用例清单显示给用户确认后才落盘;未确认不落盘
5. 不碰浏览器、不执行、不产报告

**产物**:`docs/features/<feature-id>/ui功能测试/<文件前缀>-ui功能测试-spec.md`(feature-id / 文件前缀规则复用既有算法,同 write-api / run-api-test)

**异常**:

- 需求 spec 缺失 → 报错退出
- spec 无法派生功能点/验收标准 → 报错退出,不产空产物
- 同需求重复触发 → 覆盖已有用例规格

### S2 run-ui-test(执行与报告)

**前置检查(缺失不得执行)**:

1. **Playwright MCP 可用性**:校验当前会话可用;缺失 → 输出安装命令(如 `claude mcp add playwright npx @playwright/mcp@latest`)引导用户自装并退出,不替目标项目写配置
2. **需求锁定**:触发逻辑同 run-api-test(指定需求 → 读其用例规格;未指定 → 主动问);报告归指定的需求目录
3. **执行模式与入口**:headed / 无头由人工指定;入口 URL 必须明确获得(人工给或用例规格记录),不得隐式假设
4. **服务就绪**:服务启动归人工(本地或已部署测试环境);未就绪 → 暂停等待,不盲跑
5. **数据前提就绪**:按用例的数据前提暂停请人工确认备齐;未备齐不跑

**执行行为**:

- **登录**:agent 用用例记录的登录账号自己完成登录;验证码/SSO 等无法通过 → 暂停请人工介入
- **逐用例执行**:按用例步骤操作页面,验证预期表现
- **截图**:相关截图存 `ui功能测试/` 目录,**按功能点命名**(具体格式与截取时机归 plan)
- **不验 DB**:写操作用例也只验 UI 表现
- **失败处理**:只记录失败与原因分类;不修代码、不用例、不自动重跑,交用户决定

**产物**:`docs/features/<feature-id>/ui功能测试/<文件前缀>-ui功能测试报告.md`——含逐用例结果、失败原因分类、截图引用、汇总、下一步建议;同需求重复触发 → 覆盖报告,不增量合并(同 run-api-test)

**异常速查**:

| 场景 | 行为 |
|---|---|
| Playwright MCP 缺失 | 输出安装指引并退出 |
| 用例规格缺失 | 报「请先跑 /write-ui-test」并退出 |
| 服务未就绪 | 暂停等待人工启动 |
| 数据前提未备齐 | 暂停等待人工准备 |
| 登录卡住(验证码/SSO) | 暂停请人工介入 |
| 单条用例执行失败 | 记失败 + 原因分类,不阻塞其他用例 |
| 浏览器 / MCP 崩溃 | 报执行环境异常,不产误导性报告 |

### S3 产物目录约定

`docs/features/<feature-id>/ui功能测试/`(与 plan/ 平级,按需求隔离):

- `<文件前缀>-ui功能测试-spec.md`(用例规格,write-ui-test 产)
- `<文件前缀>-ui功能测试报告.md`(测试报告,run-ui-test 产)
- 截图(按功能点命名)

跨需求不覆盖。

### S4 features 阶段派生扩展

- `deriveStage` 识别 `ui功能测试/` 子目录下的 `-ui功能测试报告.md` → 派生「已验证」(语义:UI 功能测试也是一次验证)
- 只影响「已验证」探测;「已规划」「已规格」的识别逻辑与优先级顺序(已验证 > 已规划 > 已规格)不变
- 存量产物与既有命名不回退、不受影响

## 锁定决策(不可留到实现期)

1. 两件套拆分:write-ui-test 不碰浏览器;run-ui-test 不派生用例、不改用例
2. 用例从需求 spec 派生,一功能点一用例,用户确认后才落盘
3. 产物落需求目录 `ui功能测试/`:用例规格 + 报告 + 截图;截图按功能点命名
4. agent 自己登录(账号记在用例里),验证码/SSO 暂停找人
5. 不验 DB,只看 UI 表现(数据层验证归接口测试)
6. 测试数据全部人工备,执行前暂停确认备齐
7. 服务启动归人工,headed / 无头人工指定
8. 与接口测试仅推荐顺序,非硬前置
9. Playwright MCP 不随 install 捆绑,执行时校验、缺失引导自装
10. 失败只报告,不修代码、不自动重跑
11. UI 功能测试报告计入「已验证」阶段派生

- 影响半径:**LOW**——纯新增;唯一的代码改动是加法式识别扩展

## 验收标准

1. 给定含明确功能点的需求 spec,`/write-ui-test` 产出用例规格:一功能点一用例,含数据前提/登录账号要素,落盘位置与命名符合 S3
2. 无 Playwright MCP 的环境,`/run-ui-test` 输出安装指引并退出,不盲跑报错
3. 数据前提未备齐或服务未就绪时,`/run-ui-test` 暂停等待,不执行
4. 真实需求完整跑通:截图按功能点命名存于 `ui功能测试/`,报告含逐用例结果、失败分类、截图引用
5. agent 能用用例记录的账号自己完成登录;验证码卡住时暂停找人
6. 全程不查 DB、不修代码、不自动重跑
7. `ui功能测试/` 下有 `-ui功能测试报告.md` 的需求,`cgraphx features list` 派生为「已验证」;存量需求的阶段识别不受影响
8. FLOW-MAP 含 UI 功能测试流程节
