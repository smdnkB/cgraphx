## 1. 目标与范围

### 1.1 目标

AI 交付的代码对人是黑盒:报告看不懂、不知道接口间的业务调用关系、不知道改动落在流程哪个部位。本需求在 cgraphx 流程中新增**交付讲解**能力:

- AI 交付代码时,生成一份人能读懂的**交付讲解**(派生视图),按业务场景故事线组织,讲清每个组件的角色、何时使用、调用顺序;
- 改动已有流程时,讲清改动在流程中的部位、前后逻辑对比、波及范围;
- 提供**导读对话**入口,接收者对任何部位可随时追问。

达成标准是接收者「像自己写过一样」——理解的本质不是记住代码做了什么,而是**能重新推导每个部分为什么存在**,讲解内容契约围绕"让读者可推导"设计。

### 1.2 包含范围(v1)

- 新增交付讲解 skill(主 SKILL.md + 场景模板),置于 `assets/claude-template/skills/`,随 `cgraphx install` 部署;
- 两个场景模板:多角色流程(审批流真实案例)、改动型(骨架 + 拟真案例,标注待真实使用替换);
- 交付收尾集成:implementation / subagent-implement 收尾增加讲解环节;
- FLOW-MAP.md 与 cgraphx-guide 流程说明同步更新;
- 导读对话与结论回写。

### 1.3 明确的非目标(v1 不做)

| 非目标 | 说明 |
|---|---|
| 存量代码按需讲解 | v1.5,同一生成能力换入口,不在 v1 |
| 管道型 / CRUD / 后台作业场景模板 | 无真实案例不预建;走通用骨架兜底 + 沉淀提示 |
| HTML 输出 | v1 仅 markdown + mermaid |
| 替代 write-design-doc / write-prd / write-api-doc | 分工不同,见 §8 |
| 验收报告 / 工作量汇报 | 讲解面向理解代码,不面向业务验收(已有 write-workload 等) |
| 依赖 cgraph 引擎 | 调用关系的事实来源由 plan 定;v1 不以引擎为先决条件 |

## 2. 术语与业务对象

| 术语 | 含义 |
|---|---|
| **交付讲解** | 交付时生成的人类可读讲解文档,归档 `docs/features/<feature-id>/<前缀>-交付讲解.md`;是派生视图 |
| **派生视图** | 从 spec + diff + 代码现实生成;过期整体重生成;永不人工维护与代码的一致性(同「features 需求阶段派生」范式);不进需要维护一致性的文档序列 |
| **场景故事线** | 讲解的组织骨架:谁、在什么环节、按什么顺序、干什么;主轴由交付物用法形态决定 |
| **用法形态** | 交付物被使用的方式分类:多角色流程 / 单入口管道 / 管理 CRUD / 后台作业 / 改动型 |
| **组件四问** | 每个接口/函数/模块必答的四项:何时用 / 做什么 / 用了之后使什么成为可能 / 挂点 |
| **锚点法** | 把新东西挂在读者已知事物上讲的方法(已知 = 知识库实体 / 既有流程 / 相似既有模式) |
| **导读** | 讲解文档结尾的对话入口:接收者对任意章节追问,AI 读文档 + 代码作答 |
| **场景模板** | 每种用法形态一个模板文件,统一结构:判断特征 / 故事线主轴 / 维度要求 / 图表类型 / 完整参考案例 / 常见讲错 |

---

## 3. 使用者与触发场景

- **读者**:未写该代码的技术接收者(默认即需求负责人本人);目的是看懂代码,不是业务验收。
- **场景 A(新交付)**:AI 交付一批接口 / 一条流程 → 讲解给出:业务场景中的调用关系(谁先谁后)+ 每个入口的核心逻辑。
- **场景 B(改动已有流程)**:AI 修改既有逻辑 → 讲解给出:改动在整个流程中的部位、前后逻辑对比、波及谁。
- **导读场景**:接收者任意时刻(含数日后、跨会话)对讲解的任何部位追问。

---

## 4. 讲解文档的定位

1. **派生视图,不是维护对象**:从 spec + diff + 代码现实生成;过期重生成;无人工维护一致性的义务。
2. **不是契约**:不得重新定义 spec 已锁定的契约;发现 spec 与代码现实矛盾 → 标【待确认】并上报,不自行解释。
3. **可作事后文档素材**:write-design-doc 发布后合成时可引用交付讲解(可选,非义务)。
4. **重生成语义**:对同一 feature 重新执行 skill = 重生成并替换旧文档;**导读回写的结论不得在重生成中静默丢失**(保留或合并后再生成)。

---

## 5. 讲解内容契约(核心)

### 5.1 通用骨架(所有场景必有,按此顺序)

| 节 | 内容 |
|---|---|
| 1. 30 秒看懂 | 一两句:解决了什么业务问题、在现有系统的哪个位置 |
| 2. 全景 | 本次交付参与的业务流程图(mermaid),**高亮本次新增/修改的部分** |
| 3. 场景故事线 | 按用法形态分节(可多条);主轴见 §5.2 |
| 4. 组件挂接 | 每个接口/入口/模块按四问(§5.3)展开 |
| 5. 改动定位 | 仅当改动已有流程:改在哪个部位(引全景图标出)、前后对比、波及范围(哪些调用方/场景的行为受影响) |
| 6. 已验证与已知边界 | 验证跑通的路径 + 已知限制(业务确认砍掉的、暂不支持的) |
| 7. 导读入口 | 提示任意章节可追问,并给出针对本次交付的示例问题 |

### 5.2 形态 → 故事线主轴

| 用法形态 | 故事线主轴 | 图表类型 |
|---|---|---|
| 多角色流程(审批/退款类) | 角色 × 环节:谁在第几步干什么 | sequenceDiagram |
| 单入口管道(导入/同步任务) | 处理步骤:输入如何一步步变成输出 | flowchart |
| 管理 CRUD(配置管理类) | 对象生命周期:状态 + 每个操作推动到哪 | stateDiagram |
| 后台作业(定时任务/事件消费) | 触发时机:何时触发 / 干了什么 / 结果落哪 | flowchart |
| 改动型 | 原流程中的部位:原故事线第 N 步,前后对比 | stateDiagram / flowchart |

- 形态判断取材于 spec 的场景/角色/状态章节 + 代码接口形状;**拿不准 → 问用户,不猜**;
- 一次交付含多种形态 → 多条故事线,各成一节。

### 5.3 组件四问(每个组件必答)

1. **何时用**:谁触发、前置条件(哪个环节之后才轮到它);
2. **做什么**:核心逻辑,业务语言,3 句以内;
3. **用了之后使什么成为可能**:解锁的下一环节 + 副作用(写什么表、发什么事件、调谁);
4. **挂点**:前置环节 → 本组件 → 后续环节。

协议细节(参数/返回值字段)降级为附录或指向 spec,不占故事线主线。

### 5.4 讲法底线(所有内容适用)

- **锚点法**:新东西先挂在读者已知的事物上(知识库实体/既有流程/相似既有模式);知识库为空 → 不编造锚点,用通用讲法;
- **目的优先**:每个部分先答「你为解决什么问题而存在」,再讲结构;
- **请求走查**:至少一次带真实数据的完整请求/任务走查(故事式,非清单式);
- **代码指针**:每个结论指向代码(文件:行号 或 文件:符号);无法回代码验证的结论不写进讲解;
- **图优先 mermaid**:对齐 write-design-doc 既有图表规范。

## 6. Skill 结构契约

### 6.1 主 SKILL.md(薄,只管流程与底线)

1. 识别场景形态(spec 场景/角色章节 + 代码接口形状;拿不准 → 问用户);
2. 读对应场景模板 → 按模板生成讲解;
3. 模板未覆盖 → 用通用骨架生成 + **沉淀提示**(这类讲法验证有效 → 经用户确认后沉淀为新模板);
4. 结尾导读入口;
5. §5 讲法底线与派生视图规则。

### 6.2 场景模板(每形态一个文件,结构统一)

六项,不得缺省:**判断特征 / 故事线主轴 / 讲解维度要求 / 图表类型 / 完整参考案例 / 常见讲错**。

- 「完整参考案例」是 AI 模仿的对象,**必须尽量用真实案例**;
- 「常见讲错」列反模式(不允许出现的讲法)。

### 6.3 v1 模板清单

| 模板 | 案例来源 |
|---|---|
| 多角色流程 | 审批流真实案例(真实接口清单来源见 §14) |
| 改动型 | 骨架 + 拟真案例,模板内标注「待真实使用替换」 |

管道型 / CRUD / 后台作业:v1 不建模板,通用骨架兜底 + 沉淀提示。

### 6.4 进化闭环

- 使用中发现讲解未满足理解 → 导读先解决当次问题,再判断是**个例**(这次没讲好)还是**模板缺陷**(这类形态的讲法整体不对);
- 模板缺陷 → 提示更新该场景模板(经用户确认后写入);
- 模板调整不改动主流程;模板是唯一迭代单元。

## 7. 交付集成契约

1. **收尾必须给出讲解**:implementation / subagent-implement 交付收尾时,用户必须得到交付讲解或明确的讲解入口,**不允许静默缺失**;触发形态(自动生成 / 提示后确认)为 plan 决策项(§10)。
2. **讲解对象 = 本次交付的增量**:本次新建/修改的内容;纯探索无代码改动 → 不生成。
3. **无 feature 目录(需求外的临时任务)** → 不擅自建目录,讲解直接在回复中输出(内容仍遵循 §5 骨架)。
4. FLOW-MAP.md 同步增加交付讲解环节;cgraphx-guide 的流程说明同步更新。

## 8. 与既有文档的分工

| 文档 | 层 | 时机 | 维护方式 |
|---|---|---|---|
| spec | 业务契约(为什么、应满足什么) | 实现前 | 唯一契约 |
| 知识库 | 跨需求业务语义(实体/流程/决策/坑) | 收尾沉淀 | knowledge-write |
| **交付讲解(本需求)** | 实现层 + 变更层(在哪、是什么、谁调谁) | 交付时 | 派生视图,可重生成 |
| 设计文档 | 设计意图长期归档 | 发布后按需 | write-design-doc 合成 |

阅读次序:交付讲解看懂交付了什么 → spec 回看为什么 → 知识库查业务概念。四者不互相替代、不互相维护一致性(spec 除外,它是唯一契约)。

## 9. 异常与边界场景

| 场景 | 行为 |
|---|---|
| 无 spec(简单任务直接实现) | 从当前任务上下文 + diff 生成,文档头部标注 spec 缺省 |
| 无 diff / 无代码改动 | 不生成 |
| 知识库为空 | 锚点法跳过,用通用讲法,不编造锚点 |
| 形态判错 | 用户纠正后重生成 |
| 单次交付过大(多场景/多任务) | 按场景/任务分节组织,各故事线自洽 |
| spec 与代码现实矛盾 | 标【待确认】,上报用户,不自行解释 |
| 代码指针无法定位 | 该结论不写进讲解,或显式标注「代码位置待确认」 |
| 重生成与回写内容冲突 | 回写内容保留或合并,不得静默覆盖 |

## 10. 留给 plan 的手段决策

- skill 命名(暂拟 write-delivery-guide,定名需用户确认);
- 触发形态:收尾自动生成 vs 收尾提示后确认(参考 knowledge-write 沉淀提示模式);若选择带来业务可观察差异 → 回跳 spec;
- 导读结论回写的具体机制(回写讲解文档 vs 沉淀知识库 vs 兼有);
- 调用关系事实来源:AI 现场读代码 vs 未来接 cgraph 引擎(v1 不依赖引擎;引擎成熟后接入有准确性收益,届时另议);
- 通用骨架各节的行文细则与模板文件书写规范。

## 11. 验收标准与测试关注点

### 11.1 核心场景验收
- 用审批流真实案例(或其复演)生成讲解:故事线覆盖创建→提交→待办→详情→通过/拒绝全程;每个接口四问齐全;不看代码能回答「谁调谁、何时用、做什么」;
- 用改动型拟真案例生成讲解:含改动定位(部位/前后/波及);
- 讲解中每个结论可经代码指针回溯到代码。

### 11.2 结构验收
- skill 主流程冒烟:形态识别 → 读模板 → 生成 → 导读入口;
- implementation / subagent-implement 交付收尾呈现讲解环节(不静默);
- 模板未覆盖形态走通用骨架兜底路径可用;
- FLOW-MAP.md 与 cgraphx-guide 已同步。

### 11.3 测试关注点
- §9 边界场景(无 spec / 无 diff / 知识库为空 / 形态判错);
- 回写内容在重生成时的保留语义。

## 13. 不可留到实现期的决策

- 派生视图定位:不人工维护,过期整体重生成(§4);
- 形态 = 文档 + 导读:文档承载全景并归档,导读随时追问(§3、§5.1);
- 通用骨架七节及其顺序(§5.1);
- 形态 → 故事线主轴映射与图表类型(§5.2);
- 组件四问(§5.3);
- 讲法底线:锚点法 / 目的优先 / 请求走查 / 代码指针 / mermaid 优先(§5.4);
- 场景模板统一六项结构(§6.2);
- v1 模板清单 = 多角色流程 + 改动型;其他形态不预建(§6.3);
- v1 范围 = 交付时增量讲解;不做存量按需讲解(§1.3);
- 收尾必须给出讲解,不静默缺失(§7.1);
- 四类文档分工;讲解不重定义 spec 契约(§4.2、§8);
- v1 仅 markdown,无 HTML(§1.3)。
