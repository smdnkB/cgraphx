## 一、我们要解决的问题:澄清环节的对齐失效

**一句话**:AI 在澄清环节抛出的决策问题,超出了人「能看懂、能预见后果」的能力范围,导致人拍板时是盲的;错误的决策零成本地流过 spec → plan → 实现,到任务完成才暴露——小差距打补丁可接受,大差距(尤其架构级)触发大量返工,要让这种大返工尽量少出现。

### 失效链条(三个断点)

```
AI 抛出决策问题
   │
   ├─ 断点① 问题本身看不懂 —— 技术黑话 / 抽象维度,人无法回答 → 瞎答或放弃
   │
   ├─ 断点② 看懂了也预见不了后果 —— 想象不出选 A 和选 B 做出来差别是什么样
   │        → 拍板等于抛硬币
   ▼
错误的决策被锁定(澄清阶段纠错成本为零,人感知不到错了)
   │
   ▼  错误沿 spec → plan → 实现逐级放大、固化
   │
任务完成,人第一次看到真实效果 → 差距此刻才暴露
   │
   ├─ 差距小 → 打补丁(可接受,保留)
   └─ 差距大 / 架构级 → 大量返工(要消灭的目标)
```

| # | 子问题 | 本质 |
|---|---|---|
| 1 | 问题不可读 | 缺「把问题翻译成人能懂的形态」的环节 |
| 2 | 后果不可见 | 缺「决策 → 最终效果」的预览映射;现有 visual-explain / write-wireframe 是被动触发,不在关键路径 |
| 3 | 纠错时机后置 | 错误暴露点在实现完成后,纠正成本最低点在澄清中;缺「拍板前就看到效果」的机制 |

### 衡量目标

人每次拍板时:(a) 看得懂问题在问什么;(b) 能预见所选答案对最终产出的影响;澄清结束时,人与 AI 对「最终会长成什么样」的预期一致。事后返工限定在补丁级别,架构级返工趋近于零。

### 明确的非目标

- 不消除所有偏差——小补丁允许且接受,不为此加重前期流程
- 不把人训练成技术专家——改造 AI 侧的提问与呈现,不要求人升级
- 不砍掉打补丁机制——补丁保留,只是不再兜架构级的底

## 二、解决思路(四条互补,非四选一)

| 思路 | 打哪 | 内容 |
|---|---|---|
| 问得少 | 断点①源头 | 默认值确认制:AI 先推完整默认,人只否决不答题(已吸收进「提案-改稿」形态) |
| 问得准 | 断点③ | 决策影响分级:资源聚焦架构级决策,表现级宽容 → 最终落实为「两环节分层 + 功能分类」 |
| 问得懂 | 断点①② | 功能点提案-改稿:AI 给端到端行为链,人改具体元素(核心形态,见下) |
| 最后兜底 | 断点③ | 验收剧本前移:功能方案整体亮相时人在脑中走一遍使用流程,终检 |

### 核心态转变

人的角色从**答题者**变成**审稿者**:答题要人凭空生成答案(难,容易不懂装懂);审稿只需对具体内容挑错(易,看不懂的地方自己暴露)。默认值不再是零散的,是嵌在功能链里的。

## 三、两环节结构

```
环节一:定业务(人拍板)              环节二:细节设计(AI 负责)
─────────────────────────         ─────────────────────────
全部是人可感知的业务语义:           全部是人无感知的实现细节:
点「导出」→ 等待框 →                函数命名、同步/后台机制选型、
近 90 天、按创建时间的数据           任务表设计、超时策略、文件格式
```

分层判据:**有没有使用后果**。程序员在环节二以「设计评审」姿态介入(看结论、看风险点),不逐条共创。

**体验变体上浮规则(两环节不漏气的关键)**:任何有使用后果的技术决策,不允许躲在环节二定——必须以「体验变体」形态提到环节一让人选(如「同步等待 vs 后台任务+通知」实现上是细节,但用户等 30 秒转圈和立刻收通知是两种体验)。

### 改稿的深度(已锁定)

- 业务值改动(90→30、条件、命名):一拍即合,直接采纳
- 链结构改动(等待框→后台任务):AI 回报新链 + 影响面 → 人确认 → 锁定(二拍循环)

## 四、环节一工序(七步)

```
⓪ 现实探索(前置门)
① 功能点识别 + 分类标注
② 清单对齐(人增删改,分类辅助)
③ 逐点提案改稿(带落地依据 + 关联标注)
④ 收拢《需求功能方案》草稿
⑤ 功能合理性专项审核(对抗式)
⑥ 人终确认 → 功能方案锁定,喂给环节二
```

### ⓪ 前置探索(防空中楼阁的进门条件)

- 项目现状:已有功能、既有实现、约定惯例
- 表结构:本地 DDL 知识库(docs/schema-knowledge/)优先;没有先 /export-table-ddl 建基线;必要时 db-query 兜底
- 业务知识:knowledge-recall 召回相关概念、历史决策
- 产出:**现实约束清单**(不是方案),同时作为环节二的输入,避免二次探索

**现实校验贯穿**:每张功能点卡片标注「⚓ 落地依据」(字段、表、既有实现),依据不成立的卡片在③拦截。现实校验不是前置工序,是每张卡片的验收条件。

### ① 功能分类(注意力分配依据)

| 类别 | 含义 | 人的默认姿态 |
|---|---|---|
| 核心 | 需求的根本问题,缺了不成立 | 必须逐张细审 |
| 支撑 | 让核心可用的配套 | 审关联,不抠细节 |
| 建议新增 | AI 识别出用户没提但可能需要的 | **默认砍**,显式要才留;必须注明「基于现有 XX 能力/表可支撑」 |
| 边界外排除 | 明确不做的,防蔓延 | 只确认不做 |

类别决定审的深度:大需求几十个功能点,核心拿到最多对齐资源,建议新增被 YAGNI 默认拦截。

### ② 先粗后细的顺序

清单层面砍一个点成本是一行字,提案层面再砍是整张卡片的讨论——粗筛先做,错误越早拦截越便宜。

### ③ 功能点卡片形态

```
📦 功能点:项目导出  [核心]
   点「导出」→ 页面弹出等待框 → 按创建时间取近 90 天数据
   ⚓ 落地依据:orders 表有 created_time 字段(DDL 已核实);
      已有类似实现 report_export
   🔗 关联:与「导出记录查看」共用任务表
```

有依赖或冲突的功能点必须标注关联,防止人在孤立卡片上拍板、到④才发现互相矛盾。

### ⑤ 专项审核(对抗式)

由**独立子 agent** 执行(不带立场、专门挑刺),审核四个维度:

- **矛盾**:功能点之间逻辑冲突
- **遗漏**:核心缺支撑(有导出没权限判断)、异常路径没人认领
- **过度**:非核心占比过高、建议新增实际无人需要
- **分类失真**:支撑标成核心、该排除的留下

产出问题清单回人裁决,不自行修改。审核发现回对应工序修正。
