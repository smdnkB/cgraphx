## 本任务范围

- 在 core 建一张**产物注册表**作为唯一事实源:产物类型 → 路径规则 → 头部字段。现在三处各自维护的识别口径都改读它:features 阶段派生(`src/core/features/scanner.ts` 的 `deriveStage`)、本地 web 产出分类(`src/core/task/artifacts.ts`)、平台上报的产物映射(`src/core/sync/artifacts.ts`)。
- 新产物统一头部,由 skill 写入:`> 产物:`(类型)、`> 负责人:`、`> 任务:`(可选)、`> 依据:`(派生产物所依据的 spec 版本,用来检测 spec 改了以后哪些下游产物过期)。识别优先级:有头部按头部,没有按路径规则。
- 注册表补上目前没登记的产物:交接文件 `-交接提示词.md`、交付讲解 `-交付讲解.md`、收口档案 `-收口档案.md`、事后文档 `-需求文档.md` / `-设计文档.md`(或 `.html`)/ `-接口文档.html`。
- 负责人读取只定义一处:`features list --mine` 与任务负责人判定共用 `readFeatureOwner`(主 spec → 交接文件),注册表接管这一口径。
- 派生视图与校验命令:`cgraphx features show <id>`(一个产出目录有哪些产物、处在哪个阶段、哪些已过期);`cgraphx features check`(校验新产物头部,供门禁或 hook 调用;`2026-10-18-skill瘦身` 会把 skill 里能交给程序的规则迁到这里)。
- 每类产物「首屏结论先行」的要求登记在注册表里(spec 已有「一图看懂」);各 skill 模板的落地归 `2026-10-18-skill瘦身`。
- 对接平台协议 1.2 / 1.3 的客户端部分(协议文档见「依赖」第一条):
  - 能力按服务端协议版本分档,用已有的 `protocolAtLeast`(`src/core/sync/version.ts`)比较:≥ 1.1 任务声明与任务键(已实现);≥ 1.2 交付文档类型、产出带任务键;≥ 1.3 拉 `GET /spec`、项目自定义类型、`release_record`。
  - 可上报的类型集合:1.3 取 `/spec` 返回的本项目类型表(协议里该接口可选,建议接:接入后拉一次,之后每轮同步前刷新);1.2 为固定 18 类;≤ 1.1 为固定 13 类(报了表外类型会整批 `validation_failed`,会话被隔离)。`/spec` 返回 404 或请求失败时退回默认类型表,不阻塞上报。不在客户端写死「类型 → 环节」,产出也不带环节字段。
  - 映射补齐:交付讲解 `delivery_brief`、收口档案 `closure_record`、接口文档 `api_doc`、需求文档 `prd`、设计文档 `design_doc`(1.3 起后两类归设计环节);`release_record` 视「未决问题」而定。协议类型里的产出 `type` 从 13 类枚举放宽成字符串。
  - 产出带 `taskKey`:文件所在产出目录的 feature-id,只用于平台的「跨任务产出」提示,不影响归属。
  - 回执告警要让用户看得到:现在只计数,后台同步的输出被丢弃、也没有同步日志;至少记进同步状态,`cgraphx sync status` / `sync now` 能看到。`artifact_type_unknown`(1.3 含义:本项目类型表没配这个类型)的条目会被丢弃,管理员补配后不会自动恢复,客户端要能重报;现状是会话的 `extrasHash` 不变就不重发,被丢的产出再也不会报。(供 plan 参考的做法:上报前先按可上报类型集合过滤再算 `extrasHash`,补配后只有含该类型的会话哈希变化,自动重报。)
  - 与平台参考映射对齐:UI 截图 `ui功能测试/*.png` 不再单独声明,平台从结果 JSON 里读截图(截图须与 JSON 在同一个 commit);UI 测试结果 JSON 已符合平台公开的 `UiTestResultV1`,不用改。

## 已锁定决策

- 已有产出目录里的文件**不重命名**;旧产物永久靠路径规则识别。
- 对接的协议是已发布的 `@cgraphx-server/contract`:只增不改,新字段一律可选。
- 产出目录 `docs/features/<feature-id>/` 是**一个任务的产出**,不是平台上的「需求」;平台的项目、模块、需求由管理员在平台维护,客户端只对接任务这一层。
- `> 负责人:` 是任务负责人的判定依据,必须与负责人本人的 `git config user.name` 逐字一致;`> 任务: T-xx` 只在关联平台已有任务时写。
- 新能力遵循「服务端先上线、客户端按协议版本启用」:看 `connect` / `ingest` 响应里的 `protocolVersion`,按「主.次」数值比较,不按日期猜。
- 产物属于哪个环节、算不算完整度,由平台按项目类型表决定(7 个环节 + 必需环节,见「共享背景」);客户端只报 `type`。
- 交接文件只在本地识别,不作为平台产物上报(平台的 cgraphx 参考映射同样不列)。

## 未决问题

- 旧产物要不要补头部:推荐不动,只靠路径规则识别。
- `> 依据:` 的取值与过期判定:推荐取 spec 文件的 commit hash,spec 有更新的 commit 即视为下游产物过期;也可以用日期。
- 原设想的 `> 需求:` 头部要不要:推荐不要——平台需求由管理员维护,协议没有需求字段,客户端写了也到不了平台;如果要,只作本地提示,不参与归属。
- 发布记录 `release_record` 怎么产出:任务要有发布环节的产出,平台才显示「已发布」;cgraphx 现在不产出这类文件,任务最多到「已测试」。平台只要求内容至少有版本号或 tag、上线时间,文件形态和位置由客户端定。选项:新增发布记录 skill、并进 `/end` 顺带产出、暂不做。推荐单独成文件 `<前缀>-发布记录.md`,由 `/end` 顺带生成——收口档案属于交付文档环节,不推进阶段,代替不了发布记录。
- 项目自定义类型怎么声明:平台允许项目管理员自建类型(如 `review_record` 评审记录),客户端按该 `type` 上报即可;cgraphx 的路径规则只认内置类型。推荐 `> 产物:` 直接写平台类型标识(小写字母、数字、下划线),有头部按头部;本地注册表不认识的标识,只要在 `/spec` 的本项目类型表里就照报。
- 存量知识要不要补报:平台「项目资产」页只列上报过的知识经验产出,不会到仓库按目录列文件;从没在记录过的会话里改过的存量知识文件(`docs/knowledge/` 等四个目录)在平台上看不到。推荐一次性补报存量知识文件(不归属任务,幂等可重复)。
- 平台必需环节缺失要不要提醒:需求开发必需 设计 + 实现 + 测试 + 知识经验,缺陷修复必需 实现 + 知识经验,缺了完整度不满,任务完成时要补齐或填豁免理由;cgraphx 流程里测试和沉淀是支线或可选。另外知识文件在产出目录外,另开会话只写知识库、不碰产出目录时,自动关联认不出任务,这条知识经验不计入该任务。推荐在 `cgraphx features show` 里列出按平台环节的覆盖与缺口(任务类型在平台上设置,客户端拿不到,按默认「需求开发」估),交付提示里带一句,不阻塞流程。
