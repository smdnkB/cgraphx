## 本任务范围

- 在 core 建一张**产物注册表**作为唯一事实源:产物类型 → 路径规则 → 头部字段。现在三处各自维护的识别口径都改读它:features 阶段派生(`src/core/features/scanner.ts` 的 `deriveStage`)、本地 web 产出分类(`src/core/task/artifacts.ts`)、平台上报的产物映射(`src/core/sync/artifacts.ts`)。
- 新产物统一头部,由 skill 写入:`> 产物:`(类型)、`> 负责人:`、`> 任务:`(可选)、`> 依据:`(派生产物所依据的 spec 版本,用来检测 spec 改了以后哪些下游产物过期)。识别优先级:有头部按头部,没有按路径规则。
- 注册表补上目前没登记的产物:交接文件 `-交接提示词.md`、交付讲解 `-交付讲解.md`、收口档案 `-收口档案.md`、事后文档 `-需求文档.md` / `-设计文档.md` / `-接口文档.html`。
- 负责人读取只定义一处:`features list --mine` 与任务负责人判定共用 `readFeatureOwner`(主 spec → 交接文件),注册表接管这一口径。
- 派生视图与校验命令:`cgraphx features show <id>`(一个产出目录有哪些产物、处在哪个阶段、哪些已过期);`cgraphx features check`(校验新产物头部,供门禁或 hook 调用;`2026-10-18-skill瘦身` 会把 skill 里能交给程序的规则迁到这里)。
- 每类产物「首屏结论先行」的要求登记在注册表里(spec 已有「一图看懂」);各 skill 模板的落地归 `2026-10-18-skill瘦身`。
- 吸收上报协议扩展的客户端部分:新类型的上报映射;按平台协议版本决定是否上报新类型(旧服务端遇到不认识的类型会判 `validation_failed`,整个会话被隔离);每条产出带上它所在产出目录的任务键(feature-id),供服务端「跨任务产出提示」使用。

## 已锁定决策

- 已有产出目录里的文件**不重命名**;旧产物永久靠路径规则识别。
- 对接的协议是已发布的 `@cgraphx-server/contract`:只增不改,新字段一律可选。
- 产出目录 `docs/features/<feature-id>/` 是**一个任务的产出**,不是平台上的「需求」;平台的一个需求下挂多个任务,由管理员在平台整理。
- `> 负责人:` 是任务负责人的判定依据,必须与负责人本人的 `git config user.name` 逐字一致;`> 任务: T-xx` 只在关联平台已有任务时写。
- 新类型的上报遵循「服务端先上线、客户端按协议版本启用」。

## 未决问题

- 旧产物要不要补头部:推荐不动,只靠路径规则识别。
- `> 依据:` 的取值与过期判定:推荐取 spec 文件的 commit hash,spec 有更新的 commit 即视为下游产物过期;也可以用日期。
- 原设想的 `> 需求:` 头部要不要:推荐不要,需求由管理员在平台挂;如果要,只作挂需求的提示,不参与归属。
- 交接文件要不要作为平台产物类型上报:推荐不上报,只在本地识别。
- 新类型在平台上的分组、是否计入完整度:与 `2026-10-18-产物类型扩展-服务端` 一起定,类型名以那边发布的契约为准。
