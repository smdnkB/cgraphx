# 功能方案: agent看板优化(讨论稿 v2)

> 讨论稿,不是契约:人终确认的那一版由 `/dev-spec` 原样收录为 spec 第一节,之后以 spec 为准,本文件不再维护。
> 图用支持 PlantUML 的 Markdown 预览打开(IDEA:设置 → 语言和框架 → Markdown → 启用 PlantUML)。

**一句话**:原来看板只按最近活动列任务,看不出哪个任务属于哪个版本,发版前想知道「这一版做了哪些」要去翻发版审核报告;这次每个任务挂上版本,看板顶部按版本过滤,下拉里每个版本带任务数。

功能点和口径接着 agent看板 的 spec 往后编(那里是 F1–F4、K1–K14),文中的 F1、F2 指那里的任务列表和任务下的会话。

**功能清单**

| 编号 | 功能点 | 类别 | 从哪进 → 到哪去 | 一句话 |
|---|---|---|---|---|
| F5 | 任务认版本 | 核心 | 跑 `cgraphx board` 或点「刷新」,补录后计算 → F6、F7 | 按合入记录和副本登记现算每个任务的版本,不用人登记,也不写绑定 |
| F6 | 显示版本 | 核心 | F5 → F1 左栏任务行、F2 右栏摘要卡 | 任务行和摘要卡上看到版本,以及这个版本发没发 |
| F7 | 按版本过滤 | 核心 | 看板顶部版本下拉 → F1 左栏只列这个版本的任务 → 点任务看 F2 | 选一个版本只看它的任务;下拉每项带任务数 |
| — | 新增登记、手工给任务指定版本 | 边界外 | — | 不做:全从副本登记和合入记录现算,没开过副本的需求就是无版本 |
| — | 改合入、发版流程 | 边界外 | — | 不做:合入需求的合并说明、发版打的 tag 都照旧 |
| — | 按版本统计工作量、出报表 | 边界外 | — | 不做:发版审核报告里已有 |

### F5 任务认版本(核心)

看板每次启动或点「刷新」,补录完逐个任务现算版本,和认任务一样不写任何东西;算出的版本给 F6 显示、F7 过滤用。认版本的任务照 K1 来(有讨论稿或 spec 的需求目录、开过副本的需求),本机有没有挂上会话都算——F7 选了具体版本时要列出本机没有会话的任务。

| 编号 | 哪一步 | 怎么判定 | 算 / 不算(例子) | 依据 |
|---|---|---|---|---|
| K15 | 合入过版本分支? | 版本分支 dev/x.y.z 自己那一段上有这个任务的合入。那一段:从版本分支沿第一父往回走,走到主干第一父链上的提交为止。合入认两种,满足一种就算:① 合并说明是「合入需求：<任务标题>」或后面带「(第 N 次)」;② 副本登记的需求分支被这一段上的某个合并并了进来(手工 `git merge`、说明改过、标题对不上的都靠这条认)。直接合进主干的不算 | 算:dev/2.0.14 上「合入需求：agent看板(第 2 次)」;dev/2.0.16 上「Merge branch 'feat/订单导出' into dev/2.0.16」,订单导出的副本登记的需求分支正是 feat/订单导出。不算:主干上「合入需求：安装只留选中的agent」;dev/2.0.15 从主干拉出之前,主干上已有的合入 | 合并提交说明、`refs/heads/dev/*` 的第一父链、副本登记的需求分支 `branch`;任务标题见 K13;沿用 dev-merge 的合并说明、发版审核「本版本的需求」(手工合并也算合入) |
| K16 | 挂上哪些版本 | 合入过几个版本就挂几个,版本号新的在前;同一版本里合入几次只算一个 | 2.0.15 合入一次、2.0.16 又合入「第 2 次」→「2.0.16 未发、2.0.15」;agent看板在 2.0.14 合入两次 →「2.0.14」 | 同 K15;新定 |
| K17 | 已发还是未发 | 有 tag `v<版本号>` 的算已发,没有的算未发 | 有 v2.0.14 → 2.0.14 已发;dev/2.0.15 还没打 tag → 2.0.15 未发 | `refs/tags/v*`;沿用发版审核说「发」时打的 tag |
| K18 | 有从版本分支拉出的副本? | 这个需求开过副本、起点分支是 dev/x.y.z 的,x.y.z 是计划版本;已删的副本也算;同一个需求开过几次副本,取最近开的那次 | 算:开副本建好需求目录从 dev/2.0.15 拉出 → 计划 2.0.15。不算:发版后打tag并退出版本流程从主干拉出 | 副本登记的起点分支 `baseBranch`、开副本时间 `createdAt`;新定 |
| K19 | ② 没赶上 | 计划版本已发(K17),这个任务却没合入过任何版本分支 | dev-del丢弃副本:从 dev/2.0.14 拉出,一直没合入,2.0.14 已发 →「计划 2.0.14 · 没赶上」 | 同 K17、K18;新定 |
| K20 | ① 无版本 | 没合入过版本分支,也没有从版本分支拉出的副本 | skill瘦身(没开过副本);安装只留选中的agent(从主干拉出、直接合进主干) | 新定 |

### F6 显示版本(核心)

行为链:F5 算完 → F1 左栏任务行在阶段色块后面显示版本标签:「2.0.14」「2.0.15 未发」「计划 2.0.15」「计划 2.0.14 · 没赶上」,挂了几个版本用「、」连(顺序见 K16)→ F2 右栏摘要卡在「阶段」后面加一格「版本」,内容同左栏。

边界:① 无版本(K20):左栏任务行不显示版本标签,摘要卡「版本」一格显示「无版本」

---

以下供 spec 使用,可不细读

**必须在 spec 前解决的问题**:无

**已锁定技术约束**:
- 不新增登记、不写绑定:版本全从副本登记的起点分支和 git(合并提交、tag)现算,和认任务一样补录后现算(用户声明)
- 看板网页只读,除补录外不写任何东西(沿用 agent看板 spec)
- 版本分支命名照现有的 `dev/x.y.z`,tag 照 `v<版本号>`(沿用版本流程)

**留给 spec 的细节决策**:
- 版本归属算在哪一层:看板现在只经 project、timeline、features、replica、agents 五个门面取数;git 合入记录与 tag 的读取放 release 门面(多一个依赖),还是放基础层
- 看板认任务用的 `ReplicaRef` 带上 `baseBranch`、`createdAt`
- 版本分支截段的算法:沿 `dev/x.y.z` 第一父往回走、碰到主干第一父链上的提交即停;主干分支名取 main / master
- K15 ② 怎么判断需求分支被这一段并进来:需求分支还在时看它的末端是不是这一段某个合并的第二父能到的;需求分支已删时只能靠 ① 的合并说明
- 合并说明里标题的匹配规则和 dev-merge 数「第 N 次」的规则一致(`^合入需求：<标题>(\(第 [0-9]+ 次\))?$`)
- 几个项目组指向同一个仓库时,git 结果按仓库复用
- `BoardTask` 加的版本字段形状(版本号、已发 / 未发、合入 / 计划 / 没赶上),下拉在页头的位置
- 版本号排序按数字逐段比(2.0.10 排在 2.0.9 前面)

**后续阶段的决策**:无

**影响半径与风险**:LOW——只动看板的数据装配和页面,加只读的 git 查询;每次启动和刷新每个仓库多跑几条 git 命令。风险:需求分支已删、合并说明又对不上的,认不到合入,退回计划版本,版本发了以后会显示「没赶上」;版本分支本地删了(tag 不一定打在发布合并上,找不回那一段),那个版本的任务退回计划版本或无版本。
