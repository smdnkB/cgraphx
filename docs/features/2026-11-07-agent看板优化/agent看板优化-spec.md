## 功能方案

> 原样收录 clarify 终确认的功能方案(讨论稿 v2);业务要变,回 clarify 改,再同步这一节。

**一句话**:原来看板只按最近活动列任务,看不出哪个任务属于哪个版本,发版前想知道「这一版做了哪些」要去翻发版审核报告;这次每个任务挂上版本,看板顶部按版本过滤,下拉里每个版本带任务数。

功能点和口径接着 agent看板 的 spec 往后编(那里是 F1–F4、K1–K14),文中的 F1、F2 指那里的任务列表和任务下的会话。

**功能清单**

### F6 显示版本(核心)

行为链:F5 算完 → F1 左栏任务行在阶段色块后面显示版本标签:「2.0.14」「2.0.15 未发」「计划 2.0.15」「计划 2.0.14 · 没赶上」,挂了几个版本用「、」连(顺序见 K16)→ F2 右栏摘要卡在「阶段」后面加一格「版本」,内容同左栏。

边界:① 无版本(K20):左栏任务行不显示版本标签,摘要卡「版本」一格显示「无版本」

## 怎么实现

### 细节方案:F5 任务认版本

| # | 决策 | 选择 | 没选的(为什么) | 理由(依据) | 影响面 |
|---|---|---|---|---|---|
| D15 🔒 | 模块边界 | release 门面新增两个只读函数:`readVersionHistory(dir)` 读出这个仓库的版本历史(各版本分支那一段、合入说明里的标题、有哪些 `v*` tag),`resolveBranchTips(dir, branches)` 取需求分支的末端提交;看板新增依赖 release 门面(第六个),任务 → 版本的认定在看板里另起一个纯函数文件(和 `match.ts` 同样的写法),只吃数据、不碰 git | 看板直接调 git——版本分支 `dev/x.y.z`、合入说明、`v*` tag 这些版本流程的约定会散到看板,版本流程一改要改两处;放基础层——基础层不认识任何子系统的约定 | `src/core/release/index.ts` 的职责就是「版本流程的程序侧」,`VERSION_BRANCH_PATTERN` 已在 `release/constants.ts:6`;release 只依赖基础层 `git-hooks`,不依赖看板,不成环 | 看板门面注释、`CLAUDE.md` 的「只经五个门面」改成六个 |
| D16 | 版本分支那一段(K15) | 主干取 `main`,没有 main 有 master 用 master;`git rev-list --first-parent <主干>` 一次做成集合;本地每个过 `VERSION_BRANCH_PATTERN` 的 `refs/heads/dev/*`,`git rev-list --first-parent dev/x.y.z` 往回走,碰到第一个在主干集合里的提交 B 就停,走过的就是这一段的第一父链;再 `git rev-list dev/x.y.z ^B` 得这一段的全部提交(D18 用)。不是 git 仓库、没有主干、git 命令失败 → 版本历史为空,所有任务只按计划版本或无版本认,不报错 | merge-base 截段——已发的版本分支整条并进了主干,截出来是空的;按 tag 区间 `v<上一版>..v<这一版>`——tag 位置不统一,v2.0.14 打在主干直接合入的需求上 | 讨论稿现实约束清单「现有版本分支」「现有 tag」两行 | 每个仓库 1 条 + 每个版本分支 2 条 git 命令 |
| D17 | 合入说明(K15 ①) | 这一段第一父链上有两个以上父提交的提交,说明第一行匹配 `^合入需求：(.+?)(\(第 [0-9]+ 次\))?$`(全角冒号),取出的标题和任务标题(K13)全等才算 | 模糊匹配——标题相近的需求会互相认错 | dev-merge `SKILL.md:122`–`127` 数「第 N 次」用的就是这个正则 | 无 |
| D18 | 需求分支并进来(K15 ②) | 任务的全部副本登记(含已删)的需求分支,`resolveBranchTips` 取到末端 T;T 在这一段的全部提交里、又不在这一段的第一父链上,就算合入这一版。T 在第一父链上说明分支刚拉出来、一个提交都没有,不算。分支已删取不到 T,只靠 D17 | 每对(分支, 版本)跑一次 `git merge-base --is-ancestor`——24 个登记 × 5 个版本 × 2 次,命令数涨两个数量级 | 副本登记的 `branch`(`replica/types.ts`) | 每个仓库多 1 条 `git rev-parse` 批量取末端 |
| D19 | 认版本(K16–K20) | 纯函数输入任务、副本登记、版本历史,给每个任务一个 `versions` 数组,元素 `{ version: '2.0.14', released: boolean, merged: boolean }`:合入过的(D17 或 D18)按版本去重,版本号逐段按数字倒序(2.0.10 排在 2.0.9 前面);一个都没合入时,取这个需求最近开的那份副本登记(`createdAt` 最大),起点分支过 `VERSION_BRANCH_PATTERN` 的给一个 `merged: false` 的计划版本;都不是给空数组(无版本)。`released` 看版本历史里有没有 `v<版本号>` 这个 tag。「没赶上」不单存,页面按 `merged: false && released: true` 判 | 存拼好的文案(「计划 2.0.14 · 没赶上」)——过滤和计数要按版本号分组,还得把文案解析回来 | `ReplicaEntry.baseBranch`、`createdAt`(`replica/types.ts`);`ReplicaRef` 加这两个字段 | `BoardTask` 加 `versions` |
| D20 | 同一个目录只读一次 | 一次装配里按项目组第一个在用主目录的 realpath 缓存版本历史和需求分支末端;几个项目组指向同一个目录时共用 | 每个项目组各读一次——本机 `cgraphx` 和 `github.com-smdnkB-cgraphx` 两组是同一个目录,白读一遍;按 `git rev-parse --git-common-dir` 认仓库——要先调 git 才拿得到缓存键,看板就得自己碰 git,违背 D15;同一仓库的两个 worktree 都当主目录的情况少见,多读一次也只是几条 git 命令 | `enumerateBoardGroups` 按项目名分组,同一目录可以出现在两组 | 无 |
| D21 | 没挂会话的任务(K23) | 装配时 K1 的全部任务都认版本;本机没挂上会话、`versions` 不为空的任务放进项目的新数组 `noSession`(按标题排),没挂会话又无版本的照旧不要;`tasks`、`older`、`unsorted` 的内容和现在一样 | 把没会话的任务也放进 `tasks` / `older`——选「全部版本」时会冒出来,改了 K2 现有的行为 | `compute.ts:415` `if (hits.length === 0) continue;` | `BoardProject` 加 `noSession` |
