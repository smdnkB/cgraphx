## 目标与范围

**目标**:让 `cgraphx features` 呈现的「需求走到哪一步」由 `docs/features/<feature-id>/` 下的**产物存在性实时派生**,取代当前手填、无人维护、必然腐烂的头部 `> 状态:` 字段。派生值随每次查询从文件系统计算,无缓存、无陈旧。

**包含范围**:
- `features` 子系统(`src/core/features/`):阶段派生、`list` 展示列、过滤参数、`sync` 个人索引(my-features.md)、对外记录字段。
- `write-spec` / `write-plan` 两个 skill 的头部约定:不再产出 `> 状态:`。

**明确非目标**:
- 不设「已实现 / 已交付」阶段——代码完成不落在 `docs/features/`,纯产物派生不可见;本次**不引入** git / timeline 信号。
- 不做状态生命周期 / 流转 / 回写(不引入任何「在某个时机把状态改成 X」的机制)。
- 不主动迁移、改写存量文档里已有的 `> 状态:` 行。
- 不动 `> 负责人:` / `> 日期:` 及其解析与 `--mine` 行为。
- 不动 docs / db / timeline 三个子系统。

## 术语与业务对象

- **需求目录**:`docs/features/<feature-id>/`,一次需求的工作目录。
- **产物**:需求目录内由 skill 流程生成的文件 / 子目录,包括 spec(`*-spec.md`)、plan(`plan/` 及其 index)、单元测试规格与报告、接口测试规格与报告、设计文档、接口文档等。
- **阶段(stage)**:本规格新增的派生量,表示需求在主线流程上**已达到的最高里程碑**。取值见「阶段枚举」。
- **派生 vs 手维护**:阶段不由人或 agent 写入任何文件,而是查询时从产物存在性计算得出——这是本规格的核心取舍(手动维护必陈旧,派生永远最新)。

## 阶段枚举与派生口径(核心契约)

### 阶段枚举(3 值 + 未规格)

| 阶段 | 含义 | 由何产物定义 |
|---|---|---|
| 已规格 | 已产出 spec 契约 | spec 产物存在 |
| 已规划 | 已产出 plan | plan 产物存在 |
| 已验证 | 已执行过测试 | **任一测试报告**存在(单元测试报告 或 接口测试报告) |
| (未规格) | 无任何可识别产物 | 仅目录名可解析、无 spec / plan / 报告——展示为 `-` |

### 派生规则

1. **单一当前阶段** = 该需求已达到的**最高**里程碑。优先级:**已验证 > 已规划 > 已规格**。
2. 三个里程碑**各自独立**按其产物探测;允许跨阶——例如 spec + 接口测试报告但无 plan,阶段直接为 **已验证**(不要求先经过「已规划」)。
3. **「已验证」= 测试已执行(报告存在),不含「测试通过」语义**。通过 / 失败是报告正文的内容,不进入阶段;有报告即已验证,无论结果。
4. **测试「报告」≠ 测试「规格」**:仅「报告」(run-api-test 的测试报告、write-unit-test-code 的单元测试报告)计入已验证;测试规格(write-api 测试规格、write-unit-test-spec 规格)是设计产物,不算。
5. spec 按流程约定是必有产物,故正常需求目录阶段 ≥ 已规格;`-`(未规格)仅出现在缺 spec 的异常 / 历史目录。
6. 阶段在**每次** `list` / `sync` 调用时实时计算,不持久化、不缓存;文件系统变了,下次查询即反映。

## 系统行为

### `features list`

- 展示列中原「状态」列**替换为「阶段」列**,值为派生阶段(已规格 / 已规划 / 已验证 / `-`)。
- 其余列(日期 / 负责人 / 标题 / 目录)保持不变。
- 过滤参数:
  - **新增 `--stage <阶段>`**:对派生阶段做**精确匹配**过滤(如 `--stage 已验证` 只返回阶段为「已验证」的需求)。
  - **移除 `--status`**(被 `--stage` 取代,见「兼容性」)。
  - `--mine`(按负责人)、关键词过滤等既有能力**不变**。

### `features sync` 与个人索引

- 生成的 `.cgraphx/my-features.md` 表格中,原「状态」列**替换为「阶段」列**(派生值)。
- 个人索引仍按负责人(git user)过滤,行为不变。

### 对外记录字段

- features 对外暴露的需求记录中,原表示手填状态的字段**由表示派生阶段的字段取代**(JSON 输出同步变化,见「兼容性」)。
- 原内部 `source` 字段从对外记录**移除**(JSON 输出不再含 `source`)。

### skill 头部约定

- `write-spec` / `write-plan` 的头部约定**移除 `> 状态:`**:头部 = feature-id / 负责人 / 日期(每行 `> 字段: 值`)。两个 skill 不再指示 agent 填写或维护状态。
- 负责人声明逻辑(默认 `git config user.name`、向用户确认)与日期不变。

## 数据、状态与口径

- **阶段是本规格唯一的「状态」概念**,且为派生量,不写入任何文件。
- 原 features 记录中的手填 `status`(来自头部 `> 状态:`)**不再被读取或使用**。
- 头部 `> 负责人:` / `> 日期:` 的解析口径**完全不变**(沿用现有正则与容错:读不到为 null)。
- 原内部 `source`(spec / plan / directory,元数据来源标记)**删除**:经核验无程序消费、仅随 `--json` 外露,其「无头部」语义已由 `owner=null` 自证;删除属本次 breaking 的一部分(用户拍板)。

## 接口、页面与系统边界

- 受影响命令面:`features list`(列与过滤参数)、`features sync`(my-features.md 列)。
- 不受影响:`features list --mine`、关键词过滤、docs / db / timeline 全部命令。
- 无新增持久化、无 DB、无 schema(保持 features 轻形态:纯文件系统派生)。

## 兼容性、迁移与存量数据(含 Breaking)

本变更为**破坏性**:

- `--status` 过滤参数移除,由 `--stage` 取代,**不提供过渡别名**;依赖 `--status` 的脚本会失败。
- `features list` 输出列「状态」→「阶段」;JSON 输出中表示状态的字段由表示阶段的字段取代。依赖这些的下游需适配。
- 对外记录(JSON)中 `source` 字段移除;依赖它的下游需适配(经核验无内部消费方)。
- **存量 `> 状态:` 行**:不主动改写(留在旧文档中为无害死文本);程序**忽略**它(不再据此展示或过滤);新文档(write-spec / write-plan)不再产生。
- 阶段对存量目录同样按产物存在性派生——旧目录带不带 `> 状态:` 行,阶段结果一致。
- `> 负责人:` / `> 日期:` / `--mine` 保持兼容,不受影响。

## 异常与边界场景

| 场景 | 阶段 / 行为 |
|---|---|
| 仅 spec | 已规格 |
| spec + plan | 已规划 |
| spec + plan + 单元测试报告 | 已验证 |
| spec + 接口测试报告(无 plan) | 已验证(跨阶) |
| 仅有测试规格、无报告 | 不计已验证(按其余产物定阶) |
| 报告存在但测试全部失败 | 仍 已验证(阶段不含通过语义) |
| 无 spec、仅有 plan | 已规划(各里程碑独立探测) |
| 纯目录名、无可识别产物 | `-`(未规格) |
| 头部带旧 `> 状态:` 行 | 忽略该行,阶段照常派生,不报错 |
| 头部缺负责人 / 日期 | 沿用现有容错(null),不影响阶段派生 |

## 验收标准与测试关注点

可验证行为:

1. 给定仅含 spec 的需求目录,`features list` 该条阶段 = 已规格;spec + plan = 已规划;再加任一测试报告 = 已验证。
2. spec + 接口测试报告(无 plan)→ 阶段 = 已验证(验证跨阶优先级)。
3. 纯目录(无产物)→ 阶段显示 `-`。
4. `--stage 已验证` 精确过滤,只返回阶段为已验证的需求;`--status` 不再可用。
5. `my-features.md` 含「阶段」列、无「状态」列。
6. 存量带 `> 状态:` 的旧文档:阶段按产物派生,旧状态行被忽略,不报错。
7. write-spec / write-plan 新产出文档头部无 `> 状态:`。
8. `--mine`、负责人 / 日期解析不受影响。
9. 全量测试通过、`npm run build` 通过。

测试关注点:features 现有测试中对 `status` 的断言需迁移到派生 `stage`;补充阶段派生的产物组合用例(上表各场景);skill 改动属文档,人工核对措辞一致。

## Plan 编写约束

- **不得**改 docs / db / timeline 子系统。
- **分层**:`src/core/features` 不得依赖 `src/cli` / `src/web`。
- **负责人 / 日期解析与 `--mine` 行为不变**。
- **features 轻形态不变**:无 DB、无 schema、纯文件系统派生。
- **复用**既有 `findMetaFile` / `listFeatures` / `sync` 机制,在其上扩展产物探测,不另起炉灶。
- 阶段值用中文常量(已规格 / 已规划 / 已验证),与展示列一致;具体产物文件名 / 目录匹配规则(glob / 正则)、记录字段命名,由 plan 定。

## 不可留到实现期的决策

- 阶段枚举与含义(已规格 / 已规划 / 已验证 / `-`)。
- 派生口径:各阶段由何产物定义;单一当前阶段 = 最高已达;优先级 已验证 > 已规划 > 已规格;各里程碑独立探测、允许跨阶。
- 「已验证」= 测试**报告**存在(非规格),且不含「通过」语义。
- 无产物 → `-`(未规格)。
- `--status` 移除、`--stage` 取代(精确匹配),**不留过渡别名**;`list` / my-features 列「状态」→「阶段」;JSON 状态字段 → 阶段字段。
- 存量 `> 状态:` 行不改写、程序忽略;新文档不再产生状态。
- 负责人 / 日期 / `--mine` 不动。
- 原内部 `source` 字段删除(用户拍板)。
