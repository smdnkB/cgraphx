局部:plan 长什么样

index 和现在一样放背景和共用部分;不同的是一个任务一个文件,契约只在 index 里写一遍,另外多了执行顺序和统一验证。

目录

docs/features/<feature-id>/plan/
├── <前缀>-index.md
├── <前缀>-01-数据库.md
├── <前缀>-02-后端-订单.md
├── <前缀>-03-后端-支付.md
├── <前缀>-04-前端.md
└── <前缀>-05-配置.md

一个典型业务需求的样子:后端一个子 agent 做不完,按两个互不依赖的模块拆成两个任务。文件名写 spec 时定。

index 里写什么

  • 设计预览:重点决策表,给你看 不变
  • 背景、范围、明确不包含 不变
  • 任务清单:任务和文件一一对应 改动
  • 执行顺序:分几步,哪几个可以同时跑 新增替掉原来的「分批」和每批一句的启动语
  • 必须严格执行的契约 改动只写在这里,任务文件按编号引用
  • 实现手段决策、适用规范、提交规范、风险、待确认项 不变
  • 统一验证:全部做完后跑的命令和要看的结果 新增
  • 启动语:一句 /subagent-implement 改动

任务文件里写什么

  • 目标、对应 spec 条款、强制引用的规范 不变
  • 涉及范围:改哪些文件 改动要和同时跑的任务不重叠
  • 必须严格执行、允许局部适配、具体要求、完成条件 不变
  • 契约 改动写「按 C-1」,不再抄原文
  • 提交点 改动一个任务可以有好几笔,比如一个 skill 一笔;原来是「独立提交:是或否」
  • 依赖 去掉写进 index 的执行顺序
  • 验证方式 去掉写进 index 的统一验证,最后一起跑

怎么拆

先按任务类型拆:数据库、后端、前端、配置、文档……

每个任务都问一遍

一个子 agent 做得完吗?
做得完就这样,不再拆。拆得越细,子 agent 之间交接越多
做不完按并行度往下拆:拆成改的文件不重叠、只靠 index 契约衔接的几块,每块再问一遍,拆到做得完为止

多大算做不完(比如预估改多少个文件),写 spec 时定一个数。

按新拆法重拆 skill瘦身:7 个任务,分两步

步骤任务为什么这样排
第 1 步,同时跑T1 代码(注册表、features check、web 提示)· T2 合并与废弃 · T3 设计侧 skill · T4 执行侧 skill · T5 其余 skillskill 这一类太大,一个子 agent 做不完,按并行度拆成 T2 到 T5 四块;五个任务改的文件不重叠,模板标题要和注册表一致这条契约已在 index 定死
第 2 步,同时跑T6 文档(FLOW-MAP、模板 CLAUDE.md、cgraphx-guide、README、CHANGELOG、知识库)· T7 提交门禁文档写的是改完以后的 skill,要等第 1 步做完;门禁必须和 skill 写头部同时上线或者更晚

局部:subagent-implement 跑一次

主会话只读 index,不读任务文件正文,也不读代码;它要做的是派任务、提交、最后统一测试和修复。

1

读 index

读任务清单、执行顺序、提交规范和统一验证。新开会话接着跑时,可以指定从哪个任务开始。

2

派任务

按执行顺序一步一步派;同一步里标了可同时跑的,一起派。子 agent 读 implementation、index 和自己的任务文件,只改文件。

  • 停下问你子 agent 报 PLAN_CONFLICT 或者卡住:已经在跑的让它跑完,后面的不再派
3

提交

每回来一个任务,按它报的提交点提交;不构建、不测试。

  • 程序拦每一笔都照常过提交门禁:先按提交规范自查,再跑 features check,有失败项改对才能提交
4

统一测试

全部任务做完后,跑 index「统一验证」里的命令,看要看的结果。

5

修复

有问题由主会话负责:小问题直接改;修复量大时派一个子 agent 去修,主会话跑测试确认。修复单独提交,修完再跑一遍,直到通过。

6

交给你

汇报做了哪些任务、测试结果、哪些任务按 plan 做了局部调整,并把要你验证的清单一起给你。

  • 等你确认你按清单验证
  • 提示问一句要不要沉淀知识,提醒平台环节还缺什么
  • 提示提示你跑 /code-review,不自动跑
