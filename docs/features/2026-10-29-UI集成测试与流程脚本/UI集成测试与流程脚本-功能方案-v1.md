# 功能方案: UI集成测试与流程脚本(讨论稿 v1)

> 讨论稿,不是契约:人终确认的那一版由 `/dev-spec` 原样收录为 spec 第一节,之后以 spec 为准,本文件不再维护。

**一句话**:原来 UI 测试只看页面、不验数据,而且每次都由 agent 从头摸索页面;这次把 `ui-case` / `ui-run` 升级成浏览器集成测试——写操作在页面通过后还要核实数据库和 Redis;agent 第一次测某个业务流程时边探索边写成 Playwright 脚本,以后直接跑脚本,页面局部改了只修那一步;脚本也能不经 agent 单独跑。

**业务口径**

| 编号 | 口径 | 怎么判定 | 算 / 不算(例子) | 依据 |
|---|---|---|---|---|
| K1 | 一步成功 | 做完这一步,10 秒内看到它的成功标志:进了下一个页面、该出现的内容出现了或按钮变得可点、出现成功提示 | 算:点「下一步」后出现「活动规则」标题。不算:点了没报错,但 10 秒内页面没变化;一直在转圈 | 新定(用户原话「记录每一步成功的经验」) |
| K2 | 可修的失败 / 功能出错 | 脚本某一步失败时:这件事在页面上还能做成、只是做法变了 → 可修,只改这一步;系统给出错误结果 → 功能出错,记失败、不改脚本;两种都说得通 → 问开发者 | 可修:「下一步」改名「保存并继续」;多了必填项「活动类型」;多了一个确认弹窗;页面加载变慢、原来的等待不够。功能出错:提交后提示「系统异常」;格式填对了还提示格式错误;数据核实不符。问开发者:「新建」按钮不见了(可能挪了位置,也可能是权限出错) | 沿用 Playwright 修复流程的分法(改定位、改等待算技术修复,分不清有意改动还是回归就问人);新定:数据不符一律算功能出错 |
| K3 | 写操作用例 | 用例里有一步会新增、修改、删除数据,或改状态(提交、审核、发布、上下架) | 算:新建活动、编辑活动、审核通过、下架;会留导出记录的「导出」。不算:列表筛选、查看详情、只下载文件不留记录的导出 | 沿用 api-run「写接口必须查库」的范围,换成页面操作的说法 |
| K4 | 流程 | 一个角色从固定的入口页出发、做成一件业务事的一串页面操作;按做成的事命名,多条用例共用 | 算:「活动创建」= 运营在活动列表点「新建」,到提示「提交成功」;「登录」也算一个流程。不算:单个按钮(并进它所在的流程);「建活动 → 审核 → 报名」一整串(那是一条用例,由 3 个流程组成,见 F7) | 新定 |
| K5 | 数据核实通过 | 用例写的每个核实点都对上:查到预期的行数,写明的字段值相等,没写的字段不查;时间字段只看是否落在本次执行期间;异步写入每 2 秒查一次,最多等 30 秒;缓存:该有的键在且值对,该失效的键查不到 | 算:activity 表按本次活动名查到 1 行,status=0,create_time 10:30:05(本次在 10:30–10:31 执行)。不算:同名查到 2 行(重复提交);status=1;30 秒内没查到;该失效的 activity:detail:1024 还在 | 沿用 api-run 核实规范(新增查新行、更新查字段、删除查消失);新定:时间、异步、缓存 |
| K6 | 脚本跑通 | 生成或修改后,不经 agent 单独连跑 2 遍都过;首测中途遇到功能出错(K2)时,出错之前的那几步连跑 2 遍都能走到出错处,就算这几步跑通 | 算:2 遍都过;首测第 4 步提示「系统异常」,第 1–3 步 2 遍都走到了第 4 步。不算:第 1 遍过、第 2 遍在第 3 步超时(先修等待);要 agent 中途帮一把才过 | 新定 |

例子里的活动、审核、表名和缓存键名都是举例,不是真实项目。

**功能点**

| 编号 | 功能点 | 类别 | 行为链(已锁定) | 边界 | 落地依据 |
|---|---|---|---|---|---|
| F1 | 首次测试边探索边生成脚本 | 核心 | 开发者跑 `/ui-run`,用例要用的流程(K4)还没有脚本 → 第一次用时在 `docs/playwright/` 生成测试工程(依赖、配置、查库和查缓存的辅助、使用说明),装依赖和浏览器前先问一句 → agent 按用例步骤逐步探索页面,每步见到成功标志(K1)才往下走 → 每走通一步写进该流程的脚本:一步一段,注释写成功标志和坑(如「活动时间是日期范围组件,不能直接输入,先点开始日再点结束日」)→ 用例脚本调用流程脚本、填本用例的数据,末尾写预期表现和数据核实(F3、F4)→ 单独跑通(K6)才算记下;报告写「流程『活动创建』:新生成 6 步」 | ① 一步换了 3 种找法还没成 → 停下问开发者,如「第 3 步找不到『报名上限』,页面上有个收起的『高级设置』,要展开找吗?」;指的路写进注释,下次不再问 ② 「登录」也是流程:遇到验证码或 SSO,请开发者在弹出的浏览器里登一次,登录状态存本机,之后脚本直接用,过期了再找人 ③ 账号密码不进脚本,从本机配置读;别人跑要配自己的账号 ④ 项目已装 Playwright(有 playwright.config)→ 脚本放进它的测试目录、沿用它的配置,不另起一套 ⑤ 换环境(本地 → 测试环境)不改脚本,只换入口地址 ⑥ 中途遇到功能出错(K2)→ 出错前的几步照记,出错那步在脚本里标「待修复后补全」;功能修好后再跑,从这一步接着探索 | Playwright MCP 每做一步都回报实际执行的代码(本机 0.0.83 已核实);Playwright 1.64 自带「计划 → 生成 → 修复」流程;api-case 首次接入在 `docs/bruno/` 生成骨架、密钥留空由人填(同类先例);提交门禁只查 `docs/features/`;装了 cgraphx 就有 Node(cgraphx 要求 Node 22.5 以上) |
| F2 | 复测直接跑脚本,只修失败的那一步 | 核心 | 用例已有脚本 → agent 直接跑脚本,不再逐步探索 → 全过 → 「通过」,脚本情况「直接跑通」→ 某步失败 → 按 K2 判断:可修 → 停在这一步看当前页面,只改这一步,跑通(K6)后存回脚本,报告写「修了第 4 步:『下一步』→『保存并继续』」;功能出错 → 记失败,脚本不动;分不清 → 停下问开发者 | ① 数据核实不符 → 一律算功能出错,不改脚本里的预期;开发者说「需求变了」才改 ② 用例改过(重跑过 `/ui-case`)→ 这条用例的脚本按新用例重新生成,流程脚本照用 ③ 一个流程被多条用例共用:修好它,用到它的用例都受益;这次没选的用例不跑 ④ 同一步修了 3 次还过不了 → 记「失败-元素缺失」,报告写清试过哪些改法 ⑤ 功能出错的用例照旧只报告:不重跑、不修代码、不改用例 | Playwright 修复流程:让失败的用例停在出错处、看页面、改定位、重跑;「分不清有意改动还是回归 → 停下问人」是它的原规则(本机 1.64 已核实) |
| F3 | 写操作核实数据库 | 核心 | 写操作用例(K3)提交后页面提示成功 → 按用例写的核实点查库,如 activity 表按本次活动名「测试活动-1029-1430」查到 1 行,status=0(草稿);activity_rule 表查到它的 1 行,signup_limit=100 → 全对上(K5)→ 通过;任一不对 → 「失败-数据核实」,写明「预期 status=0,实际 1」→ 核实写在脚本里,用 cgraphx 只读查库(和 db-query 共用连接配置),单独跑(F9)也验数据 | ① 本机没配查库连接 → `/ui-run` 开跑前提示并给配置示例;不配也能跑,写操作用例记「失败-数据核实」,备注「未配置查库连接」 ② 异步写入(MQ 消费后才落库)→ 按 K5 每 2 秒查一次,最多等 30 秒 ③ 一个用例涉及多个库(微服务)→ 每个核实点写明查哪个连接 | `cgraphx db query` 支持 MySQL、PostgreSQL 和 HTTP 只读接口,可输出 JSON;api-run 已有查库核实规范 |
| F4 | 写操作核实 Redis | 核心 | 写操作后按用例写的核实点查 Redis,如编辑活动保存后,键 activity:detail:<活动 id> 已删除;发布后集合 activity:online 里有这个活动 id → 对上算过(K5);对不上 → 「失败-数据核实」,写明「预期 activity:detail:1024 已删除,实际还在,3540 秒后过期」→ 由 cgraphx 新增只读 Redis 查询,连接和查库配在一起,只放行读命令 | ① 键名带 id → 用本次查库拿到的 id 拼 ② 进程内缓存(Caffeine 这类,不在 Redis 里)→ 外部查不到,用例里不写这类核实点 ③ 没配 Redis 连接 → 同 F3 ① ④ 只读:查值、查剩余过期时间、按前缀找键;写命令一律拒绝 | cgraphx 现在没有任何 Redis 支持,要新增;查库连接配置可以加一类 Redis 连接;依赖约束只禁原生依赖和 wasm,纯 JS 的 Redis 客户端可用 |
| F5 | 用例里写明数据核实点 | 支撑 | 跑 `/ui-case` 生成用例,写操作用例(K3)多两项:「走的流程」(如「活动创建」,已有脚本 / 还没有)和「数据核实」(第几步之后查哪张表的哪几个字段、哪个缓存键,如「第 6 步提交后:activity 按本次活动名查到 1 行,status=0;Redis 键 activity:list 已删除」)→ 用例清单交开发者确认时,核实点一起列出;改过的以开发者为准 | ① spec 没写数据怎么落 → 按表结构和代码推断,标「推断」,确认时重点看 ② 只读用例 → 不写数据核实 ③ 缓存键在代码里拼出来 → 写成模式,如 activity:detail:{活动 id} ④ 本地没有表结构 → 按 db-query 的规矩连库查 | api-case 在 .bru 里写「// DB 预期」注释供 api-run 核实(同类先例);spec 有数据模型一节;`docs/schema-knowledge/` 有本地表结构 |
| F6 | 报告里带上数据核实和脚本情况 | 支撑 | `/ui-run` 跑完,xlsx 报告「用例」表每条用例多两列:数据核实(如「✓ activity.status=0;✗ activity_rule.signup_limit 预期 100,实际 0」)、脚本情况(「新生成 6 步」/「直接跑通」/「修了第 4 步:『下一步』→『保存并继续』」)→ 数据不对的用例结果为新增的第 7 种状态「失败-数据核实」,红底 → 「汇总」表多一项它的计数;结果 JSON 升到 schemaVersion 2 | ① 只读用例 → 数据核实列写「不涉及」 ② 首测在第 4 步遇到功能出错 → 脚本情况写「记到第 3 步,第 4 步待修复后补全」 ③ 单独跑(F9)不生成这份 xlsx,也不会覆盖它 | 报告由 `cgraphx report ui-test` 从结果 JSON 生成,现有 6 种状态;结果 JSON 是研发管理服务端直接读的契约,改状态枚举要升 schemaVersion |
| F7 | 一条用例串起多个流程和角色 | 建议新增 ➕ | 一条用例按顺序调用多个流程,每段用各自的账号:运营跑「活动创建」→ 审核员跑「活动审核」→ 用户在 H5 上跑「活动报名」→ 每换一个角色开一个独立的浏览器会话、用这个角色的登录状态,不退出重登 → 最后核实,如 signup 表新增 1 行、activity.signup_count 加 1 | ① 中间某段失败 → 后面几段不跑,报告写「第 2 段『活动审核』第 3 步失败」 ② 不同端入口不同(管理后台 /admin、H5 /h5)→ 用例规格概览里列多个入口 ③ 登录说明按角色列账号:运营 admin、审核员 auditor、用户 13800138000 | 流程脚本是函数,可以按顺序调用(F1);Playwright 一个用例里能开多个互相隔离的浏览器会话;用例规格 §4 已有登录说明,改成按角色列 |
| F8 | 用流程脚本造前置数据 | 建议新增 ➕ | 用例需要前置数据,如测「审核通过活动」要先有一个待审核的活动 → 用例规格的数据前提写「待审核活动 1 个:用流程『活动创建』造」→ 开跑前确认数据前提时列出「这 2 项由流程自动造,这 1 项需要你准备」→ 跑这条用例时先跑造数据的流程,再进被测步骤 | ① 造数据的流程失败 → 这条用例记「跳过」,备注「前置数据没造成:『活动创建』第 4 步失败」,不算被测功能失败 ② 页面上造不出来的数据(三个月前的历史订单、批量导入的数据)→ 照旧人工准备 ③ 造数据只看流程每一步成功(K1),不做数据核实 | 用例规格 §3 有数据前提清单(现在全是「待人工备」);流程脚本可以直接调用(F1) |
| F9 | 不经 agent 直接跑脚本 | 支撑 | 测试同学第一次在脚本目录(默认 `docs/playwright/`;项目原有 Playwright 时是它的测试目录)装依赖和浏览器,按使用说明配好自己的账号和查库连接 → 跑某个需求:`npx playwright test cases/活动报名上限`;跑全部:`npx playwright test`;想看着跑加 `--headed` → 看 Playwright 自带的报告:每条用例每一步过没过,失败的有截图和执行回放 → 有失败交给开发者跑 `/ui-run` 判断并修脚本 | ① 没配账号 → 登录那步失败,提示「本机没配运营账号的密码,见使用说明」 ② 没配查库或 Redis 连接 → 写操作用例以「未核实」失败 ③ 遇到验证码或 SSO、本机还没有登录状态 → 提示先用 `--headed` 跑一次手动登录 ④ 不生成需求目录里的 xlsx,也不改脚本 ⑤ 换环境:指定入口地址,如 BASE_URL=https://test.example.com | Playwright 原生命令,自带报告和执行回放;用例脚本按需求分目录,和 `docs/bruno/` 按需求分一样 |
| — | 文字版操作手册 | 边界外 | 不做:脚本就是经验,坑写在脚本注释里,不另写一份文字手册(两份会不同步) | — | — |
| — | 配 CI 流水线 | 边界外 | 不做:脚本放进流水线也能跑,但这次不负责配 | — | — |
| — | 核实 MQ 消息、ES 索引、文件存储 | 边界外 | 不做:这次只核实数据库和 Redis | — | — |
| — | 清理测试数据 | 边界外 | 不做:查库查缓存都只读,测试产生的数据不删;要删就在用例里加删除步骤 | — | — |
| — | 视觉回归、跨浏览器、性能测试 | 边界外 | 维持现状,不做 | — | — |
| — | 测试中发现的业务事实回写业务文档 | 边界外 | 不做:如「审核通过才能报名」,归「业务与经验回写」需求;本需求只管页面怎么操作 | — | — |

**体验决策**:

- 经验就是脚本:不另写文字手册,坑写在脚本注释里(F1、F2)。
- 脚本提交进仓库 `docs/playwright/`,团队共用;别人拉代码会多出这个目录,不装、不跑就不受影响(F1)。
- 首测卡住时停下问开发者,问过的写进脚本,下次不再问(F1)。
- 复测修好的那一步直接存回脚本,报告里写一句修了什么(F2)。
- 数据核实写进脚本,单独跑也验数据;没配连接的机器上,写操作用例以「未核实」失败(F3、F9)。
- Redis 由 cgraphx 新增只读查询,只放行读命令(F4)。
- 数据不对用新增的第 7 种状态「失败-数据核实」,结果 JSON 升到 schemaVersion 2(F6)。
- 单独跑用 Playwright 原生命令,看 Playwright 自带的报告(F9)。
