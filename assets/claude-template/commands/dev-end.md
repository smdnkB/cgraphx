## 你的任务

对一个**做完的需求**「正向合成」一份收口档案,落 `docs/features/<feature-id>/<前缀>-收口档案.md`(文件前缀 = feature-id 去掉日期段 `YYYY-MM-DD`)。

- **正向汇总、不从代码倒推**;痕迹缺失的字段诚实标来源,不假装是过程留痕。
- 确认已上线时,顺带写发布记录(见「发布记录」)。

## 输入(使用者提供)

- 目标 **git 仓**路径 + 该需求的 **SHA 范围**(或时间窗)
- **测试报告**(格式不限 → 你用语义理解读,不做机械解析)
- **AI 会话留痕**(Claude Code / Cursor 的 transcript,带时间戳)——AI+开发默认有
- **是否已上线**;已上线的话,版本号或 tag、上线时间

## 产出 schema(逐条照填;H2 标题独占一行、精确等于规范标题;半角冒号)

```
---
req_id: <簇名>
簇: <目标标识/路径>
status: 已收口
mode: poor
created: "<YYYY-MM-DD>"
git_range: "<首SHA>..<末SHA>"
---

# 收口档案:<需求名>

> 产物: closure_record
> 依据: spec@<主 spec 指纹前 7 位,用 cgraphx features show <feature-id> 查;没有主 spec 就删掉这一行>

## 历时
- 立项:<日期> · 完成:<日期> · 日历跨度:<N 天>
- 实际投入(估算,到小时):<以会话活跃时段为主 + commit 时间戳佐证,综合判断,约 X 小时 ≈ Y 工作日;标估算性质>
## 产物清单
- 文档:<路径> · 代码:<SHA> <一句> · 决策锚点:<锚>
## 测试汇总
- 结果:<pass/fail> · 覆盖:<测到的功能点数/功能点总数,未测的写 F 编号> · review:<pass/fail/cannot_verify>
## 知识引用归纳(命中)
- [hit] <知识 id/path> — <这次怎么用上的一句>  [来源: AI会话 | 事后补录]
- 确认无: <非占位理由>
## 澄清记录(缺口)
- [gap] <被迫问人的一句>  [来源: AI会话 | 事后补录]
- 确认无: <非占位理由>
## 新确认(沉淀候选)
- [new] <值得沉淀的一句>  [来源: AI会话 | 事后补录]
- 确认无: <非占位理由>
```

## 填法要点

- **历时(两层)**:
    - 日历跨度 = 首末 commit 天数,**诚实标注它只是日历跨度**(常与真实投入差很远,如 40 天日历实际只十来天在动)。
    - 实际投入(**到小时**)= AI+开发默认有会话,**以会话活跃时段为主信号**(反映实际坐着开发的时段,含 commit 之间的调试/思考),commit 时间戳分布为辅佐证。**你综合判断**估「约 X 小时 ≈ Y 工作日」:靠近的活跃时段并成连续工作累加、隔远算中断——**宽松思路、不是死阈值**,别机械卡点。标估算性质。诚实局限:低估「攒着末尾提一次」、不计离线开会/调研;是代理不是精确测量。
    - 注意: 开发历史与实际投入**必须派 `task-history` 子 agent 获取**(Agent tool,`subagent_type: "task-history"`,prompt 传入:目标任务编号/名称 + git 仓路径 + SHA 范围或时间窗 + 关注点「工作量/活跃时长」)。直接采纳其返回的「工作量结论」节(timeline 实测的活跃时长区间 + 局限标注)填入本节,**不要自己跑 `cgraphx timeline query` 重查**;子 agent 报「覆盖不足」时才退回上面的会话活跃时段估算法,并在档案标注非 timeline 实测。
- **产物**:git log 取 SHA 范围 + 关键交付路径;决策锚点无 HOW 文档就据 commit/会话补。
- **测试汇总**:语义读测试报告,别机械归一化解析。
- **命中/缺口/新确认(核心)**:痕迹不在文档时——**有 AI 会话就从会话正向读、标 `[来源: AI会话]`**(一手正向留痕,可信 > 补录);**无会话才向人补录、标 `[来源: 事后补录]`**。都不假装是过程文档留痕。
- **`[来源: AI会话]` 真实性铁律**:标它 = 你**真在会话 transcript 里读到** AI 召回/引用了那条知识、或被迫问了那个问题。**能读到真实会话就必须真读**,别拿 git 仓/handoff/中间文档**反推冒充**——「决策恰好和某文档吻合」是**内容吻合、非真召回**(倒推),只能标 `[来源: 事后补录]` 并注明推断。命中尤其别只找「显式引用」:遍历关键决策逆向问「做这步必须先知道什么」得到**候选**,但**必须回会话确证**才标 `[来源: AI会话]`,否则标事后补录。带**可抽审锚点** `[来源: AI会话 · <会话id/行号>]` 更佳。
- **三格别拔高凑数**:命中 = 库里已有知识这次被召回用上(✗ 复用自己写的函数 / 跑某流程 ≠ 命中);缺口 = 知识库缺了某条被迫问人(✗ 正常方向决策 ≠ 缺口);新确认 = 值得沉淀的新知识/规则。**纯机制需求三格全「确认无」是正常诚实收口**,别找复用/决策/经验来凑。
- **知识格内只放** `- [hit]/[gap]/[new]` 条目 **或** `- 确认无: <理由>` 行,别塞注释/散文。理由**不可**是占位符(空 / 无 / N/A / TODO / TBD / 待定 / 待补…)。

## 产出后自检
1. 六节齐全(历时 / 产物清单 / 测试汇总 / 命中 / 缺口 / 新确认),H2 标题精确等于规范标题。
2. 三个知识格每格 ≥1 条 `[hit]/[gap]/[new]` **或**一条非占位「确认无」。
3. poor 的每条 `[hit]/[gap]/[new]` 带 `[来源: AI会话]` 或 `[来源: 事后补录]`(任一)。
4. frontmatter 五键齐(req_id / 簇 / mode / created / git_range),created / git_range 带引号包成字符串。
- **内容质量**(命中准不准 / 澄清真不真 / 历时估得合不合理):**非机械可验**,交人工 review 或 LLM-judge。**禁止往档案塞关键字假装验证过内容**——校验查的是结构与非占位,不是内容对。

## 发布记录(确认已上线才写)

- 收口时问用户:这个需求上线了吗?确认已上线才写;没上线就不写,告诉用户上线后再跑一次 `/dev-end` 补。
- 再跑 `/dev-end` 时,如果收口档案已经在,只补发布记录,不重写收口档案。
- 文件 `docs/features/<feature-id>/<前缀>-发布记录.md`;同一需求多次发布写在同一个文件里,在「版本与上线时间」表里追加一行。
- 至少有版本号或 tag、上线时间;关联 commit、分支、发布说明按需加。版本号和上线时间问用户,不猜。
- 写了它,平台上的任务才会显示「已发布」(服务端协议 1.3 及以上)。

范例:

```markdown
# 发布记录: 积分发放规则

> 产物: release_record

## 版本与上线时间

| 版本或 tag | 上线时间 | 说明 |
|---|---|---|
| v2.3.0 | 2026-10-20 15:30 | 首次上线:下单积分按会员等级发放 |
| v2.3.1 | 2026-10-22 10:00 | 修复退款时少扣 1 分 |

## 关联提交

- v2.3.0:`a1b2c3d..e4f5a6b`,分支 `release/2.3`
```
