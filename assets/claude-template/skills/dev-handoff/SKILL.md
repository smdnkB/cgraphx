# 会话交接 (dev-handoff)

## 定位

探索或澄清结束后,把工作交给 1~N 个新会话继续:每个目标落一个产出目录 + 一份交接文件,新会话凭启动语接着干;当前会话尚未确定归属时,先写主任务目录即绑定到主任务。

- **功能方案原样带走**:clarify 不落文件,终确认的功能方案只在对话里,交接文件是它进新会话的唯一载体——新会话的 `/dev-spec` 从这里原样收录为 spec 第一节。所以照抄:不概括、不补充、不重新编号。
- **拆会话按功能点分**:每个功能点只归一个会话,编号沿用功能方案;每份交接文件只带本会话负责的功能点。

| 交接时 | 交接文件 | 下一步 |
|---|---|---|
| 澄清已终确认 | 带「功能方案」节 | `/dev-spec` |
| 只做了探索,还没澄清 | 不写「功能方案」节;拆多个会话时按要分别澄清的需求拆 | `/dev-clarify` |
| spec 已写好 | 不抄功能方案,本任务范围指向 spec | 按规模 `/dev-plan` 或 `/dev-impl` |

## 流程

1. **定交接目标(1~N 个)** —— 有功能方案、要拆成多个会话时,先给分配提案,一行一个会话:

   ```text
   F1 按会员等级发放积分、F2 退款扣回积分 → 积分发放(主任务)
   F3 兑换按新流水校验余额 → 积分兑换,依赖 F1、F2 写入的积分流水
   ```

   功能点全部分完,一个只归一个会话;互相依赖紧的放一起,分开的写进「依赖」。没有功能方案时,问清每个新会话要继续做什么。用户确认后,每个目标确认一个 feature-id:
   - `docs/features/` 下已有对应目录 → 直接复用,不重新命名。
   - 没有 → 按 dev-spec 第 0 步和「产物位置与命名」新建(业务 ID、标题语言由用户确认,不把中文转成英文 slug)。
   - feature-id 一旦确认即固定,新会话里的 `/dev-spec` 直接复用。
2. **确认主任务与负责人** —— 多个目标时让用户指定主任务(默认第一个);负责人按 dev-spec 第 0 步确认:取 `git config user.name`,必须和负责人本人的一字不差。
3. **看当前会话归属,再写交接文件** —— 先跑 `cgraphx task current`:
   - 未绑定,或来源是「自动(读)」→ 先写主任务目录,当前会话由此确定绑定到主任务。
   - 来源是「自动(写)」或「显式绑定」→ 写交接文件**不改变**当前会话的归属(确定后不切换),如实告诉用户当前会话仍归哪个任务;此时主任务只决定共享背景放在哪里。
   - 然后先写主任务目录的交接文件,再写其余目录;路径 `docs/features/<feature-id>/<文件前缀>-交接提示词.md`,文件前缀 = feature-id 去掉开头的日期。正文照下方样例写,各节写法见样例后的说明。
4. **输出启动语** —— 每个目录一条,原样给用户;内容只有 `先读 docs/features/<feature-id>/<文件前缀>-交接提示词.md 再继续。`,不附加摘要或交接全文。

## 交接文件样例

澄清已终确认,按功能点拆成两个会话:主任务「积分发放」负责 F1、F2,「积分兑换」负责 F3。

`docs/features/2026-10-18-REQ-1024-积分发放/REQ-1024-积分发放-交接提示词.md`:

```markdown
# 交接: 积分发放规则

> 产物: handoff
> feature-id: 2026-10-18-REQ-1024-积分发放
> 负责人: zhangsan
> 日期: 2026-10-18
> 主任务: 本任务

## 本任务范围

- 负责 F1 按会员等级发放积分、F2 退款扣回积分,功能方案见下节
- 不含 F3 兑换按新流水校验余额(归 `2026-10-18-REQ-1024-积分兑换`)

## 功能方案

> 澄清终确认的原文,只含本任务负责的功能点;`/dev-spec` 原样收录为 spec 第一节。

**一句话**:原来下单统一返 1% 积分;这次按会员等级发放,退款时按原比例扣回,兑换按新的积分流水算余额。

用户会这样用:

    订单支付 ──→ 按等级发积分 ──→ 积分流水 ──→ 兑换页算余额
    订单退款 ──→ 按原比例扣回 ──→ 积分流水

| 编号 | 功能点 | 类别 | 行为链(已锁定) | 边界 | 落地依据 |
|---|---|---|---|---|---|
| F1 | 按会员等级发放积分 | 核心 | 订单支付成功 → 普通会员 1 元 = 1 分、黄金会员 1 元 = 2 分,立即到账 → 积分流水记一条(订单号、规则版本) | ① 实付不足 1 元 → 不发积分,不记流水 ② 付款后会员等级变了 → 按付款时的等级发 | member 表有 level;积分流水表 points_ledger 已有 |
| F2 | 退款扣回积分 | 支撑 | 订单退款成功 → 按原发放比例扣回 → 积分流水记一条扣回 | ① 部分退款 → 按退款金额比例扣回,不足 1 分舍去 | 退款回调 refund_notify 已有 |
| — | 积分有效期调整 | 边界外 | 不做:有效期维持自然年,次年 1 月 1 日清零 | — | — |

**体验决策**:积分在支付成功后立即到账,不走次日批量发放。

## 已锁定决策

- 积分计算放在现有 points 模块,不新起服务(用户指定)
```

给用户的启动语(每个目录一条,原样分别发给对应新会话):


- **本任务范围**必须是第一节(`cgraphx features check` 校验首个二级标题):负责哪几个功能点,不含的归哪个目录。
- **功能方案**:一句话、「用户会这样用」流程图照抄;功能点表只抄本会话负责的行,编号不重排;编号「—」的不做项跟着相关的功能点走,拿不准的放主任务;体验决策只抄管到本会话功能点的;审核结论和结尾问句不抄。
- **已锁定决策**:只放功能方案之外用户拍板的事,比如指定的技术约束;没有就省略。
- **未决问题**:还没拍板的问题,一条写「问题——待谁确认;推荐…」;有这一节,「下一步」写 `/dev-clarify`(先定未决问题,再 `/dev-spec`);没有就省略。
- **依赖**按功能点写;**共享背景**只写在主任务文件里(需求来由,加上探索核实过、写 spec 时不用重查的事实),非主任务文件只写一行指向主任务交接文件。

## 不做什么

- 不写 spec / plan / 代码。
- 不改写功能方案;没终确认的提案不进「功能方案」节,用户没拍板的推荐不进「已锁定决策」——放「未决问题」并附推荐。
- 不把一个功能点分给两个会话。
- 不自动开启新会话——启动语交给用户,由用户贴给新会话。
- 不把交接全文或摘要塞进启动语。
