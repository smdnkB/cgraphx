# 泳道图画法

PlantUML activity-beta。dev-clarify 的功能方案讨论稿和 doc-delivery 的设计文档共用这套画法;完整的图见同目录 `功能方案-讨论稿范例.md` 和 doc-delivery 的 `references/设计文档.md`。

澄清讨论稿里各功能点的图(接口内逻辑图、编排图等)另守同目录 `功能点配图.md`;设计文档不适用。

- 每张图开头照抄 `@startuml` 和这段样式头,结尾写 `@enduml`;样式头逐字一致(改样式时同步所有样例):

  ```text
  @startuml
  skinparam backgroundColor #FFFFFF
  skinparam Activity {
    BackgroundColor #F1F1F1
    BorderColor #181818
    FontColor #000000
  }
  skinparam Swimlane {
    BorderColor #181818
    TitleBackgroundColor #FFFFFF
    TitleFontColor #000000
  }
  skinparam ArrowColor #181818
  ```

- 泳道用 `|泳道名|`,先写用户/调用方,再写系统;按声明顺序排,不再从右往左。
- `start` 起;步骤写 `:文字;`;结果写 `:结果文字;` 再 `stop`;用户/调用方的泳道要有起点和结果,每个分支各接一个结果。
- 判断写 `if (条件?) then (是) ... else (否或业务标签) ... endif`。同一个 `if` 的两个分支第一步放同一泳道;必须分属左右两侧时,`then` 分支放左边、`else` 放右边,并且两个分支的标签都按物理左右检查(PlantUML 把任意分支标签按左右贴,不只 是/否);标签可以写「是/否」或业务词(如「超时或报错」),但必须和实际分支内容一致。分属两侧又无法满足左右顺序时,把分支第一步改回同一泳道,不要调换泳道或反转条件。
- 澄清讨论稿的判断框写一句意思加口径编号(如 `有订单? K1、K2`),完整定义写在图下的口径表;设计文档没有口径表,直接写业务条件(如 `这笔订单发过积分?`),不造 K 编号。
- 这次新增或改动的活动末尾加 `<<#FFF3B0>>`;改动的判断在 `if` 行末加 `<<#FFF3B0>>`(PlantUML 1.2026.9 支持给判断菱形上色)。
- 讲一个环节或一个功能点怎么走的图,正常走通的路径标绿:活动之间写 `-[#2E7D32,bold]->`;`if/else` 的分支入口也要标绿,把 `-[#2E7D32,bold]->` 单独写一行放在 `then`/`else` 后面(不要写成 `then -[...]-> :...;`),再写分支的第一步。
- 一张图不超过 15 个框/节点(活动、判断、开始/结束都算),超了就拆。
- 图里只写业务语言,不写类名、方法名、行号和 SQL。
- 活动文字不用半角分号和半角引号;中文直角引号 `「」` 可以用于界面原文;括号只用于 `if (...)` 条件;换行用 `\n`。
- 完整样例见 `功能方案-讨论稿范例.md`。
