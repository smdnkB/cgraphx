# 澄清需求 (dev-clarify)

## 定位

- **提案-改稿,不是问答**:AI 给完整的端到端行为链提案,人只做「采纳 / 改具体元素」——判断永远比生成便宜,看不懂的地方自己会暴露。人不答题,人审稿。
- **两个环节,本 skill 是环节一**:环节一定业务(业务口径 + 人可感知的行为链:操作 → 表现 → 结果数据);环节二定细节方案(机制选型、数据模型、接口契约,归 spec;函数命名等代码细节归实现)。分层判据是**有没有使用后果**。
- **讨论稿就是审稿面**:不看源码就能把一个需求看懂的样子 = 功能清单 + 每个功能点一张图 + 图里每一步的口径。提案直接写进讨论稿,对话里只说写到了哪几节、哪几处要人拍板;图和口径表只有讨论稿里这一份。
- **口径挂在步骤上**:图里要取数、判断、计算的步骤(哪些订单算、近 90 天按哪个时间、金额扣不扣退款)都是口径,口径换一种,用户看到的数据就不一样,所以归本阶段。每个这样的步骤都在图下的口径表里有一行;缺了哪一行,那一步就是没定——图看着具体,其实没定。
- **体验变体上浮规则**:任何有使用后果的技术决策,不允许躲在环节二定——必须以「体验变体」形态在本阶段让人选。「同步等待 vs 后台任务+通知」实现上是细节,但等 30 秒转圈和立刻收通知是两种体验,所以必须上浮。
- **现实校验是每张图、每条口径的验收条件**:口径的依据写到表名.字段;没有表结构和既有实现做依据的提案就是空中楼阁,依据不成立,不写进讨论稿。

<HARD-GATE>
功能方案经用户终确认之前:不写 PRD/spec/plan/代码,不搭脚手架,不采取任何实现动作。无论任务看起来多简单。
**只有用户能锁定决策**——AI 的提案不是确认,采纳才算。
不妄下断言,不掩饰困惑,坦诚权衡。
</HARD-GATE>

## 流程

```
⓪ 现实探索 ──→ ① 识别功能点+分类 ──→ ② 清单对齐 ──→ ③ 口径分歧 ──→ ④ 逐点写讨论稿、改稿
                                                                             │
              ⑦ 人终确认 ←── ⑥ 对抗式专项审核 ←── ⑤ 收拢讨论稿 ←─────────────┘
```

按情形裁剪;允许回跳——后面发现前面没搞清,退回对应工序重做:

| 情形 | 走哪几步 | 讨论稿怎么写 |
|---|---|---|
| 多功能点的需求 | 全工序 | 照范例 |
| 单功能点小需求 | ⓪ → ③ → ④ 一节 → ⑤ → ⑦ | 照范例,功能清单一行,不做的另起「—」行 |
| bug 修复 | ⓪ → ③ → ④ → ⑤ → ⑦ | 两条链:「现在:点导出 → 转圈 30 秒 → 报系统错误」「改后:超过 1 万条自动转后台,做完站内通知」;图只画「改后」,修的地方标黄,「现在」那条链写在图前那句说明里 |
| 重构 / 技术改造 | ⓪ → ④ → ⑤ → ⑦ | 一句话写「用户感知:无变化」;那一节列必须不变的行为:导出入口、文件格式、列顺序、权限判断、统计口径 |
| 数据任务(修数 / 迁移 / 回填) | ⓪ → ③ → ④ → ⑤ → ⑦ | 圈数据的条件就是口径,写进口径表;改前 / 改后各一条真实样例:「#A1023 channel 空 → web」 |

- ③ 只在口径有分歧时走,没有就跳过;其余口径在 ④ 直接写进图下的口径表。数字不对的 bug 多半是口径错了:口径表只写改后的口径,现在按什么算写在那一节开头的说明里(「现在:已取消的订单也算进金额」)。
- 走哪几步里没有 ⑥ 的不派审核,澄清结果里也不写「审核结论」那一行。

### ⓪ 现实探索(前置门,必做)

1. 会话中没用过 `knowledge-recall` 则先召回相关概念;命中的实体主条目 = 代码阅读入口。
2. 读项目结构/文档/代码/测试/API;`db-query`(查库/DDL 必须用,本地 `docs/schema-knowledge/` 优先,没有先提示跑 `/init-ddl` 建基线)、grep/Read(调用关系必须用)。调用前告知用户。接口类功能点要读到入口里的每个判断(开关、参数校验、调下游、异常处理),图照代码顺序画。
3. 路径:从实体主条目的代码入口 + 相关表指针进代码,不盲目全局搜。**产出是现实约束清单(事实,不是方案)**:表结构(表写全名)、既有实现、接口类功能点的入口位置(文件:行),以及知识库和既有报表里已有的口径;收拢时写进讨论稿 `---` 以下,环节二直接复用。

### ① 识别功能点 + 分类标注

AI 识别需求包含哪些功能点,每个点打类别。分类决定人审的深度——大需求几十个点,人不可能个个细审:

| 类别 | 含义 | 人的默认姿态 |
|---|---|---|
| 核心 | 需求的根本问题,缺了不成立 | 必须逐节细审 |
| 支撑 | 让核心可用的配套 | 审关联,不抠细节 |
| 建议新增 | AI 识别出用户没提但可能需要的 | **默认砍**,人显式要才留 |
| 边界外排除 | 明确不做的,防蔓延 | 只确认不做 |

「建议新增」必须注明「基于现有 XX 能力/表可支撑」,注不出来就砍。

功能点按 F1、F2… 编号,边界按 ①②… 编号,清单锁定后不再变;spec、plan、测试按编号引用(如 F1②),不抄原文。

### ② 清单对齐(粗粒度、低成本)

给功能点清单(带类别),人做增/删/改:「漏了导出记录的查看」「不要批量导出」「导出和报表算一个点」。清单锁定后才进提案——清单层面砍一个点成本是一行字,提案层面再砍是整节的讨论,粗筛先做。

### ③ 口径分歧

口径有分歧的先拍板,再写讨论稿:新定的和既有报表不同、系统里同一个词已有两种算法时,像体验变体一样给两个选项让人选;能查库就给出两种口径下的实际数:「9 月按下单时间是 3,412 单,按支付时间是 3,389 单,差的是跨月支付的订单——对账按支付时间,还是跟销售日报一致按下单时间?」

- **先沿用,再新定**:知识库实体条目里已有的口径 → 既有报表、实现里的口径(同一个词不出第二种算法)→ 都没有才新拟。没有分歧的口径不在这一步过,④ 直接写进用到它的那张图下面。
- **写稿时才发现的分歧**:④ 写到某一步才发现的,也照这样给两个选项和实际数,列进那一批「要你拍板的」;口径表先写默认那种,编号后标(待你定),人选了去掉。
- **业务方说了算的口径**:开发者定不了的(活跃客户、有效订单这类要运营、财务认的),照样给默认值写进口径表,编号后标【待确认】并写明找谁,列进讨论稿「必须在 spec 前解决的问题」,不算锁定。
### ④ 逐点写讨论稿、改稿

每个功能点在讨论稿里写一节,**全部业务值给具体值,不留问号**,结果写到用户能看见的程度(导出哪几列、页面显示什么、提示原文)——人看到的是一稿完整默认,不是一个待填空的问题。讨论稿写第一节时就建,放哪见 ⑤;一节照这样写(整份见 `references/功能方案-讨论稿范例.md`):

````markdown
### F1 订单导出(核心)

订单服务收下导出请求就返回,后台导出任务异步取数、生成文件,做完站内通知;导出记录和 F2 共用,运营到 F2「我的导出」下载。

```plantuml
(编排图:运营、订单服务、导出任务三条泳道,照 references/功能点配图.md 画)
```

| 编号 | 哪一步 | 怎么判定 | 算 / 不算(例子) | 依据 |
|---|---|---|---|---|
| K4 | ② 谁能导出 | 有「订单导出」权限点的角色 | 算:运营、财务;不算:客服 | `role_permission.perm_code`(新增一个导出权限点);新定 |
| K1 | 取订单 · 哪些算订单 | 已支付的订单,后来退款的也算 | 算:已支付、已退款;不算:待支付、已取消 | `orders.status`;沿用「销售日报」 |
| K2 | 取订单 · 近 90 天 | 按支付时间,含今天往前数 90 天 | 今天 10-21:07-24 支付的算,07-23 的不算;07-23 23:59 下单、07-24 00:01 支付的算 | `orders.paid_time`;新定(销售日报按下单时间) |
| K3(待你定) | 生成文件 · 金额 | 实付金额,不扣退款;退款另起一列 | 实付 100、退了 30 → 金额 100,退款 30 | `orders.paid_amount`、`refund_record.amount`;新定(销售日报扣了退款) |

🎭 体验变体(待你定):后台任务 + 完成通知(图里画的这种,立刻返回,做完提醒)vs 等待框(盯着转圈,最长 30 秒)
````

- **图**:按 `references/功能点配图.md` 选图、画图;从哪个功能点进来、回到哪个功能点,活动图写在触发方的第一步和最后一步,别的图种写在图前的行为链里,都和功能清单的「从哪进 → 到哪去」对上。图上的分支就是边界:空数据、超量、没权限、重复操作时用户看到什么(提示原文、按钮在不在),只画这个功能点真会遇到的;失败分支带 ①② 编号、写提示原文;改结构后边界编号跟着分支走,不重排,新加的分支接着往后编。第一次给讨论稿路径时附一句查看提示(见下面对话示例)。只改一句文案、一两步的页面操作不画图,那一节写一行「行为链:操作 → 表现 → 结果」(写到显示哪几项、提示原文)和一行「边界:① …」,两行之间空一行;一节里画了图、另有一两步页面操作的(范例 F2 的列表页),那部分写一行行为链放在图前。
- **口径表**:跟在每张图下面,没画图的跟在行为链后面。
  - 口径按 K1、K2… 编号,全文唯一,锁定后不变,新的接着往后编;spec、plan、测试按编号引用,不重写定义。
  - 这一节里每个取数、判断、计算的步骤各一行,行按图前行为链和图里的先后排;参数为空这种纯校验、点按钮、提示文字不写。取数、判断、计算的框里写一句意思加编号(`取近 90 天的订单 K1、K2`、`有订单? K1、K2`),表里写全。
  - 例子落到边界:含不含当天、跨零点算哪天、退款扣不扣——人看定义会点头,看到「07-23 的不算」才会说「要算」。
  - 依据写到表名.字段;这次才有的数据写业务说法并注明「新数据,存哪由 spec 定」,不起表名;再写沿用哪个功能或报表,还是新定。表名、字段只放这一列,「怎么判定」只写业务说法。
  - 共用的口径只在第一次用到的那一节写全,别处写「见 Fx」;一条口径在几步各用一部分的,按步骤拆成几行,每行只写这一步那部分;同一节里后面的判断只是沿用前面取数的结果(`有订单? K1、K2`),不另起一行。
- **关联**:页面怎么串,写进功能清单的「从哪进 → 到哪去」;共用数据、互相依赖或冲突的,写进那一节开头的说明(「和 F2 共用导出记录」),防止人在孤立的一节上拍板、到 ⑤ 才发现互相矛盾。
- **现成的和新做的**:这次新增或改的照 `references/功能点配图.md` 各图的标法标黄;时序图的消息、状态图的转移标不了黄,新加或改了的写进那一节开头的说明。不标黄、说明里也没写的就是现成的,「收入、欠费本来就按 custId 查」这类依据靠它表达;表结构、行数、索引这类技术事实写进 `---` 以下的现实约束清单,不进图。
- **🎭 体验变体**:凡有使用后果的技术分叉,在那一节最后写一行,给 2 个变体让人选,图画默认那种;人选定后改成「🎭 体验决策:…」。无使用后果的细节不写。常见的分叉按用户感觉到的差别写:

  | 技术分叉 | 用户感觉到的差别 |
  |---|---|
  | 同步 / 异步 | 盯着转圈等 vs 立刻返回、做完通知 |
  | 实时查 / 缓存或定时汇总 | 看到此刻的数 vs 最多旧 10 分钟 |
  | 硬删 / 软删 | 删了找不回 vs 回收站里能恢复 |
  | 全量 / 分页或限量 | 一次看全 vs 只能翻页、超过 1 万条要缩小范围 |
  | 整批回滚 / 部分成功 | 要么全成要么全不成 vs 成功的留下、失败的列出来 |

- 涉及新页面、界面布局,或 🎭 变体会改界面 → 提示一句「要不要用 `/dev-wireframe` 出个方案对照,看着界面选?」;用户不需要就继续。

写完一批,对话里只说写到了哪几节、哪几处要拍板,不重抄图和口径表:

```markdown
讨论稿 v1 写好了 F1、F2 两节:`docs/features/2026-10-21-REQ-1024-订单导出/REQ-1024-订单导出-功能方案-v1.md`(用支持 PlantUML 的 Markdown 预览打开;IDEA:设置 → 语言和框架 → Markdown → 启用 PlantUML)。

要你拍板的:
- 🎭 F1 导出方式:后台任务 + 完成通知(图里画的这种)vs 等待框(最长 30 秒)
- K3 金额扣不扣退款(写到「生成文件」定导出哪几列时才对出来,销售日报的金额扣了退款):不扣、退款另起一列(口径表里写的这种)vs 跟销售日报一样扣掉;9 月合计不扣是 128.6 万,扣了是 124.1 万
- 【待确认】K6 文件留几天:默认 7 天,跟报表导出一致,找运营认

其余照图和口径表,不改就是采纳;要改直接说编号(F1②、K2)。
```

人的改稿动作分两档(收拢后再改,先照 ⑤「放哪」出下一版,在新版里改):

| 改动 | 流程 |
|---|---|
| 业务值(90→30、换筛选条件、改功能命名、增删功能点) | **一拍即合**:直接采纳,在讨论稿里原地改图和口径表,功能清单里写到这处的一起改;删掉的那一节里写全过的口径,挪到下一个用到它的节写全 |
| 链结构(等待框→后台任务、改变触发方式) | **二拍循环**:AI 在这一节口径表下面加一行「**改法候选(待确认,影响边界 ③ ④)**」再接候选图(一个功能点同时只放一张,候选不算新版本),回报影响面 → 人对照两张图确认 → 候选替换原图、删掉这一行,口径表的行序和「哪一步」、功能清单里写到这处的跟着改;不采纳就把候选和这一行一起删掉 |

一次写几节以人能审完为准(建议核心类一批、其余一批);人不改就是采纳,不追问「确定吗」。

### ⑤ 收拢讨论稿

全部功能点锁定后收拢:删掉「写稿中」那行;体验变体都改成体验决策,口径编号后的(待你定)都去掉;照 `references/功能点配图.md` 核一遍有没有漏画、口径表有没有缺行,共用的数据和依赖写进节开头没有;在 `---` 以下补齐供 spec 用的各项。方案整体亮相正是终检点:人顺着功能清单的「从哪进 → 到哪去」把各节的图连起来走一遍,逐点讨论看不见的整体问题(点与点不衔接、整体体验不像想象的那样)在此暴露。

- **放哪**:`docs/features/<feature-id>/<前缀>-功能方案-v<N>.md`。④ 写第一节时建 v1:标题、两行头注、一行「> 写稿中,收拢时补齐其余各节。」、一句话、功能清单,再一节一节往下写;收拢前都在 v1 里原地改。之后改一次出一版,N 往上加,旧版保留:⑥ 回修、⑦ 时再改、写完 spec 回来改,都先把最新那一版复制成下一版,在新版里改。需求目录里已经有讨论稿时(换了会话、回来改),接着最新那一版:带「写稿中」那行的在它里面接着写(换会话的照交接文件「澄清进度」从 ④ 接着写);带「审卡中」那行的是旧版格式(各功能点只有「Fx 怎么走」的图),先照范例补上一句话、功能清单和各节的口径表,标记换成「写稿中」再接着写;已收拢的出下一版。还没有需求目录时,按 dev-spec 第 0 步和「产物位置与命名」新建(业务 ID、标题语言及规范里的其他段由用户确认)。
- **不是契约**:不写 `> 产物:` 头部,不登记;spec 原样收录人终确认的那一版 `---` 以上的正文,之后以 spec 为准,讨论稿不再维护。
- **`---` 以下**:写一行「以下供 spec 使用,可不细读」,spec 不收录:
  - 必须在 spec 前解决的问题:标【待确认】的口径和没拍板的事,一条写「问题——找谁;默认…」;没有写「无」。不挡 spec、后续阶段才定的,另写一行「后续阶段的决策」
  - 已锁定技术约束:用户声明 + 兼容性边界;没有写「无特别约束」
  - 留给 spec 的细节决策:机制选型、数据模型、接口契约等;有使用后果的已作为体验变体选过
  - 影响半径与风险:相关时写,LOW / MEDIUM / HIGH / CRITICAL
  - 现实约束清单:⓪ 的事实,表写全名

### ⑥ 功能合理性专项审核(对抗式)

派**独立子 agent** 审核讨论稿:把同目录 `function-plan-reviewer-prompt.md` 全文作为 prompt,后接用户原话、⑤ 讨论稿全文和 `references/功能点配图.md` 的绝对路径。它按矛盾 / 遗漏 / 过度 / 分类失真四个维度挑刺,只报会导致大返工的问题。

产出问题清单回人裁决,不自行修改;发现的问题回对应工序修正,改完出下一版讨论稿。

### ⑦ 人终确认

按「澄清结果」输出,用户说「对了」才算结束;不自动继续。

## 澄清结果

澄清结果是 spec 的输入,不是契约:决策只有写进 spec 才成为义务——讨论稿 `---` 以上的部分会被 dev-spec 原样收录为 spec 第一节,所以要写成离开对话也读得懂的样子。对话里按下面的示例给,输出后停止,不自动调任何下游:

```markdown
**一句话**:原来运营要找开发导订单;这次在订单列表加「导出」,运营自己下载近 90 天的订单去对账。

**讨论稿**:`docs/features/2026-10-21-REQ-1024-订单导出/REQ-1024-订单导出-功能方案-v2.md`(功能清单、各功能点的图和口径表都在里面)

**功能点**:F1 订单导出(核心)· F2 导出记录查看(支撑)· 自定义导出列(建议新增,✂️ 已砍)

**体验决策**:导出走后台任务 + 完成通知,不让运营盯着转圈。

**必须在 spec 前解决的问题**:无

**审核结论**:对抗审核 1 个问题,已回修成 v2:K6 图上写「超过 7 天」,口径写「满 7 天过期」,整 7 天那一刻两种说法相反,统一成满 7 天。

**以上功能方案对吗?要改的直接说编号(K1、F2)。**
```

- **只用业务语言**:讨论稿 `---` 以上和对话里不出现模块、文件、函数名;图例外,照 `references/功能点配图.md` 写对外接口名、服务名、开关和请求头字段;口径表的依据列例外,写表名.字段。`---` 以下照 ⑤ 写,入口位置写到文件:行。
- **给澄清结果时 `---` 以上只留采纳了的**:没采纳的改法候选、没选上的体验变体都删掉;标【待确认】的口径照 ③ 留在口径表里。

### 结束条件

用户看完说「对了」,澄清才算结束;发现不对就改,改完出下一版讨论稿再给一次。结束前要满足:意图、全部功能点(含类别、图或行为链、边界)、每个取数判断计算步骤的口径、体验变体的选择、主要非目标都已锁定;要业务方确认的口径列进「必须在 spec 前解决的问题」,其余剩下的问题不挡 spec。

## 拷问模式(对已有方案)

用户带着现成想法/决策/方案来要求 grill 时:不走全工序,逐个决策点给「具体场景 + 该决策下的真实体验」做单问拷问——「你说导出要实时,那就是每次点导出用户盯着转圈等到数据出来,最长可能 2 分钟,这是你要的吗?」

## 推荐下一步

| 规模 | 条件 | 推荐 |
|---|---|---|
| 小需求 | 单点变更、1 到 3 个文件、单个模块 | `/dev-impl` |
| 大需求 | 预估变更文件 ≥10,且跨 ≥3 个相互独立的模块 | 先 `/dev-plan`,再 `/dev-impl-subagent` |
| 拿不准 | 其余情形 | 先 `/dev-plan` |

- 判断看需求规模,不看任务量;小全栈需求(加 1 个字段、改 1 个接口、加 1 处页面展示,跨 3 层)仍算小需求。
- 用户说「对了」后给下一步,由用户选:`/dev-spec` · `/dev-handoff`(换新会话继续,或按功能点拆成几个会话) · `/dev-wireframe`(涉及 UI 且还没线框,或决策改变了界面) · `/dev-plan`(大需求,写完用 `/dev-impl-subagent` 跑) · `/dev-impl`(小需求)。
- 事后文档发布后按需走 `/doc-delivery`。

## 红线(绝对不能做)

1. ❌ **不抛抽象问题** —— 任何决策点都以「嵌在行为链里的具体值」形态出现,不问「容忍度是多少」「客户怎么算」这种空维度题;默认值由 AI 先给足。
2. ❌ **不在此拍板实现细节** —— 机制选型、表设计归 spec,函数命名归实现;口径只定业务含义,写成什么查询条件归 spec;本阶段只收用户声明的约束。
3. ❌ **不跳过终确认** —— 用户没明确说「对了」,功能方案不算锁定;对抗审核的问题清单必须回人裁决,不自行修改。
4. ❌ **不编造** —— 无法明确的标【待确认】或列为后续阶段决策。
5. ❌ **不把未采纳的提案当成已锁定**。
6. ❌ **不自动继续下游** —— 输出澄清结果即停;写什么、做不做,归用户。
7. ❌ **不在对话里重抄提案** —— 图、口径表、行为链只写进讨论稿,也不另写功能点卡片;对话里只说写到了哪几节、要拍板什么。
