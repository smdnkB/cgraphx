# 澄清需求 (dev-clarify)

## 定位

- **提案-改稿,不是问答**:AI 给完整的端到端行为链提案,人只做「采纳 / 改具体元素」——判断永远比生成便宜,看不懂的地方自己会暴露。人不答题,人审稿。
- **两个环节,本 skill 是环节一**:环节一定业务(人可感知的行为链:操作 → 表现 → 结果数据);环节二定细节方案(机制选型、数据模型、接口契约,归 spec;函数命名等代码细节归实现)。分层判据是**有没有使用后果**。
- **体验变体上浮规则**:任何有使用后果的技术决策,不允许躲在环节二定——必须以「体验变体」形态在本阶段让人选。「同步等待 vs 后台任务+通知」实现上是细节,但等 30 秒转圈和立刻收通知是两种体验,所以必须上浮。
- **现实校验是每张卡片的验收条件**:没有表结构和既有实现做依据的提案就是空中楼阁,依据不成立,卡片不进确认。

<HARD-GATE>
功能方案经用户终确认之前:不写 PRD/spec/plan/代码,不搭脚手架,不采取任何实现动作。无论任务看起来多简单。
**只有用户能锁定决策**——AI 的提案不是确认,采纳才算。
不妄下断言,不掩饰困惑,坦诚权衡。
</HARD-GATE>

## 流程

```
⓪ 现实探索 ──→ ① 识别功能点+分类 ──→ ② 清单对齐 ──→ ③ 逐点提案改稿
                                                              │
              ⑥ 人终确认 ←── ⑤ 对抗式专项审核 ←── ④ 功能方案草稿
```

按情形裁剪;允许回跳——后面发现前面没搞清,退回对应工序重做:

| 情形 | 走哪几步 | 卡片怎么写 |
|---|---|---|
| 多功能点的需求 | 全工序 | 照③范例 |
| 单功能点小需求 | ⓪ → ③ 一张卡 → ⑥ | 照③范例,类别和不做的写在卡里 |
| bug 修复 | ⓪ → ③ → ⑥ | 两条链:「现在:点导出 → 转圈 30 秒 → 报系统错误」「改后:超过 1 万条自动转后台,做完站内通知」 |
| 重构 / 技术改造 | ⓪ → ③ → ⑥ | 「用户感知:无变化」+ 必须不变的行为:导出入口、文件格式、列顺序、权限判断 |
| 数据任务(修数 / 迁移 / 回填) | ⓪ → ③ → ⑥ | 改哪些数据 + 改前 / 改后各一条真实样例:「#A1023 channel 空 → web」 |

走哪几步里没有 ⑤ 的不派审核,澄清结果里也不写「审核结论」那一行。

### ⓪ 现实探索(前置门,必做)

1. 会话中没用过 `knowledge-recall` 则先召回相关概念;命中的实体主条目 = 代码阅读入口。
2. 读项目结构/文档/代码/测试/API;`db-query`(查库/DDL 必须用,本地 `docs/schema-knowledge/` 优先,没有先提示跑 `/init-ddl` 建基线)、grep/Read(调用关系必须用)。调用前告知用户。
3. 路径:从实体主条目的代码入口 + 相关表指针进代码,不盲目全局搜。**产出是现实约束清单(事实,不是方案)**,同时供环节二复用。

### ① 识别功能点 + 分类标注

AI 识别需求包含哪些功能点,每个点打类别。分类决定人审的深度——大需求几十个点,人不可能个个细审:

| 类别 | 含义 | 人的默认姿态 |
|---|---|---|
| 核心 | 需求的根本问题,缺了不成立 | 必须逐张细审 |
| 支撑 | 让核心可用的配套 | 审关联,不抠细节 |
| 建议新增 | AI 识别出用户没提但可能需要的 | **默认砍**,人显式要才留 |
| 边界外排除 | 明确不做的,防蔓延 | 只确认不做 |

「建议新增」必须注明「基于现有 XX 能力/表可支撑」,注不出来就砍。

功能点按 F1、F2… 编号,边界按 ①②… 编号,清单锁定后不再变;spec、plan、测试按编号引用(如 F1②),不抄原文。

### ② 清单对齐(粗粒度、低成本)

给功能点清单(带类别),人做增/删/改:「漏了导出记录的查看」「不要批量导出」「导出和报表算一个点」。清单锁定后才进提案——清单层面砍一个点成本是一行字,提案层面再砍是整张卡片的讨论,粗筛先做。

### ③ 逐点提案改稿(功能点卡片)

每个功能点一张卡片,**全部业务值给具体值,不留问号**,结果写到用户能看见的程度(导出哪几列、页面显示什么、提示原文)——人看到的是一稿完整默认,不是一个待填空的问题:

```
📦 F1 订单导出  [核心]
   运营在订单列表点「导出」按钮
     → 页面弹出等待框
     → 下载「订单导出_20261021.xlsx」:订单号 / 客户 / 金额 / 创建时间,
       近 90 天、按创建时间筛选
   ⚠️ 边界:① 近 90 天没有订单 → 提示「近 90 天无数据」,不生成文件
           ② 没有导出权限的角色看不到按钮
   ⚓ 落地依据:orders 表有 created_time 字段(本地 DDL 已核实);
      项目已有类似实现 report_export
   🔗 关联:与「导出记录查看」共用任务表
   🎭 体验变体:等待框(用户盯着转圈,最长 30 秒)
              vs 后台任务+完成通知(立刻返回,做完提醒)
```

- **⚠️ 边界**:空数据、超量、没权限、重复操作时用户看到什么,写具体表现(提示原文、按钮在不在);只写这个功能点真会遇到的。
- **⚓ 落地依据**必有:字段、表、既有实现;依据不成立的卡片在此拦截,不进确认。
- **🔗 关联标注**:有依赖或冲突的功能点必须标注,防止人在孤立卡片上拍板、到④才发现互相矛盾。
- **🎭 体验变体**:凡有使用后果的技术分叉,给 2 个变体让人选;无使用后果的细节不上卡片。常见的分叉按用户感觉到的差别写:

  | 技术分叉 | 用户感觉到的差别 |
  |---|---|
  | 同步 / 异步 | 盯着转圈等 vs 立刻返回、做完通知 |
  | 实时查 / 缓存或定时汇总 | 看到此刻的数 vs 最多旧 10 分钟 |
  | 硬删 / 软删 | 删了找不回 vs 回收站里能恢复 |
  | 全量 / 分页或限量 | 一次看全 vs 只能翻页、超过 1 万条要缩小范围 |
  | 整批回滚 / 部分成功 | 要么全成要么全不成 vs 成功的留下、失败的列出来 |

- 卡片涉及新页面、界面布局,或 🎭 变体会改界面 → 提示一句「要不要用 `/dev-wireframe` 出个方案对照,看着界面选?」;用户不需要就继续。

人的改稿动作分两档:

| 改动 | 流程 |
|---|---|
| 业务值(90→30、换筛选条件、改功能命名、增删功能点) | **一拍即合**:直接采纳 |
| 链结构(等待框→后台任务、改变触发方式) | **二拍循环**:AI 回报新链 + 影响面 → 人确认 → 锁定 |

一次呈现的卡片数以人能审完为准(建议核心类一批、其余一批);人不改就是采纳,不追问「确定吗」。

### ④ 收拢《需求功能方案》草稿

全部功能点锁定后收拢成一份完整方案(格式见「澄清结果」)。方案整体亮相正是终检点:人拿着完整方案在脑中走一遍使用流程,逐点讨论看不见的整体问题(点与点不衔接、整体体验不像想象的那样)在此暴露。

### ⑤ 功能合理性专项审核(对抗式)

派**独立子 agent** 审核草稿:把同目录 `function-plan-reviewer-prompt.md` 全文作为 prompt,后接用户原话、④ 草稿全文、⓪ 现实约束清单。它按矛盾 / 遗漏 / 过度 / 分类失真四个维度挑刺,只报会导致大返工的问题。

产出问题清单回人裁决,不自行修改;发现的问题回对应工序修正。

### ⑥ 人终确认

按「澄清结果」输出,用户说「对了」才算结束;不自动继续。

## 澄清结果

澄清结果是 spec 的输入,不是契约:决策只有写进 spec 才成为义务——上半部分会被 dev-spec 原样收录为 spec 第一节「功能方案」,所以要写成离开对话也读得懂的样子。输出后停止,不自动调任何下游。

### 对话版(按此示例写,不写文件)

```markdown
**一句话**:原来侧栏的「数据库」入口是灰的,点不了;这次把它做成能点的页面,团队在浏览器里看本地导出的表结构和探索经验,只读本地文件,不连库。

**功能方案**(✅ 已采纳 · 🔧 你改过 · ➕ 建议新增已留 / ✂️ 已砍)

用户会这样用:

    侧栏「数据库」
          │
          ▼
    工程列表 ──(只有一个工程时跳过)──→ 表清单 ──→ 单表 DDL(原文 + 经验分区)
                                          │
                                          └──→ 经验沉淀(本工程经验按标签汇总)

| 编号 | 功能点 | 类别 | 行为链(已锁定) | 边界 | 落地依据 |
|---|---|---|---|---|---|
| F1 | 浏览表结构 | 核心 | 工程列表 → 表清单 → 单表 DDL 原文 | ① 工程还没导出过表结构 → 提示「先导出表结构」,不显示空列表 | docs/schema-knowledge/ 本地文件 |
| F2 | 经验汇总 | 支撑 | 按标签分组,点表名跳详情 | ① 还没有经验 → 显示「暂无探索经验」 | schema-knowledge 的 DISCOVERED 块已有标签 |
| — | 重跑导出 | 边界外 | 不做——页面上没有任何写操作 | — | 保持只读,连库操作留在 CLI |

**体验决策**:等待类操作一律不出现——页面纯只读,无转圈场景。

**审核结论**:对抗审核 0 问题(或:N 个问题已回修,见上表 ✅)。

**以上功能方案对吗?要改的直接说哪个功能点。**

有没看懂的地方,可以说「画个图讲讲」,我出一页图解。
```

- **流程图**:有角色、步骤、页面跳转或状态流转时必画(ASCII,对话里 mermaid 不渲染)。
- **功能点表**:每行一张已锁定的卡片摘要(编号/类别/行为链/边界/落地依据);被砍的建议新增和边界外也要列,编号写「—」,写明为什么不做。
- **只放业务口径**:不出现模块、文件、函数名;技术约束、影响半径放下半部分。
- **未确认的不进表**,放下半部分「必须在 spec 前解决的问题」。
- **结尾提醒**:最后一句照范例写,只提醒,不自动出页面。

### 结束条件

用户看完说「对了」,澄清才算结束;发现不对就改,改完再给一版。结束前要满足:意图、全部功能点(含类别、行为链与边界)、体验变体的选择、主要非目标都已锁定,剩下的问题不挡 spec。

### 下半部分:供 spec 使用(以 `---` 分隔,标注"以下供 spec 使用,可不细读")

- **确认的意图**
- **功能点清单**(编号 / 类别 / 行为链 / 边界 / 落地依据 / 关联)
- **体验变体的选择记录**(选了哪个、为什么)
- **明确的非目标**(被砍的建议新增 + 边界外排除,附理由)
- **已锁定技术约束**(用户声明 + 兼容性边界;无则写"无特别约束")
- **影响半径与风险**(相关时;LOW/MEDIUM/HIGH/CRITICAL)
- **留给 spec 的细节决策**(机制选型、数据模型、接口契约等,spec 用设计决策表拍板;有使用后果的已作为体验变体在本阶段选过)
- **⓪ 的现实约束清单**(表结构、既有实现等事实,环节二直接复用)
- **必须在 spec 前解决的问题** / **后续阶段的决策**
- **下游就绪判断**:Spec 可写否 / Plan 可写否 / 是否需先探索
- **用户控制的下一步**:`/dev-spec` · `/dev-handoff`(换新会话继续,或按功能点拆成几个会话) · `/dev-wireframe`(涉及 UI 且还没线框,或决策改变了界面) · `/dev-plan`(大需求,写完用 `/dev-impl-subagent` 跑) · `/dev-impl`(小需求) · `/doc-delivery`(发布后按需)

不要把 agent 提案但用户未采纳的写进"已锁定"。

## 拷问模式(对已有方案)

用户带着现成想法/决策/方案来要求 grill 时:不走全工序,逐个决策点给「具体场景 + 该决策下的真实体验」做单问拷问——「你说导出要实时,那就是每次点导出用户盯着转圈等到数据出来,最长可能 2 分钟,这是你要的吗?」

## 推荐下一步

| 规模 | 条件 | 推荐 |
|---|---|---|
| 小需求 | 单点变更、1 到 3 个文件、单个模块 | `/dev-impl` |
| 大需求 | 预估变更文件 ≥10,且跨 ≥3 个相互独立的模块 | 先 `/dev-plan`,再 `/dev-impl-subagent` |
| 拿不准 | 其余情形 | 先 `/dev-plan` |

- 判断看需求规模,不看任务量;小全栈需求(加 1 个字段、改 1 个接口、加 1 处页面展示,跨 3 层)仍算小需求。
- 事后文档发布后按需走 `/doc-delivery`。

## 红线(绝对不能做)

1. ❌ **不抛抽象问题** —— 任何决策点都以「嵌在行为链里的具体值」形态出现,不问「容忍度是多少」这种空维度题;默认值由 AI 先给足。
2. ❌ **不在此拍板实现细节** —— 机制选型、表设计归 spec,函数命名归实现;本阶段只收用户声明的约束。
3. ❌ **不跳过终确认** —— 用户没明确说「对了」,功能方案不算锁定;对抗审核的问题清单必须回人裁决,不自行修改。
4. ❌ **不编造** —— 无法明确的标【待确认】或列为后续阶段决策。
5. ❌ **不把未采纳提案写进"已锁定"**。
6. ❌ **不自动继续下游** —— 输出澄清结果即停;写什么、做不做,归用户。
