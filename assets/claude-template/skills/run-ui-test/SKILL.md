# Run UI Test

## 定位

打靶 skill:在 `write-ui-test` 生成用例规格之后,通过 Playwright MCP 驱动浏览器执行 + 截图 + 出报告。不改用例、不修代码、不重跑,失败交用户决定。

`write-ui-test` 负责"造弹药",`run-ui-test` 负责"打靶"。两者独立,同一份用例规格可被多次复用(改代码或改用例后重跑)。

与接口测试的分工:**接口测试验接口契约与数据层(查库),本流程只验页面表现与交互(渲染/跳转/提示/回显),不验库**——两层各司其职。

## HARD-GATE

- **不验库** —— 写操作用例也只验 UI 表现,数据层正确性归 `/run-api-test`
- **失败只报告** —— 不修代码、不改用例、不自动重跑,交用户决定
- **MCP 缺失不盲跑** —— 当前会话无 playwright MCP 工具 → 输出安装指引并退出
- **数据前提未备齐不跑** —— 用例规格 §3 清单逐项请用户确认,未备齐暂停等待
- **报告永远归一个 feature 目录** —— 归用户触发时指定的需求目录,不混

## Trigger

**使用此 skill 当**:
- 用户完成 `/write-ui-test` 后,要求"跑 UI 功能测试""界面上验一下"
- 用户说"run-ui-test""跑下需求 X 的页面测试"
- 代码改完后,用户要重跑验证修复

**不要使用此 skill 当**:
- 生成用例 → 用 `/write-ui-test`(本 skill 假设用例规格已存在)
- 接口测试 → 用 `/run-api-test`
- 视觉回归 / 跨浏览器兼容 / 性能测试 → 非本流程目标,不接
- 修代码 / 改用例 → 用户手动或走 `/implementation`(本 skill 只测不修)

## 与既有 skill 边界

| skill | 关系 | 说明 |
|---|---|---|
| `write-ui-test` | 上游 | 产用例规格;本 skill 消费它跑测试,不调它也不改用例 |
| `run-api-test` | 平行(推荐先跑) | 接口层验证 + 查库;本流程不重复验库;先接口后 UI 仅推荐顺序,非硬前置 |
| `implementation` / `subagent-implement` | 下游 | 测试失败后由用户决定是否调起修 bug |

## 依赖

- 用例规格已存在(由 `/write-ui-test` 生成,在 `docs/features/<feature-id>/ui功能测试/<文件前缀>-ui功能测试-spec.md`)
- 目标项目已安装 Playwright MCP(R0 校验,缺失给安装指引)
- 服务已由人工启动(本地或已部署测试环境);入口 URL 明确(用例规格记录或用户给)
- 用例规格 §3 数据前提已由人工备齐

## feature-id 与文件前缀规则

复用既有规则(同 `/write-api` / `/run-api-test` 的算法):

- feature-id 格式:`YYYY-MM-DD-[业务ID-]<标题>`
- 文件前缀:有业务ID = `<业务ID>-<标题>`,无业务ID = `<标题>`
- 文件名不得包含 `/`、`:`、`*`、`?`、`"`、`<`、`>`、`|`

产物文件名(归用户指定的 feature 目录):

- 结构化结果:`docs/features/<feature-id>/ui功能测试/<文件前缀>-ui功能测试结果.json`(agent 写)
- 测试报告:`docs/features/<feature-id>/ui功能测试/<文件前缀>-ui功能测试报告.xlsx`(`cgraphx report ui-test` 生成)
- 截图:`docs/features/<feature-id>/ui功能测试/<功能点名>.png`(同功能点多张追加 `-2`/`-3`)

格式见 `references/report-format.md`。

## 触发逻辑(用户给的是什么?)

```
用户触发 /run-ui-test
      ↓
用户给的是什么?
      ├─ 指定了需求(feature-id / spec / 需求名)
      │   → 查该需求的 ui功能测试/<文件前缀>-ui功能测试-spec.md
      │   → 不存在 → 报"需求 X 无 UI 用例规格,请先跑 /write-ui-test"并退出
      │
      └─ 未指定
          → 主动问"请指定需求(feature-id/spec/需求名)"
          → 拿到后回到上面分支
```

**关键约束**:锁定一个 feature-id,报告归该 feature 目录;用例清单必须显示给用户确认后才执行。

## 工作流

按 R0-R6 顺序执行,报告规范见 `references/report-format.md`。

### R0. Playwright MCP 就绪

- **行为**:确认当前会话可用 playwright MCP 工具(浏览器导航/点击/输入/截图能力)
- **缺失** → 输出安装指引并退出,不盲跑:
  ```
  claude mcp add playwright npx @playwright/mcp@latest
  ```
  (安装后重启会话再触发本 skill;本 skill 不替目标项目写 MCP 配置)

### R1. 锁定需求与用例范围

- **前置**:R0 通过
- **行为**:按触发逻辑读用例规格;显示用例清单(功能点名 + 步骤摘要)给用户确认
- **用户取消** → 退出

### R2. 执行参数确认

- **行为**:
  - **运行模式**:问用户 headed(可视)还是无头——由人工定,不默认
  - **入口 URL**:默认读用例规格 §1 记录值;用户触发时给了新值 → 以用户为准;两处都没有 → 向用户要。**不得隐式假设**

### R3. 服务就绪 + 数据前提确认

- **行为**:暂停请用户确认两项:
  1. 服务已启动(本地或已部署测试环境),入口 URL 可访问
  2. 用例规格 §3 数据前提清单已逐项备齐(全人工备)
- **任一不满足** → 等待,不执行、不盲跑

### R4. 登录

- **前置**:用例规格 §4 标注需要登录
- **行为**:agent 用 §4 记录的测试账号自己走登录动线
- **卡住**(验证码/SSO/账号失效)→ 暂停请人工介入;人工处理完继续
- **无需登录** → 跳过本步

### R5. 逐用例执行

- **行为**:按用例规格 §2 逐条执行:
  1. 按操作步骤驱动页面
  2. 验证预期表现(只验 UI,不查库)
  3. 预期验证点截图,存 `ui功能测试/<功能点名>.png`
- **单条失败** → 记录状态与原因,**继续下一条**,不阻塞
- **浏览器 / MCP 崩溃** → 记「失败-环境」;能继续则继续,不能则停止执行出报告,如实标注未完成部分

### R6. 产出测试报告

- **前置**:R5 完成
- **行为**:
  1. 按 `references/report-format.md` 写 `<文件前缀>-ui功能测试结果.json`(每条用例一项,含截图路径)
  2. 生成 xlsx:
     ```bash
     cgraphx report ui-test docs/features/<feature-id>/ui功能测试/<文件前缀>-ui功能测试结果.json
     ```
  3. 退出码 2 → 按 stderr 逐条修正 JSON,回到 2;**只修 JSON,不重跑用例、不改结果判定**
- **xlsx 不手写**:报告只由命令生成;旧的 md 报告由命令删除
- **报告归属**:归用户指定的 feature 目录
- **同需求重复触发**:覆盖该需求的 JSON 与 xlsx,不增量合并

## 状态枚举

| 状态 | 含义 |
|---|---|
| `通过` | 步骤执行通 + 预期表现验证通 |
| `失败-预期不符` | 步骤执行通,但 UI 表现与预期不符(疑似功能 bug) |
| `失败-元素缺失` | 页面结构不符/定位不到元素(改版或实现缺失) |
| `失败-环境` | 服务中途不可用 / 浏览器或 MCP 异常 |
| `失败-登录` | 登录无法完成(账号/验证码/SSO) |
| `跳过` | 用户取消该用例 / 前置不满足主动跳过 |

## 异常速查

| 场景 | 行为 |
|---|---|
| 用例规格缺失 | 报"需求 X 无 UI 用例规格,请先跑 /write-ui-test"并退出 |
| playwright MCP 不可用 | 输出安装指引(`claude mcp add playwright npx @playwright/mcp@latest`)并退出 |
| 入口 URL 不明 | 向用户要,不隐式假设 |
| 服务未就绪 | 暂停等待人工启动,不盲跑 |
| 数据前提未备齐 | 暂停等待人工准备 |
| 登录卡住(验证码/SSO) | 暂停请人工介入 |
| 单条用例失败 | 记状态 + 原因,继续其他用例 |
| 浏览器 / MCP 崩溃 | 记「失败-环境」,出报告如实标注,不产误导性结论 |
| 同需求重复触发 | 覆盖该需求报告,不增量合并 |
| 生成命令校验失败(退出码 2) | 按报错修正 JSON 后重新执行命令,不重跑用例、不改结果判定 |

## 质量检查

跑完后自检:
- JSON、xlsx、截图归指定 feature 目录的 `ui功能测试/`,截图按功能点命名
- 结构化结果 JSON 已写出,且 `cgraphx report ui-test` 以退出码 0 生成了 xlsx
- 目录中没有旧的 md 报告
- 每条用例都有状态(六枚举之一),失败用例有原因分类
- 全程没查库、没修代码、没改用例、没自动重跑
- 五道前置关都过了才执行,没盲跑(MCP/URL/服务/数据)
- 登录失败时暂停找了人,没硬闯
- 用户确认环节有执行(用例清单显示给用户)

## 收尾

提示用户:
1. 测试报告位置(`<文件前缀>-ui功能测试报告.xlsx`)、结构化结果 JSON 与截图目录
2. 通过 / 失败 / 跳过汇总
3. 失败用例清单 + 原因分类
4. 下一步建议(只在对话中给出,不写入报告):
   - 失败-预期不符 → 疑似功能 bug,走 `/implementation` 修,修完重跑 `/run-ui-test`
   - 失败-元素缺失 → 确认页面结构是否改版;用例过时 → 走 `/write-ui-test` 重新派生
   - 失败-环境 → 服务/浏览器问题,恢复后重跑
   - 失败-登录 → 核对用例规格 §4 的测试账号

不主动调用 `/implementation` 或其他下游 skill。不写 knowledge 文件。不修改用例规格 / spec / plan / 代码。
