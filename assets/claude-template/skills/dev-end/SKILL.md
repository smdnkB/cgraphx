# 需求收口 (dev-end)

## 定位

对一个**做完的需求**「正向合成」一份收口档案,落 `docs/features/<feature-id>/<前缀>-收口档案.md`(文件前缀 = feature-id 去掉日期段 `YYYY-MM-DD`)。**正向汇总、不从代码倒推**;痕迹缺失的字段诚实标来源,不假装是过程留痕。确认已上线时,顺带写发布记录。

## 输入(先集齐,缺的先补或问人)

| 输入 | 从哪来 | 缺了怎么办 |
|---|---|---|
| 需求标识(feature-id) | 调用方给;或 `cgraphx features list` 找 | 问人 |
| 目标 git 仓路径 + 提交范围(SHA 范围或时间窗) | 调用方给;缺了用 `git log -- docs/features/<feature-id>/` 推,并在档案注明推法 | 同左 |
| 实际测试报告 | 调用方给(`$unit-code` 单测报告 / `$api-run` 接口报告 / 人工测试结果,格式不限、语义读) | 没有就如实标 `cannot_verify`,不编 pass |
| 补录状态(timeline) | 时间线查询 stderr 的 `[timeline] 补录状态: complete|partial|blocked` 一行 + 原因;doc-backfill 链路由 filler 传入 | 缺状态或查询命令失败 → 按覆盖不足处理 |
| 历史结果(工作量结论) | `$task-history`(本 skill 调用,见「历时」) | — |

## 历时(两层,缺一不可)

- **日历跨度**:立项取提交范围内第一个提交的日期、完成取最后一个提交的日期;首尾两天都算,同一天提交完算 1 天。**诚实标注它只是日历跨度**(常与真实投入差很远),不能当实际投入。
- **实际投入(到小时)**:调 `$task-history`,传入需求标识 + git 仓路径 + SHA 范围或时间窗 + 关注点「工作量/活跃时长」;**直接采纳其返回的「工作量结论」节**(下界~上界小时区间 + 口径 + 补录状态 + 局限)填本节,**不自己跑 `cgraphx timeline query` 重查**。补录状态缺状态/命令失败已按覆盖不足处理,由 `$task-history` 如实呈现。
  - 结论标「非 timeline 实测(会话回退)」→ 档案同样标注,不抹掉;
  - 结论标「无法估算」→ 写无法估算,**不写 0、不拿日历跨度或提交间隔凑数**;
  - 混合会话直接采用区间,不逐时段向用户确认、不额外标注不确定性。

## 产出 schema(逐条照填;H2 标题独占一行、精确等于规范标题;半角冒号)

```
---
req_id: <簇名>
簇: <目标标识/路径>
status: 已收口
mode: poor
created: "<YYYY-MM-DD>"
git_range: "<首SHA>..<末SHA>"
---

# 收口档案:<需求名>

> 产物: closure_record
> 依据: spec@<主 spec 指纹前 7 位,用 cgraphx features show <feature-id> 查;没有主 spec 就删掉这一行>

## 历时
- 立项:<日期> · 完成:<日期> · 日历跨度:<N 天>
- 实际投入(估算,到小时):约 <下界>~<上界> 小时 ≈ <Z> 工作日 · 口径:<下界=明确归属事件,上界=含混合会话候选事件 · timeline 实测 | 非 timeline 实测(会话回退) | 无法估算>
## 产物清单
- 文档:<路径> · 代码:<SHA> <一句> · 决策锚点:<锚>
## 测试汇总
- 结果:<pass/fail> · 覆盖:<测到的功能点数/功能点总数,未测的写 F 编号> · review:<pass/fail/cannot_verify>
## 知识引用归纳(命中)
- [hit] <知识 id/path> — <这次怎么用上的一句>  [来源: AI会话 | 事后补录]
- 确认无: <非占位理由>
## 澄清记录(缺口)
- [gap] <被迫问人的一句>  [来源: AI会话 | 事后补录]
- 确认无: <非占位理由>
## 新确认(沉淀候选)
- [new] <值得沉淀的一句>  [来源: AI会话 | 事后补录]
- 确认无: <非占位理由>
```

## 填法要点

- **产物**:git log 取 SHA 范围 + 关键交付路径;决策锚点无 HOW 文档就据 commit/会话补。
- **测试汇总**:语义读实际测试报告,别机械归一化解析;以真实执行结果为准——测试没跑或失败就如实写,不假装通过。
- **命中/缺口/新确认(核心)**:痕迹不在文档时——**有 AI 会话就从会话正向读、标 `[来源: AI会话]`**(一手正向留痕,可信 > 补录);**无会话才向人补录、标 `[来源: 事后补录]`**。都不假装是过程文档留痕。
- **`[来源: AI会话]` 真实性铁律**:标它 = 你**真在原始会话 transcript 里读到** AI 召回/引用了那条知识、或被迫问了那个问题,并**留可定位证据**(`[来源: AI会话 · <会话id/行号/时间>]`)。**能读到真实会话就必须真读**,别拿 git 仓/时间线摘要/中间文档**反推冒充**——「决策恰好和某文档吻合」是**内容吻合、非真召回**(倒推),只能标 `[来源: 事后补录]` 并注明推断。命中尤其别只找「显式引用」:遍历关键决策逆向问「做这步必须先知道什么」得到**候选**,但**必须回原始会话确证**才标 `[来源: AI会话]`;取不到原文 → 标来源不足,不得标会话来源。
- **三格别拔高凑数**:命中 = 库里已有知识这次被召回用上(✗ 复用自己写的函数 / 跑某流程 ≠ 命中);缺口 = 知识库缺了某条被迫问人(✗ 正常方向决策 ≠ 缺口);新确认 = 值得沉淀的新知识/规则。**纯机制需求三格全「确认无」是正常诚实收口**,别找复用/决策/经验来凑。
- **知识格内只放** `- [hit]/[gap]/[new]` 条目 **或** `- 确认无: <理由>` 行,别塞注释/散文。理由**不可**是占位符(空 / 无 / N/A / TODO / TBD / 待定 / 待补…)。

## 产出后自检

1. 六节齐全(历时 / 产物清单 / 测试汇总 / 命中 / 缺口 / 新确认),H2 标题精确等于规范标题。
2. 「历时」两层都在:日历跨度一行 + 实际投入一行(含口径与 timeline 实测/回退标注,或明确的「无法估算」)。
3. 三个知识格每格 ≥1 条 `[hit]/[gap]/[new]` **或**一条非占位「确认无」。
4. poor 的每条 `[hit]/[gap]/[new]` 带 `[来源: AI会话]` 或 `[来源: 事后补录]`(任一)。
5. frontmatter 五键齐(req_id / 簇 / mode / created / git_range),created / git_range 带引号包成字符串。
- **内容质量**(命中准不准 / 澄清真不真 / 历时估得合不合理):**非机械可验**,交人工 review 或 LLM-judge。**禁止往档案塞关键字假装验证过内容**——校验查的是结构与非占位,不是内容对。

## 发布记录(确认已上线才写)

- 收口时问用户:这个需求上线了吗?确认已上线才写;没上线就不写,告诉用户上线后再跑一次 `$dev-end` 补。
- 再跑 `$dev-end` 时,如果收口档案已经在,只补发布记录,不重写收口档案。
- 文件 `docs/features/<feature-id>/<前缀>-发布记录.md`;同一需求多次发布写在同一个文件里,在「版本与上线时间」表里追加一行。
- 至少有版本号或 tag、上线时间;关联 commit、分支、发布说明按需加。版本号和上线时间问用户,不猜。

范例:

```markdown
# 发布记录: 积分发放规则

> 产物: release_record

## 版本与上线时间

| 版本或 tag | 上线时间 | 说明 |
|---|---|---|
| v2.3.0 | 2026-10-20 15:30 | 首次上线:下单积分按会员等级发放 |
| v2.3.1 | 2026-10-22 10:00 | 修复退款时少扣 1 分 |

## 关联提交

- v2.3.0:`a1b2c3d..e4f5a6b`,分支 `release/2.3`
```

## 和其他 skill 的关系

- **`$task-history`**:历时数据来源,由本 skill 调用;口径以它的「工作量结论」为准。
- **doc-backfill**:补账链的 filler 子 agent 调用本 skill,补录状态作为上下文传入;单测规格/报告由 `$unit-spec` / `$unit-code` 补,测试结果以真实执行为准。
