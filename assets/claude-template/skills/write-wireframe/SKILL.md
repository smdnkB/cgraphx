# 生成线框 (Write Wireframe)

## 定位

- **让人看着界面做决定**:字符画和文字描述不了布局与交互;线框能点、能切状态,人一眼看出"缺了什么、哪里不对"。
- **与业务口径不分先后**:有的需求业务先定再画界面,有的要看着界面才能设计业务交互。本 skill 可在 clarify 前、clarify 后、spec 后执行,并和 clarify 来回迭代:

```
业务先行:  clarify ──→ 线框 ──→ spec
UI 先行:   线框 v1 ──→ clarify(锁定界面暴露出的业务决策)──→ 线框 v2 ──→ spec
后补:      spec ──→ 线框 ──→ spec 修订(补漏掉的交互)
```

- **不是契约**:线框是讨论工具。人确认后,由 spec 写明"页面布局与交互以 `<前缀>-线框-v<N>.html` 为准",该版本才具约束力;未被 spec 引用的版本不约束任何下游。
- **低保真**:只表达布局、内容、交互、状态。视觉打磨不在本 skill(需要时用户另行要求高保真稿)。

## 流程

1. **命名先行**:feature-id 已存在(已有 spec/线框)→ 复用;不存在 → 按 write-spec 第 0 步同规则落定(业务 ID / 标题语言 / 负责人),建 `docs/features/<feature-id>/`。
2. **收集素材**:已有的澄清结论/spec 场景表;**既有页面**(项目已有 UI 时读真实页面结构与导航,新页面要挂进既有布局);**真实数据**(用 db-query / 读本地文件取几条真实样例,写进线框——真实数据最容易暴露问题)。
3. **列页面与状态**:先在回复里列"页面 × 状态"清单(正常 / 空态 / 异常 / 加载中,按需)请人确认范围,再生成。
4. **生成**:Read [references/wireframe-template.html](references/wireframe-template.html),照它的结构与写法生成——它就是标准样张。
5. **交付**:回复里给文件路径 + "看什么"(本版要人确认的 2–3 个问题);人提出修改 → 出下一版,不覆盖旧版。
6. **衔接**:界面暴露出业务问题 → 建议回 `/clarify-requirements` 锁定;版本确认 → 提示在 spec 中引用该版本(spec 已存在则提示修订)。

## 样张要点(照 wireframe-template.html)

| 要素 | 写法 |
|---|---|
| 页面切换 | 顶部页面导航 + 页面内链接,URL hash 即当前页 |
| 状态切换 | 顶部「正常 / 空态 / 异常」按钮,每个页面每种状态都有呈现 |
| 交互编号 | 交互点标 ①②③,右侧「交互说明」随当前页显示对应条目 |
| 挂进既有布局 | 既有导航/侧栏照画,本次改动处用编号指出 |
| 灰度 | 只用灰度和边框,不用项目设计令牌,不放图片和图标库 |
| 自包含 | 单文件,内联 CSS/JS,无外部依赖,断网可开 |
| 头部注释 | 版本、feature-id、相比上一版的变化及触发它的决策、示例数据来源 |

## 产物位置与命名

- 路径:`docs/features/<feature-id>/<文件前缀>-线框-v<N>.html`,N 从 1 递增;每轮修改出新版本,旧版保留。
- 文件前缀:同 write-spec(有业务ID = `<业务ID>-<标题>`,无 = `<标题>`);标题不得中文转英文 slug。

## 红线(绝对不能做)

1. ❌ **不做视觉打磨**——不引设计令牌、不调配色字体;低保真只管布局、内容、交互、状态。
2. ❌ **不编造示例数据**——能取真实数据就取真实数据;取不到用明显的占位(`<表名>`),并在头部注释说明。
3. ❌ **不覆盖旧版本**——每轮新出 v<N+1>,头部写清变化。
4. ❌ **不把线框当契约**——不在线框里写业务规则条款;规则进 clarify/spec。
5. ❌ **不写前端实现代码**——线框是一次性讨论稿,不被实现复用。
