# init-project-guides

为项目初始化一套 `docs/guides/` 规范文件模板。**两种模式**:新项目起步立规矩(按技术栈生成起步规范),已有项目补齐(从代码和历史里挖出实际约定固化成文)。

## 何时使用

- **新项目起步**:空仓库/脚手架阶段,在写第一行业务代码前定下起步规范
- **已有项目补齐**:缺少规范文档,从现有代码风格和 git 历史提炼固化
- 团队规范化建设,需要统一的开发规范速查文档
- 起步规范用久了想校准:项目有代码后重跑,用现实修正默认值

## 何时不使用

- 项目已有完整的 `docs/guides/` 目录且内容满足需求
- 用户只是想查询某个具体规范(应直接 Read 现有文件)

## 输出产物

在项目的 `docs/guides/` 目录下生成以下文件:

| 文件 | 内容范围 | 技术栈相关性 |
|------|---------|------------|
| `coding-standards.md` | 编码规范:语言特性、代码风格、目录结构、命名约定、常量管理、错误处理 | 高 |
| `interface-standards.md` | 接口设计规范:API 路径、参数、返回值、版本控制、兼容性、调用模式 | 中 |
| `model-standards.md` | 模型/实体规范:字段命名、类型映射、关系定义、校验规则、通用字段 | 中 |
| `ddl.md` | 数据库规范:表命名、字段类型、索引、注释、迁移、模板 | 中 |
| `project-background.md` | 项目背景:是什么、给谁用、核心流程、架构分层、模块清单、技术栈 | 低 |
| `git-standards.md` | Git 提交门禁文件:① 提交消息规范(标题格式 / 票据关联 / 语言 / 正文)② 提交前检查点(项目自定义) | 低(与技术栈无关,与项目/团队绑定) |

## 执行流程

### 1. 技术栈探测

自动探测项目技术栈。
**探测不到时**(新项目/空仓库是常态):询问用户项目主技术栈(Java/Go/TypeScript/JavaScript/其他)及主要框架。

### 2. 项目信息收集

**必须项(通过用户提示 + 主动探索):**
- 项目名称/代号
- 项目简介(一句话描述)
- 目标用户/使用方
- 核心技术栈(已探测到的)

**可选项(通过主动探索补充):**
- 架构分层(读目录结构推断)
- 模块清单(读目录结构推断)
- 核心业务流程(从 README 或业务代码推断)
- 数据库类型(从依赖推断)

**探索方式:**
- 读 `README.md` 获取项目概述
- 读 `package.json`/`pom.xml`/`go.mod` 获取依赖和技术栈
- 扫描顶层目录结构推断模块划分
- 如有 `docs/` 已有内容,先读避免重复

**新项目(无可探索内容):** 跳过探索,以用户输入 + 技术栈行业惯例为准;项目背景按用户的建设目标写("要建什么"),不是"已有什么"。

### 3. 内容生成

根据技术栈和项目探索结果,动态生成每个规范文件的内容。

**内容生成原则:**
- **有项目现实可挖时,挖现实**:目录结构、命名风格、框架用法、git 历史消息风格——提炼既有约定固化成文,不发明新规矩
- **新项目无现实可挖时,按技术栈立起步默认**:行业通行做法 + 用户对有分歧处的选择;**起步规范是待演进的默认值,不是发现的约定**——文件里显式注明,项目有代码后重跑本 skill 用现实校准
- 通用规则写死(如"单文件超过 600 行必须拆分")
- 技术栈相关规则根据项目实际(或所选)的框架、工具、库生成
- 项目特定信息从收集阶段获取(如模块名、服务名)
- 关于数据库建表注释,补充必需指明关联的表和字段,比如 COMMENT ON COLUMN work_order.ASSIGNEE_STAFF IS '处理人工号,关联 users.staff_code';
- 不确定的内容标注 `【待确认】` 或留空

**各文件生成策略:**

| 文件 | 生成依据 |
|------|---------|
| `coding-standards.md` | 项目实际的目录结构、包命名、使用的框架/工具链 |
| `interface-standards.md` | 项目实际使用的 RPC/HTTP 框架、API 设计模式 |
| `model-standards.md` | 项目实际使用的 ORM、数据库类型、实体设计 |
| `ddl.md` | 项目实际使用的数据库类型、迁移工具 |
| `project-background.md` | 用户提示 + 项目探索结果 |
| `git-standards.md` | 有 git 历史:挖最近 50-100 条 message 的风格(标题格式、票据前缀、语言、正文)+ 已有 commitlint/hook 配置。无历史(新项目):给常见模式选项(如 Conventional Commits `type(scope): subject`、票据前缀式)让用户选,或用户直接给团队规范 |

**git-standards.md 是提交门禁文件(precommit-check hook 指向它),包含两部分:**

**第一部分 · 提交消息规范:**
- 标题格式:从历史 message 提炼格式模式 + 正例/反例(如 `CRM-req74181<描述>-client@req74181`、`bug54911<描述>@bug54911` 这类项目独有格式,挖不出来就问用户)
- 票据关联规则:需求号/bug 号如何进标题;**编号未知时必须问用户,不得编造或省略**
- 语言与措辞、长度约定;正文写哪些关键细节;breaking change / scope 等特殊标注
- agent 署名行(Claude Code 的 co-author 署名)与项目规范如何共存

**第二部分 · 提交前检查点(项目自定义):**
按技术栈给默认检查点 + 用户确认增删。通用种子:
- 被注释掉的开关/注册项(写该项目实际的语法:Spring 的 `@Component`/`@Scheduled`/`@JmsListener` 等注解、前端的组件注册、配置开关)——被注释 = 功能静默失效,高危
- 被注释掉的业务调用(监听注册、定时任务、关键链路入口)
- 未闭合逻辑(括号失衡、if/try/for 未配对)
- 写死的魔法字符串/数字(密码、URL、ID、阈值)
- 新增 TODO/FIXME/临时标记
项目特有项由用户补充(历史事故点、团队红线)。每个检查点写"查什么 + 为什么危险";门禁触发时 agent 自己跑 `git diff --cached` 对照逐项判断,命中报告用户,不替用户改代码。

### 4. 用户确认

**写入文件前,必须将生成的内容展示给用户,询问:**

```
我将在 `docs/guides/` 目录下生成以下 6 个文件:

1. coding-standards.md — 编码规范(技术栈:Java)
2. interface-standards.md — 接口设计规范
3. model-standards.md — 模型/实体规范
4. ddl.md — 数据库规范
5. project-background.md — 项目背景
6. git-standards.md — Git 提交规范(commit message 格式)

以下是各文件的主要内容预览:

[coding-standards.md 预览...]
[interface-standards.md 预览...]
...

请确认:
- 内容是否有误需要纠正?
- 是否有遗漏需要补充?
- 是否确认写入文件?
```

**用户确认后**才执行写入。

## 注意事项

- **不覆盖已有文件:** 如果 `docs/guides/` 下已有同名文件,询问用户是否覆盖或跳过
- **知识库联动:** 生成后建议用户运行 `/code-impact-markdown` 将规范沉淀到 `docs/knowledge/`
