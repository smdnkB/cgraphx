# init-project-guides

## 定位

为项目生成/补齐 `docs/guides/` 规范速查(5 个文件,一项开发活动 ↔ 一个文件):

| 文件 | 内容 | 强制读点 |
|---|---|---|
| `coding-standards.md` | 风格/命名/目录/错误处理 | 所有动码任务 |
| `interface-standards.md` | API 路径/参数/返回值/兼容 | 接口任务 · write-api |
| `data-standards.md` | 模型层 + DDL 层 + ORM 映射 + **schema 变更约定** | schema 任务 |
| `testing-standards.md` | 框架/单测集成边界/mock/fixture/覆盖 | 测试任务 |
| `git-standards.md` | commit 消息规范 + 提交前检查点 | precommit-check 门禁 |

两种模式:新项目起步立起步默认(文件内显式注明"待演进,有代码后重跑校准");已有项目从代码与 git 历史挖既有约定固化成文。**你只提发现和建议,决策归用户。**

## 判别:什么算"项目规范"

**规范 = 项目对默认做法的有意偏离或选定;无偏离即无规范。** 一条候选内容,两条测试都过才写:

| 测试 | 问 | 不过 → 不写 |
|---|---|---|
| 必要性 | 删掉它,懂技术栈 + 有常识、没见过本项目的工程师会做出**不一样**的东西吗? | 不会 = 显而易见 |
| 执行点 | 有没有 lint / 格式化 / 类型系统**已经在强制**它? | 有 = 工具的事,guide 不抢 |

**三类必弃**(凑进去只会淹没真规范):技术栈事实(用了 ts/java)、通用工程常识(单一职责/复用/合理拆分/"命名要有意义")、工具已强制项(缩进/引号/camelCase——ESLint/Prettier 管)。

**规范要写的是这类**:SQL 禁止 `ORDER BY` · commit 用 A 格式 · 接口路径加 `fix` 前缀 · 测试库 `xxx_test`/生产库 `xxx` · 金额一律 `decimal(12,2)` —— 推不出、没工具兜底,guide 是它唯一执行点。

**宁缺毋滥**:一个文件 3 条真规范,好过 30 条里藏 3 条。guide 是强制读 + 会被 write-plan 结晶成契约、被审查执行 —— 噪音会被放大成"被强制的噪音"。整节挖不到项目特异内容 → 该节写一行"无特殊约定,遵循默认/lint",或整节省写,不得用通用最佳实践填充。

## 流程

1. **探测技术栈** —— 自动探测;探测不到问用户(新项目/空仓库是常态)。
2. **探索** —— README、依赖清单(package.json/pom.xml/go.mod)、目录结构、git 历史(近 50-100 条 message 风格、已有 commitlint/hook)、测试基建、已有 docs/(先读避免重复)。新项目跳过探索,以用户输入 + 技术栈惯例为准。
3. **逐文件生成 + 确认** —— 按 coding → interface → data → testing → git 顺序,**一次只处理一个文件**,每个文件三步:
   - **报告发现**:挖到的项目现实(目录/命名/框架用法/测试基建/message 风格)**逐条过判别两测试,显而易见项(三类必弃)当场丢弃不进报告**;报告的都是真规范(偏离/选型/推不出的事实),**发现的约定与起步选型明确分开标注**
   - **给草案 + 建议**:挖不到的、有分歧的,给有限选项 + 推荐理由(如"message 格式挖出两种风格,推荐 A——近 50 条占 80%"),不给开放式提问
   - **用户拍板**:可改可补可否,**确认后才写入该文件**,再进下一个
   
   单文件补齐场景(如门禁中断要求补 testing-standards.md)走同一循环,只处理目标文件。
4. **写入** —— 模板在 `templates/`:
   - 栈模板 `templates/{java,go,typescript}.md`:coding / interface / data 模型层 / data DDL 层 / testing 各节
   - `data-standards.md` 合并生成:统一 H1 `# 数据与模型规范`,模型层 / DDL 层两节标题降一级合并,缺数据库映射补 `## ORM 映射约定`,末尾**逐字追加** `templates/schema-convention.md` 的约定文本
   - `git-standards.md` 按 `templates/git-standards.md` 生成(消息规范从历史挖 + 检查点种子按栈给默认、用户增删)

## 生成原则

- **有现实挖现实**:已有项目从代码/git 历史挖**偏离项 + 选型 + 推不出的事实**,固化成文,不发明新规矩。
- **无现实立选型,不立常识**:新项目没有现实可挖 → 只记用户当场拍板的选型(commit 格式 / 包管理器 / 命名前缀 / 库名映射等),其余留白 + 文件内注明"待演进,有代码后重跑校准";不填通用最佳实践充数。
- 建表注释必须指明关联表与字段(如 COMMENT '处理人工号,关联 users.staff_code')—— 这是推不出、无工具兜底的典型规范。
- 不确定内容标【待确认】或留空,不猜。

## 红线(绝对不能做)

1. ❌ **不一次性给全部文件** —— 逐文件确认,每个文件用户拍板后才写入。
2. ❌ **不替用户决策** —— 不替用户定命名风格、选提交格式、划单测/集成边界;挖不到的问,有分歧的列选项,不许填个默认就往下走。
3. ❌ **不覆盖已有文件** —— 同名文件先问用户覆盖或跳过。
4. ❌ **不自动删用户文件** —— 检测到旧结构(`model-standards.md` / `ddl.md` / `project-background.md`)只提示:前两者并入 `data-standards.md` 后删,`project-background.md` 直接删(定位由 CLAUDE.md + 知识库承担)。
5. ❌ **约定文本不转述** —— schema 变更约定逐字拷自 `templates/schema-convention.md`,不改写不省略。
6. ❌ **不写显而易见项凑篇幅** —— 技术栈事实 / 通用工程常识 / lint·工具已强制项一律不写;整节无项目特异内容宁可留白(一行"无特殊约定"或不写),不得用通用最佳实践填充。

## 知识库联动

生成后建议用户运行 `/knowledge-write` 将规范沉淀到 `docs/knowledge/`。
