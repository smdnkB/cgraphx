# 编写 PRD (Write PRD)

## 定位

把当前上下文中已经确认或给定的需求信息,整理成**给领导、客户或业务方审阅的业务需求文档**。

目标是让能拍板的人确认:业务决策是否符合预期,范围是否正确,流程是否完整,规则是否清楚,异常和验收口径是否可接受。PRD 不是给研发发挥的方案文档,而是把需要领导/业务方拍板的规则和口径摆清楚。

<HARD-GATE>
不要把 PRD 写成技术 spec、实现计划、数据库设计、接口设计或代码方案。
不要主动调用或要求使用其他 skill。按当前上下文独立完成 PRD 编写。
如果缺少会影响领导/业务方确认业务决策的关键信息,先补问 3-5 个关键问题;如果不阻塞成文,在 PRD 中标记为【待确认】。
不要编造未确认的业务规则。如果必须依赖未确认规则,先向用户确认。
</HARD-GATE>

## 输入理解

优先基于当前上下文中的以下信息写 PRD:

- 用户已确认的需求描述
- 已确认的业务目标、业务边界和非目标
- clarify 阶段产出的已锁定业务决策、已排除方案、待拍板项和下游就绪判断
- 已确认的角色、场景、流程、规则、异常和验收口径
- 客户提供的业务背景、规则、流程、样例、截图或接口说明
- 项目里已有的业务文档、页面、模型、接口、流程或数据口径

如果当前上下文已经足够,直接写 PRD。不要重新澄清已经确认过的内容。

如果只有一句模糊想法,不要硬写完整 PRD。先用 3-5 个问题补齐最影响业务决策确认的内容。

## 受众和边界

面向领导、客户、业务方、产品负责人、项目干系人。文档应当业务可读,不要求审阅者懂代码。

可以写:

- 业务背景和目标
- 需求范围和非范围
- 用户角色和使用场景
- 业务流程
- 功能需求
- 业务规则
- 数据口径的业务含义
- 权限和可见性
- 异常场景
- 验收标准
- 待确认项

不要写:

- 代码实现步骤
- 数据库表结构和字段设计
- 接口参数细节,除非客户需要用它确认业务含义
- 类名、函数名、模块拆分
- 开发排期和任务分解
- 技术选型论证
- 测试用例明细,除非作为客户可读验收口径

## 工作流程
在写任何 prd 内容前,**必须**先与用户确认两件事:

1. **业务 ID**:本次需求是否有对应的工单号 / 需求单号 / 项目代号?允许留空,但**留空也必须显式确认**(用户明确说"没有/留空"),不得默认跳过。
2. **标题语言**:用中文 / 英文 / 中英混合?由用户选定,**禁止** Agent 因为"目录看起来更整齐"/"和现有 feature 命名一致"/"避免中文路径问题"等原因,擅自把中文需求转成英文 slug。

- 用户主动给过完整 feature-id 或文件名 → 直接复用,跳过本步。
- 用户用 `/write-prd` 触发但未给命名决策 → **第一步就问这两个问题**,问完再写。
- 不得"先写 prd 内容,命名最后再说"。命名决策必须在内容产出之前落定,否则会在文件名上反复返工。

1. **检查上下文完整性**
    - 确认当前上下文是否已有明确需求范围。
    - 识别缺失的业务目标、角色、范围、流程、规则、异常或验收口径。
    - 只补问会影响领导/业务方拍板业务决策的问题。
    - 如果 clarify 总结里有"必须在 PRD/spec/plan 前解决的问题",先处理这些问题,不要绕过。

2. **确定 PRD 粒度**
    - 简单需求写轻量 PRD。
    - 跨流程、跨角色、跨系统或规则复杂的需求写完整 PRD。
    - 不为了显得完整而堆砌无关章节。

3. **转换语言**
    - 把技术描述翻译成客户可理解的业务语言。
    - 保留必要的业务名词、状态名、角色名、入口名、单据名、产品名。
    - 避免内部实现术语干扰客户审阅。

4. **编写 PRD**
    - 先讲业务目标和范围,再讲流程和规则。
    - 对领导/业务方最需要确认的业务决策使用清单、表格或流程说明。
    - 明确区分"已确认规则"、"待拍板规则"、"明确不做"。
    - 对未确认内容标记【待确认】,不要偷偷补齐。

5. **自检**
    - 检查客户是否能通过文档判断“是不是我要的”。
    - 检查是否混入实现方案。
    - 检查范围、非范围、异常、验收是否清楚。

## 推荐输出结构

根据需求复杂度裁剪。默认使用以下结构:

```markdown
# 业务需求文档: <需求名称>
> feature-id: <feature-id>
> 状态: 草稿
> 日期: YYYY-MM-DD

## 1. 背景与目标

## 2. 需求范围
### 2.1 本次包含
### 2.2 本次不包含

## 3. 用户角色与使用场景

## 4. 业务流程

## 5. 功能需求

## 6. 业务规则

## 7. 数据口径与状态说明

## 8. 需拍板的业务决策

## 9. 权限与可见性

## 10. 异常与边界场景

## 11. 验收标准

## 12. 待确认项
```
简单需求可以合并章节,但至少保留:背景目标、范围、业务流程或功能说明、业务规则、验收标准、待确认项。

## 产物位置

在可写项目上下文中,默认创建或更新:

`docs/features/<feature-id>/<文件前缀>-需求文档.md`

文件前缀规则见下一节。

如果没有可写项目上下文,或用户明确只需要正文,则直接在回复中输出 PRD 内容。

## feature-id 与文件前缀规则

**feature-id 格式**:`YYYY-MM-DD-[业务ID-]<标题>`

1. 日期使用当前日期。
2. 业务ID 是**可选**段落(字母数字 + 连字符,如 `CRM-req19230`)。skill 启动时提示用户填写,允许留空。
3. 标题段允许中文、英文或混合(例:`号百商品详情查询接口`、`features目录结构调整`)。**不得**对中文做英文 slug 转换。
4. 业务ID 段与标题段用连字符连接,组成 `<业务ID>-<标题>`。
5. 写入前检查 `docs/features/` 下是否重名;重名时追加简短后缀。
6. 若当前上下文或用户已提供 feature-id,则复用。

**文件前缀算法**:
- 有业务ID:文件前缀 = `<业务ID>-<标题>`(如 `CRM-req19230-号百商品详情查询接口`)
- 无业务ID:文件前缀 = `<标题>`(如 `features目录结构调整`)

**默认产物路径**:`docs/features/<feature-id>/<文件前缀>-需求文档.md`

例:
- 有业务ID:`docs/features/2026-06-10-CRM-req19230-号百商品详情查询接口/CRM-req19230-号百商品详情查询接口-需求文档.md`
- 无业务ID:`docs/features/2026-07-03-features目录结构调整/features目录结构调整-需求文档.md`

**敏感字符拒绝**:文件名不得包含 `/`、`:`、`*`、`?`、`"`、`<`、`>`、`|`。用户提供时若含敏感字符,skill 必须要求用户重命名,不得自动替换字符。

**与旧目录共存**:skill 始终用新命名,不主动探测旧目录的 `prd.md`。旧 feature 目录里继续更新会出现 `prd.md`(旧)和 `<文件前缀>-需求文档.md`(新)并存,由用户自行处理。

## 章节写法

### 背景与目标

说明为什么要做,解决什么业务问题,客户期望得到什么业务结果。不要写技术原因作为主线。

### 需求范围

明确本次做什么和不做什么。非范围必须写清楚,防止客户误以为包含。

### 用户角色与使用场景

说明谁使用、谁受影响、在什么业务场景下触发。角色名称应使用客户或项目里的叫法。

### 业务流程

按客户能理解的步骤描述。从触发条件开始,到业务结果结束。复杂流程可用编号步骤、状态流转表或 Mermaid 流程图。

### 功能需求

按业务能力拆分。每条需求写清楚:

- 用户动作或系统动作
- 前置条件
- 系统应表现出的业务行为
- 业务结果

### 业务规则

写领导/业务方需要确认的判断规则、限制条件、计算口径、状态变化、优先级、冲突处理。规则必须可验证。

### 数据口径与状态说明

只写业务含义,不写数据库设计。说明关键字段、状态、数量、金额、时间、来源、统计口径等对业务决策有影响的内容。

### 需拍板的业务决策

集中列出只有领导、客户或业务方能决定的规则和口径,例如:

- 统计维度、过滤条件、时间范围、去重规则
- 状态含义、状态流转、例外处理
- 权限边界、数据可见范围、审批权
- 兼容历史数据或旧流程的取舍
- 异常场景的业务处理方式

已确认的写入"已确认";未确认但影响后续 spec/plan 的写入【待确认】,不要让研发或 agent 在实现期自行拍板。

### 权限与可见性

说明哪些角色能看、能操作、不能操作;不同组织、租户、部门、区域或客户范围是否隔离。

### 异常与边界场景

说明失败、重复、撤销、超时、空数据、无权限、数据不存在、部分成功、历史数据等客户可能关心的场景。

### 验收标准

用客户可判断的业务结果表达。避免“接口正常”“代码完成”这类开发视角表述。

### 待确认项

列出仍需客户或业务方确认的内容。不要把待确认项藏在正文里。

## 写作原则

- 面向客户确认业务逻辑,不是面向研发交付实现。
- 面向领导/业务方确认业务决策,尤其是只有业务负责人能拍板的规则、口径和例外。
- 先结论后细节,先范围后流程,先规则后例外。
- 用业务语言表达,少用技术术语。
- 必要技术边界只作为约束背景,不要展开设计。
- 不确定就标【待确认】。
- 已确认的非目标要明确写出。
- 简单需求轻量写,复杂需求完整写。
- 不要把用户没确认的头脑风暴选项写成正式需求。
- 不要把需要领导拍板的业务规则留给 spec、plan 或 implementation 阶段临场决定。
- 不要自动进入 spec、plan 或 implementation。

## 质量检查

输出前确认:

- 领导/业务方能看懂这个需求要解决什么问题。
- 领导/业务方能确认本次做什么、不做什么。
- 领导/业务方能按文档检查业务流程是否符合预期。
- 需要拍板的业务规则、口径、权限、异常和验收项没有被藏到技术文档或实现阶段。
- 关键业务规则没有遗漏或被技术术语掩盖。
- 异常和边界场景不会导致明显理解偏差。
- 验收标准是业务结果,不是开发动作。
- 所有未确认内容都标为【待确认】。

## 收尾方式

输出 PRD 后,只提示领导、客户或用户可以审阅业务决策并指出需要调整的地方。不要主动继续写技术 spec、实现计划或代码。
