cgraphx skill 一览

每个 skill 一行

点一行展开看怎么用;搜名字、用途或产物,比如「工时」「接口测试」「线框」。整体流程见 cgraphx 怎么用。

需求设计
/dev-clarify动手前先把需求说清:AI 出功能点提案,你审稿式改说话就行
什么时候用
接到需求、想法、bug、重构请求,在写任何文档和代码之前;也能拿现成方案让它拷问。
怎么用
直接说需求,如「想给订单列表加个导出」;要拷问就说「拷问一下这个方案」。
要你拍板
功能点清单增删;业务口径(哪些数据算、按哪个时间、怎么算)改具体值;每张功能点卡片采纳或改具体值;体验变体二选一;整份《需求功能方案》你说「对了」才算完。
产出
对话里的《需求功能方案》:口径表(K1、K2…)加功能点表(F1、F2…);多功能点需求另写一份带 mermaid 流程图的讨论稿 <前缀>-功能方案-v<N>.md;spec 会原样收录。
前后
之前可以先用 knowledge-recall 对齐概念;之后 /dev-spec,要换会话用 /dev-handoff,没看懂用 /visual-explain。
/dev-wireframe涉及界面时出低保真线框,看着界面定布局和交互说话就行
什么时候用
需求涉及页面、表单、展示或交互变化;澄清前、澄清后、spec 写完后都能画。
怎么用
说「画个线框」「页面长什么样」。
要你拍板
先确认要画哪些页面和状态;看着线框定下版本,或发现业务问题回去改澄清。
产出
docs/features/<需求目录>/<前缀>-线框-v<N>.html,浏览器直接打开,能点击跳转、切换正常/空态/异常;改一次出一版。
前后
和 /dev-clarify 来回迭代;你确认的版本由 spec 引用后才算数。
/visual-explain没看懂就画一页图解说话就行
什么时候用
对话里的方案、某个文件或话题没看懂时;你不说,它不主动出。
怎么用
说「没看懂」「画个图讲讲」。
产出
一个 HTML 页:先一张总图,再展开关键节点,每个结论配例子。和需求有关的放 docs/features/<需求目录>/,其余放 .cgraphx/visual/;是讨论稿,不当契约。
前后
随时可用,常跟在澄清结果、spec、plan 之后。
/dev-handoff换新会话接着干,或按功能点拆成几个会话说话就行
什么时候用
探索或澄清结束、上下文太长要开新会话;一个需求要分给几个会话做。
怎么用
说「交接一下」「拆成两个会话」。
要你拍板
哪几个功能点归哪个会话;每个会话的需求目录名;主任务和负责人。
产出
每个会话一份 docs/features/<需求目录>/<前缀>-交接提示词.md(澄清已确认时带功能方案,有讨论稿就指向它),外加一句启动语,贴给新会话。
前后
之前 /dev-clarify;新会话里接着 /dev-spec。
/dev-spec写唯一契约:收录功能方案,再定怎么实现说话就行
什么时候用
澄清确认之后、动代码之前;没走澄清的小需求,它会先补一份功能方案让你确认。
怎么用
说「写 spec」。
要你拍板
需求目录名(业务 ID、标题语言)和负责人;标 🔒 的难回头决策(表结构、对外接口、模块边界、安全边界)逐条确认。
产出
docs/features/<需求目录>/<前缀>-spec.md:第一节原样收录功能方案,其余每个功能点一张设计决策表。
前后
之前 /dev-clarify;之后大需求 /dev-plan、小需求 /dev-impl,测试也都从它派生。
/dev-plan大需求拆成子 agent 能照做的任务说话就行
什么时候用
预估改 10 个以上文件、跨 3 个以上独立模块的大需求;拿不准也可以先写。
怎么用
说「写 plan」。
要你拍板
设计预览里 🔒 决策落在哪些任务和文件,你确认后才进实现。
产出
docs/features/<需求目录>/plan/ 下一个 index 加每个任务一个文件,index 末尾一句 /dev-impl-subagent 启动语。
前后
之前 /dev-spec;之后 /dev-impl-subagent。
开发
/dev-impl按 spec、plan 或当前上下文改代码并验证说话就行
什么时候用
小需求、bug 修复,或任何明确的改代码任务。
怎么用
说「实现一下」「按 spec 改」。
要你拍板
没有 spec 和 plan 时,加表改字段、对外接口这类难回头的改动先问你;要人验证的(页面效果、真机)等你回复结果再提交。
产出
代码改动和一份汇报:原来怎样、现在怎样、改了什么、验证了什么;SQL 写错改对后记进 docs/schema-knowledge/SQL避坑.md。
前后
之前 /dev-spec 或 /dev-plan;之后补测试(/api-case、/unit-spec),需求做完 /dev-end。
/dev-impl-subagent大需求一个会话跑完:按任务派子 agent说话就行
什么时候用
plan 已经写好的大需求。
怎么用
贴 plan index 末尾那一句,如 /dev-impl-subagent docs/features/<需求目录>/plan/<前缀>-index.md。
要你拍板
在 main 或 master 上会先问要不要建分支;子 agent 报冲突或卡住时停下问你。
产出
按提交点逐笔提交的代码、统一验证结果和收尾汇报;不 push。
前后
之前 /dev-plan;之后 /code-review。
测试
/api-case从 spec 的接口契约生成 bruno 接口测试说话就行
什么时候用
接口写完要测,不想手工录接口。
怎么用
说「写接口测试」「准备 bruno 测试」。
要你拍板
接口清单确认后才生成。
产出
需求目录下的 <前缀>-接口测试-spec.md;用例在 docs/bruno/<服务>/<需求前缀>/,带真实参数和断言,bruno 能直接打开。
前后
之前 spec 和实现都已完成;之后 /api-run。
/api-run跑 bruno 接口测试,写接口一律查库验数据说话就行
什么时候用
/api-case 生成用例之后,或改完代码想验证修复。
怎么用
说「跑一下订单导出的接口测试」。
要你拍板
只给接口时让你选测哪个需求;服务没就绪会停下等你;失败只报告,修不修你定。
产出
docs/features/<需求目录>/<前缀>-接口测试报告.md;HTTP 200 不算通过,写接口要查库核对数据。
前后
之前 /api-case;失败交 /dev-impl 修,通过后推荐 /ui-case。
/unit-spec从 spec 列出该测的单元测试场景说话就行
什么时候用
spec 写好就能跑,代码还没写也行。
怎么用
说「写单元测试规格」。
要你拍板
spec 没写清的标【待确认】交给你;已有同名规格会先问是否覆盖。
产出
docs/features/<需求目录>/<前缀>-单元测试-spec.md,按主路径、边界、异常分组,每条标 spec 编号(如 F1②、D3)。
前后
之前 /dev-spec;之后 /unit-code。
/unit-code按测试规格写测试代码、跑测试、出报告说话就行
什么时候用
测试规格审过、实现代码已经有了。
怎么用
说「写单元测试」「跑单元测试」。
产出
项目测试目录下的测试文件,加 docs/features/<需求目录>/<前缀>-单元测试报告.md;被测代码缺的场景先跳过占位,不假装通过。
前后
之前 /unit-spec,没有测试规格会直接退出;失败交 /dev-impl 修。
/ui-case从 spec 派生 UI 测试用例,一个功能点一个用例说话就行
什么时候用
需求要在界面上验一遍。
怎么用
说「写 UI 测试用例」。
要你拍板
功能点清单和用例清单各确认一次才落盘。
产出
docs/features/<需求目录>/ui功能测试/<前缀>-ui功能测试-spec.md:操作步骤、预期表现、数据前提、登录账号。
前后
之前 spec 和实现已完成,推荐在接口测试之后;之后 /ui-run。
/ui-run用 Playwright 在浏览器里跑 UI 用例并截图说话就行
什么时候用
/ui-case 写好用例之后;项目要先装 Playwright MCP。
怎么用
说「跑一下 UI 测试」。
要你拍板
执行模式和入口 URL 由你给,服务就绪、测试数据由你确认;遇到验证码或 SSO 会停下找你。
产出
docs/features/<需求目录>/ui功能测试/ 下的 xlsx 报告、结构化结果和按功能点命名的截图;只看界面表现,不查库。
前后
之前 /ui-case;失败交 /dev-impl 修。
安全审计
/audit-login-security查登录和认证有没有能被绕过的漏洞说话就行
什么时候用
上线前、等保或甲方测评前自查;改过登录/鉴权代码;怀疑有人绕过登录、越权看数据、被爆破。
怎么用
说「帮我做一次登录安全审计」「登录有没有漏洞」,可选告诉它审哪个模块、能不能起本地服务。
要你拍板
审计范围(哪个系统/模块);要不要做本地动态验证;有没有 A/B 两个角色的测试账号——没有就先只做白盒。
产出
对话里一份按严重度排序的清单:认证入口表、认证链路、每条发现的 输入 → 代码路径(file:line) → 结果 证据链,以及待验证项;默认不落盘。
前后
独立可跑;设计缺陷交 /dev-spec,实现 bug 交 /dev-impl;它自己不改代码。
知识与数据库
knowledge-recall聊到业务时查知识库,对齐术语和历史决策自动
什么时候用
提到业务名词、项目黑话,或任务开始要查历史决策。
怎么用
agent 自己调;你也可以问「X 是什么」「之前有没有记录过」。
产出
对话里列出命中的概念:名字、文档路径、一行说明。
前后
常在 /dev-clarify 之前;内容来自 /knowledge-write 写进去的条目。
/knowledge-write把业务概念、决策、坑写进知识库说话就行
什么时候用
实现收尾时提示你沉淀,或者你想把对话里聊清楚的业务存下来。
怎么用
说「沉淀一下」「记到知识库」。
要你拍板
重建知识库索引前问你。
产出
docs/knowledge/*.md,写完先过 cgraphx docs validate 校验。
前后
下次 knowledge-recall 就能召回。
/init-knowledge接手陌生项目,批量探索、建知识库敲命令
什么时候用
新接手一个不熟的项目,知识库还是空的。
怎么用
敲 /init-knowledge;中途断了再敲一次,接着上次的进度跑。
要你拍板
开跑前选要探索的语言和排除的目录。
产出
一批 docs/knowledge/*.md 条目,最后合并跨模块的概念。
前后
之后日常靠 knowledge-recall 召回、/knowledge-write 补充。
db-query查数据、看表结构,优先读本地 DDL自动
什么时候用
要验证数据假设、找测试数据、看表结构。
怎么用
agent 自己调;连库配置在 .cgraphx/db-profiles.json,支持 MySQL、PostgreSQL 直连,或经 HTTP 只读接口。
要你拍板
连哪个库不确定时问你;表关系弄不清先问你,不瞎试。
产出
只读查询结果;探索出的字段含义、隐式关系写回 docs/schema-knowledge/<工程>/ddl/<表>.sql 的 DISCOVERED 块。
前后
先跑 /init-ddl 建好本地 DDL,大部分查结构不用连库。
/init-ddl把项目用到的表结构导到本地敲命令
什么时候用
项目接入时跑一次,表结构变了再跑。
怎么用
敲 /init-ddl。
要你拍板
连哪个库;要导的表清单(默认从代码里找)确认后才批量拉。
产出
docs/schema-knowledge/<工程>/ 下的 INDEX.md 和 ddl/<表>.sql,一表一文件;重导时保留 DISCOVERED 块。
前后
之后 db-query 优先读这些本地文件。
规范与收尾
/init-guides生成项目规范,开发时按任务自动送达敲命令
什么时候用
项目刚接入,或写 plan 时提示规范缺失。
怎么用
敲 /init-guides。
要你拍板
五份文件逐个看草案,你拍板后才写入。
产出
docs/guides/ 下编码、接口、数据、测试、git 五份规范,只写本项目和默认做法不一样的。
前后
之后 /dev-plan 按任务类型标「强制引用」,dev-impl 执行时读;git 规范用于提交门禁。
/dev-end需求做完写收口档案,上线后补发布记录敲命令
什么时候用
需求做完收口;上线以后再跑一次,补发布记录。
怎么用
敲 /dev-end,给出 git 仓、提交范围(或时间窗)和测试报告。
要你拍板
上线没有;上线了的话,版本号或 tag、上线时间由你给。
产出
docs/features/<需求目录>/<前缀>-收口档案.md,实际投入时长取自开发时间线;已上线时加 <前缀>-发布记录.md。
前后
之前实现和测试都已完成。
/doc-backfill老需求补头部、补单测产物和收口档案敲命令
什么时候用
规范建立前做完的老需求,文档参差不齐时。
怎么用
敲 /doc-backfill。
要你拍板
这次补哪些产物(单元测试规格、单元测试报告、收口档案);不齐全的需求清单由你确认。
产出
补好头部的主 spec,加上勾选范围内缺的产物;已经齐全的需求直接跳过。
前后
一次性补账,之后的需求照常走流程。
/doc-delivery上线后按实际交付补需求、设计、接口文档敲命令
什么时候用
发布以后,要给客户或团队交文档。
怎么用
敲 /doc-delivery。
要你拍板
要哪几种文档,可以多选。
产出
需求目录下的 <前缀>-需求文档.md、<前缀>-设计文档.md(或 .html)、<前缀>-接口文档.html。
前后
不在开发主线上;写的是实际交付的行为,不重新定义 spec。
回顾与工具
/doc-report从开发记录生成日报、周报、月报敲命令
什么时候用
要汇报最近做了什么、做阶段复盘,或看自己的使用习惯。
怎么用
敲 /doc-report 出一份上周的周报。
要你拍板
时间范围、输出格式、给谁看,没说清的一次问完。
产出
对话里的摘要,或 docs/reports/timeline/ 下的 Markdown、HTML 报告。
前后
数据来自 cgraphx 自动记录的开发时间线,不用手动记。
/doc-workload按功能点 × 工作内容出工作量汇报敲命令
什么时候用
需求交付后给甲方结款、内部对账;开发前报价也能用(汇报标「预估」)。
怎么用
敲 /doc-workload 2026-10-18-REQ-1024-订单导出,只给需求编号也行。
要你拍板
工时从哪来(给记录、让它估、留空你填);汇报给谁;对不上功能点的工作算不算需求变更。
产出
docs/features/<需求目录>/<前缀>-需求工作量.md:工时汇总加拆解表(人天、理由、交付物);没数字的行写 [__] 等你填。
前后
功能点取自 spec 第一节;没有 spec 时先整理一份功能点让你确认。
/cgraphx-guidecgraphx 怎么装、怎么接入、日常怎么用说话就行
什么时候用
新人上手,或想知道有哪些 skill、怎么配合。
怎么用
问「cgraphx 怎么用」「有哪些 skill」。
产出
对话里的使用说明;给人看的页面是 cgraphx 怎么用 和本页。
/my-query开工前评估要不要先查知识库、数据库补上下文敲命令
什么时候用
开始一个任务前,不确定 agent 手里的上下文够不够。
怎么用
敲 /my-query。
产出
对话里的判断:该先用 knowledge-recall、db-query 补哪些上下文。

没有匹配的 skill,换个词试试

「敲命令」只能自己敲 /名字 触发;「说话就行」用自然语言说就会触发,也可以敲命令;「自动」由 agent 按需调用。按 / 跳到搜索框,Esc 清空。
