cgraphx 安装与使用

cgraphx 怎么用

本地优先的 AI agent 研发系统 · skill 流程 + 知识库 / 数据库 / 时间线

最后更新:2026-10-27

每个 skill 怎么用:skill 一览(一个 skill 一行,默认折叠,可搜索)

安装

bash — 安装 cgraphx
$ npm install -g cgraphx # Node.js ≥22.5 <27(内置 node:sqlite,无原生依赖)
# ── 项目级 · 每项目一次 ──────────────────────
~/my-project $ cgraphx install
# 建 .cgraphx/ + 部署 skills 到 .claude/ + 接入 hooks/statusLine + 写工作方式
# 重启 Claude Code 即可
# ── 升级 ────────────────────────────────────
~/my-project $ cgraphx upgrade # npm 自更新 + 自动刷新本项目 skills/hooks(自动清理旧 skill)
# 其他项目各自 cd 进去跑一次;只换包不动项目:cgraphx upgrade --no-install
# ── 卸载 · 可选 ──────────────────────────────
~/my-project $ cgraphx uninstall # 清 .claude/ skills/配置 + 删 .cgraphx/
$ npm uninstall -g cgraphx

最佳起步实践

接入只是第一步。推荐这个顺序——先立规范、再聊业务、然后做需求:

立规范 · /init-guides

生成 docs/guides/ 五份规范(编码/接口/数据/测试/Git)。规范 = 项目对默认做法的有意偏离——「SQL 禁止 ORDER BY」「金额一律 decimal(12,2)」这类最容易偏离又没有工具兜底的约定。这些 guide 是后续任务的强制读点:编码/接口/数据三份会被 /dev-plan 结晶成契约(测试规范不走 plan,由 unit-code 执行前自读,内容全是单测向,接口测试规范由 api-case 读 interface-standards.md 送达;Git 结晶进 plan 提交规范节)。

聚合项目 · 需求目录带上模块名

想让需求目录名带上模块名(如 order-2026-10-25-REQ-1024-订单导出),在 docs/guides/feature-standards.md 的「需求目录命名」一节写清格式、模块取值表与跨模块取法,之后建需求目录都按它命名;没写这一节的项目照旧按默认的 YYYY-MM-DD-[业务ID-]<标题>。

# 需求目录规范

## 需求目录命名

格式:`<模块>-YYYY-MM-DD-[业务ID-]<标题>`

| 模块 | 代码目录 |
|---|---|
| order | order-service/ |
| user | user-center/ |

- 跨模块需求:取主改动模块
- 表外的改动:公共代码记 `common`
- 例子:`order-2026-10-25-REQ-1024-订单导出`

汇集发版 SQL 时按目录名里的日期排,别按目录名排序。

聊业务 · 和 Claude Code 聊项目

做需求前先聊业务。agent 会自动从知识库召回已沉淀的概念、对齐术语;边聊边用 /knowledge-write 把业务实体沉淀下来。接手陌生项目可以跑 /init-knowledge 批量探索建档。知识库越用越厚,重复解释和重复踩坑越少。

做需求 · /dev-clarify 起步

进入主工作流:澄清 → 规格(/dev-spec)→ 实现 → 测试。有了前两步,澄清才有共同语境,而不是从零问起。

先有规范(agent 懂「规矩」),再对齐业务(agent 懂「黑话」),然后做需求才事半功倍。

工作流全景

knowledge-recall(自动召回) │ ▼ /dev-clarify ───────────→ /dev-spec ────→ /dev-plan(大需求必走) 澄清 + 功能方案 唯一契约 一个任务一个文件 │ │ │ ┌───────────────────────────┘ ▼ ▼ /dev-impl(小需求)· /dev-impl-subagent(大需求,一个会话跑完,做完 /code-review) │ ┌────┴─────────────────────────────┐ ▼ ▼ ▼ /api-case /unit-spec 交付收尾: → /api-run → /unit-code /knowledge-write 沉淀 接口测试 单元测试 /dev-end 收口 + 发布记录 commit 门禁(含产物检查) ── 发布后 · 按需(不在主链)────────────── /doc-delivery(需求文档、设计文档、接口文档)

日常默认两步:澄清 + 实现。大需求先 /dev-plan,再 /dev-impl-subagent 一个会话跑完;复杂需求按需补规格和测试;哪里没看懂,说「画个图讲讲」出一页图解。timeline 自动记录开发事件,你不需要主动跑命令。

版本发布 · 可选:/release-start 开版本 → 每个需求 /dev-start 开副本 → /dev-merge 合入 → /release-review 审核并合入主干;副本单独也能用。不用就照旧在当前分支上开发。

各流程详解

做需求的主线。

  • 必经 /dev-clarify 澄清(先探索项目现实、定业务口径,再以功能点为单位给行为链提案、人审稿式改稿,体验变体让人选);结束时给《需求功能方案》,多功能点需求另写一份带 mermaid 流程图的讨论稿
  • 核心 /dev-spec 环节二:唯一契约(第一节原样收录功能方案,主体写怎么实现:每个功能点出设计决策表——机制选型/数据模型/接口契约,🔒 难回头的等你确认)
  • 大需求必走 /dev-plan(小需求可跳过):拆执行计划,不重新选型(以 spec 设计决策表为准,缺口回 spec);index 加一个任务一个文件,先按任务类型拆,一个任务预估超过 15 个文件再按并行度拆;大需求给一句 /dev-impl-subagent 启动语
  • 必经 /dev-impl(小需求)或 /dev-impl-subagent(大需求):大需求在一个会话里按任务派子 agent,主会话按提交点提交,全部做完统一验证、修复,最后提示跑 /code-review;判据是需求规模(预估变更文件 ≥10,且跨 ≥3 个相互独立的模块),不是任务量
  • 随时 /visual-explain:哪里没看懂,说「画个图讲讲」,出一页图解;clarify 结尾、dev-spec 请你确认难回头决策、dev-plan 请你确认设计预览时会提醒
  • 收尾 沉淀知识 → /knowledge-write;平台环节缺口提醒;需求做完 /dev-end 写收口档案,已上线时写发布记录

日常默认 2 步:澄清 + 实现。spec 是唯一契约——「没有任何业务义务存在于 spec 之外」,变更时只改 spec 一处,下游重新派生。

可选——按版本发版、每个需求在自己的副本里做时用;不用就照旧在当前分支上开发。

  • /release-start 开版本:在主干上打上个版本的 tag v<版本号>、拉出版本分支 dev/<下个版本号>、装上提交拦截 —— 发完一个版本、要开发下一个时跑
  • /dev-start 开副本:在主目录旁边写时复制出 <主目录名>@<文件前缀>,拉好需求分支、建好需求目录,给出到副本开新会话的启动语 —— 开始做一个需求时跑,开了版本时每个需求都要
  • /dev-merge 合入:副本里跑,先同步主目录当前分支、就地解决冲突;主目录里跑 /dev-merge <需求>,预演没冲突就以「合入需求：<标题>」合入当前分支 —— 需求做完、/code-review 过了之后
  • /release-review 发版审核:出 docs/releases/v<版本号>-发版审核.md 并提交,你说「发」再合入主干、列出可以清理的副本 —— 发版那天改好版本号之后

版本分支上直接提交会被拦下,只放行合并提交和以 chore(release): 开头的整版改动;副本里的会话、提交、任务归属记进主目录,知识库索引和「我的需求」索引各目录各建各的。副本单独也能用:没开版本时 /dev-start 从主目录当前分支拉,/dev-merge 合回这个分支,合完问要不要删副本。需要 git 2.38 以上;副本只支持 macOS、Linux。

需求开发完成后,从 spec 到测试报告的全自动闭环。测试产物基于开源工具 bruno:docs/bruno/ collection 可用 bruno app(GUI)直接打开,可视化浏览、手工调试接口;自动化执行依赖其 CLI(@usebruno/cli),需 npm install -g @usebruno/cli(每机器一次,也可项目本地装;未装时 /api-run 报错退出并指向该命令)。

  • /api-case 基于 spec 接口契约自动生成 bruno 测试接口(.bru + 内嵌断言 + 真实参数 + 多环境配置)
  • /api-run 跑测试 + 核实写接口 DB 副作用 + 出报告 —— 写接口必须查 DB 验数据,HTTP 200 ≠ 通过

产物落在 docs/bruno/ + docs/features/<前缀>/(测试规格 + 报告)。两个 skill 顺序依赖,但 api-run 也可独立跑(针对已有 .bru)。失败只报告不修代码不重跑,交用户决定。

需求开发完成后的独立流程,共享 spec 作为输入(与接口测试同节奏)。

  • /unit-spec 基于 spec 产出测试规格文档(零代码依赖——该测哪些路径/边界/异常)
  • /unit-code 基于测试规格 + 已有实现,填实测试代码 + 跑测试 + 出报告 —— 找不到测试规格则退出要求先跑 unit-spec

产物落在 docs/features/<前缀>/(测试规格 + 报告)+ 项目测试目录。

两个知识积累闭环,用得越多越值钱。

业务知识(沉淀 → 召回)

  • /knowledge-write 把有价值的知识沉淀到 docs/knowledge/(开发收尾自动提示,也可随时手动触发)
  • knowledge-recall 做需求前自动召回相关概念、对齐术语,精确查询也走它 —— agent 自动触发
  • /init-knowledge 接手陌生项目时批量探索建档 —— 可选,只跑一次
  • /knowledge-migrate 把 Claude Code 自动记忆按去向迁进知识库、项目根目录 CLAUDE.md 或本人 ~/.claude/CLAUDE.md,再关掉本人的自动记忆 —— 用过自动记忆的项目,每人跑一次

数据模型(导出 → 探索 → 回写)

  • /init-ddl 按工程批量导出 DDL 基线(一表一文件)—— 项目接入时跑一次,schema 变了重跑
  • db-query 查数据时首选读本地 DDL(便宜),只在知识库没有或要实际数据时才连库(贵,兜底);探索发现回写 DISCOVERED 块 —— agent 自动触发

业务知识落在 docs/knowledge/*.md(写前必过 cgraphx docs validate);数据模型落在 docs/schema-knowledge/<工程>/。重 dump 时 DISCOVERED 块自动保留,积累不丢。

发布后 · 按需——不在开发主链上,不参与流程门禁。

  • 发布后 /doc-delivery 需求文档、设计文档、接口文档(运行时选,可多选)

设计原则:前期文档越少,变更回归成本越低;发布后写的是实际交付的行为,不存在文档与系统漂移的问题。

按需 · 不在开发主链——上线前、等保或甲方测评前自查。

  • 按需 /audit-login-security 枚举全部认证入口(密码、短信、扫码、SSO、token 刷新、后台登录),沿认证链路五段逐条查绕过、越权、凭据、会话、爆破
  • 每条发现给三段式证据链:攻击者输入 → 代码路径(file:line) → 结果,按致命/高/中/低 + 置信度排序
  • 白盒为主;本地或测试环境才做最小动态验证,不碰生产、不爆破、不扫描;只报告不修代码,默认不落盘

设计缺陷交 /dev-spec,实现 bug 交 /dev-impl。已怀疑被入侵(要查谁怎么进来的)不是这个 skill,是日志取证。

  • /doc-report 从自动记录的开发事件流生成日报/周报/月报/阶段总结/使用习惯分析
  • /doc-workload 产出需求工作量汇报,按功能点 × 工作内容拆工时(内部对账/甲方结款依据)

timeline 通过隐藏 hook 自动记录(每次约 5ms,不阻塞工作流),数据一直在 .cgraphx/cgraphx.db——不用回忆,不用拼凑。

docs/ 目录速查

翻文档时知道去哪儿找——哪个目录由哪个 skill 维护。

必有 可选(按需) 发布后按需 
docs/
├── features/   需求目录(单次需求工作目录,spec 必有)
│   └── <feature-id>/
│       ├── <前缀>-spec.md             /dev-spec             必有  唯一契约
│       ├── plan/                      /dev-plan             可选  大需求
│       ├── <前缀>-<主题>-v<N>.html    /visual-explain       可选  要图解时
│       ├── <前缀>-需求文档.md         /doc-delivery         发布后  按需
│       ├── <前缀>-设计文档.md         /doc-delivery         发布后  按需
│       ├── <前缀>-接口文档.html       /doc-delivery         可选  发布后按需
│       ├── <前缀>-接口测试-spec.md    /api-case             可选  开发完成后
│       ├── <前缀>-接口测试报告.md     /api-run              可选  api-case 后
│       ├── <前缀>-接口测试验证.jsonl  /api-run              可选  自动产出
│       ├── <前缀>-单元测试-spec.md    /unit-spec 可选  开发完成后
│       ├── <前缀>-单元测试报告.md     /unit-code 可选  开发完成后
│       ├── <前缀>-收口档案.md         /dev-end              可选  需求做完
│       └── <前缀>-发布记录.md         /dev-end              可选  已上线时
│
├── knowledge/   业务知识库(跨需求共享)
│   └── *.md                          /knowledge-write 沉淀  /init-knowledge 批量建档  /knowledge-migrate 迁入记忆
│
├── bruno/   接口测试(bruno app 可直接打开)
│   ├── bruno.json
│   ├── environments/                 local / staging / production
│   └── <服务>/<需求前缀>/<接口>/<场景>.bru
│
├── schema-knowledge/   数据模型知识库
│   └── <工程>/
│       ├── INDEX.md                  表清单 + 注释(agent 入口)
│       ├── pending-comments.sql      DBA 待执行 COMMENT(action 队列)
│       └── ddl/<table>.sql           DDL + DISCOVERED 块(探索积累)
│
├── security/   安全审计报告(/audit-login-security 默认不落盘,要归档才写)
│   └── <日期>-登录安全审计.md
│
├── releases/   发版审核报告(/release-review 开了版本才有)
│   └── v<版本号>-发版审核.md
│
└── guides/   项目规范(/init-guides 生成)
    ├── coding-standards.md
    ├── interface-standards.md
    ├── data-standards.md
    ├── testing-standards.md
    └── git-standards.md              commit 门禁指向此文件

两个核心目录——docs/features/ 是单次需求工作目录(必须有 spec),docs/knowledge/ 是跨需求共享的业务知识库。bruno/、schema-knowledge/、security/、releases/、guides/ 按需出现。
