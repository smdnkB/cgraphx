# 需求工作量汇报 (doc-workload)

## 定位

- **按功能点 × 工作内容拆**:一级是功能点,直接用 spec 第一节功能方案的编号、名称、类别——需求方在澄清时确认过这张表,拿着汇报能逐个对上自己要的功能;二级是每个功能点下实际做的事,一件事一行。需求澄清与方案设计、联调上线这类跨功能点的工作单列「公共」。
- **每行三件套**:人天 + 理由 + 交付物。理由写事实(做了什么、核对了什么、测了几个场景),它就是这一行工时的依据;交付物写能核验的接口、页面、表、报告。
- **工时数字不编**:只来自用户给的记录,或用户明确授权你估;都没有就留 `[__]`。
- **交付物以代码为准**:写进汇报前回代码核实;spec、plan 写的和代码不一致,以代码为准。

## 工作流程

0. **定需求,问两件事**:定位 `docs/features/<feature-id>/`(用户只给编号或一句话时先找目录),用 `AskUserQuestion` 一次问完:
   - 工时数字从哪来:我给记录(工时表、日报)/ 你按交付物估 / 先留空,我来填
   - 汇报给谁:甲方或财务(交付物写到接口、页面、表)/ 内部对账(写到文件和提交)
1. **取功能点**:spec 第一节功能点表里有编号的行就是一级骨架,编号、名称、类别照抄;编号「—」的(砍掉的建议新增、边界外)不计工时。
2. **列工作内容**:每个功能点从这几处收集做过的事——spec「怎么实现」里它的设计决策和契约、plan 里标了它的任务、这个需求的提交记录、测试报告。代码量小但费时的事单独成行,不并进开发那一行:需求待确认项核实、外部接口联调、跨服务契约确认、配置或映射纠正、返回值核对、多场景自测。
3. **核实交付物**:grep / Read 逐项确认接口、页面、表、文件真实存在,跨服务的每个服务分别核实。spec、plan 和代码对不上的地方(方法名、URL、返回结构、映射表)以代码为准,纠正这些出入花的时间也算一行工作内容。
4. **填工时**:按第 0 步的来源填。每行 0.5~2 人天(用户另有粒度按用户的),超过 2 天拆细,不到 0.5 天并进同一功能点的相邻行。用户只给了总数:按工作内容分摊到各行,工时来源写「总数来自 <出处>,逐行为分摊估算」。
5. **核对后落盘**:各功能点小计加起来等于合计;每行三件套齐全;每个计工时的功能点都有行。

做过的事对不上任何功能点、也不算公共:不塞进某个功能点,列给用户定——算需求变更就单列,编号写「变更」,理由写谁在什么时候提的;不算就不计。

| 情形 | 怎么做 |
|---|---|
| 已交付(默认) | 照上面的流程 |
| 开发前报价 | 工作内容取自 spec 设计决策和 plan 任务,跳过第 3 步;交付物写计划产出;标题写「需求工作量(预估)」 |
| 没有 spec,或 spec 是旧格式、没有功能点表 | 第 1 步先照功能点表的格式(编号 / 功能点 / 类别),从需求文档和提交记录整理功能点,用户确认后再拆 |

## 范例

````markdown
# 需求工作量: 订单导出

> feature-id: 2026-10-18-REQ-1024-订单导出
> 负责人: zhangsan
> 日期: 2026-10-30
> 工时来源: zhangsan 工时表(2026-10-18 ~ 10-29)

**一句话**:原来运营要找开发导订单;这次在订单列表加「导出」,运营自己下载近 90 天的订单去对账。共 2 个功能点,合计 6.5 人天。

## 工时汇总

| 编号 | 功能点 | 类别 | 人天 |
|---|---|---|---|
| F1 | 订单导出 | 核心 | 4 |
| F2 | 导出记录查看 | 支撑 | 1 |
| 公共 | 需求澄清与方案设计、联调上线 | — | 1.5 |
| | **合计** | | **6.5** |

## 工时拆解

| 编号 | 工作内容 | 人天 | 理由 | 交付物 |
|---|---|---|---|---|
| F1 | 导出任务表 | 0.5 | 新建 1 张表;增量建表脚本,全量表结构同步 | export_task 表、建表脚本 |
| F1 | 导出接口与后台生成 | 1.5 | 提交任务、下载文件 2 个接口;后台异步生成 xlsx,复用报表查询并加近 90 天条件 | `POST /api/orders/export`、`GET /api/exports/:taskId/file` |
| F1 | 对接站内通知 | 1 | 通知中心文档写返回 `id`,实际返回 `msgId`;逐个字段核对后按实际结构对接 | 「导出完成」站内通知 |
| F1 | 订单列表「导出」按钮 | 0.5 | 按角色控制显隐;近 90 天无数据时提示、不生成文件 | 订单列表页「导出」按钮 |
| F1 | 多场景自测 | 0.5 | 无数据、无权限、连点两次、跨 90 天边界,共 4 个场景 | 接口测试报告 |
| F2 | 「我的导出」列表与重新下载 | 1 | 沿用报表任务列表,加 7 天过期判断和提示;过期、重新下载 2 个场景自测 | 「我的导出」页 |
| 公共 | 需求澄清与方案设计 | 1 | 3 轮澄清锁定 2 个功能点;定 3 条设计决策 | 规格说明 |
| 公共 | 联调上线 | 0.5 | 测试环境联调、生产发布、上线冒烟 | 发布记录 v2.3.0 |
````

- **汇总表**:每个计工时的功能点一行,公共一行,合计一行;编号、名称、类别和 spec 第一节一字不差。
- **拆解表**:按功能点编号排,同一功能点的行挨着,公共放最后;「人天」列只写数字或 `[__]`。
- **理由只写事实**:不写「工时合理」「经得起核对」这类话。
- **交付物按受众写**:给甲方或财务写接口、页面、表、报告(范例即此);内部对账写到文件路径和提交 SHA。
- **工时来源**:记录写出处;估算写「估算(按交付物,用户授权)」;有占位写「标 `[__]` 的待填」。
- 对接外部系统多时,拆解表后加「涉及系统」一节,每个系统一行:对接了什么、核对了什么。

## 产物位置与命名

- `docs/features/<feature-id>/<文件前缀>-需求工作量.md`,文件前缀 = feature-id 去掉开头的日期;放需求目录根下。
- 头部不写 `> 产物:`——需求工作量不是平台登记的产物类型。

## 收尾

回复里给出工时汇总表和工时来源;有 `[__]` 的逐行列出,等用户给数。用户改哪一行,改完文档再给一版。

## 红线(绝对不能做)

1. ❌ **不编工时数字**——没有记录、没授权估,就留 `[__]`。
2. ❌ **不写没核实过的交付物**。
3. ❌ **不改功能点的编号、名称、类别**——和 spec 第一节一致,需求方才对得上。
4. ❌ **不把功能方案外的工作塞进某个功能点**——列给用户定。
