# 编写 Spec (Write Spec)

## 定位

- **Spec = 任务的唯一契约**:归档系统必须满足的行为、规则、数据、接口、权限、异常、兼容性、约束和验收口径——plan 的稳定输入。Spec 之后,后续 agent 不重新解释业务规则、数据口径、接口契约、权限边界或异常行为。
- **没有任何业务义务存在于 spec 之外**:澄清总结、PRD、聊天记录都是输入和证据,不是契约——决策只有写进 spec 才成为义务;在 clarify 里谈过但没进 spec 的,不具约束力。
- **Spec 写业务可观察的要求与后果,不写实现手段选型**(同步/异步、缓存、定时任务归 plan);不展开成任务列表、文件级修改步骤、代码实现细节。

<HARD-GATE>
缺少影响规格正确性或 plan 正确性的关键信息 → 先补问 3-5 个;不阻塞成文的标【待确认】。
不编造未确认的业务规则、接口行为、数据结构或技术约束;必须依赖未确认规则时,先向用户确认。
会影响 plan 写死或实现正确性的【待确认】,不能伪装成已确认规格。
</HARD-GATE>

## 边界

- 澄清总结 = spec 的输入,**无损接收**:已锁定的入正文,未解决的入【待确认】,不悄悄丢,不伪装成已确认。
- Plan 说明如何改代码满足 spec,不得重新定义 spec;实现手段选型在 plan 阶段结合代码规划、用户拍板。
- Implementation 按 plan 编码,不得重新设计 spec 已锁定的契约。

## 输入理解

- 优先基于当前上下文:用户已确认的需求 · clarify 产出(已锁定业务决策/已排除方案/下游就绪判断)· 业务目标/边界/非目标 · 角色/权限/流程/状态/规则/异常/验收口径 · 已有 PRD/接口说明/业务文档/代码上下文/数据口径/影响分析 · 项目已有的模块/页面/接口/模型/任务/队列/权限系统约束。
- 上下文足够 → 直接写,不重新澄清已确认内容。
- **只有一句模糊想法 → 不硬写完整 spec,提醒用户走 clarify 流程。**

## 工作流程

0. **命名先行**(写内容前必须落定):① 业务 ID——有无工单号/需求单号?允许留空但**必须显式确认**;② 标题语言——中/英/混合,用户选定,**禁止擅自中文转英文 slug**;③ 负责人——默认 `git config user.name`,向用户展示确认,写入头部 `> 负责人:`(「我的需求」检索以此为准)。用户已给 feature-id → 直接复用。
1. **检查完整性**:识别缺失的行为/规则/数据/接口/权限/异常/兼容性/验收;只补问影响正确性的;clarify/PRD 中未拍板的规则不得写成已确认;无损接收 clarify 锁定决策。
2. **定粒度**:简单需求轻量;跨模块/跨系统/涉数据/权限/兼容性 → 完整;不为显得完整展开无关技术细节。
3. **归档规格**:业务描述 → 系统应满足的行为和约束;明确输入/输出/状态/规则/数据/权限/异常/验收;plan 必须遵守的用明确措辞;写清哪些契约不允许 implementation 自行调整。
4. **标记不确定**:不阻塞的标【待确认】;推测 ≠ 已确认;影响 plan 拆分/契约/权限/验收的,标明"不解决前不可写死 plan"。
5. **自检**:能否指导 plan;是否混入实现步骤/代码方案;规则/数据/权限/异常/兼容性/验收是否清楚。

## 结构(动态组织,不是固定模板)

面向研发/技术负责人/Code Agent/测试/plan 编写者:清楚、可引用、可验证。

优先级:项目既有格式(`docs/features/`、历史 spec、团队模板)> 轻量结构(简单需求)> 按业务流程/模块/接口/数据/权限/迁移等实际风险组织(复杂需求)。无关内容不留空章节;plan 需要而模板没有的,新增项目特定章节。

- **头部**:`# 规格说明: <需求名称>` + feature-id / 状态 / 负责人 / 日期(每行 `> 字段: 值`)。
- **最小结构**:目标与范围 / 已确认规格 / 关键约束 / 不可留到实现期的决策 / 验收与验证关注点 / 待确认项。
- **复杂需求按需扩展**:术语与业务对象 / 业务规则 / 系统行为 / 数据、状态与口径 / 权限、安全与审计 / 接口、页面与系统边界 / 时效、幂等与一致性预期 / 兼容性、迁移与存量数据 / 异常与边界场景 / 验收标准与测试关注点 / Plan 编写约束。

## 内容模块池(按需取用,不逐项填表,不留空章节)

| 模块 | 写什么 |
|---|---|
| 目标与范围 | 目标、包含范围、明确非目标;范围应约束后续 plan |
| 术语与业务对象 | 实现/测试必须理解的概念(角色/单据/状态/产品/订单/账户/套餐/任务等),含易混同名辨析 |
| 业务规则 | 经确认的判断/限制/计算/状态变化/优先级/冲突处理/例外,每条可验证 |
| 系统行为 | 各触发条件下的行为;按场景/用户动作/事件/接口/状态组织;维度:前置条件/触发/行为/输出/失败行为 |
| 数据、状态与口径 | 读写/迁移/回填的数据及业务含义;可描述模型/字段/状态预期,**不展开完整数据库设计** |
| 权限、安全与审计 | 角色权限/可见性/租户・组织・区域隔离/审计/脱敏 |
| 接口、页面与系统边界 | 受影响的页面/接口/外部系统/任务/队列/模块;写业务级 IO 与边界,**不写代码级步骤** |
| 时效、幂等与一致性预期(业务可观察) | 结果时效/数据新鲜度/重复请求预期(幂等)/失败・重试・超时预期/用户是否需感知中间状态/进度/通知/可观测性。**写预期与可观察后果,不写手段**——同步/异步・MQ・缓存选型由 plan 定;手段产生信封外可观察后果 → 先补 spec |
| 兼容性、迁移与存量数据 | 旧用户/旧接口/历史数据/旧流程兼容;迁移/回填/默认值/灰度 |
| 异常与边界场景 | 无权限/数据不存在/重复/并发/部分成功/回滚/空数据/外部失败 |
| 验收标准与测试关注点 | 可验证的行为与业务结果;可给测试关注点,**不写详细测试脚本** |
| Plan 编写约束 | 不能改的旧行为/必须复用的机制/不能引入的依赖/必须兼容的接口/必须覆盖的风险 |
| 不可留到实现期的决策 | 业务规则/口径/维度/时间范围/去重 · 状态含义/流转/异常 · API IO/错误语义/兼容性 · 权限/安全/审计/可见性 · 迁移/回填/默认值/灰度 · 时效/新鲜度/一致性预期/幂等(**实现手段不入此列,由 plan 定**)。未确认 → 待确认项 + 注明"不解决前不能进严格 plan" |
| 待确认项 | 仍需用户/业务方/技术负责人确认的内容,不藏在正文里 |

## 质量检查(输出前)

- plan 编写者能据此拆解;规则/行为/边界没有混在一起含糊。
- 数据/状态/权限/异常/兼容性/验收口径明确。
- 没滑向客户 PRD / 任务计划 / 代码方案;未确认全标【待确认】;"不可留到实现期"已列出;Plan 约束足以防跑偏。

## 产物位置与命名

- 路径:`docs/features/<feature-id>/<文件前缀>-spec.md`。无可写项目上下文 → 回复中直接输出正文。
- **feature-id**:`YYYY-MM-DD-[业务ID-]<标题>`。业务ID 可选(字母数字 + 连字符);标题允许中/英/混合,**不得**中文转英文 slug;重名追加短后缀;同目录已有 PRD 优先复用同一 feature-id。
- **文件前缀**:有业务ID = `<业务ID>-<标题>`,无 = `<标题>`。
- 敏感字符(`/ \ : * ? " < > |`)拒绝,要求用户重命名,不自动替换。
- 与旧目录共存:始终新命名,不探测旧 `spec.md`。

## 收尾

产物落盘后自动跑 `cgraphx features sync`(更新 `.cgraphx/my-features.md` 本人需求索引——本地文件、幂等、不问用户)。然后只提示用户审阅并指出需要调整的地方。**不主动继续写 plan 或代码。** 用户日后找需求目录:`cgraphx features list --mine`。

## 红线(绝对不能做)

1. ❌ **不编造**未确认的业务规则/接口行为/数据结构/技术约束——标【待确认】或先确认。
2. ❌ **不把【待确认】伪装成已确认规格**(尤其影响 plan 写死的)。
3. ❌ **不把实现手段选型写进 spec**(同步/异步、缓存、定时任务归 plan)——写可观察后果与预期。
4. ❌ **不展开成任务列表/文件级修改步骤/代码实现细节**。
5. ❌ **不重新澄清已确认内容**;模糊想法 → 提醒 clarify 流程,不硬写。
6. ❌ **不自动进入 plan/implementation**——输出后提示即停。
7. ❌ **不擅自中文转英文 slug**——命名归用户。
