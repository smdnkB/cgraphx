# Audit Login Security(登录安全审计)

## 定位

对**当前项目**的认证功能做白盒审计,回答一个问题:

> 攻击者现在能不能**不登录**,或**登成别人**,或**登成管理员**?

不是背 OWASP、不是跑扫描器、不是合规测评。结论只给在对话里,不落盘、不修代码。

- **白盒为主**:证据是代码行,不是推测。动态验证只用来确认已经看到疑点的那几行。
- **范围是认证与身份边界**:登录、会话、鉴权执行、找回/改绑。登录后的**越权**属于本 skill;支付、上传、反序列化等业务漏洞不属于。
- **已怀疑被入侵** → 不是本 skill(取证与日志分析,见边界表)。

## HARD-GATE

1. **先枚举全部入口,再谈单个登录页。** 只审主登录页是最常见的漏报来源。最少覆盖:密码登录、短信/邮箱验证码、扫码/第三方 SSO、免密/记住我、token 刷新、后台/运维登录、注册即登录。**漏一个入口 = 结论不成立。**
2. **每条发现必须有证据链**,固定三段式:
   `攻击者输入 → 代码路径(file:line) → 结果`
   写不出这条链的,只能进「待验证」,不许进发现列表。
3. **不碰生产、不爆破。** 动态验证只对 localhost 或用户明确指认的测试环境;最小请求验证(每个疑点 ≤ 3 次,规则见 R4);禁止字典、批量、并发压测;测试账号向用户要,不自己注册、不试真实用户。
4. **只报告,不改代码。** 发现致命项也不顺手修——审计和修复同一个人做,证据会失真。修复走 `/write-spec`(设计缺陷)或 `/implementation`(实现 bug)。
5. **区分 bug 与风险。** 代码写错、可复现 = **bug**;设计或配置缺失、有条件才可利用 = **风险**。分开列,不用一个「中危」糊过去。
6. **不编造。** 没读到就写「无法判定:未找到 X」,不写「可能被攻击」「建议关注」。**不把 checklist 条目当发现**——每条发现必须落到本项目的某一行。

## Trigger

**使用此 skill 当**:
- "我们登录有没有漏洞 / 帮我做一次登录安全审计 / 登录渗透测试"
- 上线前、等保整改、甲方安全测评前自查
- 改过登录/鉴权代码,想确认没引入绕过
- 怀疑有人绕过登录、越权看数据、暴力破解

**不要使用此 skill 当**:
- 已被入侵、要查谁怎么进来的 → 日志与取证分析(本 skill 不做日志取证)
- 要出具等保/ISO 合规结论 → 合规测评,不是代码审计
- 只想修某个已知漏洞 → `/implementation`;本 skill 只审计报告,修复是另一个流程的决定
- 全站渗透(上传、反序列化、SSRF、前端 XSS 全扫) → 超出范围
- 只想看某个接口入参校验 → `/run-api-test`

## 与其他 skill 的边界

| skill | 关系 | 说明 |
|---|---|---|
| `write-spec` | 下游 | 设计缺陷类发现(缺限流、会话策略、MFA)转成需求再改 |
| `implementation` | 下游 | 实现 bug 类发现直接修;本 skill 不改代码 |
| `run-api-test` | 复用 | 项目已有 `docs/bruno/` 时,从中取登录请求的入参与环境变量改用 curl 复现,不新建也不改测试文件 |
| `db-query` | 复用(只读) | 看用户表/登录日志的字段与索引;不导真实密码、不查真实手机号做例子 |
| `knowledge-recall` | 可选前置 | 先召回项目的账号体系、多租户、SSO 相关业务概念,避免审错模型 |
| `iboc-check`、`write-unit-test-*` | 无关 | 不涉及测试产物与文档补账 |

## 核心模型:认证链路五段

渗透者不找「看起来像登录页」的那段,而是找**五段里最弱的一环**。

| 段 | 必须回答的问题 | 典型漏洞落点 | 代码在哪找 |
|---|---|---|---|
| ① 入口 | 一共几种登录方式?各自强度一致吗? | 短信/扫码入口无限流、免密可枚举、后台登录无 MFA | 路由/控制器、网关白名单、前端登录页、`docs/bruno/` |
| ② 凭据校验 | 密码怎么存、怎么比?账号状态查了吗? | 弱哈希、时序比对、SQL 注入、逻辑短路(密码错也发 token)、停用账号可登录 | service 层、mapper/SQL、密码工具类、用户状态字段 |
| ③ 会话签发 | token 怎么生成、验签了吗、过期多久? | JWT 不验签/`alg:none`/密钥硬编码、token 无过期、session id 可预测、cookie 缺 HttpOnly | JWT util、session 配置、cookie 设置、网关鉴权插件 |
| ④ 鉴权执行 | 拦截器覆盖全部路径吗?权限从哪来? | 白名单绕过、路径匹配缺陷、角色/租户 id 取自请求、IDOR | 拦截器/中间件/注解、`@PreAuthorize`、权限查询、网关路由 |
| ⑤ 终结与找回 | 登出真的失效吗?重置链接可预测吗? | 登出只清前端、旧 token 仍可用、重置 token 弱/可复用、改绑手机不验旧号 | logout、refresh、reset、bind 接口 |

**跨段检查**:①的每个入口都要走到⑤;⑤的每个出口(登出/改密/改绑/踢人)都要能销毁③签发的会话。链路断在哪一段,就是哪一段的风险。

## 流程

### R0 锁范围(问清三件事)

1. 审哪个系统/模块(单体? 后台? APP API? 多服务仓库让用户指定)
2. 允不允许起本地服务做动态验证(用户没答 → 只做白盒)
3. 有没有 A/B 两个角色的测试账号(越权验证必需;没有则越权类全标「无法判定」)

用户没指定时,默认审当前工作目录的主应用;范围不清就先问,**不猜**。项目里根本没有认证功能(纯库、纯静态站)→ 直接说明,不硬套清单。

### R1 枚举认证入口

四处交叉扫,别只看一处:

1. **路由/控制器**:`grep -rn -iE "login|signin|sign-in|authenticate|token|session|password|passwd|pwd|captcha|otp|sms|mfa|2fa|sso|oauth|wechat|dingtalk|ldap"`,再对照框架的路由注册方式(Spring `@RequestMapping`/`@PostMapping`、Express `app.post`、Nest `@Post`、Django `urls.py`、Laravel `routes/`、Go `HandleFunc`)
2. **前端登录页与网关**:登录页调了哪些接口、有没有「记住我」;nginx/网关的 `permitAll`、白名单路径、`/api/**` 放行规则(绕过高发区)
3. **契约与测试资产**:OpenAPI/Swagger、`docs/bruno/**/*.bru`、Postman 集合
4. **数据层(可选,`db-query`)**:用户表、登录日志表、第三方绑定表——能看出有没有多套账号体系、有没有历史遗留字段(如 `plain_password`)

**产出入口清单,先给用户确认再往下**:

| # | 入口 | 协议/路径 | 账号体系 | 是否主流程 | 初判 |
|---|---|---|---|---|---|

### R2 画链路

每个入口沿五段定位实现,只读认证路径,不读整个项目。产出链路表(段/实现位置/机制/证据)。读到公共拦截器、鉴权注解、网关过滤器时,**必须全量确认覆盖范围**,不能只看一个接口。

入口 > 3 个、或认证相关代码超过约 2000 行时,按入口派只读子 agent 并行读(每个子 agent 只回链路表 + 证据链,不回整段代码),主 agent 汇总——否则上下文会被第一个入口占满。

### R3 逐条核查

按 `references/attack-checklist.md` 的顺序走:**先绕过与越权,再凭据/会话,最后加固项**。每项给三态之一:

- **命中**(附证据链)
- **未命中**(附一句依据,例如「登录接口有 IP+账号双维度限流 `AuthRateLimiter.java:42`」)
- **无法判定**(写清缺什么:代码没找到 / 需要运行时 / 需要测试账号)

**未命中也要写依据**,否则等于没查。

### R4 动态验证(可选,受控)

代码里看到疑点、且用户允许本地/测试环境时才做。规则与安全探针见 `references/dynamic-probes.md`。原则:

- 只验证**已看到疑点**的那几行,不漫游扫描
- 每个疑点 ≤ 3 次请求;不并发、不挂字典
- 只对测试账号;命中 WAF 或连续 5xx 立即停
- 记录原始请求/响应作为证据;失败不重试

### R5 出报告(对话内)

按**可利用性**排序,不按 checklist 顺序。结构:

```markdown
# 登录安全审计 · <系统/模块>
**结论**:<一句话:攻击者能否绕过/接管/提权,风险集中在哪一段>
**范围**:<仓库/分支> · 入口 N 个 · 核查 M 项 · <白盒 / 本地动态>
**风险分布**:致命 a · 高 b · 中 c · 低 d · 待验证 e

## 认证入口
| # | 入口 | 协议/路径 | 账号体系 | 主要风险 |

## 发现
### F1 [致命] <标题>
- **类型**:bug / 风险
- **位置**:`path:line`
- **攻击链**:<输入> → <代码路径> → <结果>
- **证据**:<≤10 行代码或请求响应>
- **影响**:<谁能做什么,需不需要前置条件>
- **修复方向**:<一句话,不写完整补丁>
- **置信度**:高 / 中 / 低

## 待验证
| # | 疑点 | 缺什么 | 怎么验 |

## 下一步
<1. 建议先修的 1~2 项 + 走 /implementation 还是 /write-spec>
```

### R6 收尾

- 致命/高危:明确一句「建议先修 X」,给转交方式
- 问一句「要不要归档?」——**默认不落盘**;用户说要才写 `docs/security/<日期>-登录安全审计.md`
- 不自动改代码、不自动建需求目录、不自动提交

## 严重度(按前置条件判,不按 OWASP 编号)

| 级别 | 判据 | 登录场景的例子 |
|---|---|---|
| **致命** | 不需要任何前置条件,直接拿到身份 | 认证逻辑短路、JWT 不验签/`alg:none`、硬编码后门账号、登录处 SQL 注入直接成功、验证码万能码 + 任意手机号 |
| **高** | 需要一个普通账号或公开信息,可越界 | 任意用户数据越权(IDOR)、重置任意账号、弱哈希且可离线破解、token 永久有效/密钥硬编码、登出改密后旧会话仍有效、社交登录按邮箱自动合并 |
| **中** | 需要额外条件(网络位置、用户交互、时间窗) | 用户名枚举、验证码可复用、无限流或锁定策略可 DoS、CSRF 登录、开放重定向、OAuth state 缺失 |
| **低** | 纵深防御缺失,单独不可利用 | cookie 缺 Secure/SameSite、无 HSTS、错误信息含栈、无登录审计日志 |

**唯一标准是「攻击者需要什么前置条件」**——不需要前置条件的往上判。

## 去噪(这几类最常见的误报)

- **看到 MD5 就报**:先确认这个字段是不是密码(`password`/`passwd`/`pwd`),有些人用 MD5 做的是文件指纹/签名
- **看到 `@PreAuthorize` 就认为全覆盖**:注解只在被 Spring 代理的 bean 上生效,同类内部调用、网关直连、非 Controller 路径都会漏
- **看到前端隐藏菜单就当越权**:前端隐藏不是权限,要看后端接口有没有角色校验;反过来,后端有校验也别急着判「未命中」,要确认校验用的是**服务端会话里的角色**而不是请求参数
- **把测试环境的 debug 开关、默认密码当生产漏洞**:先确认配置文件的环境归属(`application-dev.yml` ≠ 生产)
- **把框架默认行为当缺陷**:先看版本与配置是否覆盖了默认(如 Spring Security 默认 CSRF、cookie 属性)
- **把「代码里没看到」写成「不存在」**:改为「无法判定:未找到 X 的实现」

## 禁止

- 不做全站渗透、不测生产、不跑扫描器扫全站
- 不导出真实用户密码/手机号/身份证做例子,证据里打码
- 不把 OWASP 条目当发现,不给没有证据的「可能」
- 不边审边改代码,不在审计过程中提交
- 不因为「高危」就跳过报告直接修——修复是另一个流程的决定
