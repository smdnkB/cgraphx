# 知识库提炼整理 (knowledge-refine)

## 定位

- **定期体检,不是日常沉淀**:日常沉淀走 `/knowledge-write`(一次写一篇);本 skill 隔一段时间(建议每月或攒了几个需求后)从整体看知识库:词表乱没乱、该有条目的词有没有条目、需求文档里定过的口径进没进知识库、条目跟不跟得上代码。
- **两段式**:①**体检**——只读,产出一份整理清单(`docs/knowledge/.refine/<日期>-整理清单.md`),每一项都带证据;②**执行**——人在清单里勾选后,按勾选项改知识库,勾什么做什么(新建、改头部、改正文、合并、删除都可以)。体检这一轮**只写清单,不动任何知识文档**。
- **依赖**:`knowledge-write` 的模板与规则(条目怎么写、术语条目、合并规则、validate);cgraphx CLI(`cgraphx docs …`);Node(跑本 skill 自带脚本)。
- **自带脚本**(在本 SKILL.md 同目录的 `scripts/` 下,下文写作 `<skill目录>/scripts/`;只读、不联网):
  - `kb-inventory.cjs`:知识库盘点——概念用量、缺主条目的概念、类名式概念、疑似近义、路径/链接失效、相关代码在条目更新后又改过、draft 条目
  - `harvest-terms.cjs`:从本项目 Claude Code 会话里挖术语线索——只取用户本人打的字,出新候选词、已有术语的口语变体、术语热度

## 用法

| 输入 | 做什么 |
|---|---|
| `/knowledge-refine` | 五项全体检,出清单 |
| `/knowledge-refine 词表 主条目 需求口径 腐烂 会话`(任选几项) | 只体检这几项 |
| `/knowledge-refine 执行 [清单路径]` | 执行最近一份(或指定)清单里**已勾选**的项 |
| 体检后用户在对话里说「全做」「做 A1 B2 D3」「A 类都做」 | 等同于勾选这些项,然后执行 |

## 体检

### 0. 准备

1. `cgraphx docs concepts --json` 能跑(报没装过 → 请用户先 `cgraphx install`,停)。`docs/knowledge/` 不存在或没有文档 → 告诉用户先用 `/knowledge-write` 或 `/init-knowledge` 建库,停。
2. 读上一份清单(`docs/knowledge/.refine/` 下日期最新的):记下**上次体检日期**和标了「不做」「已判断」的项——本次不重复提,除非理由变了(相关文档又改过)。
3. 跑盘点(秒级):
   ```bash
   node <skill目录>/scripts/kb-inventory.cjs . > <临时目录>/kb-inventory.md
   node <skill目录>/scripts/kb-inventory.cjs . --json > <临时目录>/kb-inventory.json   # 需要精确数据时
   ```
4. 知识文档 ≤ 15 篇:后面要读文档的步骤自己读;更多:按批派子 agent(每批 8 篇知识文档或 4 个需求目录,同时最多 4 个),主会话只收结论。

### A. 词表归一

看盘点的「类名式概念」「疑似近义 / 包含关系」「别名又是概念」三节,逐个判断:

- **类名式概念**(`WorkOrderCust`、`TaskType`):如果它和某个中文实体/术语指的是同一个东西(看「常同现」和文档内容)→ 提「改名」:中文规范名进各文档 `concepts`,类名移进那个实体/术语条目的 `aliases`。文档本身就是在讲这个类的实现(机制文档)时可以保留类名,但要同时引用中文名。
- **近义/拆分**(`回单质检` / `回单质检要求` / `回单质检判定记录`):是同一概念的几个侧面 → 提「合并」到上位概念;确实是不同的东西 → 写一条「已判断:不同概念,不合并」(下次不再提)。
- **包含关系**(`接单人` ⊂ `接单人匹配`):通常是「实体 vs 讲它的机制」,不合并;检查机制文档有没有同时引用实体名,没有就提「补引用」。
- 判断不了的,带上两边文档的一句话说明列进清单,标「待人判断」。

### B. 补主条目

候选来源:盘点的「缺主条目的概念」+ 会话线索(E)里的业务新词 + 读文档时发现的「文档依赖但知识库没解释的业务词」。

逐个判断建不建、建成哪种(按 `knowledge-write`「双层结构」):
- **实体**(有属性和生命周期)/ **术语**(黑话、分类/口径词、类型标签、阶段名,满足口径易错、一词多义、有口语变体、新人听不懂之一)→ 建;机制概念、动作概念、通用技术词 → 不建。
- 每个要建的写清:类型(实体/术语)、一句话定义草稿、证据(表.字段、类的文件路径、哪篇文档哪节)、aliases 草稿、要在哪些文档 `concepts` 里补上它。
- 证据不够写定义的,不提新建,提「待补证据」并说缺什么。

### C. 吸收需求文档口径

范围:`docs/features/*/` 下 `*-spec.md`、`*-收口档案.md`、`*-设计文档.md`,只看**上次体检之后改过**的(`git log -1 --format=%cs -- <文件>` 或修改时间;首次体检看全部)。

每个需求只读这些章节:附录、决策(设计决策表、已锁定的业务决策)、口径(口径表、业务口径)、待确认、不做/明确非目标/本轮不实现、术语与业务对象。提取三类:
1. **口径**:哪个词、怎么算(算/不算的例子)、出处(feature-id + 章节)→ 提「追加口径」到对应实体/术语条目的「命名与边界」;没有条目就并进 B 一起提新建。
2. **延期方案**(本轮不实现、留待后续):先查后来的需求有没有实现它(`grep` 后续 feature 的 spec)→ 没实现 → 提「新建 decision 文档」(标题「<主题>延期方案」,正文只写结论要点 + 链到原文);已实现 → 不提。
3. **新术语**:并进 B。

和条目现有写法冲突的口径,不要自己选边,列成「口径冲突」项,写清两边原文和出处。

### D. 查腐烂

看盘点的「腐烂」「可能过期」「draft 条目」:
- **related_code 不存在**:先找去向(`git log --follow --diff-filter=R --name-status -- <路径>`,或按文件名在仓库里找)→ 找到提「改路径」,找不到提「删除这条引用」。
- **related_documents / 正文链接断**:同上,找不到就删引用。
- **可能过期**(相关代码在条目 updated 之后有提交):看那几次提交的说明(`git log --oneline --since=<updated> -- <文件>`),只有和条目内容相关的才提「复核」项,写明哪次提交可能影响哪段;纯格式/无关改动不提。
- **draft 且有 Open Questions、超过 30 天没动**:提「补全或标 deprecated」。

### E. 会话线索

```bash
node <skill目录>/scripts/harvest-terms.cjs . > <临时目录>/harvest.md
# 兄弟项目共用一套业务词时,把它们从对照语料里排除,否则业务词会被当成通用词:
node <skill目录>/scripts/harvest-terms.cjs . --baseline-exclude=<目录名片段1>,<片段2>
```

- **新候选词**:只挑业务词(脚本已去掉常见通用词,剩下的「名称、创建、导出」这类仍要人工剔除),并进 B。
- **口语变体**:脚本按「同长只差一个字、文档里几乎不用」挑,会混进真不同的词(`市级管理员` ≈ `省级管理员`)。只有确认是同一个词的错别字/口语说法(`代办人` → 待办人、`派单模版` → 派单模板)才提「加 aliases」。
- **术语热度**:提问占比很高(≥5%)又是人人都懂的常用词 → 可提「设 `inject: false`」(只建条目、不自动注入),由人定。
- **隐私**:清单里只写词和次数,**不写会话原文**;会话内容不出本机。

### F. 写整理清单

按 [references/整理清单模板.md](references/整理清单模板.md) 写 `docs/knowledge/.refine/<YYYY-MM-DD>-整理清单.md`(同一天再跑加 `-2` 后缀):

- 每项一行复选框 + 编号(A1、B2…)+ 动作 + 涉及文件 + 证据/理由;按价值排序(口径冲突、缺主条目的高频词、腐烂在前)。
- 末项固定是「重建知识库索引」(默认勾上)。
- `.refine/` 以点开头,`cgraphx docs index` 不扫,不污染知识库。
- 回报用户:清单路径、各类各几项、最值得先做的 3 项;请用户在文件里勾选,或在对话里说要做哪些。**到此停下,不执行。**

## 执行

1. 读清单,只取勾了的项(`- [x]`)和用户在对话里点名的项;没勾的一律不做。
2. 先按 `knowledge-write` 的规则做(条目模板、术语条目写法、aliases 只放专指说法、不写行号);按项的类型:

| 动作 | 怎么做 |
|---|---|
| 改名 / 合并概念 | 改清单列出的每篇文档 `concepts`;旧名进规范条目的 `aliases`;改完 `cgraphx docs find --concept=<旧名>` 应为空 |
| 补引用 | 只在 `concepts` 末尾追加,**不改 `updated`**(见下方「updated 的含义」) |
| 新建实体/术语条目 | 按 `knowledge-write` 模板写,证据落到「代码入口」「相关表」「命名与边界」;顺带改清单里列的引用文档 |
| 追加口径 | 在条目「命名与边界」追加一段,写明「定于 <feature-id>」;不改原有口径(冲突项单独处理) |
| 口径冲突 | 按用户在清单里写的裁决改;用户没写裁决就跳过并标「待裁决」 |
| 新建 decision | `document_type: decision`,正文只写结论要点 + 原文链接 |
| 改路径 / 删引用 | 改 `related_code` / `related_documents` / 正文链接,**不改 `updated`** |
| 复核过期 | 读那几次提交的改动,只改条目里确实变了的说法,`updated` 改今天 |
| 合并文档 / 删除文档 | 按 `knowledge-write`「合并检查」:读全文 → 带日期标题追加进保留文档 → 合并 frontmatter → 删被合并的文件;删除前把引用它的文档改掉 |
| 加 aliases / 设 inject | 改条目头部,**不改 `updated`** |

**updated 的含义**:`updated` 表示「内容最后一次和代码核对的日期」,D 项「可能过期」就是拿它和相关代码的提交日期比。只改头部元数据(路径、引用、concepts、aliases、inject)不算核对内容,改了 `updated` 会把真过期的条目藏起来;只有新建、追加口径、复核、合并、改正文这类动了内容的才改成今天。

3. 每改完一篇就 `cgraphx docs validate <文件>`,不合法修到合法;一项失败不影响其他项。
4. 全部做完跑 `cgraphx docs index`(清单末项),再抽查 1–2 个改过的概念 `cgraphx docs find --concept=<名>`。
5. 回写清单:每项标结果(✅ 做了 / ❌ 失败+原因 / ⏭ 不做);没勾的标「⏭ 不做」,用户说了理由就记上——下次体检据此不再重复提。
6. 回报:做了几项、失败几项、改了哪些文件。不提交;提醒用户按项目提交规范提交(知识文档和清单一起)。

## 红线(绝对不能做)

1. ❌ **体检阶段改知识文档**——体检只写清单。
2. ❌ **执行没勾选的项**——用户没点名的不做,哪怕看起来顺手。
3. ❌ **清单里的项没有证据**——每项都要能指到文件、章节、表字段或提交。
4. ❌ **会话原文进清单或知识库**——只写词和计数;会话内容不发任何外部服务。
5. ❌ **跳过 validate**——每篇改完都要过 `cgraphx docs validate`。
6. ❌ **自己裁决口径冲突**——列出两边,由人定。
