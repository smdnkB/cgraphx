# write-workload — 需求工作量汇报(对账 / 结款)

把一个**已交付的需求**量化成一份经得起甲方/财务追问的工作量汇报,作为内部对账、结款依据。

## 这个 skill 的灵魂(先读这段)

用户说「汇报工作量」时,最自然的反应是直接开写一份工时表。**别这样**。这个 skill 的全部价值在于五条心法,它们是从实战里踩出来的,每一条都对应一个真实翻车点:

1. **维度先于内容** — 受众和口径不同,骨架完全不同(给业务方讲进度 / 给财务对账 / 给技术评审是三套东西)。直接写必返工。所以第一步永远是**问清口径再动笔**,哪怕只问两三个问题。
2. **对账必配佐证** — 结款场景最致命的反问是「就改了这几个文件,要 X 人天?」。**代码量小但工时不少是常态**,因为联调、契约核实、外部对接都不体现在代码行数。工时拆解骨架如果不配一层「影响范围佐证」,工时数字就站不住。
3. **隐性工时显性化** — 把代码里看不见的工作逐项列成工时项:需求待确认项的逐一核实、外部接口联调、跨服务契约逆向确认、配置映射纠正、返回键核对、多场景自测。**这是「工时比代码看着多」的合法性来源**,也是佐证层的主干。
4. **工时数字不编** — 结款是钱。**你(Claude)不能凭空给工时数字。** 要么用户给真实记录,要么用户明确授权「你来估」并给区间,你才能填且标注是估算。被发现编数字是对账场景的信任灾难。
5. **查代码核实交付物** — 需求文档 / plan 和实际代码经常有出入(方法名、URL、响应结构、映射表、查询方式都可能被改过)。不核实就按文档报,会虚报或错报,对账时穿帮。**汇报前必须回代码核实每一项交付物真实存在。**

把这五条内化后,下面的流程就是它们的展开。

## 何时触发

- 用户交付完一个需求,要向甲方 / 内部出工作量汇报、结款依据、工时统计。
- 关键词:工作量汇报 / 需求工作量 / 工时(汇报|统计) / 结款 / 对账 / 向甲方汇报 / 工作量评估 / 做了多少东西 / effort / workload / billing。
- 即使没明说「结款」,只要意图是**量化已交付工作并对外汇报**,就走本 skill。

> 不触发:纯进度同步(轻量,几句话即可)、未交付的纯技术方案评估(走 write-spec/plan)、代码质量评审(走 code-review)。

## 输入

一个需求,通常在 `docs/features/<feature-id>/` 下,含:需求文档 / spec / plan / 已落地代码。用户也可能只给一个需求编号或一句话描述,需要你先定位需求目录。

## 流程

### Step 0 · 摸清汇报口径(先问,不先写)

这是最关键的一步,跳过它后面全错。用 `AskUserQuestion` 一次性问清(2~3 个问题):

- **受众是谁?** — 内部对账/财务(要量化、可核验)/ 甲方项目经理(要进度+数字)/ 甲方技术负责人(要方案合理性)/ 内部领导。受众决定深度和口径。
- **代码处于什么阶段?** — 已联调自测通过 / 代码写完未联调 / 还没写只是预估。决定汇报是「已交付」还是「预估」。
- **结款按什么口径?** — 任务工时拆解(T&M,按人天)/ 交付物计价(按交付的文件接口)/ 功能点法。决定主维度骨架。

> 问问题的目的不是走流程,是让骨架选对。问完你心里要有数:这份报告主维度是什么、要不要加固层、工时数字从哪来。

### Step 1 · 读需求 + 查代码核实交付物

1. 读需求文档 / spec / plan,理清这个需求做了什么。
2. **用 grep / read 核实代码**:
   - 核实每一项交付物**真实存在**:接口、实现类、新建文件、MDA 常量、配置、外部对接。
   - **识别 plan / 需求文档与实际代码的出入**(方法名变没变?URL 对不对?响应结构是平铺还是嵌套?映射表准不准?批量查询方式?)。这些出入既是核实,也是隐性工时的来源(纠正它们花了时间)。
3. 核实跨服务契约:依赖的下游服务方法是否真按预期返回(返回键、分支逻辑)。

> 这一步的产出是一份「真实的交付物清单 + plan 与代码的 diff」。后面工时和佐证都基于它,不是基于需求文档的描述。

### Step 2 · 定维度与骨架

基于 Step 0 的口径选主维度骨架。**用 `AskUserQuestion` 带 preview 让用户对比骨架**(preview 里放每种骨架的报告结构 ASCII 图,用户一眼能选):

- **任务工时拆解 + 影响范围佐证**(结款/对账默认推荐):工时拆解为主,叠加跨服务/外部对接佐证层,人天作汇总。
- **交付物 + 影响范围**:以客观交付物(文件/接口/外部对接/测试)为主轴,影响范围作定价加权。适合交付物计价/验收结款。
- **功能点法**:EI/EO/EQ/EIF/ILF 估算 UFP → 复杂度加权 → 折算人天。适合大型正式验收,单接口偏重。

> 为什么用 preview:骨架的差别用文字讲不清,但用结构图对比用户一秒就能选。别省这一步。

### Step 3 · 定内容策略

两个决策(可并入 Step 2 的提问):

- **工时口径**:按真实报(代码看着少但实际多,差额靠佐证解释)/ 按预估(还没做,给区间)。
- **要不要加固层**:对账场景**默认要加**影响范围佐证层,这是对冲「几个文件要这么多天」的唯一手段。

### Step 4 · 补工时

参见下方「工时补全规则」。**数字不编,每项配理由 + 对应交付物。**

### Step 5 · 出文档

按「文档结构:必含要素 + 按需组装」组织章节(不套固定模板),保存到需求目录(见「hx 项目约定」的命名规则)。

## 工时补全规则

- **每项工时落在 0.5~2 天**(用户给的范围默认值,可按项目调整),超出要拆分或说明。
- **每项必须配三件套**:工时数字 + 一句话理由(为什么是这个天数)+ 对应交付物(可核验,指向具体文件/接口/外部对接)。三件套缺一不可,这是对账时逐项核对的依据。
- **数字来源优先级**:
  1. 用户给真实人天记录 → 直接填。
  2. 用户授权「你来估」+ 给区间 → 你按代码复杂度和隐性成本估,每项标注理由,**合计处可注明「估算」**。
  3. **都没有 → 不填数字,留 `[__]` 占位并明确告诉用户「这是核心数字,我不编,你填」。** 绝不凭空写一个看似合理的数。
- **隐性工时必须显性化成独立工时项**:需求待确认项核实、外部接口对接联调、跨服务契约逆向确认、配置/映射纠正、返回键核对、多场景自测 —— 这些代码行数小但耗时大,是工时主要构成,**必须单列**,不能藏在「开发」一项里。
- **总量自检**:合计 ÷ 交付物数量 是否合理?隐性工时占比是否说得通?如果总数看起来「虚」,要么补佐证,要么调数字,别硬交。

## 文档结构:必含要素 + 按需组装(不要套固定章节)

不同需求的章节不一样——单服务小改动和跨服务外部对接的汇报,章节数、标题、侧重都不同。**别强行套固定模板。** 但结款汇报有几个必含的逻辑要素,缺了就不合格;其余按需求伸缩。

### 必含要素(逻辑闭环,缺一不可)
1. **工时拆解**(主维度)—— 结款的核心数字。用工时三件套(任务项 / 工时 / 理由 / 对应交付物)。
2. **工时合理性佐证** —— 对冲「几个文件要这么多天」。形式自由:可独立成节,也可融进工时表「理由」列(每项配了为什么,本身就是佐证)。跨服务 / 外部对接 / 隐性工时多时,建议独立成节把隐性工时摊开。
3. **可核验交付物清单** —— 文件 / 接口 / 外部对接 / 测试,让每条工时能对照到实物。
4. **工时数字来源声明** —— 心法 #4。一句话注明:真实记录 还是 估算。

### 按需要素(看情况取舍)
- **需求背景**:给非技术读者(财务)或需求复杂时写;简单需求 / 技术读者一句带过或省略。
- **影响范围**(跨服务 / 外部对接):跨度大单独成节;单服务改动并入工时理由即可。
- **遗留 / 风险**:有就写,没有不硬凑。

### 组织原则
- 章节数量、标题、合并 / 拆分**按需求定,没有固定形态**。唯一不能省的是上面四个必含要素的**逻辑**(形式可变)。
- 简单需求(单服务、小改动):工时表(理由列即佐证)+ 交付物清单,两节足矣。
- 复杂需求(跨服务 / 外部对接):工时拆解 + 独立佐证节 + 交付物 + 遗留,四到五节。

> 复杂需求四到五节的范例见下方「真实样例」(req74442)。那是「一种」组织方式,不是「唯一」模板。

## 项目约定

- **需求目录**:`docs/features/<feature-id>/`。先定位用户给的 feature 目录。
- **文件命名**:`<前缀>-需求工作量.md`。**前缀沿用该需求目录里已有文件的命名前缀**(如 `CRM-req74442-电渠批量违约金试算接口`),保持族内一致。保存到该需求目录根下(不进 plan/ 子目录)。
- **查代码**:用 grep / Read;跨服务契约定要分别核实每个服务。
- **元信息表日期**:用当天日期(会话上下文里的 currentDate)。
- **术语对齐**:用 CLAUDE.md 和 docs/knowledge/ 里的项目术语(prodInst / offer / bizCode / atom / @Center 等),别自造。

## 收尾自检(交文档前)

- [ ] 主维度和受众口径匹配(Step 0 确认过)
- [ ] 每项工时有三件套,数字有来源(没编)
- [ ] 工时合理性佐证在(独立成节 或 融进工时表理由列),能回答「几个文件要这么多天」
- [ ] 交付物清单每一项都核实过真实存在
- [ ] 文件名前缀和需求目录族内一致,存对位置
- [ ] 遗留/风险如实写(测试地址待切生产、入参口径出入等),不藏
