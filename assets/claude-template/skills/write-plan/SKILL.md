# 编写 Plan (Write Plan)

## 定位

- **Plan = spec 的执行契约**:把"做什么"拆成 coding agent 可执行且应忠实执行的任务清单(顺序、依赖、范围、验收、风险)。过审后是 implementation 的唯一依据,不是建议稿。
- **手段按业务可观察性分档(默认自主,越信封才回跳)**:判别一句——**手段有没有 spec 信封外的业务可观察后果?**
  - **无 → plan 自主**(内部结构、复用哪个既有模块、规范内命名、同步内的实现细节):结合 spec 容忍度 + 既有代码模式定(优先复用,YAGNI),记入 index「实现手段决策」节(选项 + 推荐 + 理由),透明可复审,plan 拍板即锁定。
  - **有 → 回跳 write-spec**(选异步 ⇒ 用户要看到"处理中"、软删 ⇒ 审计口径、选三方 ⇒ 成本/能力):这是伪装成技术决策的业务决策,回跳让业务拍板补契约,再定手段;拍板前推荐不是锁定。
- **两种读者两种写法**:index 开头的「设计预览」写给**人**——一段话说清改动落在哪,加一张重点决策表,人看完决定放不放行;其余部分写给子 agent(见「消费模型与防漂移」)。
- **优先级**:spec 显式契约 > plan > docs/guides/ 规范;规范与 spec 冲突时 spec 赢,例外写进风险/备注。
- **内容边界**:plan 写具体文件/模块/接口/表,不写实际代码改动、不写 PRD/spec、不排测试任务(测试是代码完成后的独立流程)。澄清总结 = 输入;spec = 唯一契约(plan 不得重新定义);implementation 只有局部工程适配空间。

<HARD-GATE>
缺少影响计划正确性的关键信息 → 先补问 3-5 个;不阻塞成文的标【待确认】。
不编造代码结构、接口、表结构、任务链路——没查到的一律【待确认】。
spec 中"不可留到实现期的决策"或影响任务拆分的【待确认】,必须先解决或明确阻塞,不许留给 implementer 自行决定。
</HARD-GATE>

## 输入与上下文

- **读**:spec(重点:Plan 编写约束、不可留到实现期的决策、待确认项、**业务容忍度**——手段决策的硬依据)、既有代码(结构/模块/接口/模型/任务/队列/页面/测试/构建)、已有 PRD/影响分析/历史 plan/团队约定。缺关键代码上下文 → 先读再写,不凭空规划不存在的模块。
- **工具**:`knowledge-recall`(知识库:历史决策、业务概念)、`db-query`(查库、查 DDL)、grep 和 Read(调用关系、符号定位);涉及的已有代码直接读代码确认。

## 工作流程

0. **命名沿用 spec**:feature-id、文件前缀沿用 spec 所在的需求目录;没有 spec 时按 write-spec 第 0 步和「产物位置与命名」定。
1. **读输入,查缺口**:对照 spec 的"不可留到实现期的决策"和"Plan 编写约束";关键缺口 → 补问或标【待确认】(影响拆分的不得伪装成已确认)。
2. **识别范围 + 拆任务**(见「拆分规则」);明确不涉及的部分,防 implementer 扩范围。
3. **读已有代码**:涉及的已有模块、调用方直接读代码确认,不凭印象写。
4. **定手段 + 读规范**:手段按业务可观察性分档——无业务可观察后果的 plan 自主定(记入 index),越信封的回跳 write-spec 补契约再定;读 docs/guides/ 适用规范并落进契约(见「适用规范」——**规范缺失是硬门,中断提示 init-project-guides**)。
5. **生成文件**:index 加每个任务一个文件,见「任务文件」。
6. **Plan Review**:默认派 `plan-document-reviewer` 子 agent(同目录 `plan-document-reviewer-prompt.md`),独立复核完整性/Spec 对齐/可执行性/跨任务一致性/执行契约清晰度/**规范遵循**;校准:只标真正阻塞 implementer 的问题。返回 issues → 修 → 必要时复审。跳过条件:用户明确说不用、plan 极小、时间紧;跳过时在 index 里写一句理由。

## 拆分规则

- 先按任务类型拆:数据库、后端、前端、配置、文档等,一类一个任务。
- 一个任务预估改动超过 15 个文件,算一个子 agent 做不完,再按并行度往下拆:拆成改的文件不重叠、只靠 index 契约衔接的几块,拆到每块不超过 15 个文件为止,不拆到底。超过 15 个文件但改动强耦合、找不到并行边界的,不硬拆,在任务文件里写明原因。
- **测试不进 plan**:单元测试 / 接口测试是代码完成后的独立流程(`write-unit-test-spec` → `write-unit-test-code`、`write-api` → `run-api-test`,各自从 spec 派生),plan 不排测试任务、不写必测路径 / 测试命令、implementer 实现期不写新测试。plan 对测试的唯一要求是完成定义:任务提交后既有测试不被弄红(改动弄红的既有测试须同步修正)。
- 高风险任务写保护条件和回退思路。
- **提交点**:每个任务写清分几笔提交,每笔的提交说明和包含的文件;一个任务可以有好几笔,比如一个 skill 一笔。大需求由 subagent-implement 的主会话按提交点提交,中间的提交不保证能构建。
- **执行顺序(写进 index)**:分几步,每步哪些任务;同一步里能同时跑的要标出来。能同时跑的条件:改的文件不重叠,依赖的契约已在 index 定死;拿不准就分成两步。
- 不重新打开 spec 已锁定的契约;不把简单需求拆碎。
- **执行方式**:小需求一个会话跑 `/implementation`;大需求(预估变更文件 ≥10,且跨 ≥3 个相互独立的模块;拿不准按小需求)用 `/subagent-implement` 在一个会话里跑完,index 末尾给一句启动语:`/subagent-implement docs/features/<feature-id>/plan/<前缀>-index.md`。

## 消费模型与防漂移

**plan 的读者是子 agent**(可能是第三方模型):每个只读 index 和自己的任务文件,看不到你的上下文、不知道你脑中的默认,遇到模糊处会默默自行补全。写法纪律由此反推。

- **共享的只写在 index**:跨任务共享的契约(签名、接口形态、命名)只写在 index,带编号(C-1、C-2……);任务文件按编号引用,写「按 C-1」,不抄原文。任务文件加上 index,就是执行者需要的全部;「见 T-3 的定义」这种指向别的任务文件的写法不行。
- **双向追溯**:任务标注对应 spec 条款编号(有疑义读 spec 原文,不猜转述)。权威链:任务 ← plan ← spec,冲突以上层为准并按 PLAN_CONFLICT 上报。
- **契约两端同文**:T-5 消费 T-2 产出时,两边都引用 index 里同一个编号的契约,不各写一份。
- **自由必须枚举**:「必须严格执行」= 契约边界,「允许局部适配」= 裁量边界,没列进允许的一律固定。钉死契约(签名、行为、spec 规则、验证命令),放开机制(内部拆分、局部命名、实现细节)。

## 适用规范(强制读 + 结晶 + 标注)

docs/guides/ 存在时(init-project-guides 产出),写 plan 前按下表读规范、落契约、打标注:

| 任务类型 | 写前必读 | 「强制引用」标注 |
|---|---|---|
| schema(建表/改表/迁移/回填) | `data-standards.md` | `data-standards.md` |
| 接口(API) | `interface-standards.md` | `interface-standards.md` |
| 动代码(所有任务) | `coding-standards.md` 契约部分(命名/目录/分层) | `coding-standards.md` |
| 提交 | `git-standards.md` 提交消息规范 + 提交前检查点 | 结晶进 index「提交规范」节(plan 级,一次) |

- **结晶进契约**:契约级规范落进具体契约——任务直接写合规的表名/字段/签名,"按规范建表"式转交是失败(见红线)。index.md「适用规范」节列文件 + 章节标题(不写行号)。
- **标注是执行期规范送达的唯一载体**:有 plan 时 implementation 只读「强制引用」标注的规范、不再自行识别——漏标 = 规范在执行期丢失。
- **git-standards.md 与其他三份不同**:它不是每任务开工前读的规范(提交规范不随任务变),而是 plan 级**一次结晶进 index「提交规范」节**——提交消息格式 + 提交前检查点原文摘录。实施期提交时直接按 index 已结晶的规范写 message、过检查点,precommit 门禁仅作兜底(不再现场学习规范,消除多次提交的重复读取成本)。
- **规范缺失 = 中断**:docs/guides/ 不存在或所需文件缺失 → 停止写 plan,列缺失文件,提示 init-project-guides 补齐;用户明确说不需要才可继续并记入风险/备注。

## 设计预览(index 开头,写给人)

人读完这一节就能决定放不放行:一段话说清改动落在哪,再加一张重点决策表,写改错了代价最大的几条决策,以及每条为什么难回头。不画架构图、时序图、类图。按此示例写:

````markdown
## 设计预览

原来侧栏的「数据库」入口是灰的,点不了。这次新增 schema 模块:三个新文件分别负责读文件、拼 HTML、出页面,server 加一组 `/schema` 路由;全程只读本地文件,不碰 SQLite。

**需要你重点看的**(改错了代价最大,其余可略读)

| # | 决策 | 为什么难回头 |
|---|---|---|
| 1 | schema 页面函数签名**不带 db 参数**,模块永不读 `cgraphx.db` | 一旦有页面依赖 db,纯文件派生的边界就破了,后续都会往里加 |
| 2 | 工程名或表名含 `..`、`/`、`\` 时**在路由层直接 404**,不进页面层 | 路径安全边界;放到下层校验,任何新页面都可能漏 |
| 3 | URL 形态 `/schema/<工程>/<表>`,`insights` 为保留词 | 用户会收藏链接,改形态即失效 |
````

- 第一句先讲原来的情况,再说这次改了什么。
- 只放难回头的决策,不超过 3 条:持久化的数据结构和表、对外接口与 URL、模块边界与依赖方向、安全边界。内部拆分、命名、可逆的手段不进此表,放「实现手段决策」。
- 表里的文件名、函数名和下面任务原文一致;plan 改了,这张表一起改。

## index.md 必备内容

**设计预览**(开头,见上节) · 来源 spec 摘要 · 目标与范围 · 明确不包含 · 任务清单(任务和文件一一对应,每个任务标对应 spec 条款和涉及范围;主会话靠涉及范围核对子 agent 的回报) · 执行顺序(分几步,标出能同时跑的) · 必须严格执行的契约(带编号) · 实现手段决策(自主项:选项、推荐、理由;回跳项:业务拍板结论) · 适用规范(文件与章节标题) · 提交规范(从 `git-standards.md` 结晶的提交消息格式和提交前检查点) · 统一验证(全部任务做完后跑的命令和要看的结果) · 允许局部适配的范围 · Plan 冲突上报规则 · 关键风险与防跑偏约束 · 待确认项 · 启动语(大需求一句 `/subagent-implement`)。

头部范例:

```markdown
# 实现计划: <需求名称>

> 产物: plan
> 依据: spec@3f9a1c2

## 设计预览
```

依据取 `cgraphx features show <feature-id>` 显示的 spec 指纹前 7 位;各任务文件写同样两行。

## 任务文件

一个任务一个文件:`plan/<文件前缀>-<两位序号>-<任务名>.md`,序号和任务编号一致,T-1 对应 01。

| 任务类型 | 适用 | 写什么 |
|---|---|---|
| 数据库 | 新表/字段/迁移/回填 | 迁移目标与**执行顺序**(需求 sql/ 增量文件的序号依此定)、兼容与回滚、数据校验;建表/改表任务按项目 `docs/guides/data-standards.md`「Schema 变更约定」组织(增量文件 + 全量写透同步);不写不可确认的完整 DDL |
| 后端 | 业务逻辑/API/权限/任务/队列 | 规则落点、输入输出与错误处理、幂等/重试/并发 |
| 前端 | 页面/表单/交互/可见性 | 用户流程、展示字段与校验、API 对接点、loading/empty/error 状态 |
| 配置、文档 | 配置项、说明文档、模板 | 改哪些文件、改成什么;文档类写清要和哪些事实保持一致 |

## 任务写法

```markdown
### T-<编号>: <任务名称>

- 目标: ...
- 对应 spec 条款: ...(执行者据此读 spec 原文,不凭任务转述猜)
- 强制引用: ...(开工前必读的 docs/guides 文件,按映射机械标注:数据库任务标 data-standards.md,接口任务标 interface-standards.md,动代码任务标 coding-standards.md,都不涉及写「无」)
- 涉及范围: ...(改哪些文件;和同一步同时跑的任务不重叠)
- 必须严格执行:
  - ...(用到共享契约时写「按 C-1」)
- 允许局部适配:
  - ...
- 具体要求:
  - ...
- 完成条件:
  - ...
- 提交点:
  1. <提交说明>:<这一笔包含的文件>
- 风险/注意事项:
  - ...
```

任务编号 T-1、T-2 依次排,文件序号和编号一致;依赖写进 index 的执行顺序。任务足够具体让 agent 能执行,但不替 agent 写代码。

## No Placeholders

「具体要求」「完成条件」和 index 的「统一验证」必须写到执行者可直接执行。以下是 **plan 失败**:TBD/TODO/"implement later" · "add appropriate error handling"/"handle edge cases" · "similar to Task N" · 只说"做什么"不给可执行步骤/命令/验证条件 · 引用未在任何任务定义的符号 · "implementer 自行决定方案"(关键路线/口径/契约/权限不得留到实现期)。

例外:plan 期确实无法预知的(如第三方 API 实际返回结构),标【待确认】+ "implementer 跑 X 命令后锁定"——诚实标注,不是 placeholder。

## 产物位置与命名

- 路径:`docs/features/<feature-id>/plan/<文件前缀>-index.md`,任务文件见「任务文件」;文件前缀 = feature-id 去掉开头的日期。需求目录不存在时按 write-spec「产物位置与命名」建。
- 无可写项目上下文时,在回复里直接输出同等结构的正文。

## 收尾

产物落盘后跑 `cgraphx features sync`。然后请人确认设计:回复里给出设计预览的那段话和重点决策表,问「**设计预览是否符合你的预期?确认后再开始实现。**」,问完加一句:设计预览哪里没看懂,可以说「画个图讲讲」。人不确认不进实现;人提出修改就改 plan(预览一起改)后再问。确认后:小需求提示 `/implementation`;大需求给出 index 末尾那一句 `/subagent-implement` 启动语,说明在本会话直接跑或新开会话跑都行。不自动开始实现。找需求目录:`cgraphx features list --mine`。

## 红线(绝对不能做)

1. ❌ **不编造**代码结构/接口/表/命令——没查到的一律【待确认】。
2. ❌ **不把影响契约的决策留给实现期临场决定**(业务规则/口径/接口/权限 + 关键技术路线)。
3. ❌ **规范不转交**——"按规范建表"是失败,契约级规范必须落成具体契约;plan 契约不得违反规范条目(违反须记例外);规范缺失 → 中断,提示 init-project-guides。
4. ❌ **不把待确认伪装成已确定任务**,不把猜测变成任务。
5. ❌ **不重新打开 spec 已锁定的契约**;手段越信封 → 回跳 spec,不在 plan 夹带。
6. ❌ **不写实际代码改动**进 plan。
7. ❌ **不自动开始实现**——收尾停下,归用户。
