# 编写 Plan (Write Plan)

## 定位

- **Plan = spec 的执行契约**:把"做什么"拆成 coding agent 可执行且应忠实执行的任务清单(顺序、依赖、范围、验收、风险)。过审后是 implementation 的唯一依据,不是建议稿。
- **实现手段决策在本阶段做**:同步/异步、缓存、定时任务、选型 = spec 容忍度 + 现有代码 → **选项 + 权衡 + 推荐,用户拍板才锁定**。推荐 ≠ 确认。依据是 spec 的业务可观察要求和既有代码模式(优先复用,YAGNI),不是偏好。
- **回跳规则**:手段产生 spec 信封之外的业务可观察后果(如选异步 ⇒ 用户要看到"处理中",而 spec 没写)→ 先回 write-spec 补契约,再定手段。
- **优先级**:spec 显式契约 > plan > docs/guides/ 规范;规范与 spec 冲突时 spec 赢,例外写进风险/备注。

<HARD-GATE>
缺少影响计划正确性的关键信息 → 先补问 3-5 个;不阻塞成文的标【待确认】。
不编造代码结构、接口、表结构、任务链路、测试命令——没查到的一律【待确认】。
spec 中"不可留到实现期的决策"或影响任务拆分的【待确认】,必须先解决或明确阻塞,不许留给 implementer 自行决定。
</HARD-GATE>

## 边界

- 澄清总结 = 输入;spec = 唯一契约(plan 不得重新定义);implementation 按 plan 执行,只有局部工程适配空间。
- plan 可写具体文件、模块、接口、表、测试命令;**不写实际代码改动,不写 PRD/spec 内容**。

## 输入与上下文

- **读**:spec(重点:Plan 编写约束、不可留到实现期的决策、待确认项、**业务容忍度**——手段决策的硬依据)、既有代码(结构/模块/接口/模型/任务/队列/页面/测试/构建)、已有 PRD/影响分析/历史 plan/团队约定。
- **工具**:`knowledge-recall`(知识库:历史决策/业务概念)、`db-query`(查库/查 DDL)、grep/Read(调用关系/符号定位)。
- 缺关键代码上下文 → 先读再写,不凭空规划不存在的模块。

## 工作流程

0. **命名先行**(写内容前必须落定):① 业务 ID——有无工单号/需求单号?允许留空但**必须显式确认**;② 标题语言——中/英/混合,用户选定,**禁止擅自中文转英文 slug**;③ 负责人——有 spec 继承 spec 头部的负责人,无 spec 则默认 `git config user.name` 并向用户确认,写入 index.md 头部 `> 负责人:`。用户已给 feature-id → 直接复用。
1. **读输入,查缺口**:对照 spec 的"不可留到实现期的决策"和"Plan 编写约束";关键缺口 → 补问或标【待确认】(影响拆分的不得伪装成已确认)。
2. **识别范围 + 拆任务**(见「拆分规则」);明确不涉及的部分,防 implementer 扩范围。
3. **定手段 + 读规范**:手段议题给选项 + 推荐,用户拍板;读 docs/guides/ 适用规范并落进契约(见「消费模型与防漂移 · 适用规范」——**规范缺失是硬门,中断提示 init-project-guides**)。
4. **生成文件**:index.md 必须;01-04 按需,不建空文件(不涉及 → index 中标记)。
5. **Self-Review**(发现即 inline 修):
   - Spec 覆盖度:spec 每条要求都能对应到任务,遗漏补任务
   - Placeholder 扫描:TBD/"add appropriate error handling"/"similar to Task N" 等全修掉(见「No Placeholders」)
   - 跨任务一致性:签名/命名/接口跨任务引用逐字一致
   - 每个任务有可验证完成条件(具体命令/步骤,不是"应该工作")
   - Plan 忠实度:spec 契约完整落到任务,没把关键方案留给 implementer
6. **Plan Review**:默认派 `plan-document-reviewer` 子 agent(同目录 `plan-document-reviewer-prompt.md`),审完整性/Spec 对齐/可执行性/跨任务一致性;校准:只标真正阻塞 implementer 的问题。返回 issues → 修 → 必要时复审。跳过条件:用户明确说不用 / plan 极小 / 时间紧(在 Self-Review 里写跳过理由)。

## 拆分规则

- 按依赖和风险拆,不按模板拆:数据/契约 → 后端 → 前端 → 测试(依实际依赖调整)。
- **默认合并**(减少审查次数,写明理由):测试并入实现任务(同 implementer 写码 + 测试);同文件多章节改写归单 implementer;schema 改动 + 对应 migration 测试合一。拆开仅限:测试有独立复杂度(e2e/大集成/多 fixture)、任务过大撑爆上下文、强耦合需实时反馈。
- 能独立验证的尽量独立成任务;高风险任务写保护条件和回退思路。
- 可并行任务显式成批 + 写明文件集/公共契约/测试状态互不冲突;不确定 → 串行。
- 不重新开放 spec 已锁定的契约;不把简单需求拆碎。

## 消费模型与防漂移

**plan 的读者是被逐任务派出的隔离 subagent**:看不到全篇、不知道你脑中的默认、遇模糊处默默自行补全。写法纪律由此反推。

- **自包含 + 引用不指涉**:每个任务携带(或引用)执行者所需的一切。"见 T-3 的定义"是指涉——implementer 手里可能没有 T-3;写出契约原文是引用。依赖只管执行顺序;跨任务共享的契约(签名、接口形态、命名)在每个引用任务里各写一份同样的原文。
- **双向追溯**:任务标注对应 spec 条款编号(有疑义读 spec 原文,不猜转述);index 任务清单让 spec 每条要求找到承载任务。权威链:任务 ← plan ← spec,冲突以上层为准并按 PLAN_CONFLICT 上报。
- **契约两端同文**:T-5 消费 T-2 产出时,接口形态(签名/字段名/错误语义)在 T-2 输出和 T-5 输入里逐字一致。
- **自由必须枚举**:「必须严格执行」= 契约边界,「允许局部适配」= 裁量边界,没列进允许的一律固定。钉死契约(签名、行为、spec 规则、验证命令),放开机制(内部拆分、局部命名、实现细节)。
- **适用规范(强制读)**:docs/guides/ 存在时(init-project-guides 产出),写 plan 前读本需求相关规范——schema 任务读 `ddl.md` + `model-standards.md`,接口任务读 `interface-standards.md`,所有任务参考 `coding-standards.md` 契约部分(命名/目录/分层)。**契约级规范落进具体契约**(任务直接写合规的表名/字段/签名,"按规范建表"式转交是失败);index.md「适用规范」节列文件 + 章节标题(不写行号),任务「必须严格执行」引用具体条目;风格级规范由实现阶段读取。**规范缺失 = 中断**:docs/guides/ 不存在或所需文件缺失 → 停止写 plan,列缺失文件,提示 init-project-guides 补齐;用户明确说不需要才可继续并记入风险/备注。

## index.md 必备内容

feature-id/状态/负责人/日期/来源 spec 摘要 · 目标与范围 · 明确不包含 · 计划文件清单(哪些存在/不涉及) · 总任务清单(每个任务标对应 spec 条款) · 全局依赖图(Mermaid 或文本;没有依赖就直说,不强行造依赖) · 推荐执行顺序 · 可并行批次(文件/模块/验证状态不重叠依据) · 必须严格执行的契约 · 已锁定的实现手段决策(选项、权衡、推荐、拍板结论) · 适用规范(文件 + 章节标题) · 允许局部工程适配的范围 · Plan 冲突上报规则 · 关键风险与防跑偏约束 · 待确认项。

## 子计划文件(按需,不建空文件)

| 文件 | 适用 | 写什么 |
|---|---|---|
| `-01-schema.md` | 新表/字段/迁移/回填 | 迁移目标与顺序、兼容与回滚、数据校验;不写不可确认的完整 DDL |
| `-02-backend.md` | 业务逻辑/API/权限/任务/队列 | 规则落点、输入输出与错误处理、幂等/重试/并发、要更新的测试 |
| `-03-frontend.md` | 页面/表单/交互/可见性 | 用户流程、展示字段与校验、API 对接点、loading/empty/error 状态 |
| `-04-test.md` | 独立测试任务(默认并入实现后所剩) | 必测业务路径、边界异常、测试命令、手工验收、不测的与原因 |

## 任务写法

```markdown
### T-<编号>: <任务名称>

- 目标: ...
- 对应 spec 条款: ...(implementer 据此读 spec 原文,不凭任务转述猜)
- 依赖: ...
- 涉及范围: ...
- 必须严格执行:
  - ...
- 允许局部适配:
  - ...
- 具体要求:
  - ...
- 完成条件:
  - ...
- 验证方式:
  - ...
- 风险/注意事项:
  - ...
```

编号可按文件域(`S-1`/`B-1`/`F-1`/`T-1`);跨文件依赖必须在 index 体现。任务足够具体让 agent 能执行,但不替 agent 写代码。

## No Placeholders

"具体要求/完成条件/验证方式"必须写到 implementer 可直接执行。以下是 **plan 失败**:TBD/TODO/"implement later" · "add appropriate error handling"/"handle edge cases" · "write tests for the above"(无具体 case)· "similar to Task N" · 只说"做什么"不给可执行步骤/命令/验证条件 · 引用未在任何任务定义的符号 · "implementer 自行决定方案"(关键路线/口径/契约/权限不得留到实现期)。

例外:plan 期确实无法预知的(如第三方 API 实际返回结构),标【待确认】+ "implementer 跑 X 命令后锁定"——诚实标注,不是 placeholder。

## 质量检查(输出前)

- index 能看懂全局;按需文件都有真任务,无空文件。
- 每个任务有完成条件 + 验证方式;文件间依赖清楚。
- 双向追溯齐全;跨任务契约两端同文;契约级规范已落进具体契约。
- 手段决策已拍板;超信封后果已回跳 spec。
- 没重新定义 spec、没混入代码、没要求实现非目标、没把关键方案留给实现期。
- 待确认项没被伪装成已确定任务。

## 产物位置与命名

- 路径:`docs/features/<feature-id>/plan/<文件前缀>-index.md`(+ 按需 `-01-schema` / `-02-backend` / `-03-frontend` / `-04-test`)。无可写项目上下文 → 回复中直接输出同等结构正文。
- **feature-id**:`YYYY-MM-DD-[业务ID-]<标题>`。业务ID 可选(字母数字 + 连字符);标题允许中/英/混合,**不得**中文转英文 slug;重名追加短后缀;同目录已有 PRD/spec 优先复用同一 feature-id。
- **文件前缀**:有业务ID = `<业务ID>-<标题>`,无 = `<标题>`。
- 敏感字符(`/ \ : * ? " < > |`)拒绝,要求用户重命名,不自动替换。
- 与旧目录共存:始终新命名,不探测旧文件。

## 收尾

产物落盘后自动跑 `cgraphx features sync`(更新本人需求索引,本地幂等)。全部通过后推荐执行模式一句话:**1-3 文件/单模块 → `/implementation`;跨域多任务 → `/subagent-implement`。** 不自动开始实现,停下等用户。找需求目录:`cgraphx features list --mine`。

## 红线(绝对不能做)

1. ❌ **不编造**代码结构/接口/表/命令——没查到的一律【待确认】。
2. ❌ **不把影响契约的决策留给实现期临场决定**(业务规则/口径/接口/权限 + 关键技术路线)。
3. ❌ **规范不转交**——"按规范建表"是失败,契约级规范必须落成具体契约;规范缺失 → 中断,提示 init-project-guides。
4. ❌ **不把待确认伪装成已确定任务**,不把猜测变成任务。
5. ❌ **不重新打开 spec 已锁定的契约**;手段越信封 → 回跳 spec,不在 plan 夹带。
6. ❌ **不写实际代码改动**进 plan。
7. ❌ **不擅自中文转英文 slug**——命名归用户。
8. ❌ **不自动开始实现**——收尾停下,归用户。
