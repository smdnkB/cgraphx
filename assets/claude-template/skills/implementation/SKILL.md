# Implementation

## 定位

根据当前上下文、已确认的 plan/spec 或用户明确任务,实际修改代码并完成验证。

这个 skill 是执行阶段。目标是把计划落成可工作的代码,同时保持范围、质量和验证清楚。若存在已确认 plan,实现阶段应忠实执行 plan,不重新设计业务规则、数据口径、接口契约、权限或核心方案。

## 基本原则

- 先读必要上下文,再改代码。
- 优先遵守已有 plan/spec;如果它们与代码现实冲突,说明冲突并上报,不要自行改写已锁定方案。
- 优先沿用项目现有架构、命名、风格、工具和测试方式。
- 控制范围,不要顺手重构无关代码。
- 不编造业务规则。规则不清且会影响实现时先问;不阻塞的小细节可做保守假设并说明。
- 保护用户已有改动,不要回滚自己没做的变化。
- 实现后运行合理验证;无法验证时说明原因和剩余风险。

## 默认工作方式

按任务需要灵活执行,不要机械套流程:

1. **理解输入**
    - 读取用户请求、相关 plan/spec/PRD、任务清单或错误信息。
    - 找到要实现的具体范围、非目标和验收口径。

2. **读取代码上下文**
    - 查看相关文件、调用链、测试、配置和项目约定。
    - 读 plan 引用的适用规范(`docs/guides/` 下:ddl / model / interface / coding);无 plan 时自行识别——动 schema 必读 ddl.md,新增接口读 interface-standards.md。风格级规范(错误处理/日志/注释)是写法约束;契约与规范冲突时按 spec > plan > 规范 服从上层,实质冲突上报。
    - 只读取足以安全实现的上下文。

3. **实现变更**
    - 小步修改,保持代码风格一致。
    - 复用已有工具、模型、组件、服务和测试模式。
    - 需要新增抽象时,确保它解决真实重复或复杂度。

4. **验证**
    - 运行最相关的测试、类型检查、lint、构建或手工检查。
    - 前端或可视化变更按项目需要做浏览器/截图验证。
    - 失败时判断是实现问题、环境问题还是既有问题,并继续修正可控问题。

5. **汇报**
    - 简要说明改了什么、验证了什么、还有什么风险或未完成项。

## 处理 plan/spec

如果存在 `docs/features/<feature-id>/plan/` 或类似计划目录:

- 优先读取 `index.md`。
- 按需要读取 `01-schema.md`、`02-backend.md`、`03-frontend.md`、`04-test.md`。
- 先批判性评审计划:检查计划是否和当前代码结构一致、任务依赖是否合理、是否缺少关键上下文、是否包含未确认业务规则、是否存在高风险或破坏性操作、验证方式是否可执行。
- 如果发现关键问题或 plan 与代码现实严重冲突,先向用户说明并请求确认,不要自行换方案。
- 如果只是代码现实导致的小调整,且不改变业务规则、数据模型、接口契约、权限、安全、迁移策略或验收口径,说明调整原因后继续。
- 按依赖顺序执行,但不要盲目执行错误计划。
- 完成后可在回复中说明完成了哪些任务编号。

如果没有 plan,但用户任务明确,直接根据当前上下文实现。不要强迫用户先补文档。

## 动态编码计划

默认从 `docs/features/<feature-id>/plan/` 读取编码计划。

如果 plan 目录存在:

- 先读 `index.md`。
- 按需读 `01-schema.md`、`02-backend.md`、`03-frontend.md`、`04-test.md`。
- 以 plan 中的任务、依赖图、执行顺序和约束为主。
- 再结合真实代码上下文,细化当前编码顺序。

动态编码计划用于决定当前实现顺序,例如:

- schema/migration -> VO/DTO/type -> mapper/repository -> service/domain -> controller/API/job -> frontend/client -> test
- 或根据项目实际依赖调整

不要重写 plan 文档。不要脱离 plan 扩大范围。如果发现 plan 与代码现实冲突,区分:

- `PLAN_ADAPTED`:文件名、helper、局部代码组织、测试 fixture 等小偏差适配,不改变契约,可继续并报告。
- `PLAN_CONFLICT`:需要改变业务规则、数据口径、schema、API、权限、安全、迁移、验收或任务范围,必须暂停并请求确认。

## 按任务执行

当 plan 已经拆成任务时,按任务推进:

- 明确当前任务目标和依赖。
- 根据真实代码上下文细化编码顺序。
- 实施最小必要改动。
- 运行相关验证。
- 记录完成情况、偏差、plan 忠实度和未解决风险。

不要为了完成任务清单而跳过验证。不要把待确认项当成已确定任务。

## 变更边界

可以做:

- 修改业务逻辑、接口、页面、组件、模型、配置或测试
- 新增必要文件、测试、迁移或类型定义
- 调整与任务直接相关的代码结构
- 修复实现过程中暴露出的直接相关问题
- 局部工程适配:复用现有 helper、调整内部函数拆分、补充必要测试 fixture、适配真实文件路径

避免做:

- 无关重构
- 未要求的产品行为扩展
- 未确认的数据破坏性操作
- 大范围格式化无关文件
- 私自改变公共契约、权限规则或业务口径
- 私自改变 plan/spec 已锁定的数据模型、接口形态、统计口径、状态流转、安全策略、迁移策略或验收标准

## 质量底线

完成前尽量确保:

- 代码能解释为满足用户任务或 plan/spec。
- 关键路径有验证。
- 新增逻辑有适当测试或说明为什么无法测试。
- 错误、空值、权限、兼容性等明显风险被处理或说明。
- 如果存在 plan,最终能说明 `PLAN_FOLLOWED` / `PLAN_ADAPTED` / `PLAN_CONFLICT` 的状态。
- 最终回复清楚列出变更和验证结果。

## 知识沉淀提示(实现结束后)

汇报完变更和验证结果后,**主动评估本次会话是否产生了值得沉淀的知识**。不是每次都问 —— 只在本次实现中确实出现了下面任一情况时,提示用户:

- 踩了一个非显而易见的坑 / 陷阱(读代码看不出来,下次还会踩)
- 发现一个隐式约束或业务规则(代码里没写明,但影响实现)
- 做了一个有取舍的技术决策(存在替代方案,为什么选这个)
- 跨系统 / 跨文件的依赖关系,单看代码看不出来
- 历史背景 / 遗留约束解释了代码为什么是现在这样
- **本次功能让某业务实体参与了新业务,或出现了新实体**(实体 = 能用名词指代、有属性和生命周期的业务对象,如"商品"、"礼包")——这是实体主条目(`concept` 条目)新建/更新的最佳时点,相关流程条目也要在 concepts 里声明该实体(正向引用,供反查)

满足时,在汇报末尾加一句:

```text
本次实现中 [简述发现],是否需要用 code-impact-markdown skill 沉淀到 docs/knowledge/?
```

用户同意 → 调 `code-impact-markdown` skill 走它的完整流程(查已有概念 → 写文件 → `docs validate` 校验 → 合并检查 → 询问扫描)。用户拒绝或没有值得沉淀的内容 → 不提,正常结束。

**不要自己造沉淀流程** —— 必须走 `code-impact-markdown` skill,它有 frontmatter 规范、校验、合并检查、命名规则。直接 Write 一个 .md 不校验不查重,等于往知识库灌坏文件。

## 遇到阻塞

遇到以下情况时暂停并向用户说明:

- 业务规则互相矛盾
- plan/spec 与代码现实严重冲突
- 发现更优方案但会偏离 plan/spec 已锁定契约
- 必须执行高风险或破坏性操作
- 需要用户提供外部凭据、环境或不可推断决策

除此之外,尽量自主推进到可验证结果。
