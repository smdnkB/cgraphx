# Implementation

## 定位

- **执行阶段**:按已确认的 plan/spec 或用户明确任务改代码、验证、汇报。
- **有 plan 就忠实执行**:不重新设计业务规则、数据口径、接口契约、权限或核心方案;没有 plan 但任务明确 → 直接按当前上下文实现,不强迫用户先补文档。
- **自由的只有局部工程适配**:复用 helper、内部拆分、适配真实路径——契约级改动一律要确认。

## 流程

灵活执行,不机械套流程;简单任务各步快速过。

1. **理解输入** —— 用户请求 / plan/spec/PRD / 任务清单 / 错误信息;找到范围、非目标、验收口径。
2. **读上下文** —— 相关文件 / 调用链 / 测试 / 配置 / 项目约定;只读足以安全实现的量。**读适用规范**:**有 plan → 读 plan「强制引用」标注的规范,不自行识别**(规范要求已结晶进 plan 契约);**无 plan → 自行识别**(动 schema 必读 data-standards.md,新增接口读 interface-standards.md,动代码读 coding-standards.md)。**规范缺失 → 中断,提示 init-project-guides 补齐**(或用户明确表示不需要)。冲突按 spec > plan > 规范服从上层,实质冲突上报。
3. **有 plan 先评审** —— 读 `index.md`,再读要做的任务文件;批判性检查(与代码结构一致 / 依赖合理 / 上下文完整 / 无未确认规则 / 无高风险操作 / 验证可执行)。严重冲突 → 说明并请求确认,不自行换方案;不改变契约的小适配(文件名 / helper / 局部组织 / fixture)→ 说明后继续(`PLAN_ADAPTED`)。按依赖顺序执行,不盲目执行错误计划。
4. **实现变更** —— 小步、保持风格一致;复用已有工具 / 模型 / 组件 / 服务;新增抽象必须解决真实重复或复杂度。
5. **验证** —— 最相关的测试 / 类型检查 / lint / 构建 / 手工检查;有 plan 时,全部任务做完后再跑 index「统一验证」里的命令;前端或可视化变更按项目需要浏览器/截图验证;失败时判断是实现/环境/既有问题,继续修正可控部分。**本机验证不了、要交给人验证的**(浏览器效果、真机、外部环境)→ 列验证清单(测什么 | 预期),相关任务**等人明确回复验证结果后再提交**;人的回复没提验证结果(如只说"提交")→ 追问一次"页面测过了吗?",人明确说不测才提交,并在汇报里注明"未经人工验证"。
6. **汇报** —— 改了什么 / 验证了什么 / 风险与未完成项;有 plan 则说明 `PLAN_FOLLOWED` / `PLAN_ADAPTED` / 是否出现过 `PLAN_CONFLICT`。按下方「汇报范例」写:先说原来怎样,再说现在怎样,然后列改了什么、验证了什么。
7. **沉淀提示** —— 确有内容才问(见下)。
8. **平台环节缺口提醒** —— 有需求目录时才做(见下)。

> **提交点**:plan 的任务文件写了「提交点」时,每完成一个任务并通过验证后,按提交点和 index「提交规范」节(从 `git-standards.md` 结晶)逐笔提交;precommit 门禁自查按 plan 检查点过后用 `CGRAPHX_PRECOMMIT_REVIEWED=1` 重试即可。plan 没写提交点的不擅自提交,交用户决定;push 永远归用户。

## 变更边界

- **可以做**:修改业务逻辑 / 接口 / 页面 / 模型 / 配置 · 修正被改动弄红的既有测试 · 新增必要文件 / 迁移 / 类型 · 调整与任务直接相关的代码结构 · 修复实现中暴露的直接相关问题 · 局部工程适配。
- **避免做**:无关重构 · 未要求的产品行为扩展 · 大范围格式化无关文件。

## 中断与上报

- **`PLAN_CONFLICT`**:需要改变业务规则 / 数据口径 / schema / API / 权限 / 安全 / 迁移 / 验收或任务范围 → **必须暂停请求确认**。
- 其他暂停情形:业务规则互相矛盾 · 更优方案但偏离已锁定契约 · 必须执行高风险/破坏性操作 · 需要用户提供凭据/环境/不可推断决策。
- 除此之外,自主推进到可验证结果。

## 知识沉淀(实现结束后)

本次实现确有下面任一情况时,在汇报末尾加一句问用户("本次实现中 [简述发现],是否用 knowledge-write 沉淀到 docs/knowledge/?"):

- 非显而易见的坑 / 隐式约束或业务规则 / 有取舍的技术决策 / 跨文件跨系统关系 / 历史遗留背景
- **出现了新实体或实体参与了新业务**(实体 = 名词可指代、有属性和生命周期的业务对象)→ 新建/更新实体主条目(`business-entity`)的最佳时点,相关流程条目在 concepts 里声明该实体(正向引用供反查)

用户同意就走 knowledge-write;拒绝或没有可沉淀的内容就不提。

## 平台环节缺口(实现结束后)

有需求目录时跑 `cgraphx features show <feature-id>`;「平台环节」里标「缺(必需)」的,在汇报末尾提一句还缺哪些环节、可以用哪个 skill 补,例如「平台环节还缺:测试。可以跑 `/write-api` 或 `/write-unit-test-spec` 补。」只提醒,不拦;没有需求目录就跳过。

## 质量底线

- 代码能解释为满足用户任务或 plan/spec;关键路径有验证;新增逻辑的测试覆盖由独立测试流程(代码完成后 `write-unit-test-spec` → `write-unit-test-code` / `write-api` → `run-api-test`)负责,实现期不写新测试,改动弄红的既有测试已同步修正;错误 / 空值 / 权限 / 兼容性风险被处理或说明。
- 最终回复清楚列出变更和验证结果。

## 红线(绝对不能做)

1. ❌ **不编造业务规则**——不清且影响实现 → 先问;不阻塞的小细节可保守假设并说明。
2. ❌ **不私自改变已锁定契约**(业务规则 / 口径 / 接口 / 权限 / 安全 / 迁移 / 验收 / 公共契约)——冲突上报,不改写。
3. ❌ **不顺手重构扩范围**、不做未要求的行为扩展。
4. ❌ **不执行未确认的数据破坏性操作**。
5. ❌ **不回滚用户已有改动**——保护自己没做的变化。
6. ❌ **不为完成任务清单跳过验证**;无法验证 → 说明原因和剩余风险。
7. ❌ **不把待确认项当已确定任务执行**。
8. ❌ **不自造沉淀流程 / 直接 Write .md**——沉淀走 knowledge-write(不校验不查重 = 往知识库灌坏文件)。
