# Developer Timeline 报告生成

## 定位

这个 skill 用 Developer Timeline 事件流生成**有用的工作报告和习惯洞察**。`cgraphx timeline` CLI 是底层数据源,不是最终目标。

目标是把 prompt、工具调用、文件改动、验证动作和 git commit 聚合成:

- 给领导/业务方看的日报、周报、月报、阶段成果汇报
- 给技术负责人看的项目复盘、交付范围、验证与风险说明
- 给自己看的使用习惯分析、工作节奏、效率瓶颈和改进建议

报告要提炼成果,不要把 timeline 原始事件流水账贴给用户。

## 适用场景

按用户意图选择报告类型:

| 场景 | 输出重点 |
|---|---|
| 日报 | 今日/昨日完成、关键进展、验证、风险、明日计划 |
| 周报 | 本周重点成果、项目/目标分组、交付物、验证闭环、下周计划 |
| 月报 | 本月核心成果、项目维度总结、趋势、质量与效率、下月重点 |
| 阶段总结 | 某个 feature / 时间窗口 / 会话范围内的目标、过程、产出、遗留 |
| 使用习惯分析 | 活跃时段、工具分布、读写比、验证习惯、上下文切换、改进建议 |
| 交付汇报 | 面向领导/团队的价值、结果、风险和下一步 |
| 历史查询 | 某文件/commit/会话最近发生了什么,可直接回答或轻量总结 |

如果用户没有指定报告类型,根据措辞判断:

- "今天/昨天" → 日报
- "本周/上周/最近 7 天" → 周报
- "本月/上月/最近 30 天" → 月报
- "使用习惯/效率/分析一下我怎么用" → 使用习惯分析
- "最近做了什么" → 默认最近 7 天工作总结,除非上下文明显指向今天或本月

## 输出模式

支持三种输出:

| 模式 | 适用 |
|---|---|
| `chat-summary` | 聊天内快速总结,默认最轻量 |
| `markdown-report` | 可复制到周报/月报/文档 |
| `single-page-html` | 正式汇报、归档、浏览器查看、打印或截图 |

生成单文件 HTML:

- 内联 CSS,无外部资源,无脚本依赖。
- 默认路径:`docs/reports/timeline/`
- 建议命名:
  - 日报:`YYYY-MM-DD-daily.html`
  - 周报:`YYYY-Www-weekly.html`
  - 月报:`YYYY-MM-monthly.html`
  - 习惯分析:`YYYY-MM-DD-habits.html`
- 如果项目没有 `docs/reports/timeline/`,可以创建。
- 页面布局和风格参考本 skill 目录下 `demo-single-page-report.html`, 内容可以适当调整

## 报告生成流程

### 1. 确认必须明确的维度

报告生成前必须把以下维度敲定。核心原则:**用户已经明确给出的不重复问,未给出的必须主动问,不可推断**。

| 维度 | 已明确 → 直接用,不问 | 未明确 → 必须问 |
|---|---|---|
| 时间范围 | "昨天/今天/上周/本月/最近 N 天"等措辞清楚 | 必须问,不推断 |
| 输出格式 | 用户指定 chat 摘要 / Markdown / HTML | 必须问,不推断 |
| 受众 | 用户指明给领导/自己/团队/业务方 | 必须问,不推断 |
| 报告类型 | "日报/周报/月报/阶段总结/习惯分析"措辞清楚 | 从措辞推断,不强制问 |

举例:

- "总结昨天的日报" → 时间已明确、报告类型已明确,只问输出格式和受众
- "总结最近工作" → 时间、格式、受众都未明确,一次问完
- "做一份本月 HTML 月报发给领导" → 全部明确,直接做,不问

询问规则:

- 用 `AskUserQuestion` 一次性把所有缺失维度问完,不逐条追问。
- 询问优先级:输出格式 > 时间范围 > 受众。
- 报告类型不强制问,从措辞合理推断。
- 用户已经明确说出的维度,**绝不重复问**(说"昨天"就不要再问"什么时候")。

### 2. 采集 timeline 数据

优先用 table 格式,减少 token:

```bash
cgraphx timeline query --since=<date-or-range> --until=<date-or-now> --format=table
```

按需补充统计:

```bash
cgraphx timeline stats --since=<date-or-range> --until=<date-or-now>
```

按需钻取单条详情:

```bash
cgraphx timeline show <id>
```

常用时间范围:

- 日报:今天 00:00 到现在;昨日用昨日 00:00 到今日 00:00
- 周报:本周一 00:00 到现在;上周用上周一到本周一
- 月报:本月 1 日 00:00 到现在;上月用上月 1 日到本月 1 日
- 最近 N 天:用 `--since=Nd`

### 3. 聚合事件,不要流水账

把事件归并成"目标 / 成果 / 证据 / 验证 / 风险":

- 按用户 prompt 和会话边界识别工作目标。
- 按文件路径、模块、feature-id、commit message 聚类。
- 把 Read/Edit/Bash 等工具调用转译成工程动作,不要当作成果本身。
- commit 是交付证据之一,不是唯一成果。
- 探索、调试、验证、未提交改动也要识别,但要说明状态。
- 将未验证、未提交、被中断、失败命令、反复修改集中列为风险或遗留。

### 4. 选择叙述方式

按受众调整语言:

- 给领导/业务方:强调业务价值、交付结果、风险闭环、下一步计划;少讲工具细节。
- 给技术负责人:强调模块、文件范围、接口/测试/验证、质量风险。
- 给团队:强调协作影响、变更范围、阻塞项、需要 review 的地方。
- 给自己:强调工作节奏、工具使用、上下文切换、验证习惯和改进建议。

### 5. 生成报告

默认先给高层结论,再给证据。不要先贴原始表格。

如果生成 HTML:

1. 先组织报告内容。
2. 使用 `demo-single-page-report.html` 的布局风格作为参考。
3. 根据报告类型裁剪章节。
4. 写入目标 HTML 文件。
5. 检查是否单文件、无外链、无脚本、可打印。

## 报告模板

模板是结构参考,不是死板填表。无内容的章节可以省略。

### 日报

```markdown
## 今日完成
## 关键进展
## 验证与交付
## 风险/阻塞
## 明日计划
```

### 周报

```markdown
## 本周摘要
## 重点成果
## 项目/模块进展
## 验证与交付证据
## 风险与遗留
## 下周计划
```

### 月报

```markdown
## 本月核心成果
## 项目/模块维度总结
## 质量与效率指标
## 关键风险处理
## 经验沉淀
## 下月重点
```

### 使用习惯分析

```markdown
## 工作节奏
## 工具使用分布
## 读写与验证习惯
## 上下文切换与中断
## 交付闭环
## 改进建议
```

### 单页面 HTML

推荐章节:

- 标题区:报告名称、时间范围、项目、生成时间
- 一页摘要:3-5 个核心结论或关键数字
- 重点成果:按目标/项目聚合,不按工具流水账
- 证据与交付物:commit、文件、验证命令、产物
- 使用习惯分析:工具分布、读写比、验证习惯、工作节奏
- 风险与遗留:未验证、未提交、阻塞、敏感项
- 下一步计划:建议转化成可执行事项

页面风格:

- 工作报告风,信息密度高,适合领导和技术负责人快速扫描。
- 不做营销页、不做装饰性 hero、不放无意义图形。
- 使用表格、指标块、短列表、标签和时间线组织信息。
- 内容优先,视觉只服务可读性。

## 使用习惯分析指标

按数据可得性取用,不要为了凑指标编造:

- 活跃时间段:上午/下午/晚上、连续工作时长、长会话/短会话比例
- 工具使用:Read/Edit/Bash/搜索/测试/提交分布
- 读写比:读取上下文与实际编辑的比例
- 验证习惯:测试、lint、build、diff check、手工验证频率
- 上下文切换:涉及项目/模块/文件数量,是否频繁中断
- 交付闭环:commit 数、未提交改动、失败命令、未验证改动
- 工作类型:探索、实现、修复、文档、评审、调试、汇报
- 风险模式:改多测少、探索多沉淀少、频繁返工、长时间无验证

## 内容质量规则

- 不要逐条复述 raw timeline 事件。
- 不要把 "Read/Edit/Bash" 当作工作成果;要翻译成目标和结果。
- 不夸大:没有 commit 不等于没成果,但没有验证也不能说已交付。
- 明确区分完成、进行中、探索、未验证、未提交、阻塞。
- 对失败命令、回滚、重复尝试要总结原因和影响,不要隐藏。
- 敏感信息默认摘要化;不要直接暴露完整 prompt、命令参数、token、密钥、客户数据或长日志。
- 用户要求给领导时,语言要结果导向;用户要求自我分析时,可以更直接指出习惯问题。
- 如果 timeline 数据不足,说明覆盖范围和不确定性,不要编造缺失事件。

## CLI 数据源参考

Developer Timeline 记录项目本地事件流:

- `user_prompt`:用户提出的任务
- `pre_tool_use` / `post_tool_use`:工具调用、文件、命令
- `stop`:会话结束
- `git_commit`:提交记录

数据存在项目本地 `.cgraphx/cgraphx.db`,per-project 隔离。

### 命令

```bash
cgraphx timeline recent --limit=20 --format=table
cgraphx timeline query --since=7d --format=table
cgraphx timeline query --since=2026-06-01 --until=2026-07-01 --format=table
cgraphx timeline query --file=src/auth/login.ts --since=30d --format=table
cgraphx timeline query --type=git_commit --since=7d --format=table
cgraphx timeline stats --since=7d
cgraphx timeline show <id>
```

### 时间格式

`--since` / `--until` 接受:

- ISO 8601:`2026-06-01` / `2026-06-01T00:00:00Z`
- 相对:`7d` / `12h` / `30m` / `now`

**时区语义(重要)**:

- 所有 `ts` 字段存储为 UTC ISO。
- 日期字符串 `2026-06-01` 按**本地时区**解释(本地零点,不是 UTC 零点)。`--since=2026-06-01` 覆盖的是本地 6/1 全天,而非 UTC 6/1(后者在 UTC+N 时区会漏掉本地凌晨的工作)。
- `--format=table` 的 `ts(local)` 列、stats 的 `Window (local)` 行、`byDay` 按日分组 —— **全部按本地时区呈现**,直接是用户墙上时钟的时间,无需再做转换。
- `--format=json` 的 `ts` / `windowStart` / `windowEnd` **保留 UTC ISO**(带 `Z` 后缀)作为机器可读契约,程序消费时再自行转本地;只有 `byDay[].day` 是本地日期 `YYYY-MM-DD`(分组键,人看的)。

生成 HTML 报告时,从 `--format=table` 拿到的时间已经是本地时间字符串,直接贴进 HTML 即可,不要把 UTC ISO 原样展示给用户。

### 输出选择

- `table`:推荐给 agent 读,密度高。
- `json`:需要完整字段或程序处理时使用。
- `show <id>`:单条钻取。

## 跟其他工具的边界

| 想知道 | 用 |
|---|---|
| 代码结构、调用关系 | `cgraphx` skill |
| 业务决策、概念定义 | `code-impact-api` skill |
| 数据库数据 | `db-query` skill |
| 开发活动历史、报告、习惯分析 | 本 skill |
| 只要 commit 列表 | `git log` 更轻量 |

## 前置条件和失败处理

- 项目必须已 `cgraphx install`(会建 `.cgraphx/`)。
- Timeline hooks 必须安装(`cgraphx timeline install` 或 `cgraphx install`)。
- Kill-switch:`CGRAPHX_NO_TIMELINE=1` 时 hooks 静默不记录。
- 如果 timeline 无数据,说明原因并建议检查 hooks;可以退化到 `git log` + 当前工作区状态,但必须标明覆盖不足。
- Timeline 全量记录 prompt、命令和文件路径,不脱敏;报告时默认摘要化敏感内容。

## 探索结果收口(给 clarify/spec/plan)

只有当本 skill 用于恢复上下文、承接未完成工作或进入 clarify/spec/plan 前置探索时,才做简短收口。普通日报、周报、月报、历史查询和习惯分析直接按用户要求生成报告,不套这个模板。

按需使用以下 4 项,无内容可省略:

- **查到的关键事实**:最近目标、读过/改过的文件、跑过的命令、commit 或未提交改动。
- **对决策的影响**:哪些上下文可复用,哪些必须重新问用户确认。
- **应进入 PRD/spec/plan 的内容**:已完成任务、剩余任务、验证缺口、需要保护的用户改动。
- **仍不确定/需确认**:只是探索未确认、尚未验证、未提交或需要用户重新拍板的点。
