# 代码地图沉淀 (Code Map Write)

## 定位

- **代码地图 = 从代码派生的系统视图,给人看**:人靠它建立系统全貌;每次需求的设计预览挂在它上面,人只需理解增量。
- **和知识库分工**:

| | 知识库(`docs/knowledge/`) | 代码地图(`docs/code-map/`) |
|---|---|---|
| 存什么 | 为什么、规则、约束(重构后仍成立) | 怎么走、在哪里(随代码变) |
| 谁写 | 人 + AI 沉淀 | 从代码生成 |
| 防过期 | 只存稳定内容 | 记录 `source_commit`,相关文件变了即过期,整体重生成 |
| 连接 | 流程条目 | 视图 `concepts` 用知识库规范概念名,`knowledge` 指向对应流程条目 |

- **只沉淀现状,不沉淀计划**:视图只从已写出的代码生成;plan 设计预览里的图是"计划",不进地图。
- **边界**:召回已有视图 → `code-map-recall`;业务知识 → `knowledge-write`。

## 两类视图

| 视图 | 文件 | 内容 | 粒度 |
|---|---|---|---|
| 系统交互 | `docs/code-map/系统交互.md` | 系统/服务/外部依赖之间的调用(RPC / HTTP / 消息 / 库) | 一个项目一份;服务多时按业务域拆 `系统交互-<域>.md` |
| 流程视图 | `docs/code-map/flows/<流程名>.md` | 代码链路(`sequenceDiagram`)+ 数据流转(`flowchart`:谁写/读哪些表、文件、消息) | 一个业务流程一份;流程名与知识库流程条目同名 |

标准样张(照着写,结构与字段逐项对齐):[references/flow-view-example.md](references/flow-view-example.md)、[references/system-view-example.md](references/system-view-example.md)。

## 流程

1. **定图谱工具**:读项目 `CLAUDE.md`「项目约定」的 `代码图谱:` 行 → 有则用;无 → 探测 `command -v gitnexus` / `command -v codegraph`;都装了 → 问用户一次,把选择写进该行;都没有 → `ai`(不劝装)。有工具时先跑其状态命令确认索引新鲜度:索引落后于 HEAD → 问用户是否重建索引(重操作,不擅自跑);不重建 → 改动过的文件降级为 AI 读代码。
2. **定范围**(列清单请用户确认后再生成):
   - **收尾模式**:`git diff --name-only <起点>..HEAD` 得改动文件 → 找 `related_code` 含这些文件的已有视图(待刷新)+ 本次新出现的流程(取自 spec/plan,待新建);跨服务调用有变 → 系统交互视图待刷新。
   - **指定模式**:用户点名的流程/系统。
   - **批量初建**:`grep -l "document_type: business-flow" docs/knowledge/*.md` 列出全部流程条目,每条一份流程视图 + 一份系统交互;条目多时按业务域分批。
3. **取结构**:按下表向图谱工具取;命令名以本机 `<工具> --help` 为准,先跑 `--help` 确认,没有的能力降级为 AI 读代码。

| 要的结构 | gitnexus | codegraph | ai(没装工具) |
|---|---|---|---|
| 从入口展开调用链 | `context <入口>` 逐层展开;入口有执行流时直接取执行流 | `callees <入口>` / `explore` | Read 入口,沿调用逐层读 |
| 两点间路径 | `trace <from> <to>` | 逐层 `callees` | 同上 |
| 跨服务调用 | `route-map`(HTTP 路由 → handler → 消费方);RPC 边视版本而定 | 无 → ai | 读 RPC / HTTP 客户端、路由、配置 |
| 代码访问哪些表 | 无 → ai | 无 → ai | 读 SQL / mapper / ORM 实体,对照 `docs/schema-knowledge/` 的 DDL |

   入口从哪来:知识库流程条目的 `related_code`(先 `cgraphx docs find --concept=<流程>`)> spec/plan 的接口与页面 > 用户指定。
4. **生成**:Read 样张,按样张结构写;业务标注(每一步在业务上是什么意思)必须读代码确认,图谱工具只给结构。
5. **盖戳**:`source_commit` = `git rev-parse --short HEAD`;`related_code` 列出图中出现的全部文件(过期判定靠它);相关文件有未提交改动 → 先提示用户提交,或在「已知盲区」注明"含未提交改动"。多 git 子工程项目:每个文件在其所属仓库取 commit,`source_commit` 写成 `<子工程>:<hash>` 列表。
6. **对照设计预览**(本次需求有 plan 时):对比 plan index「设计预览」与生成结果,回复里列偏离表(预览 | 实际 | 原因);原因取自实现汇报的 `PLAN_ADAPTED` 记录,查不到就如实写"未记录"。偏离只汇报,不回写 plan。
7. **汇报**:新建/刷新了哪些视图 + 偏离表(如有)+ 仍过期未刷新的视图(如有)。

## 过期判定(code-map-recall 同口径)

```bash
git diff --name-only <source_commit> HEAD -- <related_code...>   # 非空 → 过期
git status --porcelain -- <related_code...>                      # 非空 → 含未提交改动
```

## 写法要点

- **每张图前一句「看什么」**;参与者/节点一般 ≤12 个,超了拆成多张或下沉到子流程视图。
- **节点索引表必有**:每个节点一行,`代码指针`(文件:符号,不写行号)+ `来源`(`图谱` / `AI 读代码`)。
- **不确定的边**:用虚线 + 「待确认」标注,并写进「已知盲区」;两边都没确认的边不画。
- **头部提示语固定**:"派生视图:从代码生成,不手工修改……"(见样张)。

## 红线(绝对不能做)

1. ❌ **不画没有代码指针的节点**——指不回代码的结论不写。
2. ❌ **不编造调用关系**——图谱和读码都没确认的边不画。
3. ❌ **不把计划写进地图**——视图只从已写出的代码生成。
4. ❌ **不手工修补视图**——过期就整体重生成。
5. ❌ **不写进 `docs/knowledge/`**——知识库只存稳定知识。
6. ❌ **不擅自安装图谱工具或重建索引**——重操作先问用户。
