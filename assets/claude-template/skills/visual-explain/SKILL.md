# Visual Explain

## 定位

- 降低人看懂 AI 输出的成本:把对话里说过的内容,或者用户指定的文件、话题,画成一页图解。
- 用户说「没看懂」「画个图讲讲」「图解一下」时用;用户没要求时不主动出页面。
- 图解是讨论稿,不是契约,看完不再维护。

## 流程

1. 定要讲什么:先用一句话说清用户看完要懂什么。
2. 选主线:按「讲法」表选;拿不准沿哪条线讲,先问用户。
3. 画全局:一张图看清整体,标出新增、改动、去掉的地方和需要人确认的关口。
4. 展开局部:关键节点写细节,每个结论配一个例子。
5. 写成一页:按「页面要求」写,版式照 `references/范例-澄清结果.html`。
6. 存好、打开:按「放在哪」存;用系统浏览器打开,macOS 用 `open`,Linux 用 `xdg-open`,Windows 用 `start`;打不开就把文件路径给用户。

## 讲法:全局加局部

- **全局**:一张图看清整体走向,标出新增、改动、去掉的地方和需要人确认的关口。主线沿读者熟悉的那条线排,见下表。
- **局部**:关键节点展开写细节。业务写口径和逻辑,即判断条件、计算规则、取数范围;流程或工具调整写头部、拦截、强制规范和产出;代码写输入、判断条件和输出。每个结论配一个例子。

| 要讲的内容 | 主线沿着 | 全局 | 局部 |
|---|---|---|---|
| 一个功能的流程 | 业务流程 | 流程图画业务走向,标出新增和改动的步骤 | 「计算优惠」节点写清取数范围和计算规则 |
| 流程或工具调整 | 使用顺序 | 按做需求的顺序串起各步,标出新增、改动、去掉 | 每一步写做什么、在哪会被拦、产出什么 |
| 一段代码 | 调用顺序 | 调用链一张图,标出入口和数据最后落在哪 | 关键函数写输入、判断条件和输出 |
| 一份 plan | 执行顺序 | 任务和执行顺序一张图,标出能同时跑的 | 重点决策写清为什么难回头 |
| 几种方案对比 | 对比维度 | 一张表看清每个方案在各维度上的差别 | 推荐的方案写清理由和代价 |

## 页面要求

- **形式**:一律出一页 HTML:单个文件,样式内联,断网能打开;浅色、深色下都看得清;手机宽度下不横向滚动;图例写清每种颜色和标记的意思。
- **开头**:一段话先给结论;讲改动时,第一句先讲原来的情况。
- **澄清结果的图解**:分「要做的事情」和「会得到的结果」两部分:前者是定下的每条决策,各配一个例子;后者是改完以后的样子。

## 放在哪

- 和某个需求有关的,放进该需求目录:`docs/features/<feature-id>/<前缀>-<主题>-v<N>.html`,澄清结果的主题叫「澄清结果」,文件名就是 `<前缀>-澄清结果-v<N>.html`;和需求无关的,放 `.cgraphx/visual/<主题>-v<N>.html`,只存在本机,不进 git。
- N 从 1 递增,改一次出一版,旧版保留。
- 讨论稿,不是契约:不写 `> 产物:` 头部,不登记产物类型,不上报平台,看完不再维护。
- 和需求有关但还没有需求目录时,按 write-spec 的命名规则定 feature-id、建目录。
- 拿不准和哪个需求有关,先问用户。

## 范例

`references/范例-澄清结果.html` 是 skill瘦身 的澄清结果图解,属于「流程或工具调整」:开头一段加四个数字,「要做的事情」是两组决策表,「会得到的结果」每部分先全局再局部。要出页面时先读它,版式、配色、深浅色和窄屏表格照它写,内容换成要讲的东西。

## 红线

1. ❌ 用户没要求时不主动出页面。
2. ❌ 不写 `> 产物:` 头部,不登记,不上报,不当契约引用。
3. ❌ 不加载外部的脚本、字体和图片,断网要能打开。
4. ❌ 不编造:图里的每个节点、每条结论都要在对话、文件或代码里有依据。
