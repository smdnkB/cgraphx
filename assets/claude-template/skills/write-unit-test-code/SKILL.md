# Write Unit Test Code

## 定位

**测试填实 + 验证 skill**:消费 `write-unit-test-spec` 产出的测试规格文档,基于已有实现代码填实测试代码,跑测试验证,出测试报告。

**和 write-unit-test-spec 的分工**:
- write-unit-test-spec:产**测试规格文档**(该测哪些场景,基于 spec,零代码依赖)
- 本 skill(write-unit-test-code):基于测试规格 + 已有实现,填实测试代码 + 跑 + 出报告

两个 skill 顺序依赖:本 skill 找不到测试规格文档时报错退出。

**和 implementation 的关系**:平行线路。implementation 写业务实现代码,本 skill 写测试代码。本 skill 假设被测代码已存在(典型场景:用户跑完 implementation 后回来补测试);代码缺失的场景用 `it.skip` + TODO 占位。

## HARD-GATE

- **不写业务实现代码** —— 本 skill 只写测试代码 + 测试报告,业务实现是 implementation 的事
- **依赖测试规格文档** —— 当前 feature 没有 `<前缀>-单元测试-spec.md` 时,报错退出:"找不到测试规格,请先跑 /write-unit-test-spec"。不自己现场派生测试场景(那是 write-unit-test-spec 的职责)
- **不编造被测目标** —— 测试里 import 的函数/类/模块必须**已存在**。不存在 → 对应场景用 `it.skip` + `// TODO: 实现提供后填实` 占位,不自己造签名
- **不修实现代码** —— 测试失败时如实报告,不替用户改业务代码
- **不假装通过** —— 测试断言不调到"假绿"。失败就是失败,如实标在报告里

## Trigger

**使用此 skill 当**:
- 用户跑完 `/write-unit-test-spec`,想填实测试代码
- 用户跑完 implementation,想基于测试规格补测试
- 用户明确说"填实测试 / 写单元测试代码 / 跑单元测试 / write-unit-test-code"

**不要使用此 skill 当**:
- 没有测试规格文档 —— 先跑 `/write-unit-test-spec`
- 想写业务实现 —— 用 `/implementation`
- 想产测试规格(不填实)—— 用 `/write-unit-test-spec`
- 纯文档 / 配置 / 无行为变更的需求 —— 无可测代码

## 流程

### 1. 前置检查

- 确认 `docs/features/<feature-id>/<前缀>-单元测试-spec.md` 存在。**不存在 → 报错退出**:"找不到测试规格,请先跑 /write-unit-test-spec"。不现场派生场景。
- 复用测试规格的 feature-id 和文件前缀,推导出测试文件路径和报告文件名。

### 2. 读测试规格文档

读 `<前缀>-单元测试-spec.md`,拿到:
- 必测场景清单(主路径 / 边界 / 异常,每条标 spec 依据)
- 测试骨架映射(测试文件该放哪、框架、命名)

### 3. 读已有实现代码

根据测试规格描述的被测目标,在代码库定位已有实现(用 grep / Read):
- 读函数签名、参数、返回值、抛错行为、依赖关系
- 如果测试规格里的某个场景**代码里还没实现**:
  - 对应测试用 `it.skip` + `// TODO: 实现提供后填实` 占位
  - 记入"实现缺失场景清单",汇报时告诉用户"有 N 个场景因实现缺失跳过"
  - **不自己造签名**
- 如果实现和 spec 不一致(测试规格基于 spec,但代码偏离了 spec):
  - 在测试报告里标注"实现与 spec 偏差:X(spec 说 A,代码实际 B)"
  - 测试按**代码实际行为**写(要能跑过)
  - 偏差记录留给用户决定(改代码 / 改 spec / 接受现状)

### 4. 产出测试文件(断言填实)

写到 `<项目测试目录>/<feature-id>.test.ts`(或项目约定的命名/后缀,从测试规格的"骨架映射"节读取)。形态:

- 实现已就绪的场景 → `describe` + `it`(含真实断言,基于读到的签名写,能真跑)
- 实现缺失的场景 → `it.skip` + `// TODO: 实现提供后填实` 占位
- import 被目标(已存在的模块直接 import;不存在的标 TODO 注释,不强行 import)
- 框架(vitest/jest/...)和文件后缀按项目约定
- 已有同模块测试文件 → 文件名加后缀避免覆盖(如 `<feature-id>.补充.test.ts`),在报告里提示"已有 X,是否合并由用户判断"

**AI 自己发挥的空间**:fixture / mock 怎么组织、describe 嵌套多深、断言写多细,agent 按既有测试风格判断,不强加模板。

### 5. 跑测试验证 + 产出测试报告

跑一次项目的测试命令(如 `npm test`),确认新写的测试能跑(通过或失败都行,失败说明实现有 bug 或测试断言写错)。

**产出单元测试报告**,写到 `docs/features/<feature-id>/<前缀>-单元测试报告.md`。结构轻量,至少包含:

- 测试概况:总数 / 通过 / 失败 / 跳过(it.skip 占位)/ 时长
- 逐场景详细结果:每个 `it` 的通过/失败/跳过 + 入参 + 执行过程 + 断言判定 + 失败原因(如有)
- 实现与 spec 偏差小结
- 待确认项汇总(实现缺失 / spec 不够细等)
- 下一步建议(失败 → 建议改实现 / 改测试 / 改 spec;跳过多 → 建议先补实现再回来跑)

**报告原则**:
- 通过 → 报告"测试已就绪,N 个场景覆盖"
- 失败 → 报告如实标失败 + 原因分类(测试写错 / 实现有 bug / spec 和实现偏差),**不修实现,不假装通过**
- 全部跳过(实现都没写)→ 报告标"无可跑测试,所有场景待实现",建议用户先跑 implementation

**逐场景详细结果格式**:

```markdown
### 2.1 ✅ 通过 — 主路径 · 正常输入应返回期望结果

| 维度 | 内容 |
|---|---|
| **场景** | 主路径 |
| **用例** | 正常输入应返回期望结果 |
| **状态** | ✅ 通过 |
| **耗时** | 12 ms |

#### 入参
| 参数 | 值 | 类型 | 来源 |
|---|---|---|---|
| input | `{ name: "张三", age: 25 }` | object | 测试规格 §2.1 |

#### 执行过程
```typescript
// 被测函数调用
const result = processUser({ name: "张三", age: 25 });
```

#### 断言判定
| # | 断言项 | 期望值 | 实际值 | 结果 |
|---|---|---|---|---|
| 1 | result.name | "张三" | "张三" | ✅ |
| 2 | result.age | 25 | 25 | ✅ |
| 3 | result.id | 存在 | 12345 | ✅ |
```

### 6. 汇报 + 不自动继续

告诉用户:
- 测试文件路径
- **单元测试报告路径** + 报告里的关键数字(通过/失败/跳过数)
- 实现与 spec 的偏差(如有)
- 待确认项(如有)

**不调用 implementation / write-unit-test-spec / run-api-test**,由用户决定下一步。

## 产物

| 产物 | 路径 | 形态 |
|---|---|---|
| 测试文件 | `<项目测试目录>/<feature-id>.test.ts` | describe + `it`(断言填实) / `it.skip`(实现待补) |
| 单元测试报告 | `docs/features/<feature-id>/<前缀>-单元测试报告.md` | 测试概况 + 逐场景结果 + 偏差小结 + 下一步建议 |

## 边界场景

- **找不到测试规格文档** → 报错退出,要求先跑 `/write-unit-test-spec`。不现场派生场景。
- **实现代码缺失** → 对应场景 `it.skip` + TODO 占位,汇报时告诉用户。不造签名。
- **已有同模块测试文件** → 文件名加后缀避免覆盖,报告里提示用户。不主动改既有测试。
- **跨语言项目** → 按测试规格文档里标注的语言约定产出。一次调用不产多语言测试。
- **实现与 spec 偏差** → 测试按代码实际行为写(要能跑过),偏差记录在报告里,汇报时提示用户。
- **纯文档/配置需求** → 检测到测试规格无可测场景 → 提示"规格里无可测场景,不建议继续"并退出。

## 不做的事

- 不写业务实现代码(那是 implementation 的事)
- 不现场派生测试场景(那是 write-unit-test-spec 的事,本 skill 找不到规格就退出)
- 不修实现代码(失败如实报告)
- 不假装通过(断言不调到假绿)
- 不引入硬 gate(precommit hook / 提交拦截)
- 不假设测试框架(从测试规格的骨架映射读,或运行时探测)
- 不改 write-unit-test-spec / implementation / write-plan(它们对本 skill 零依赖)

## 和其他 skill 的关系

- **write-unit-test-spec**:上游,提供测试规格文档。本 skill 找不到它就退出。
- **implementation**:平行线路,写业务实现。本 skill 读它的产物(代码),但不调它。
- **run-api-test**:不同类型的测试(接口测试 vs 单元测试),互不干涉。
