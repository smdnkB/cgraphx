# 澄清需求 (Clarify Requirements)

## 定位

- **事前理解 + 决策锁定**:把模糊请求变成锁定的意图、业务边界、技术约束——spec 的输入。像员工接领导任务:先搞清到底要做什么、哪些不做,主动挑战不稳假设,但拍板权永远在用户。
- **读无界,决策有界**:代码、数据模型、知识库尽管读(不读暴露不了真问题:维度可不可得模型说了算,读了代码才知道"系统已按周统计",定义题变确认题);但只锁定**业务决策和用户声明的技术约束**。实现手段选型(同步/异步、缓存、定时任务、选型、表设计)不在此拍板,归 plan 结合代码规划。
- **容忍度是业务边界,不是手段**:问"能容忍多久延迟、数据能容忍多旧",不问"用同步还是异步"。不问清容忍度,plan 选手段就只能猜。
- **判别标准**:业务拍板人能回答 → 这里问;需要代码现实才能回答 → 留给 plan。

<HARD-GATE>
用户确认业务边界之前:不写 PRD/spec/plan/代码,不搭脚手架,不采取任何实现动作。无论任务看起来多简单。
**只有用户能锁定决策**——推荐不是确认,拍板才算。
不妄下断言,不掩饰困惑,坦诚权衡。
</HARD-GATE>

## 流程

默认路径,按任务规模裁剪——简单任务快速过或合并。允许回跳:后面阶段发现前面没搞清,退回来重新澄清。

1. **知识库召回** —— 会话中没用过 `knowledge-recall` 则提示先聊相关概念;命中的实体主条目 = 第 2 步代码阅读的入口。
2. **探索上下文(读无界)** —— 按需读项目结构/文档/代码/测试/schema/模型/API;`db-query`(查库/DDL 必须用)、grep/Read(调用关系必须用),调用前告知用户,收集完简要陈述。**路径:从实体主条目的代码入口 + 相关表指针进代码,不盲目全局搜。产物是问题和事实,不是方案**——冒出的手段念头记入"留给 plan",不在此展开。
3. **分类任务** —— 选一个主类型(脚手架,见下)。**涉及页面/表单/展示/交互变化**(不限 `ui-ux` 类型)→ 提示一句"要不要先用 `/write-wireframe` 画个线框,看着界面再定?"——看界面才能定业务交互的需求,先画线框再回来锁定决策;用户不需要则继续。
4. **确认初步理解** —— 结构化复述(一句话意图在前;怀疑的目标/受影响区域/初步范围用短表或要点,不写长段落)+ "**这是你的意思吗?有什么要补充或纠正?**" 用户没明确说"没补充"之前,不进锁定。
5. **澄清业务边界** —— 目标/参与者/场景/包含与排除/数据归属/权限/异常/成功标准;**口径**(统计维度/时间范围/过滤/去重)与**容忍度**(延迟/新鲜度/一致性预期/中间状态感知)必须锁定;需领导拍板的规则标记"业务决策"。
6. **识别技术约束与影响(不选手段)** —— 只收三类:① 用户声明的技术约束(如实记录,不代展开);② 兼容性边界(旧 API/旧数据/旧调用方哪些不动);③ 影响半径与风险(blast radius/直接调用方/风险等级,HIGH/CRITICAL 先警告再定)。业务方案可给 2-3 选项 + 推荐,推荐不是锁定;手段选项不在此辩论,记入总结。
7. **总结并停止** —— 输出澄清总结(见「决策分层」),下一步交用户选,不自动继续;总结指向实现时按「下游实现 skill 选择」三档粗筛推荐(明显小 → `/implementation`;明显大 → plan 后 `/subagent-implement`;拿不准 → 建议先过 plan,不硬判)。

## 任务类型路由

脚手架,不是封闭枚举:项目有领域特定分类(电商 pricing/inventory、金融 compliance/audit 等)优先用项目的;无匹配时创建临时分类并说明理由。

| 类型 | 含义 |
|---|---|
| `feature` | 新能力或业务功能 |
| `change` | 修改现有行为 |
| `bugfix` | 错误行为或生产问题 |
| `workflow` | 业务流程或状态流转调整 |
| `permission` | 角色、访问控制、可见性、审批权、数据范围 |
| `integration` | 第三方或跨系统对接 |
| `data-change` | 数据订正、迁移、初始化、导入导出、回填 |
| `performance` | 速度、扩展性、稳定性、超时、可靠性提升 |
| `refactor` | 内部重构、架构清理、降依赖、可测试性 |
| `ui-ux` | 页面、交互、展示、表单、空/加载/错误状态 |
| `unknown` | 信息不足以分类 |

用主类型选主问题集;类型不是产出重点。

## 各类型关注点

启发式,不是清单;上下文已答的跳过,项目特定的主动加。

- **feature**:用户、入口、业务目标、输入输出、创建或变更的数据、与现有流程的连接、排除项、成功标准。
- **change**:当前行为、期望行为、需保留行为、兼容性、受影响调用方、迁移/灰度约束。
- **bugfix**:观察到的行为、期望行为、复现路径、影响范围、脏数据、验证方法、是否预防。
- **workflow**:触发事件、状态、流转、参与者、审批、可逆性、通知、异常、非目标。
- **permission**:角色、动作、可见性、数据隔离、默认权限、存量用户、审计、拒绝行为。
- **integration**:外部系统、真相源、数据方向、失败/重试/时效的业务容忍度(对接手段归 plan)、认证归属、回调可见性。
- **data-change**:目标/源数据、转换规则、dry-run、回滚、在线影响、审计、验证。
- **performance**:当前瓶颈、目标指标、用户体感、一致性容忍度(异步与否归 plan)、进度可见性、运维风险。
- **refactor**:行为是否可能变、目标、稳定公开契约、高风险模块、测试预期、是否分期。
- **ui-ux**:目标用户、受影响界面、痛点、期望交互、展示字段、校验、空/加载/错误状态、权限、数据范围。

## 澄清策略(按需)

- **苏格拉底单问(默认节奏)**:沿决策树一个分支一个分支走,**一次只问一个决策**,**每问先给推荐答案**,用户确认或纠正后再进下一问。**事实自己查、只问决策**(同定位「读无界,决策有界」);简单任务的琐碎确认可一并问,实质决策逐一单问。典型追问:为什么是现在?要解决什么问题?必需还是只是一条路径?不做会怎样?想优化哪个权衡?
- **确认式(锁定)**:一个分支问完后用"我理解是…… / 包含…… / 不包含…… / 对吗?"收口。
- **头脑风暴**(目标清楚但**业务方案**不清):2-3 选项 + 权衡 + 推荐,选定后回确认式锁定。手段方案不适用——归 plan。

## 问题池

按需取用,不是必问清单;上下文已回答的跳过。

- **意图与范围**:解决什么问题?为什么是现在?谁受影响?包含/排除哪些场景?哪些现有行为不许变?最低成功标准?
- **术语与对象**:关键名词对应系统里哪个既有对象/状态/流程(有实体主条目以它为准)?易混同名?本次新增/变更/只读引用?
- **规则与口径**:哪些规则要领导拍板?优先级/冲突/例外?口径:维度/过滤/时间范围(按周/按月/当前月/滚动 N 天)/去重/数据来源?临时策略 vs 长期机制?
- **行为与容忍度**:前置条件与触发(周期多少是业务定,用不用定时任务是 plan 定)?成功后各方看到什么?失败行为(报错/重试/回滚/待处理,哪些可接受是业务定)?结果可接受延迟多久?数据可接受多旧?重复请求允许重复结果吗?用户需要中间状态吗?外部失败可接受挂起重试吗?
- **权限与审计**:哪些角色能看/操作/审批/导出?隔离维度?无权限返回什么?审计/脱敏?
- **边界与兼容**:影响哪些页面/接口/任务/外部系统?新增/改旧/兼容后扩展?旧调用方/旧用户/旧数据兼容?真相源在哪?回填/灰度/回滚?
- **数据与状态**:读写/迁移哪些数据?状态枚举与流转?存量/脏数据处理?
- **验收**:怎么判断"做好了"?必验收场景?明确不测什么?
- **Plan 约束**:哪些文件/模块/接口/表/口径不能动?哪些方案已排除?

## 决策分层(即总结结构)

结束时只输出一份澄清总结——**这份总结是 spec 的输入,不是契约:决策只有写进 spec 才成为义务**。输出后停止,不自动调任何下游。

总结有两个读者:**人**(拍板业务口径)和 **spec**(无损接收全部分层)。人只读上半部分就能拍板,下半部分供 spec 使用。

### 上半部分:给人确认(按此示例写)

```markdown
**一句话**:把 web 侧栏灰置的「数据库」入口激活,让团队在浏览器里看本地导出的表结构和探索经验——只读本地文件,不连库。

用户会这样用:

    侧栏「数据库」
          │
          ▼
    工程列表 ──(只有一个工程时跳过)──→ 表清单 ──→ 单表 DDL(原文 + 经验分区)
                                          │
                                          └──→ 经验沉淀(本工程所有表的经验按标签汇总)

**需要你确认的业务决策**

| 决策 | 结论 | 举个例子 |
|---|---|---|
| 数据从哪来 | 只读 `docs/schema-knowledge/` 本地文件,不连库 | 库里刚加的字段,没重新导出就看不到 |
| 表清单显示哪些 | 只显示有 DDL 文件的表 | INDEX.md 里标 missing 的表不出现 |
| 经验怎么汇总 | 按 6 类标签分组,只汇总本工程 | 「陷阱」组列出本工程所有表的踩坑记录,点表名跳详情 |
| 能不能改 | 完全只读,页面上没有任何写操作 | 不能在页面上重跑导出 |

**口径与容忍度**:新鲜度——文件现在是什么就显示什么,不提示过期。

**不做**:连库查询 · SQL 语法高亮 · 跨工程搜表

**以上业务决策对吗?要改的直接说哪一行。**
```

- **流程图**:有角色、步骤、页面跳转或状态流转时必画(ASCII,对话里 mermaid 不渲染);纯规则调整可省。
- **决策表**:每条已锁定业务决策一行;「举个例子」用具体数据或场景说明这条决策的后果——人看例子才知道自己在拍什么板。
- **只放业务口径**:不出现模块、文件、函数名;技术约束、影响半径放下半部分。
- **未确认的不进决策表**,放下半部分「必须在 spec 前解决的问题」。

### 下半部分:供 spec 使用(以 `---` 分隔,标注"以下供 spec 使用,可不细读")

- **确认的意图**
- **已锁定业务决策**(目标/范围/角色/规则/口径/权限/异常/验收)
- **业务边界与容忍度**(延迟/新鲜度/一致性预期)
- **明确的非目标**
- **已锁定技术约束**(用户声明 + 兼容性边界;无则写"无特别约束")
- **影响半径与风险**(相关时;LOW/MEDIUM/HIGH/CRITICAL)
- **留给 plan 的手段决策**(识别到但不在此拍板;纯工程手段 plan 自主定,有业务可观察后果的 plan 会回跳 spec 业务拍板)
- **必须在 spec 前解决的问题** / **后续阶段的决策**
- **下游就绪判断**:Spec 可写否 / Plan 可写否 / 是否需先探索
- **用户控制的下一步**:`/write-spec` · `/write-wireframe`(涉及 UI 且还没线框,或决策改变了界面) · `/write-plan` · 开始实现(`/implementation` 明显小 / `/subagent-implement` 明显大,需 plan;拿不准 → 先过 `/write-plan` 终判) · `/write-prd`(发布后按需) · `/write-api-doc`(接口开发完毕后,可选) · `/write-design-doc`(发布后按需)

不要把 agent 推荐但用户未确认的写进"已锁定"。

## 终止条件

意图 ✓ 业务边界(含口径、容忍度)✓ 技术约束已识别 ✓ 主要非目标 ✓ 账本分层且剩余 open 项不阻塞 spec ✓ 用户明确说没补充/理解对了。全满足才结束。

## 下游实现 skill 选择

判断依据是**需求规模**(变更面宽度 × 单 agent 上下文能否装下),不是任务量——任务量是拆解产物,任何需求都拆得出 ≥3 个任务;跨域数也不是信号,小全栈需求天然跨 schema/backend/frontend 三域。

| 档位 | 条件 | 推荐 |
|---|---|---|
| 明显小 | 单点变更 / 1-3 文件 / 单模块 | `/implementation` |
| 明显大 | 预估变更文件 ≥10 **且** 跨 ≥3 个相互独立的模块 | plan 后 `/subagent-implement` |
| 拿不准 | 其余情形 | 只推荐 `/write-plan`,不硬判实现方式 |

- 默认倾向:拿不准 → implementation 方向(子 agent 有结构性开销,只在单上下文装不下、任务又相互独立时才值)。
- 反例:小全栈需求(加 1 字段 + 改 1 接口 + 1 页面展示,跨 3 域)→ `/implementation`——跨域、拆得出 ≥3 任务,都不是走 subagent 的理由。
- `/subagent-implement` 仍需 plan 前置;write-plan 出 index「执行方式建议」做终判,此处粗筛只给方向。

事后文档(发布后按需):`/write-prd`(业务方审阅)· `/write-api-doc`(接口开发完毕,仅新增接口)· `/write-design-doc`(设计文档)。

## 红线(绝对不能做)

1. ❌ **不在此拍板实现手段** —— 同步/异步、缓存、定时任务、选型、表设计归 plan;本阶段只收用户声明的约束。
2. ❌ **不跳过复述锁定** —— 用户没明确说"没补充/理解对了",不进决策锁定。
3. ❌ **不编造** —— 无法明确的标【待确认】或列为后续阶段决策。
4. ❌ **不把未确认推荐写进"已锁定"**。
5. ❌ **不自动继续下游** —— 输出总结即停;写什么、做不做,归用户。
6. ❌ **不放行不必要功能** —— YAGNI,主动砍。
