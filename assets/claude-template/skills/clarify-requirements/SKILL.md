# 澄清需求 (Clarify Requirements)

## 定位

这是一个**事前理解与决策锁定协议**。把用户模糊或不完整的请求,变成确认的意图、业务边界、技术约束,和下游 spec 可直接消费的决策输入。

**角色:顶级程序员 + 业务专家。** 像员工接到领导的任务安排——在做之前先搞清楚领导到底要做什么,哪些要做,哪些不要做;同时主动提出更优方案、挑战不稳假设,但所有关键决策必须由用户确认。

<HARD-GATE>
在用户确认业务边界之前,不要写 PRD、不要写详细 spec、不要写实现计划、不要写代码、不要搭建项目脚手架、不要采取任何实现动作。无论任务看起来多简单。
**只有用户能锁定决策**——agent 的推荐不是确认,用户拍板后才进"已锁定"。
不要妄下断言。不要掩饰困惑。坦诚地权衡利弊。
</HARD-GATE>

## 范围:问什么,不问什么

**clarify 只锁定业务决策和用户声明的技术约束。读无界,决策有界。**

- **读是无界的**:代码、数据模型、知识库都可以读,也应该读——不读就暴露不了真问题(统计维度可不可得,数据模型说了算;读了代码才知道"系统已按周统计",问题从定义题变成确认题)。
- **决策是有界的**:实现手段的选型(同步/异步、缓存、定时任务、选型、表设计)不在本阶段拍板——这些依赖代码现实,归 plan 阶段结合代码规划,由用户拍板。
- **判别标准**:这个问题能让业务拍板人回答 → clarify 问;需要代码现实才能回答 → 留给 plan。
- **注意:容忍度是业务边界,不是手段。** 问"结果能容忍多久延迟、数据能容忍多旧",不问"用同步还是异步"。不在 clarify 问清容忍度,plan 选手段就只能猜。

## 操作原则

- **先读上下文,再问问题**(见流程第 2 步)
- **只问对意图、业务边界、spec 正确性有实质影响的问题**;只影响后续阶段细节的,记录为后续阶段决策,不问
- **每轮默认 3-5 个高价值问题**(是默认,不是上限铁律;不淹没用户,不做清单审讯)
- **循环式复述**:每次用户回应后更新理解并复述;用户没明确说"没补充/没纠正"之前,不进入锁定。复述是理解偏差的防线——这是原则,不是仪式,简单任务可以快,但不能跳过理解确认
- 偏好自然协作;尽量用项目里的具体术语(文件名、模块、模型、API、角色)
- **不编造**:用户无法明确的,标注【待确认】或列为后续阶段决策
- **无情 YAGNI**:主动砍不必要的功能
- **允许回跳**:后面阶段发现前面没搞清,退回来重新澄清
- **简单任务轻量过**:不是每个任务都要死磕每一步

## 流程

默认路径,按任务规模裁剪——简单任务各步快速过或合并,不必逐步建任务、不必每步走满。

1. **知识库召回**
   - 检查当前会话是否用过 `knowledge-recall`;没有则提示用户先聊聊相关概念,拿到更高质量的上下文再进下一步
   - 召回命中的实体主条目同时是第 2 步代码阅读的入口

2. **探索上下文(读无界)**
   - 按需读项目结构、文档、代码、测试、schema、路由、模型、API、UI、既有约定
   - 工具:`db-query` skill(查数据库/DDL 必须用)、grep/Read(查调用关系/定位符号必须用)。调用前告诉用户"我需要先查 X 来理解背景",收集完简要陈述发现,不大段贴原文
   - **阅读路径优先走知识库**:实体主条目的代码入口 + 相关表指针 → schema-knowledge 的 DDL → 代码,而不是盲目全局搜
   - **读的目的是暴露业务问题**:模型里有哪些维度可得、现有行为哪些要保留、哪些既有约束会影响范围。**产物是问题和事实,不是方案**——读代码时冒出的手段念头记入"留给 plan 的手段决策",不在这里展开

3. **分类任务**
   - 选一个主任务类型(见「任务类型路由」);只在严重影响澄清时加次类型

4. **确认初步理解**
   - 结构化复述理解的意图、怀疑的目标、受影响区域、初步范围,明确问:"**这是你的意思吗?有什么要补充或纠正的?**"

5. **澄清业务边界**
   - 业务目标、参与者、场景、包含/排除范围、数据归属、权限、异常、成功标准
   - **业务口径**:统计维度、时间范围(按周/按月/当前月/滚动 N 天)、过滤条件、去重规则——口径是业务决策,必须在澄清阶段锁定
   - **容忍度**:结果可接受的延迟、数据可接受的新旧、一致性预期、用户是否需要感知中间状态——用业务语言问(见「Spec 就绪问题池 · 容忍度」)
   - 需要领导/业务方拍板的规则明确标记为"业务决策"

6. **识别技术约束与影响(不选手段)**
   - 只收三类:
     - **用户声明的技术约束**("必须用定时任务"、"不引入新中间件"这类组织/资源决策)——如实记录,不代为展开
     - **兼容性边界**:旧 API、旧数据、旧调用方哪些必须不动
     - **影响半径与风险**:涉及既有代码改动时,把 blast radius、直接调用方、受影响流程、风险等级(LOW/MEDIUM/HIGH/CRITICAL)报告给用户;HIGH/CRITICAL 必须先警告,再决定是否继续
   - 目标清楚但业务方案未定时(做不做、做到什么程度、口径选哪个),可给 2-3 个业务方案 + 权衡 + 推荐;用户确认前推荐不是锁定
   - **实现手段的选项和权衡不在这里辩论**——记入总结的"留给 plan 的手段决策"段

7. **总结并停止**
   - 输出澄清总结(见「最终输出」),提一句可能的下一步供用户选择,不自动继续
   - 总结指向"实现"时,根据任务规模推荐 `/implementation` 或 `/subagent-implement`(见「下游实现 skill 选择」)

## 任务类型路由

任务类型是**默认脚手架,不是封闭枚举**。

1. **默认类型不是封闭集合** —— 只是没有更具体项目分类时的基础路由
2. **项目有领域特定分类时优先用项目的** —— 电商可能有 pricing/inventory/order-lifecycle,金融可能有 compliance/audit/risk-control
3. **请求不符合任何默认类型时,创建临时分类并说明理由**

| 类型 | 含义 |
|------|------|
| `feature` | 新能力或业务功能 |
| `change` | 修改现有行为 |
| `bugfix` | 错误行为或生产问题 |
| `workflow` | 业务流程或状态流转调整 |
| `permission` | 角色、访问控制、可见性、审批权、数据范围 |
| `integration` | 第三方或跨系统对接 |
| `data-change` | 数据订正、迁移、初始化、导入导出、回填 |
| `performance` | 速度、扩展性、稳定性、超时、可靠性提升 |
| `refactor` | 内部代码重构、架构清理、降依赖、可测试性提升 |
| `ui-ux` | 页面、交互、展示、表单、空/加载/错误状态、体验改动 |
| `unknown` | 信息不足以分类 |

用主类型选主问题集。任务类型只为选问题服务,不是产出重点。

## 澄清策略

按需使用,不要每次都全跑。

### 确认式澄清(默认)

对齐事实和范围:"我理解是…… / 这包含…… / 这不包含…… / 对吗?"

### 苏格拉底式澄清

用户给了方案但没说目标、假设有风险、可能在治标不治本时使用:为什么现在需要这个变更?提出的方案要解决什么问题?这个方案是必需的还是只是一条可能的路径?不做会怎样?真正想优化哪个权衡?

### 头脑风暴式澄清

目标清楚但**业务方案**不清楚,或存在多个合理业务方案时:给 2-3 个选项 + 简短权衡,用户选定后回到确认式锁定边界。(实现手段的方案不在此列——归 plan。)

## 通用问题池

**问题池,按需取用**,不是必问清单:

- 我们在解决什么问题?为什么是现在?
- 谁使用或受影响?
- 包含哪些业务场景?明确排除哪些?
- 哪些现有行为必须保持不变?
- 创建、读取、更新、删除、导入、导出、迁移哪些数据?
- 涉及哪些角色、权限、租户、组织、数据范围?
- 重要的失败、空、重复、重试、回滚、边界情况有哪些?
- 最低成功标准是什么?必须尊重哪些约束?

## Spec 就绪问题池

来自后续 spec 的必备信息。**不是必问清单**,但答案会影响 spec 正确性的,应在澄清阶段前置解决。

### 术语与业务对象

- 关键名词在系统里对应哪个既有对象、状态、页面、接口或流程?(知识库有实体主条目时,以它为准对齐)
- 是否存在容易混淆的同名概念?需要统一叫法吗?
- 哪些业务对象是本次新增、变更或只读引用?

### 业务规则与拍板项

- 哪些规则必须由领导/业务方拍板?
- 是否有优先级、冲突处理、例外规则或豁免场景?
- 哪些规则是临时策略,哪些是长期机制?

### 系统行为

- 前置条件是什么?不满足时系统怎么表现?
- 触发动作是什么?是用户动作、系统事件、接口调用还是业务上的周期性处理?(周期是多少由业务定;用不用定时任务由 plan 定)
- 成功后用户、接口、下游系统分别看到什么结果?
- 失败时是报错、忽略、重试、部分成功、回滚还是进入待处理状态?(哪些可接受由业务定)

### 数据、状态与口径

- 读取、创建、更新、删除、导入、导出、迁移或回填哪些数据?
- 状态是否变化?状态枚举、状态含义和流转规则是什么?
- **统计/计算口径**:维度、过滤条件、时间范围、去重规则、数据来源——业务决策,必须锁定
- 存量数据、历史状态、脏数据是否需要处理?

### 容忍度与一致性预期(业务视角)

- 结果可以接受延迟多久?实时 / 当天 / 周度?(不要问"同步还是异步"——那是手段)
- 数据可以接受多旧?当前月 / 滚动 N 天 / T+1?
- 重复请求、重复点击、重复回调,业务上允许重复结果吗?
- 用户是否需要看到"处理中/部分成功"这类中间状态,还是只要最终态?
- 外部系统失败时,业务上可接受挂起重试,还是必须当场失败?

### 权限、安全与审计

- 哪些角色能看、能操作、能审批、能导出?
- 数据范围按租户、组织、区域、账号、客户还是其他维度隔离?
- 无权限时返回什么或展示什么?
- 是否需要审计日志、操作记录、敏感数据脱敏或安全限制?

### 接口、页面与系统边界

- 影响哪些页面、接口、任务、队列、外部系统或报表?
- 是新增能力、改旧能力,还是兼容旧能力后扩展?
- 旧调用方、旧用户、旧数据是否必须保持兼容?
- 真相源是当前系统、外部系统还是人工维护数据?

### 兼容性、迁移与灰度

- 老数据、老接口、老流程是否保持不变?
- 是否需要默认值、回填、迁移、dry-run、回滚或灰度?
- 不兼容变更是否允许?需要谁确认?

### 验收与测试关注点

- 用户怎么判断"这件事做好了"?
- 哪些主路径、边界、异常、权限、兼容性场景必须验收?
- 哪些场景明确不测或不覆盖?为什么?

### Plan 编写约束

- 后续 plan 必须遵守哪些技术约束?
- 哪些文件、模块、接口、表、状态、业务口径不能改?
- 哪些方案已经被排除?

## 各类型关注点

**启发式提醒,不是必问清单**:只问对理解意图/边界有实质影响的;上下文已回答的跳过;项目特定的主动加。

- **feature**:用户、入口、业务目标、输入输出、创建或变更的数据、与现有流程的连接、排除项、成功标准。
- **change**:当前行为、期望行为、需保留的行为、兼容性、受影响的用户或调用方、迁移需求、灰度约束。
- **bugfix**:观察到的行为、期望行为、复现路径、受影响范围、既有的脏数据、验证方法、是否需要预防。
- **workflow**:触发事件、状态、流转、参与者、审批、可逆性、通知、异常处理、非目标。
- **permission**:角色、允许的动作、可见性规则、数据隔离、默认权限、存量用户处理、审计需求、拒绝行为。
- **integration**:外部系统、真相源、数据方向、失败/重试/时效的业务容忍度(对接手段归 plan)、认证归属、回调可见性。
- **data-change**:目标数据、源数据、转换规则、dry-run 需求、回滚需求、在线影响、审计轨迹、验证。
- **performance**:当前瓶颈、目标指标、用户体感、一致性容忍度(异步与否归 plan)、进度可见性、运维风险。
- **refactor**:行为是否可能改变、重构目标、稳定的公开契约、高风险模块、测试预期、是否应分期。
- **ui-ux**:目标用户、受影响的界面、当前痛点、期望交互、展示字段、校验、空/加载/错误状态、权限、数据范围。

## 业务边界检查清单

结束前,确保总结能回答:

- 确认的意图、业务目标、用户或角色、触发场景
- 包含范围、排除范围、输入输出
- 数据和状态变更、统计口径
- 权限和可见性边界
- 容忍度(延迟/新鲜度/一致性预期)
- 重要的边界情况、成功标准
- 需要领导/业务方拍板的业务决策是否已明确

## 技术约束检查清单

结束前,确保总结能回答(相关时):

- 影响半径:前端、后端、数据库、job、队列、缓存、外部系统,及风险等级
- 兼容性:旧数据、旧 API、旧流程哪些必须保持
- 用户声明的技术约束(如实记录)
- 迁移或回填预期;日志、审计、安全的影响
- **明确不在本清单**:实现手段选型(同步/异步、缓存、定时任务、选型、表设计)——plan 阶段结合代码规划,用户拍板

## 决策分层

澄清总结必须把决策分层,方便 spec 直接消费:

- **已锁定业务决策**:业务目标、范围、角色、规则、口径、权限、异常、验收等已由用户确认的内容。
- **业务容忍度**:延迟、新鲜度、一致性预期——plan 选手段的依据。
- **已锁定技术约束**:用户声明的技术约束 + 兼容性边界。
- **已排除方案 / 非目标**:明确不做的业务范围。
- **留给 plan 的手段决策**:同步/异步、缓存、定时任务、选型等——由 plan 结合代码给选项和推荐,用户拍板。
- **必须在 spec 前解决的问题**:不解决会导致 spec 不可靠的问题。
- **后续阶段可处理的细节**:不影响业务决策和规格正确性的局部细节。

不要把 agent 推荐但用户未确认的方案写进"已锁定"。

## 终止条件

**只在以下条件全满足时结束:**

- 用户意图已确认
- 业务边界(含口径、容忍度)已确认
- 技术约束已识别(没有则明确"无特别约束")
- 主要非目标已确认
- 决策账本已分层,剩余 open 项不阻塞 spec
- 用户明确说没补充、没纠正、或理解对了

## 下游实现 skill 选择

澄清总结指向"开始实现"时,根据任务规模推荐:

| 维度 | `/implementation`(主会话顺序) | `/subagent-implement`(派子 agent) |
|---|---|---|
| 任务量 | 1-2 个简单任务 | ≥3 个任务 |
| 文件域 | 单文件 / 单模块 | 跨 schema/backend/frontend/test 多域 |
| 有 plan | 不一定需要,可基于 spec / 当前上下文直接做 | 需要(`docs/features/<feature-id>/plan/`) |
| 上下文压力 | 实现过程不会挤爆主 agent 上下文 | 实现过程会挤爆主 agent 上下文,需要隔离 |
| 审查模式 | 主 agent 自审 | 按风险派 spec-reviewer + quality-reviewer(最终) |

**默认推荐**:简单任务(单点改动 / 1-3 文件)→ `/implementation`;复杂 plan(多任务 / 跨域 / 需要双阶段审查)→ `/subagent-implement`。边界情况由主 agent 根据 plan 是否存在 + 任务独立性判断。

**事后沉淀环节(可选)**:实现推进过程中可按需触发:

| skill | 触发时机 | 产物 |
|---|---|---|
| `/write-api-doc` | 接口开发完毕 | `<文件前缀>-接口文档.html`(仅本次新增接口) |
