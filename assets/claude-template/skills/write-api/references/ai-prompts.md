# AI Prompt 指引(S2 + S3)

## S2 微服务识别 prompt 指引

### 输入

AI 在 S2 生成测试规格时,先读以下上下文:
- 项目结构:顶层目录、`package.json` / `pom.xml` / `go.mod` 等包描述
- `docs/bruno/` 既有子目录(避免命名漂移)
- 本次接口清单(S1 拿到)
- 接口路径前缀

### 判断

AI 判定每个接口归属的服务名,或判定为"无服务划分"。

判断依据:
- 项目根有 `services/` / `apps/` / `packages/` 等多模块目录 → 每个一级子目录视为一个服务,子目录名作服务名
- 接口路径前缀含服务名标识(如 `/so-assist-service/openapi/xxx`)→ 取路径段作服务名
- 单体项目无明显服务边界 → 判定为"无服务划分"

### 跨 feature 一致性

AI 识别时**优先参考 `docs/bruno/` 既有服务目录名**,避免同一服务在不同 feature 间命名漂移。

例:既有 `docs/bruno/so-assist-service/`,新接口也属该服务,就用 `so-assist-service`,不新取 `so-assist`。

### 输出

结果写入测试规格 §1 接口清单的"服务"列:
- 有服务归属 → 填服务名
- 无服务划分 → 填 `-` 或 `(无)`

用户可在 S3 前手动校正此列。

## S2 通用接口判断 prompt 指引

### 输入

AI 在 S2 判断每个接口是否通用时,读:
- 接口路径
- 接口语义(从代码或 spec 拿)
- `docs/bruno/common/` 既有接口(避免重复生成)

### 判断

AI 判定是否"通用接口"——跨 feature 复用的前置接口归为通用:

| 类型 | 例 |
|---|---|
| 登录 / token 刷新 | `/auth/login`、`/auth/refresh` |
| 健康检查 | `/health`、`/healthcheck`、`/actuator/health` |
| 公共字典 | `/common/dict`、`/common/enum` |
| 公共枚举 | 系统级枚举查询 |

### 跨 feature 一致性

AI 判断时**优先参考 `docs/bruno/common/` 既有接口**,避免重复生成。

例:`common/login/` 已存在,新 feature 的登录接口不重复生成,直接复用。

### 输出

结果写入测试规格 §1 接口清单的"通用"列:`yes` / `no`。

`yes` 的接口,S3 落盘时归 `docs/bruno/common/<接口名>/`,不绑 feature。

用户可在 S3 前手动校正此列。

## S3 生成 .bru prompt 指引

### 单次调用约束

**单次 AI 调用生成全部 .bru**——不拆两阶段(先程序化骨架后 AI 增强),不逐接口循环。

理由:
- 拆两阶段会让 AI 在第二阶段重新读一遍上下文,浪费 token
- 逐接口循环在接口多时上下文丢失,生成质量下降
- 单次调用让 AI 看全局,断言一致性更好

### 输入

- 接口清单(S1)
- 测试规格文档(S2 产出)
- 代码上下文:通过 grep + Read 拿 handler 源码、参数定义、默认值、必填项
- DB 数据:通过 `db-query` 查真实可用数据

### 输出

每个接口的**每个场景**一个 `.bru` 文件,符合 `bru-format.md` 规范:
- `meta { name, type: http }`
- HTTP 方法段 + `params` + `headers` + `body:json`(写接口)
- `tests { test("name", function() { ... }) }` 内嵌断言(旧版语法)
- `docs { 业务说明 }`(关联需求由 .bru 所在的 `<服务>/<需求前缀>/<接口名>/` 目录层级表达,docs 段不写关联需求列表)

### 拿不到真实数据时

AI 在以下情况拿不到真实数据:
- DB 无相关数据(表空 / 无匹配 id)
- 代码无可推断默认值(参数是用户输入型,如 `phone`、`email`)

处理:
1. 在 .bru 留 `{{var}}` 占位
2. 在测试规格 §3 标注该参数"需用户手填"
3. **不因此中断**,继续生成其他能生成的 .bru

理由:部分参数没值不代表整个 feature 不能跑测试;能跑的部分先跑,漏的让用户补。

### 失败处理

AI 调用失败(超时 / 限流):
- 报"AI 增强失败"
- 保留已生成的测试规格(S2 产出)
- **不继续 S4**(环境准备)

理由:S3 没出 .bru,S4 准备环境也没意义;让用户判断是重跑 write-api 还是手动调整。

## 跨步骤约束

### 降级处理

| 项目状态 | S3 降级行为 |
|---|---|
| 未配置 db-query profile | S3 留 `{{var}}` 占位 + 测试规格 §4 标注"DB 查询不可用";后续 `/run-api-test` 的 R4 也会降级,标"无法核实" |

降级不中断 skill,继续跑能跑的部分。
