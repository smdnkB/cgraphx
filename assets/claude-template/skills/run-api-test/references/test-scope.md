# R1 确定测试范围规范

## 输入

R1 的输入由 SKILL.md 触发逻辑(三分支)锁定一个 feature-id 后,从该 feature 的接口测试规格文档拿:

- 路径:`docs/features/<feature-id>/<文件前缀>-接口测试-spec.md`
- §1 接口清单:方法 + 路径 + 是否写接口
- §2 测试场景:每接口要测的场景名(正常/缺字段/不存在等)
- §5 接口映射:场景 → 接口 → .bru 文件路径

## 交叉校验 .bru 存在

**必须做**:遍历 §5 接口映射列出的所有 .bru 路径,逐个检查文件是否存在。

| 情况 | 处理 |
|---|---|
| 全部存在 | 进入用户确认环节 |
| 部分缺失 | 报"需求 X 接口 Y 场景 Z 的 .bru 缺失,请先跑 /write-api"并退出 |
| 全部缺失(该 feature 没跑过 write-api) | 报"需求 X 无接口测试规格或 .bru 全缺失,请先跑 /write-api"并退出 |

**理由**:跑测试前确保 .bru 都在,避免跑到一半才发现缺文件,浪费已跑的测试时间。

## 用户确认环节(不能省)

显示测试范围给用户,等用户确认后继续。

显示内容:

```
本次测试范围:
- 需求:<feature-id>
- 接口数:N
- 场景数:M(查询 K1 个 + 写 K2 个)
- 含写接口:是 / 否(若是,会做 DB 副作用核实)
- .bru 清单:(列出涉及的 docs/bruno/<服务>/<接口名>/ 目录)

确认后回车继续,或 Ctrl+C 取消。
```

**为什么不能省**:AI 反查"接口关联哪些需求"、读接口测试规格拿场景等过程中可能理解偏差;用户确认环节让用户兜底,避免跑错需求或跑错接口集合。

## 输出

R1 输出**本次跑的 .bru 清单**(路径列表),供 R3 bru run 用。清单形如:

```
docs/bruno/user-service/getUser/正常.bru
docs/bruno/user-service/getUser/不存在.bru
docs/bruno/user-service/createUser/正常.bru
docs/bruno/common/login/正常.bru
```

清单是 R3 bru run 的输入,清单决定跑哪些接口目录。

## 边界情况

| 情况 | 处理 |
|---|---|
| 用户指定需求但 接口测试-spec.md 不存在 | 报"需求 X 无接口测试规格,请先跑 /write-api"并退出 |
| 用户指定接口但接口目录不存在 | 报"接口 Y 无 .bru,请先跑 /write-api"并退出 |
| 用户指定接口但扫目录发现 0 个需求测过 | 提示"未在 docs/bruno/ 下找到测过接口 Y 的需求,请先跑 /write-api" |
| 接口测试规格 §5 列出的 .bru 实际不存在 | 报"需求 X 接口 Y 场景 Z 的 .bru 缺失,请先跑 /write-api"并退出 |
| 用户确认环节用户取消 | 退出,不进入 R2 |
