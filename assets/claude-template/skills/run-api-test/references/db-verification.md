# R4 数据库副作用核实规范

## 适用范围

**仅对写接口执行**(POST / PUT / DELETE / PATCH)。

查询接口(GET)跳过 R4,直接进 R5。

R1 清单里若没有写接口,**整个 R4 跳过**,直接 R5。

## AI 核实 prompt 指引

### 输入

每个写接口的每个跑过的场景,AI 核实时读:

- 写接口的 `.bru` — 含 docs 段业务说明 + tests 段 DB 副作用预期注释(write-api S3 写的)
- 跑测试后的响应 — R3 JSON 中间结果里的响应体
- 接口语义 — 从接口测试规格 §2 或代码拿(预期应该写什么)
- DB 状态 — 通过 `db-query` 查实际数据

### AI 动作

按以下步骤核实:

1. **确定查哪些表 / 哪些字段** — 根据 .bru tests 段的 DB 预期注释 + 接口语义
   - 新增接口 → 查主表是否有新行
   - 更新接口 → 查字段是否变化
   - 删除接口 → 查记录是否消失
   - 关联表 → 同步查(如创建用户后查 user_profile 是否同步)

2. **执行查询** — 用 `db-query` 跑 SQL,只读查询

3. **比对预期 vs 实际**
   - 预期:接口语义说应该写什么(.bru tests 段 DB 预期注释)
   - 实际:DB 里真的写了什么

4. **给结论**
   - **数据写对** — DB 数据符合预期
   - **数据写错** — 标注差异(如"预期 name=测试用户,实际 name=旧名字")
   - **无法核实** — db-query 失败或语义不清

### 输出

每个写接口的每个跑过场景,输出一条 JSON,写入 `<文件前缀>-接口测试验证.jsonl`(字段格式见 `report-format.md` § JSONL 字段)。

## 失败处理

| 情况 | 处理 |
|---|---|
| HTTP 通但 DB 数据错 | 最终状态记 `失败-DB副作用`,JSONL 记录预期 vs 实际差异 |
| db-query 连接失败 / 查询超时 | 该接口记"无法核实" + 状态 `失败-DB副作用`,**不阻塞其他接口** |
| .bru tests 段无 DB 预期注释 | AI 根据接口语义自行推断预期;不能推断时记"无法核实" |
| 同一接口多场景 | 每场景独立核实,独立记 JSONL |

**不阻塞原则**:R4 单接口核实失败不能拖垮其他接口。一个接口 DB 错或 db-query 挂,其他接口继续核实。

## 跨步骤约束

### db-query 不可用时的降级

| 项目状态 | R4 行为 |
|---|---|
| 未配置 db-query profile | 所有写接口标"无法核实" + 状态 `失败-DB副作用`;在报告 §3 失败分类标注"项目未配置 db-query,写接口 DB 核实不可用" |
| db-query 配置错(连接失败) | 同上 |

降级时仍跑 R3 和 R5,只是 R4 全部标"无法核实";用户后续配置 db-query 后重跑 `/run-api-test` 补核实。

## 与 write-api 的契约

write-api S3 生成 .bru 时,在 tests 段写 DB 副作用预期注释(格式见 `../write-api/references/bru-format.md`),形如:

```
tests {
    ...
    // DB 预期:users 表新增一行,name=测试用户,email=test@example.com
    // DB 预期:user_profile 表同步新增一行,user_id=本次返回的 id
}
```

R4 AI 读这些注释作为核实预期。注释越清晰,R4 核实越准;若 write-api 没写注释,AI 退化为从接口语义自行推断,精度下降。
