# 系统迁移 (dev-migrate)

## 定位

- **旧系统是标准答案**:业务行为以旧代码的实际表现为准,不以文档、记忆、「应该是这样」为准。迁移期间旧工程照常迭代,但新提交都要**追平**进清单(见第 5 步)。
- **行为清单是迁移的契约**:「保留功能和业务」落成清单里的一行行。每行的终态只有三种:✅ 对拍通过 / 🗑️ 人确认删除 / ⚠️ 人确认接受的差异。清单之外没有迁移义务,也没有删除权。
- **可观察行为不变,内部全部重写**:可观察 = 接口输入输出(含错误码、分页、字段名与格式)、数据副作用(读写哪些数据)、外部副作用(流程引擎、短信、消息、文件、定时任务)。分层、命名、拆分、去重、查询写法都是内部,按新工程规范写。
- **按切片推进**:一片 = 一个业务模块的全部清单行 + 它的表 + 它的数据迁移,能独立对拍。切片复用主链 dev-spec → dev-plan → dev-impl-subagent;本 skill 只管迁移特有的部分:盘点、目标、路线图、对拍对账、追平、切换。

## 产物(全部在新工程)

```text
docs/adr/<NNN>-技术栈选型.md                 # /init-tech-stack 产出
docs/features/<日期>-<系统名>迁移/             # 迁移总目录
  <前缀>-迁移总图.md        # 基线 commit、全局决策、模块映射、切片路线图、切换清单
  <前缀>-行为清单.md        # 契约;每行状态只记在这里,是唯一的进度来源
  <前缀>-表映射.md          # 旧表/字段 → 新表/字段 + 转换规则
  sql/<两位片号>-<切片>-迁移.sql、sql/<两位片号>-<切片>-对账.sql
docs/features/<日期>-<系统名>迁移-<切片>/      # 每片一个需求目录
  <前缀>-功能方案-v1.md     # 本 skill 从清单生成,dev-spec 原样收录为 spec 第一节
  <前缀>-spec.md、plan/     # 照常由 dev-spec / dev-plan 产出
  <前缀>-对拍报告.md
  对拍/                     # 两边的 bru 报告、对拍规则、对拍明细
```

四份总目录文件和切片功能方案的写法照 `references/产物范例.md`。

## 流程

### 0 · 立项

1. **定位置**:新工程目录(与旧工程平级)、迁移总目录的 feature-id(业务 ID、标题按 dev-spec 第 0 步确认)。新工程还不存在就建空仓库并 `cgraphx install`。
2. **记基线**:旧系统本体和**所有调用它的仓库**(各前端、服务间调用它的其他后端、监控探活)当前的 commit 写进总图「基线」;调用方仓库清单就是第 1 步冗余取证要搜的范围。
3. **搬知识**:旧工程 `docs/knowledge/` 复制到新工程(业务不变,概念照用);`docs/schema-knowledge/` 不搬,新库切换后另跑 `/init-ddl`。

完成:总图有每个仓库的基线 commit;新工程里 `cgraphx features list` 能列出迁移总目录。

### 1 · 盘点:行为清单

1. **机械枚举入口**:按类别用命令数出全部入口——HTTP 接口、定时任务、消息监听、应用事件监听、启动任务、流程引擎回调(监听器、委托类,以及**存在库里的流程定义**引用的 bean 与表达式,用 `db-query` 查)、拦截器和切面里的隐式行为(数据权限、多租户、审计字段填充、操作日志)、全局配置(序列化、分页、更新策略)、库里的触发器/存储过程/视图。旧栈的枚举命令和计数口径在配方里;每条命令先拿一个已知入口试一次,确认有输出再数。要查库的类别以生产库为准(只读;测试库的流程定义、触发器常和生产不一致),先测连通,连不上就把只读 SQL 留在清单里、该类标「未枚举」,不阻塞其他类。每类的数目写进清单顶部「对数表」。
2. **主会话先定共用的,再派子 agent**:旧工程大(入口上百)就按模块派子 agent 并行写行。派之前主会话定好三样,写进给子 agent 的说明(照 `references/盘点子agent说明.md`):每组的入口文件与预期数、编号简码;**记号表**——登录收尾、操作日志、数据权限这类每行都会出现的公共链路,定一个记号让各组引用;共用 Mapper 的冗余扫描归哪一组(只一组扫)。子 agent 回报清单行和对 skill 的卡点;主会话合并,清单超过 200 行时按组拆进 `行为清单/<组>.md`,总清单只留对数表、进度、待拍板和待查汇总。
3. **一行写什么**:用户看得到的行为、读代码得到的规则分支、读写的表、副作用、`file:line`。代码和知识库、旧 spec 说法不一致时以代码为准,记进疑点;读代码看到的 bug 和安全问题也记进疑点,迁移时逐条定「照旧复刻」还是「修了记 ⚠️」。高危安全问题当场告诉用户,不等迁移。
4. **找冗余,只认证据**:候选删除必须带至少一条硬证据——所在模块没打进可部署产物(看传递依赖)/ 基线里所有调用方仓库都没有**活的调用**(非注释的调用点;前端 api 函数只定义、只 import 不算)/ 实现是空方法或返回假数据、依赖的东西永远不存在 / 开关在所有环境都关着 / 和另一行行为完全重复 / 脚手架自带的演示代码或开发工具。服务间调用要按配置拼出路径再判(RMI、Feign、网关的「前缀 + 方法名」整串搜不到);后端入口不存在优先于前端有调用(调用必然 404 也算证据)。grep 判出的候选最后再过一遍生产的调用记录(操作日志、异常日志、网关访问日志):有记录的改判迁移或待查——前端动态拼的 URL grep 搜不到;候选是某张表唯一的写入点时,再查这张表最近的写入时间,近期有写入就说明还有人调(可能是没更新的前端构建)。降为「待查」的两种:免登录接口搜不到调用方(可能外部直调);知识库或 spec 写明运维在用的手动入口。
5. **人审**:候选删除按证据分批,每批整批定、点名例外;同时列出连带关系(删的是某张表唯一的写入点、背后的 service 还有别的调用方)。没拍板的按「留」。

完成:对数表每一类「枚举数 = 清单行数」,未枚举的类别留好了只读 SQL;每行有 `file:line` 和处置;候选删除每一批都有人的结论。

### 2 · 目标:技术栈、模块、表映射

1. **技术栈**:提示用户跑 `/init-tech-stack`(它是 user-invoked,需要用户逐组拍板),用户跑完把 ADR 带回来;用户已定的层(如「语言 Java」「ORM 用 JPA」)作为已拍板约束传进去,只敲定剩下的层,ADR 落新工程 `docs/adr/`。技能缺失说明 cgraphx 版本未升级 → 提示 `cgraphx upgrade` 后重跑,不临场另写一套。
2. **读配方**:读 `references/配方-<旧栈>-to-<新栈>.md`(现有 `配方-mybatis-to-jpa.md`)。没有对应配方 → 第一片做完后,把踩到的翻译规则和坑按同样结构写成新配方放进本目录。
3. **模块划分**:按业务域划模块,写「旧包 → 新模块」映射表和模块依赖方向进总图;旧工程的技术分层大平铺不照搬。新工程的 `docs/guides/` 在片 0 写 plan 之前用 `/init-guides` 按 ADR 生成(dev-plan 缺规范会中断)。
4. **表映射**:每张旧表一行——保留 / 改名 / 合并 / 拆分 / 删除(对应清单行全部 🗑️ 的表才能删),字段级写转换规则和默认值。框架自带的表(流程引擎、调度框架等)原样保留,改它们等于重写框架。新 DDL 按新工程 `data-standards.md` 的「Schema 变更约定」写。
5. **全局决策进总图**:接口契约是否兼容(前端不改就必须兼容:URL、参数、响应包装、字段名与类型、分页起始页、时间与长整型序列化格式)、ID 生成方式、数据迁移方式(同库 SQL 搬运 / 程序搬运)、切换方式(停机一次切 / 按模块切流量)、回滚方式。

🔒 ADR、模块映射、表映射、全局决策都难回头,人逐项确认后才进第 3 步;之后各片的 spec 引用它们,不重开。

### 3 · 切片路线图

排序:底座(登录、用户、组织、权限、字典)最先;核心业务按业务链从上游到下游;报表统计最后(它依赖全部数据)。片 0 = 脚手架 + 底座 + 公共约定(统一响应、异常、鉴权、审计填充、序列化格式),同样要对拍。每片在路线图里写:包含哪些清单行、哪些表、依赖哪几片、状态。

完成:清单里每一行(🗑️ 除外)都归属且只归属一片;每张保留下来的表都归属一片。

### 4 · 逐片迁移(每片一轮)

1. **出功能方案**:切片目录写 `<前缀>-功能方案-v1.md`,格式照 dev-clarify 讨论稿——一句话写「原来……在旧系统,这次搬进新工程,行为不变;删掉……」;功能清单 = 本片清单行(F 编号旁标 B 编号),本片的 🗑️ 行也列进去当不做;行为不变,各功能点那一节不画图,写行为链和边界(就是清单的规则分支),口径从规则分支提,写进那一节的口径表。人说对了再往下。
2. **走主链**:`/dev-spec` → `/dev-plan` → `/dev-impl-subagent`。spec 的设计决策引用配方条目和表映射行,不重开总图的全局决策;本片的数据迁移脚本和对账 SQL 是 plan 里的数据库任务,落迁移总目录 `sql/`。
3. **对拍 + 对账**:照 `references/对拍与对账.md` 跑。有差异默认改新系统,直到和旧系统一致;判断是旧系统 bug 的,写进报告的「待裁决差异」由人拍板——人确认才记 ⚠️,否则按旧行为改。
4. **回写**:清单行状态、路线图状态、对拍报告链接。

完成:本片每一行都是 ✅ 或人确认的 ⚠️;本片每张表对账全部通过。

### 5 · 追平(每片开工前一次,切换前一次)

旧系统每个仓库跑 `git log --oneline <基线>..HEAD`,逐个提交对到清单:新增的行为加行(归进对应片),改了的行为把该行标「需重新对拍」;全部对完把基线前移到 HEAD。

完成:基线之后的每个提交在清单里都有落点(或注明「不涉及行为」及理由)。

### 6 · 切换

进入条件:清单每行都是终态;刚追平过;全量数据迁移在生产数据副本上演练过至少一次、对账通过、记下耗时。满足后照 `references/产物范例.md` 把切换清单写进总图,交给人执行。

## 收尾

每个阶段结束时回报:停在哪一步、清单进度(✅ / 🗑️ / ⚠️ / 未迁 各几行)、下一步做什么。全部切换完成后:新工程跑 `/init-ddl` 建新库基线,用 `/knowledge-write` 更新知识库里变了的表名和代码位置。

## 红线

1. 行为以旧代码为准;想「顺便改业务」→ 记成 ⚠️ 差异交人裁决,或迁移结束后另走需求。
2. 删除只发生在人确认过的 🗑️ 行;没证据、没拍板的一律保留。
3. 旧工程不为迁移改代码;它的正常迭代走原来的需求流程,由追平同步过来。
4. 对拍没跑、或有未裁决的差异,不标 ✅。
5. 生产库只读;数据迁移与切换由人执行。
