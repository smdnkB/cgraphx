# 生成交付讲解 (Write Delivery Guide)

## 定位

- **让交付的代码对人可读**:读者是没写这批代码的技术接收者;目标是看懂代码(「像自己写过一样」),不是验收汇报。
- **派生视图,不是维护对象**:从 spec + diff + 代码现实生成;过期 → 重跑本 skill 整体重生成;永不人工维护与代码的一致性。
- **不是契约**:不重定义 spec 已锁定的契约;spec 与代码现实不符 → 标【待确认】并上报,不自行解释。
- **边界**:发布后设计文档合成 → `write-design-doc`;业务知识沉淀 → `knowledge-write`;工作量汇报 → `write-workload`。

## 依赖

- 存在代码改动(diff);无代码改动 → 不生成。
- spec / 知识库非必需但影响质量:无 spec → 从任务上下文 + diff 生成,文档头部标注「spec: 缺省」;知识库为空 → 跳过锚点法,不编造锚点。

## 流程

1. **确定范围**:feature-id(用户显式指定 > 从 cwd 向上探测最近的 `docs/features/<feature-id>/` > 都失败则询问);输出默认 `docs/features/<feature-id>/<前缀>-交付讲解.md`,用户可覆盖;无 feature 目录(临时任务)→ 不建目录,讲解直接在回复中输出。
2. **收集事实**:
   - 读 spec(场景/角色/状态/接口章节)→ 形态识别与故事线素材;
   - 读 diff → 本次交付的新增/修改清单;
   - 读改动文件的相关代码 → 每个入口的实际逻辑、调用关系;
   - `cgraphx docs find` 召回相关知识库条目(实体/流程)→ 锚点素材。
3. **识别用法形态**:见「形态 → 故事线主轴」;一次交付含多种形态 → 多条故事线各成一节;**拿不准 → 问用户,不猜**。
4. **读场景模板**:本 skill 目录存在 `template-<形态>.md` → 按模板生成(含其参考案例与常见讲错);不存在 → 按通用骨架生成 + 沉淀提示(见下)。
5. **生成**:按通用骨架 + 模板维度,执行「讲法底线」。
6. **自检**:每个结论有代码指针;本次交付的每个组件都挂进了故事线(无遗漏);四问齐全;mermaid 语法可渲染;未重定义 spec 契约;矛盾处已标【待确认】。
7. **落盘 + 导读入口**:写入路径;文档结尾给导读入口 + 示例问题(通用骨架第 7 节)。

## 通用骨架(七节,按此顺序)

| 节 | 内容 |
|---|---|
| 1. 30 秒看懂 | 一两句:解决了什么业务问题、在现有系统的哪个位置 |
| 2. 全景 | 本次交付参与的业务流程图(mermaid),**高亮本次新增/修改的部分** |
| 3. 场景故事线 | 按用法形态分节(可多条);主轴见下节 |
| 4. 组件挂接 | 每个接口/入口/模块按四问展开 |
| 5. 改动定位 | 仅当改动已有流程:改在哪个部位(引全景图标出)、前后对比、波及范围(哪些调用方/场景的行为受影响) |
| 6. 已验证与已知边界 | 验证跑通的路径 + 已知限制(业务确认砍掉的、暂不支持的) |
| 7. 导读入口 | 提示任意章节可追问,并给出针对本次交付的示例问题 |

## 形态 → 故事线主轴

| 用法形态 | 故事线主轴 | 图表类型 |
|---|---|---|
| 多角色流程(审批/退款类) | 角色 × 环节:谁在第几步干什么 | sequenceDiagram |
| 单入口管道(导入/同步任务) | 处理步骤:输入如何一步步变成输出 | flowchart |
| 管理 CRUD(配置管理类) | 对象生命周期:状态 + 每个操作推动到哪 | stateDiagram |
| 后台作业(定时任务/事件消费) | 触发时机:何时触发 / 干了什么 / 结果落哪 | flowchart |
| 改动型 | 原流程中的部位:原故事线第 N 步,前后对比 | stateDiagram / flowchart |

形态判断取材于 spec 的场景/角色/状态章节 + 代码接口形状。模板文件:`template-multi-role-flow.md`(多角色流程)、`template-change-type.md`(改动型);其余形态暂无模板,走通用骨架。

## 组件四问(每个组件必答)

1. **何时用**:谁触发、前置条件(哪个环节之后才轮到它);
2. **做什么**:核心逻辑,业务语言,3 句以内;
3. **用了之后使什么成为可能**:解锁的下一环节 + 副作用(写什么表、发什么事件、调谁);
4. **挂点**:前置环节 → 本组件 → 后续环节。

协议细节(参数/返回值字段)降级为附录或指向 spec,不占故事线主线。

## 讲法底线(所有内容适用)

- **锚点法**:新东西先挂在读者已知的事物上(知识库实体/既有流程/相似既有模式);知识库为空 → 用通用讲法,不编造锚点;
- **目的优先**:每个部分先答「你为解决什么问题而存在」,再讲结构;
- **请求走查**:至少一次带真实数据的完整请求/任务走查(故事式,非清单式);
- **代码指针**:每个结论指向代码(文件:行号 或 文件:符号);无法回代码验证的结论不写进讲解;
- **图优先 mermaid**:对齐 write-design-doc 的图表规范(flowchart / sequenceDiagram / stateDiagram 等)。

## 模板未覆盖形态的兜底 + 沉淀提示

无对应模板 → 按通用骨架生成;生成后问一句:「本次交付属于 <形态> 形态,尚无场景模板。若这份讲解有效,是否沉淀为新模板(写入 `template-<形态>.md`)?」用户同意 → 按统一六项结构写入(判断特征 / 故事线主轴 / 讲解维度要求 / 图表类型 / 完整参考案例 / 常见讲错),参考案例用本次交付;拒绝 → 不提。

## 重生成与回写

- 对同一 feature 重跑 = 整体重生成,替换旧文档;
- 旧文档含导读回写的内容 → 重生成前合并保留,不得静默覆盖。

## 模板进化

用户发现讲解不满足理解 → 导读先解决当次问题;再判断是个例(这次没讲好)还是模板缺陷(这类形态的讲法整体不对);模板缺陷 → 提示更新对应模板(经用户确认后写入)。

## 红线(绝对不能做)

1. ❌ **不编造** —— 无法回代码/spec/diff 验证的结论不写进讲解。
2. ❌ **不重定义 spec 契约** —— spec 与代码现实不符 → 标【待确认】并上报。
3. ❌ **不人工维护与代码的一致性** —— 派生视图,过期重生成。
4. ❌ **不猜形态** —— 拿不准就问用户。
5. ❌ **不编造锚点** —— 知识库为空用通用讲法。
6. ❌ **不静默丢失回写内容** —— 重生成时合并保留。
7. ❌ **不擅自创建 feature 目录** —— 临时任务直接在回复中输出。
